# 文档产出规范

状态：默认写作规则

用途：约束后续 Week 日志、设计说明、技术选型、验收标准等文档的产出风格。

---

## 总原则

文档要像工程卡片，不像教程文章。

核心要求：

- 先给结论，再给依据。
- 动机必须有，但用一句话打中核心差异。
- 信息密度高，少铺垫，少重复。
- 多写边界、规则、通过线、自检表。
- 用表格和清单承载结构。
- 读者默认有编程基础，不解释常识。

推荐长度：

```text
普通说明：1000-1500 字左右
决策记录：800-1200 字左右
验收标准：1200-1800 字左右
```

超过长度时，优先删背景、比喻、重复解释，不删结论和边界。

---

## 动机写法

动机不能消失，但必须短。

推荐格式：

```text
选择 A，因为 B 无法满足 X，而 A 能守住 Y。
```

例：

```text
选择 decimal.js，因为 big.js 更轻但能力更窄，而本项目需要长期稳定支撑均价、盈亏和误差校验。
```

不要写成：

```text
我们为什么要做这个？在软件开发中，很多时候……
```

动机的作用是解释取舍，不是写背景作文。

---

## 通用结构

以后文档优先使用这个骨架：

```text
# 标题

日期 / 状态 / 目标

## 结论
直接说本文件决定了什么。

## 动机
一句话说明为什么这么做。

## 核心规则
列出真正会约束后续开发的规则。

## 边界
说明做什么、不做什么。

## 自检表
用表格让以后快速判断是否符合规范。
```

不是每份文档都必须完整套用，但结论、规则、边界、自检至少要有其中三项。

---

## 不同文档模板

### 架构说明

重点：职责和边界。

推荐结构：

```text
结论
目录 / 模块骨架
各层职责
禁止事项
自检表
```

少写“为什么要做架构”，多写“什么代码放哪里”。

### 技术选型

重点：选择理由和使用边界。

推荐结构：

```text
选型结论
一句话动机
候选对比
使用边界
落地顺序
自检表
```

必须回答：

- 选了什么。
- 为什么不是另一个。
- 谁可以直接使用它。
- 谁不能直接使用它。

### 验收标准

重点：通过线。

推荐结构：

```text
验收结论
固定样例
手算 / 预期基准
必须通过项
测试清单
不在本次验收范围
不可推迟项
```

验收标准必须可测试，不能只写“功能正常”“体验良好”。

### 每日计划

重点：今天只做什么。

推荐结构：

```text
今日目标
产出物
完成标准
不做事项
风险 / 可砍项
```

每日计划要窄，不要把一周任务都塞进去。

### 开发日志

重点：当天完成了什么、为什么这样处理。

推荐结构：

```text
今日完成
关键决策
遇到的问题
明天入口
```

开发日志可以有一点叙述，但不能变成流水账。

---

## 禁止事项

以后生成文档时避免：

- 大段解释基础概念。
- 重复说明同一个动机。
- 用很多“为了更好地”“非常重要”“有助于”但不落到规则。
- 写太多未来幻想，不写当前边界。
- 把验收标准写成愿望。
- 把工具层、业务层、页面层职责混在一起。
- 为了显得完整而写无用章节。

---

## 推荐表达

优先写：

```text
页面不直接计算，不直接保存，不直接碰浏览器 API。
```

少写：

```text
页面层在整个系统中承担着非常重要的作用，它不仅关系到用户体验，也会影响未来项目的可维护性……
```

优先写：

```text
如果一个文件同时承担两行以上职责，优先拆开。
```

少写：

```text
我们应该尽量遵循单一职责原则，因为单一职责原则是软件工程中非常重要的原则……
```

---

## 自检表

| 问题 | 通过标准 |
| --- | --- |
| 开头是否有结论 | 第一屏能看到决定了什么 |
| 动机是否过长 | 一句话能说清核心取舍 |
| 是否有边界 | 明确写了做什么 / 不做什么 |
| 是否能指导后续开发 | 有规则、职责或通过线 |
| 是否有废话 | 删除一段后不影响执行的内容应删 |
| 是否像教程 | 如果像讲课而不是工程记录，需要压缩 |

---

## 默认要求

后续新建日志文档时，默认按本规范写。

如果某份文档需要写长，必须满足：

```text
长是因为规则更多，不是因为解释更多。
```

## 执行合同写作检查清单（2026-09-01 新增）

本节由三次真实事故归纳而来，全部发生在 Week 15 的 06 批：执行者**三次按合同停止申报，三次都正确**，其中**两次错在合同本身**。清单的目的是让同类事故不再发生。

**适用范围**：一切要交给另一个执行者（AI 或人）照做的文档——执行文档、修订、裁决、提示词。产品定义中被执行合同引用的部分同样适用。

### 一、不写具体数字作为靶子

**事故**：`06B` 修订 A 写「`JSON.parse(...) as LedgerFileV2` 共 33 处，分布 25／4／4」。实际 `JSON.parse` 只有 19／3／1；那个 33 是「含 `LedgerFileV2` **或** `ciphertextBase64Url` 字样的**行数**」——两次不同口径的统计被错误合并。执行者数不出 33，只能把目标标记为 blocked。

**规则**：

| | |
| --- | --- |
| ❌ 禁止 | 「共 N 处」「必须匹配 N 个」这类要求执行者对上某个具体数字的写法 |
| ✅ 改为 | 写**判据**（「凡符合 X 特征者均在范围内」），并要求执行者**自行枚举、公开检索命令与原始输出**，供他人复算 |
| ✅ 必附 | 「实测与本文不一致时**以实测为准**，说明差异即可，**不得去凑本文的数字，也不得因对不上而停摆**」 |

背景数字可以写，但必须**标明是记录而非判据**，并注明基线 SHA 与日期。

**审查者的职责随之改变：复核执行者的口径，而不是复核他的数值。**

### 二、不用「按文件」划范围，用「这段代码为谁而写」

**事故**：同一份修订 A 把授权限定在三个文件。实测全仓库有 11 个文件涉及相关符号，且同一文件里必然两类并存——按文件切，怎么切都是错的。

**规则**：范围按**意图**划分，不按位置划分。典型三分法：

| 类 | 含义 | 处理 |
| --- | --- | --- |
| 甲 | 断言「当前实现是这样」 | 随实现一起改 |
| 乙 | 断言「某个已冻结的旧合同是这样」 | 原样保留，一个字不动 |
| 丙 | 判不出是甲是乙 | **逐条停止申报，不得自行归类** |

**丙类的存在是必需的**：没有它，执行者遇到模糊情形只能自己猜，而猜错不会有任何灯变红。

### 三、描述某一步时，不得使用只有后续步骤才存在的概念

**事故**：`06A` 把 S-2 写作「`previous` 不再存整本，只保留发生变化的**块**的旧版本」——**在「块」尚不存在的阶段就用了「块」**。执行者据此正确推出 S-2 依赖尚未实施的 S-3，请求合并两步。

**规则**：

- 写完多步合同后，**逐步倒查**：这一步用到的每个名词，在它之前的步骤里是否已经存在？
- 描述某一步的**目标**（要消除什么成本／风险），而不是描述它的**实现形态**。目标不会预设后续步骤，实现形态会。
- `06A` 里 S-2 的真实目标是「去掉存两代造成的双倍写入」；写成「只保留变化的块」就把一种特定实现钉死了，而那种实现恰好依赖后一步。

### 四、通过线写判据，不写预设的具体值

**事故（自查发现，未酿成停摆）**：`07A` 的 Q-5 写作「四个版本号全部不变：**file 3（06 批后）**……」，预设 06 批一定把版本升到 3。若 06 被裁决缩减范围，该值不成立，通过线无法判定。

**规则**：写「相对**开工时基线**不变」，并要求执行者开工时记录实际值、收尾时逐一对照。**不引用任何预设的具体数值。**

### 五、已知必然发生的申报，提前裁决掉

**做法（自查发现并已实施）**：`07B` 原文预告「数字格式改动会影响既有断言，属 B-05，须停止申报」，并称这是「几乎必然触发的申报点」。

**既然已知它必然发生，就应当在开工前查明范围并当场裁决，而不是让它耗掉一个往返。** 实测该影响面仅 20 处、4 个文件，其中两个文件本就是被改对象自身的规格测试——改其期望值是正确的，不是弱化。据此写成预先授权加四条约束，省掉一次停摆。

**规则**：写合同时若出现「这里将来大概率要申报」的念头，**立刻去查清范围**。查得清就当场裁决，查不清才留作申报点。

### 六、通用自检（写完合同后逐条过一遍）

1. 有没有任何一处要求执行者匹配一个具体数字？
2. 范围是按意图划的还是按文件划的？有没有「判不出就申报」这一档？
3. 每一步用到的概念，在它之前是否都已存在？
4. 通过线里有没有预设的具体值？
5. 有没有「将来大概率要申报」的点，是现在就能查清并裁决的？
6. 每一条禁令，是否都写明了「触发时怎么办」（停止申报／如实记录／等待裁决）？
7. 报告要求里有没有「没做或没取得就如实写『未取得』，不得留白、不得推断、不得用别的数字顶替」？

### 七、一条不该被这份清单掩盖的事实

三次停止申报，执行者**三次都正确**，其中一次还反过来查出了产品负责人自己的错误。

**「停止并申报」机制的价值不在于阻止改动**——有些改动就是必须做。它的价值在于**把「必须偏离合同」这件事，从一次悄悄的提交，变成一次公开的、有据可查的裁决**。

反面教材见 `04D`：断言被删除、报告称未删、1,107 个用例全绿、只有第三方逐行读 diff 才发现。**那类改动天然不会让任何灯变红，恰好落在自动化的盲区里。**

因此本清单的目的是**减少无谓停摆，不是减少停摆**。宁可多停一次，不可少停一次。
