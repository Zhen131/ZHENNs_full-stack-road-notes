## 结论

Week 12 的 00 层由 Week 11 同名文件复制而来，此后只在 Week 12 副本中记录新决定，Week 11 原件作为历史现场冻结。00 层长期保存产品共识、总需求、批次地图和延期缺陷；每个新周可以从 `01` 重新开始，但文件名和标题必须同时写明周次与源码分支。每批的 `A` 与 `C` 是执行前同时生成的两份目标模式输入文档，`B` 与 `D` 是对应 AI 执行后生成的两份事实报告。

`NND = FAIL / BLOCKED` 只暂停本批目标和依赖它的后续路线，不再自动冻结整个项目。非阻塞问题进入 00D，允许先做前置已满足且与该问题无依赖的批次。每批最多立即安排一轮阻塞修复，命名为 `NNR1A / NNR1B / NNR1C / NNR1D`；复验仍未通过时暂停相关路线，不自动继续生成 R2 或一串 D 后缀。任何开发侧 PASS 都不能替代独立 PASS。

## 开发批次

`NN` 使用两位递增编号，例如 01、02、03：

| 文件 | 用途 |
| --- | --- |
| `NNA` | 开发目标模式输入：详细规定本批要实现什么、允许改什么、技术合同和开发完成线 |
| `NNB` | 开发执行报告：由执行 NNA 的 AI 记录实际修改、源码状态、测试结果、偏差和已知风险 |
| `NNC` | 独立测试审查目标模式输入：详细规定如何独立审查、测试 A/B 与源码，固定通过线、失败线和阻塞线 |
| `NND` | 独立测试审查报告：由执行 NNC 的另一 AI 记录逐项证据、通过项、失败项、阻塞项、Finding 和最终判定 |

同一周、同一源码轨道内，第一批使用 `01A–01D`，第二批使用 `02A–02D`，依次递增，不得复用。不同周允许从 `01` 重新开始，但必须使用类似 `01A_W12-main-……` 的完整文件名和标题，不能与 Week 11 的 `01A` 混淆。

`NNA` 与 `NNC` 必须基于同一批目标、同一产品合同和同一通过线成对生成。`NNC` 不是等 NNB 生成后才临时编写的结果文件；它必须在开发开始前就把“将来怎样证明代码正确”固定下来，避免执行者写完代码后再降低验收标准。

若 `NND` 出现必须立即处理的阻塞项，本批最多增加一组：

| 文件 | 用途 |
| --- | --- |
| `NNR1A` | 只修本批已确认的阻塞 Finding |
| `NNR1B` | 记录修复事实和开发侧验证 |
| `NNR1C` | 冻结该轮独立复验范围 |
| `NNR1D` | 记录独立复验结果 |

R1 不得夹带新功能，也不改变后续正常批次编号。R1 再失败时，Finding 保留在 00D，相关路线暂停；后续是否集中修复由用户另行选择。

```text
→ 下一正常批继续使用 00C 已固定的 NN 编号
```

## 防御性安全测试与故障注入规则

### 结论

后续每批都保留主动制造异常、竞态和失败组合的安全测试，但把“编写正式测试”和“独立验收”分开：开发 AI 在 NNA 阶段把风险场景写成仓库内的永久回归测试，独立 AI 在 NNC 阶段冻结候选并只读复验。不得为了减少平台误拦截而删掉安全通过线，也不得以更换措辞、执行模式或隐藏真实目的来规避平台安全措施。

这套规则的目标是把任务如实限定为本人授权仓库内的防御性软件验证，降低被误解为第三方攻击的概率；任何提示词都不能保证不触发平台额外检查。若合法任务仍被拦截，应保留已完成证据、缩小到单一防御结果后重试，或走平台反馈、支持与可信安全研究渠道，不能继续尝试绕过检查。

### 三阶段流程

#### 阶段一：先固定威胁边界和安全不变量

生成 NNA / NNC 时必须同时写清：

1. 测试对象是用户拥有并控制的本地源码仓库、固定候选分支或固定工作树，不包含第三方生产系统。
2. 本批保护的资产、信任边界和绝对不能发生的结果，例如账本错写、旧页面覆盖新 revision、损坏文件被当成成功、密码或明文跨会话残留。
3. 直接适用的 00B GATE、历史回归、已知 Finding 和本批新增风险，不能只写“做安全测试”。
4. 每个安全不变量对应的正式测试、真实浏览器证据或静态审查证据；无法取得证据时预先定义 FAIL / BLOCKED，而不是执行后降低标准。

#### 阶段二：开发侧编写正式防御性回归测试

NNA 必须授权并要求开发 AI 使用项目现有测试框架，把适用风险写入正式测试目录。优先使用确定性的故障注入、延迟 Promise、受控时钟、假文件句柄、失败适配器和代次切换，覆盖至少以下适用组合：

- 写入、加密、关闭、复读任一步失败时不得发布虚假 `saved`。
- 操作进行中 revision、文件身份或会话代次变化时，旧操作不得覆盖新状态。
- 取消、卸载、锁定、超时或权限变化后，迟到异步结果不得复活旧页面或继续写入。
- 损坏、截断、错密、未知版本和边界大小输入必须 fail closed，不得产生部分写入。
- 资源释放失败后不得继续保留可用仓库、明文或密钥引用；恢复和重试不得扩大数据风险。
- 既有 salt / metadata 漂移、旧异步选择、Hook dirty / saved、KDF 解耦、双代和 close-readback 回归不得丢失。

新增测试必须成为候选的一部分，能够被后续全量测试稳定复跑；不得只把关键证据留在 `/private/tmp`、一次性脚本或聊天文字里。必要时可以为可测试性增加最小注入接口，但不得为了测试而削弱生产安全合同。

#### 阶段三：独立 AI 冻结候选并只读验收

NNC 必须由与开发任务不同的全新任务执行，并做到：

1. 记录候选分支、提交、工作树状态和关键路径哈希，确认审查的是 NNA 实际产生的完整候选。
2. 只读执行本批正式安全回归、历史回归、全量自动测试、typecheck、lint、build、whitespace，以及适用的真实 Chrome / 真实存储流程。
3. 不修改源码，不临时创建新测试、脚本或配置，不把审查者自己的代码混入候选。
4. 若发现新的高风险场景但正式测试没有覆盖，登记“正式测试缺口”：源码和现有证据已能证明违反强制线时判 FAIL；强制线因缺少可重复证据而无法判定时判 BLOCKED，不得按假设给 PASS。
5. NND 完成后，由协调步骤把未关闭 Finding 去重登记到 00D。需要新增测试或修复时进入本批唯一一轮 NNR1A；开发侧把测试永久写入仓库后，再由 NNR1C 独立复跑。

目标模式与普通 Local 任务只是执行方式，不改变上述覆盖范围、只读边界和 PASS / FAIL / BLOCKED 标准。若长时间自动执行反复触发额外检查，可以改用全新普通 Local 任务分段执行并逐段留证，但不得因此删除测试或把开发自测冒充独立验收。

### 安全测试提示词基线

以后生成任何 NNA / NNC，尤其是文件、密码、持久化、导入、删除和恢复批次时，必须按实际角色吸收下面的基线；不得脱离本批目标原样空泛复制：

```text
这是用户本人拥有并控制的 Local-First Trading Ledger 源码仓库。本任务仅在本地隔离的开发与测试环境中进行，目标是识别、预防和修复本批范围内的数据安全与一致性缺陷。

授权边界：
- 只操作提示词中固定的本地仓库、候选分支、测试夹具和虚构 BTC / ETH / ADA 数据。
- 不访问、扫描或测试任何第三方生产系统；不获取凭据，不建立持久化，不执行数据外传，不破坏真实数据，也不生成可迁移到第三方目标的通用利用工具。
- “防御性测试”是任务的真实范围，不得靠隐去目的、拆词或改名规避平台规则。

安全目标：
- 把本批适用的安全不变量逐条映射到可重复证据。
- 主动覆盖失败注入、迟到异步结果、revision 或身份变化、取消与卸载、损坏输入、权限变化、释放失败和恢复重试。
- 对每项给出预期结果、实际结果和 PASS / FAIL / BLOCKED；缺少强制证据不得写 PASS。

角色规则：
- 若执行 NNA：允许使用项目现有框架新增永久正式回归测试，并在测试证明问题后做最小源码修复；测试和修复都留在候选分支。
- 若执行 NNC：源码和正式测试只读，只运行、审查和记录证据；发现新测试缺口时写入 NND，不临时编写测试代码，由后续 NNR1A 补成永久测试。

输出：
- NNA 执行后生成 NNB，记录实际改动、正式测试、质量门、偏差和风险。
- NNC 执行后无论结果如何都生成 NND，并按固定规则给出最终判定。
```

## 硬规则

1. 正常新批次只有取得 `NND = PASS` 最终证据后，00B 目标才从 `[ ]` 改为 `[x]`。如果产品负责人确认原合同本身不可实现并主动撤销，必须保留旧 A/B/C 历史、明确记录 C 不再执行且不得伪造 D；只有在 000、00A、00B 同时写清新合同、已有证据和风险接受后，才可以按一次性合同纠正收口目标。
2. NNA、NNC 是执行输入；NNB、NND 是执行报告。任何 AI 不得把输入文档中的预期写成已经发生的事实，也不得把 NNB 的执行者自测当成最终完成证明。
3. NNA 与 NNC 只能覆盖用户选中的同一批目标；发现缺少前置任务时必须提醒，不得静默扩大范围。
4. NNA / NNC 生成前必须重新核对当前源码、测试和 Git 状态，不能只依赖 00A、00B；两份文档必须同时固定同一目标范围、业务样例和不可降低的通过线。
5. 开发 AI 只执行 NNA 并生成 NNB，并负责把本批适用的故障注入与安全不变量补成永久正式测试；独立 AI 只执行 NNC 并生成 NND，源码和正式测试保持只读。独立审查发现的新测试缺口进入 NND 和 00D，再由用户授权的 NNR1A 写入正式仓库，不在临时副本中制造无法长期复跑的关键证据。
6. 已经执行 NNC 的独立审查，无论 PASS、FAIL 或 BLOCKED 都必须生成 NND；在执行前已由产品负责人正式撤销的 NNC 应标记为作废且不再执行，不得伪造一份 NND。
7. NND 为 FAIL 或 BLOCKED 时，00B 默认保持未勾选。该结论只暂停本批目标和依赖它的路线，不得据此自动冻结没有依赖关系的工作；后续若合同被用户正式撤销或改写，只能按硬规则 1 的一次性合同纠正处理，不能把开发侧 PASS 冒充独立 PASS。
8. NNA / NNC 一旦交给执行任务，不得事后改写通过线来配合现有实现；如合同本身确实错误，必须停止、保留旧文档并由用户确认修订。目标模式或普通 Local 任务都适用同一规则。
9. 00A–00C 和批次文档属于工作区根 Git 仓库；源码修改属于独立的 `LocalFirstTradingLedger` Git 仓库，两者不得混合提交。
10. 用户选中的目标必须先做前置闭包检查：前置要么已经完成，要么由用户同时选入本批；仍有未决 DEC 时停止生成，不得自行补全。
11. 00B 的“直接适用 GATE”必须同时进入 NNA 的开发边界和 NNC 的深度验收矩阵，不能变成额外开发目标；全部 23 项 GATE 仍需快速复核，发现疑点才升级为深测。
12. 当前开发状态、源码 README、00A 和 00B 出现事实冲突时，必须先按当前源码与 Git 核对并修正文档，不能带着冲突生成 NNA / NNC。
13. 已实际生成的正常功能批次编号不得复用。仍处于 00C 预计阶段、从未生成文件的编号，只有用户明确确认并在 000 / 00C 留下合并记录后才能调整；阻塞修复仍使用本批 `NNR1A–NNR1D`，不占用后续正常编号，未通过的相关目标不得被后续依赖批次绕过。
14. P0 一律阻塞相关路线；涉及写错、丢失、密码泄露、文件身份、旧页面覆盖或虚假保存成功的 P1 也阻塞。当前目标任一强制通过项失败时，无论标成什么级别，都按阻塞处理。
15. 不触发强制失败线、也不影响数据与密码安全的普通 P1、P2、P3，可以在 NND 中如实记录并进入 00D；它们本身不要求把最终判定降为 FAIL。
16. 00D 只登记尚未关闭的问题。01D-6 已独立关闭的历史问题不重新列为待办，但相关 salt / metadata 漂移、旧异步选择、Hook 保存状态、KDF 解耦、双代和 close-readback 测试必须保留为后续回归。
17. 独立审查 AI 只生成 NND，不直接修改 00B、00D 或源码。NND 完成后的协调步骤负责去重登记 00D；重复发现引用既有缺陷编号，不新建第二条。
18. 00D 只有取得独立复验证据后才能勾选。开发侧声称修复、关闭页面功能或用户允许继续其他路线，都不等于该缺陷已经关闭。
19. 安全测试必须以授权、本地、隔离和防御结果为边界；禁止第三方生产目标、凭据获取、持久化、外传、破坏性测试和通用利用工具。不得把“本地”当作攻击第三方同款系统的授权证明。
20. 不得承诺某份提示词一定不会触发平台额外检查，也不得通过隐藏目的或替换术语规避检查。发生疑似误拦截时，只能缩小到必要的防御结果、保留执行证据并使用官方反馈或支持渠道。
21. 不得以平台稳定性为由删除强制安全测试。若 NNC 不适合现场编写新测试，必须把该能力前移到 NNA 的永久正式测试；未覆盖的强制风险只能 FAIL / BLOCKED，不能静默消失。
