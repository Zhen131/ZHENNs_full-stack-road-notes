## 四、A、B、C 三类数据的固定含义

### 4.1 A：原始自然语言记录

A 是用户已有的原始交易材料，例如：

> 今天 65000 美元买入 0.1 BTC，手续费 5 美元。

已确认边界：

- 完整历史约 200–400 条；
- A 是原始事实来源，离线保留；
- 本阶段不开发 A → B 的专用自然语言转换器；
- 用户可使用其他 AI 或人工转换；
- 如果外部 AI 不是本地模型，必须先脱敏，不得上传不必要的真实隐私；
- 无论 B 由外部 AI 还是人工整理，转换结果都属于不可信输入，必须经过用户核对和账本确定性校验；
- A 不因 B 或 C 创建成功而删除。

### 4.2 B：账本现有导入导出格式的明文 JSON

B 不是新设计的“批量交易格式”，而是当前账本已经能导入、也能导出的 `BackupEnvelopeV1` JSON。

外层结构固定为：

```json
{
  "backupFormatVersion": 1,
  "appVersion": "...",
  "exportedAt": "...",
  "ledgerSchemaVersion": 1,
  "ledgerData": {
    "schemaVersion": 1,
    "assets": [],
    "trades": [],
    "priceSnapshots": [],
    "feeRules": []
  }
}
```

已确认边界：

- TypeScript 只负责在源码中定义合同；用户实际保存和导入的是 JSON；
- 【建议】先由账本导出合法样板，再让外部 AI / 人工填充历史交易；这是降低格式错误的稳妥做法，不是唯一允许的转换方式；
- BTC、ETH、ADA 内置资产可直接保留；
- 没有历史价格或手续费规则时，相应集合保持空数组，不能删除字段；
- 每笔交易应保留 A 中对应原句到现有 `rawText`；
- B 是明文敏感文件，必须离线或在用户认可的位置保存；
- 程序只读取 B，不移动、不删除、不主动上传 B；
- B 是救援与迁移材料，不是日常工作数据库；
- 首次历史迁移后，用户还计划定期主动导出新的 B 并保存到离线硬盘；这是人为维护的灾难恢复点，不等于自动备份，也不保证天然包含最后一次导出后的交易。

### 4.3 C：唯一正式加密工作文件

C 是账本程序日常打开和持续写入的加密文件。

已确认边界：

- 用户在系统文件选择器中决定 C 位于 Documents、iCloud Drive 或其他本地可见位置；
- iCloud Drive 在此阶段只是用户选择的文件位置，不等于应用已实现完整 iCloud 同步协议；
- 同一账本在文件夹中只出现一个正式 C；
- 程序不得为了备份自动制造一串 `C1 / C2 / C3`；
- 账本持久化范围内，IndexedDB 只允许保存文件句柄等元数据，不再保存第二份完整官方账本；
- 可重新获取的外部 K 线允许使用独立浏览器缓存，但该缓存不属于账本持久化，不进入 `LedgerData` 或 C，也不能参与估值；
- 持仓、图表和其他派生结果继续临时计算，不写入 C；
- C 不承担 B 的明文导入导出身份；
- “清空账本”只能在明确确认后清空 C 内的账本内容，不能悄悄删除整个 C 文件。

### 4.4 C 的文件外壳、扩展名和三种版本

C 采用自定义扩展名 `.lftl`，是一个 UTF-8 编码的加密 JSON 容器。

这里的“JSON 容器”只表示程序可以按严格结构读取外壳，不表示用户可以看到里面的 BTC、ETH、ADA 交易：

- C 不使用普通 `.json` 扩展名，避免与明文 B 混淆；
- C 第一版不采用自定义二进制格式；
- 未输入密码时，只能看到程序解锁所必需的技术字段和密文；
- 资产名称、交易数量、金额、平台、账本名称和保存时间等人类可读信息都必须位于密文内；
- 改动外层技术字段不能绕过校验：文件身份、版本、revision 和加密参数都必须进入 AES-GCM 的认证范围。

三种版本必须分开记录，不能再用一个含义模糊的 `version` 同时承担三件事：

| 字段 | 人话含义 | 什么时候需要变化 |
| --- | --- | --- |
| `fileFormatVersion` | 这个 `.lftl` 文件外壳怎样排版，`current` 和 `previous` 放在哪里 | 外壳字段或双代封装方式改变时 |
| `cryptoVersion` | 这把锁怎样工作，例如 PBKDF2、AES-GCM 和参数合同 | 加密算法、派生方式或认证合同改变时 |
| `ledgerSchemaVersion` | 解密后的账本内容怎样排版，例如 `LedgerData` 的业务字段 | Trade、PriceSnapshot 等正式账本结构改变时 |

可以把它理解成游戏光盘、主机解锁方式和存档格式是三层不同问题：换了存档字段，不代表光盘盒和锁也必须一起改版。

当前 IndexedDB 已实现的 `StoredLedgerEnvelopeV2.formatVersion = 2` 与未来 `.lftl` 的 `fileFormatVersion = 1` 属于两份不同合同。后者从第一版开始编号，不是把现有加密“降级到 1”。在源码真正实现前，`.lftl` 仍然是已确认设计，不是已经存在的产品能力。

### 4.5 C 第一版的目标 TypeScript 合同

字段语义和分层已经确认。后续实现可以按项目命名规范调整类型放置位置，但不得改变以下数据边界：

```ts
type LedgerFileV1 = {
  fileFormatVersion: 1;
  fileId: string;
  crypto: {
    cryptoVersion: 1;
    kdf: {
      name: "PBKDF2";
      hash: "SHA-256";
      iterations: 600000;
      saltBase64Url: string;
    };
    cipher: {
      name: "AES-GCM";
      keyLength: 256;
      tagLength: 128;
    };
  };
  current: EncryptedLedgerGenerationV1;
  previous: EncryptedLedgerGenerationV1 | null;
};

type EncryptedLedgerGenerationV1 = {
  revisionId: string;
  parentRevisionId: string | null;
  ledgerSchemaVersion: 1;
  ivBase64Url: string;
  ciphertextBase64Url: string;
};

type DecryptedLedgerPayloadV1 = {
  savedAt: string;
  ledgerData: LedgerData;
};
```

固定含义：

- `current` 和 `previous` 是两份可独立认证、解密和校验的完整账本，不是增量补丁；
- 同一个 C 的两代使用同一个密码派生合同和 salt，但每次加密必须生成新的 IV；
- `savedAt` 与完整 `LedgerData` 位于密文内；
- `fileId`、三种版本、revision 关系和解锁所需的加密参数位于外层，但必须作为 AES-GCM 附加认证数据参与认证；
- `previous = null` 只表示新账本还没有真实的上一代，不表示格式损坏。

## 六、C 的“左脚踩右脚”安全模型

用户对 C 的固定心智模型是“左脚踩右脚”：文件夹中只有一个当前工作的 C；形成真实上一历史状态后，C 内保留最近两代可用的完整账本。首次创建只有 current，允许 `previous = null`。

【建议】对外术语使用：

- 当前可用版；
- 上一可用版；
- 候选版只存在于一次保存过程。

示例：

```text
C 当前包含：
当前可用版：300 笔
上一可用版：299 笔

新增一笔 BTC 后：
先在内存生成 301 笔候选版
→ 完整校验
→ 加密
→ 安全写入
→ 关闭文件
→ 重新读取、解密、完整校验
→ 全部通过后，C 变为 301 + 300

再新增一笔 ETH：
302 候选版完成同样流程
→ 成功后，C 变为 302 + 301
```

核心规则：

1. 候选版是一份完整账本，不是只保存一条增量补丁。
2. 候选版没有通过完整 Validator 前，旧的可用版不能被覆盖。
3. 写入流关闭后必须重新读取同一个 C。
4. 只有解密、结构校验、资源策略和业务时间线全部通过，UI 才能显示“已保存”。
5. 只有密码正确、当前版不可用且上一版完整通过认证、结构、资源和业务校验时，程序才进入明确恢复状态。
6. 恢复不得静默发生；页面必须明确告诉用户“最新一次保存没有恢复，现在恢复的是上一版”。
7. 用户取消恢复时不进入账本、不写 C；用户确认后，在原 C 中用已验证的上一版生成新的 current，保留同一 `fileId`，新 current 的 `parentRevisionId` 指向被恢复的 previous revision。
8. 恢复写入仍必须经过 write → close → 同一句柄 readback → 两代认证解密 → 完整 Validator；全部通过后才能挂载普通 Dashboard。
9. 密码错误、previous 损坏、两代都损坏、外层 metadata、`fileId` 或 revision 链异常时，不得显示可恢复成功，也不得写入。
10. C 整个被删除、硬盘损坏或 iCloud 文件彻底丢失时，两代内容会一起丢失；双版本只解决最近一次写入损坏，不解决整个文件消失。
11. Git、Time Machine 或云盘可以作为外部灾难恢复，但不能代替程序自己的安全保存。
12. Git 不进入 8 月 3 日必做范围，日常保存安全不能依赖用户是否记得提交加密文件。

首次从 B 创建 C 时：

```text
B：300 笔明文，继续由用户保留
→ 在内存中形成并校验 300 笔候选账本
→ 加密并写入新 C
→ 关闭写入流
→ 重新读取、解密和完整校验

成功后：
current：300 笔
previous：null
```

第一次真实新增或修改成功后，才自然形成两代：

```text
current：301 笔
previous：300 笔
```

不在首次创建时加密两份内容相同的 300 笔，因为那不是一份真实的上一历史状态，也不能防止整个 C 被删除或丢失。第一次真实修改前，原始 B 承担外部救援材料的角色。

该模型应位于加密文件与存储层，不修改 `LedgerData` 的业务集合。

## 七、C 的单写入者、重开与密码规则

### 7.1 同一个 C 只允许一个 Chrome 标签页进入

禁止同一文件被两个账本页面同时编辑。

正确模型：

- 第一个标签页获得只存在于浏览器运行期的独占锁；
- 第二个标签页立即显示“该账本已在另一标签页使用”；
- “同一个 C”按用户实际选择的同一个物理文件判断，使用文件句柄的 `isSameEntry()` 能力；不能只用 `fileId` 作为物理文件锁键；
- Finder 字节复制件即使保留相同 `fileId`，只要 `isSameEntry()` 判定不是同一物理文件，就允许用户分别打开，程序仍不登记、扫描或合并复制件；
- 标签页关闭、跳转或崩溃后，运行时锁自动释放；
- 不在 C 或 IndexedDB 写永久 `locked=true`；
- 不提供日常“强制抢锁”按钮；
- 每次真正写文件时再取得短时文件写锁；
- 写入前比较磁盘版本和当前页面加载版本；
- 发现 C 被其他程序或外部同步修改后，拒绝旧页面覆盖，要求重新打开；
- 当前浏览器缺少可靠的物理文件比较或运行期锁能力时，C 的可写入口明确不可用，不带着风险降级写入；
- 极端浏览器故障的恢复方式是完全退出并重开 Chrome，不要求重启电脑或手工删除占位文件。

浏览器页面不能永久占有操作系统文件。这里实际需要两层短期保护：

- 同一 Chrome 运行期内的账本占用，阻止两个本应用标签页同时进入同一个 C；
- 每次写回时取得短时文件写锁，写入流关闭后释放。

### 7.2 文件身份与 revision

每个新建 C 生成一个随机 `fileId`，只生成一次：

- 改文件名、移动目录或放入 iCloud Drive，不改变 `fileId`；
- 用户在 Finder 中复制 C 时，复制件按字节保留相同 `fileId`；
- 程序不登记哪个是原件、哪个是副本，不扫描文件夹，不自动建立分叉，也不合并或修改其他复制件；
- 用户明确选择打开哪个 `.lftl`，哪个就是本次会话的当前工作文件；
- 文件名相同不能证明是同一本账，`fileId` 不同则一定不是同一个 C。

每一代使用随机 `revisionId + parentRevisionId`：

```text
打开时读到 current.revisionId = A7X9
→ 保存前重新读取磁盘
→ 仍为 A7X9：允许继续准备保存
→ 已变为 B2K8：拒绝旧页面覆盖，要求重新打开
```

新一代 `revisionId` 每次随机生成，`parentRevisionId` 指向保存前的 current。第一代的 `parentRevisionId = null`。

第一版不使用 SHA-256 `revisionHash`。三者职责必须分开：

- AES-GCM 负责发现密文或认证元数据被无密钥篡改；
- Chrome 运行期占用和短时文件写锁负责减少同时写入；
- revision 只负责发现当前选中文件在页面打开后是否已经变化，防止旧页面覆盖新状态。

普通哈希若与文件一起被攻击者修改，攻击者可以重新计算，不能取代 AES-GCM。JSON 也不是可执行代码：文件必须经过严格结构、资源和业务校验，不得使用 `eval` 或把内容当 HTML 执行；异常输入应受控拒绝，而不是继续打开或静默写回。

### 7.3 保存后的强制复读

写入流关闭后，程序必须重新读取用户当前选中的同一个 C，并至少核对：

1. 外层结构和版本合同受支持；
2. `fileId` 与本次会话加载的文件一致；
3. `current.revisionId` 是本次预期生成的新 revision；
4. `current.parentRevisionId` 指向保存前的 current；
5. 有上一代时，`previous.revisionId` 等于新的 `current.parentRevisionId`；
6. current 和 previous 各自通过 AES-GCM 认证与解密；
7. 解密后的 `LedgerData` 通过运行时结构校验、资源上限和完整业务时间线 Validator。

任一项失败都不能显示“已保存”。如果正确密码下 current 不可用而 previous 完整可用，必须进入明确恢复状态，并告诉用户“最新一次保存没有恢复，现在恢复的是上一版”；不得静默把旧数据伪装成最新状态。用户取消时零写入；用户确认后按 §6 的恢复写入规则在原 C 中生成新的 current，完成 close 后同句柄复读和完整验证后才进入账本。

### 7.4 再次打开

- 账本持久化范围内，IndexedDB 只记住上次 C 的文件句柄；独立行情缓存不改变这一账本边界；
- 有权限时直接进入该 C 的解锁页；
- 权限失效时显示“重新连接此文件”；
- C 被移动、删除或选错时，不自动创建空账本；
- 当前 C 的身份必须可核对，不能因文件名相同就认为是同一本账。

### 7.5 密码

- C 只有一个用户设定的核心密码；
- 没有恢复码、管理员后门或第二套解锁秘密；
- 新建时必须明确提示：忘记密码将永久失去对该 C 的访问；
- 用户必须两次输入一致；
- 密码只在当前标签页解锁期使用，刷新、关闭或点击“立即锁定”后失效；
- “立即锁定”同时清除内存中的解锁材料并释放当前 C 的标签页占用；
- 不做闲置自动锁定；
- 不跨 Chrome 重启保存可直接解密 C 的凭据；
- B 可用于用户自行救援，但程序不承诺 B 包含最后一次导出后的交易。

原 C 不提供“修改核心密码”按钮，也不做两代原地重新加密。换密码采用迁移流程：

```text
用旧密码解锁旧 C
→ 导出完整明文 B
→ 新建一个新的 .lftl
→ 设置新密码
→ 原子导入 B
→ 关闭并重新打开新 C
→ 核对 BTC、ETH、ADA 和交易数量
→ 用户确认后自行处理旧 C 与明文 B
```

迁移边界：

- 新 C 使用新的 `fileId`、salt、密钥和核心密码；
- 新 C 初始 `previous = null`；
- 应用不自动删除旧 C，也不自动删除 B；
- 全程明确提醒 B 是明文敏感文件；
- 当前已实现的 12–128 字符密码规则在后续实现时继续作为输入基线，若要改变必须另行讨论。

未来 Keychain / 生物识别规则：

- 核心密码仍是跨设备的唯一通用秘密；
- 每台新设备第一次必须输入核心密码；
- Mac 只在本机 Keychain 保存设备侧凭据，并由 Touch ID 放行；
- iPhone 同理使用本机 Keychain + Face ID；
- 不通过 iCloud Keychain 自动同步解锁凭据；
- 换新设备仍必须知道核心密码；
- 生物识别信息不写入 C。

## 八、B 导入 C 的固定语义

用户看到的首次流程：

```text
新建账本
→ 设置核心密码
→ 进入空账本
→ 点击导入
→ 选择 B JSON
→ 校验和确认
→ 完整数据进入并保存到用户选择的 C
```

是否先在磁盘写出零交易 C 属于实现细节，不能改变用户合同。

导入规则：

1. B 导入新空账本时采用整本替换，不做合并。
2. B 有 300 笔，成功结果就是 B 的完整 300 笔，不是与测试交易拼成 303 笔。
3. 任一硬错误都拒绝整本导入。
4. 不允许“跳过第 147 笔，先导入其余 299 笔”。
5. 失败时 B 原封不动，C 保持导入前完整状态。
6. JSON 语法错误尽可能定位行、列。
7. 业务错误至少给出 `trades[146].quantity` 这类准确路径，并附日期、资产、买卖方向等摘要。
8. 多个错误应提供可复制的完整错误清单，不能让用户每次只修一个再重新发现下一个。
9. 当前 8 MiB 文件上限继续有效；200–400 条通常不会触顶，但必须用真实 B 测量，不能凭估计宣称通过。

重复交易规则：

- 相同 ID 是硬错误；
- ID 不同但业务字段高度相同的交易只能标记为“可疑重复”，不能直接判定为重复；
- 两笔都有精确时间时，只有时间完全相同且核心字段相同才提示；
- 至少一笔只有日期精度时，同一自然日且核心字段相同就提示；
- 两笔都有不同的精确时间时，不因为同日、同价、同数量就提示，避免把 BTC / ETH / ADA 的合法拆单误判成重复；
- 核心字段包括日期规则、买卖方向、资产、数量、单价、总额和币种；
- 数值先按十进制语义规范化比较，`0.10` 与 `0.1` 视为相同；
- `id`、`createdAt`、`updatedAt`、`note`、`rawText` 和 `feeRuleId` 不参与相似度判断；
- 核心字段和 `fee + feeCurrency` 都相同，标为“高度可疑”；
- 核心字段相同但手续费或手续费币种不同，标为“一般可疑”；
- 多条完全相同的交易按一个可疑组展示，列出组内索引，不展开成所有两两组合。

可疑重复的导入交互：

- 在一个集中弹窗中列出全部可疑组；
- 明确说明继续导入可能把同一笔交易计算成两笔；
- 用户可以取消导入，自行修改明文 B；
- 用户也可以通过一次明确确认，忽略风险并按原样导入完整 B；
- 不要求逐组打勾，因为程序不会修改、删除或部分导入 B；
- 可疑重复确认不能绕过相同 ID、非法金额、超卖或其他硬错误。

导入错误与报告规则：

- 页面始终显示硬错误总数和可疑重复组总数；
- 页面直接展示前 50 项详细问题，放入内部可滚动区域；
- 提供“复制完整导入报告”，格式为人和 AI 都能阅读的 Markdown 纯文本；
- 每项至少包含错误码、准确路径、交易摘要和问题说明；
- 可疑重复报告包含等级、组内路径 / 索引、交易摘要和“未自动删除”的处理说明；
- 报告开头必须提醒其中可能包含交易日期、资产、数量和金额等隐私；
- 页面只显示前 50 项不等于丢弃后续详情；
- 为防异常文件拖死页面，详细问题最多保留和复制前 1000 项；
- 超过 1000 项时必须明确写明报告已截断，并要求用户修正后重新检查；
- 可疑重复按组计数，不把 N 条相同交易展开成 `N × (N - 1) / 2` 对。

## 九、手续费必须进入真实成本和净盈亏

用户确认完整历史手续费全部是 USD / USDT，因此 8 月 3 日不需要处理 BTC、ETH、ADA、BNB 等资产手续费导致的持仓数量变化。

确定性计算规则：

```text
买入后新增成本
= 成交总额 + 买入手续费

卖出净收入
= 成交总额 - 卖出手续费

已实现净盈亏
= 卖出净收入 - 本次卖出移除的含费成本

未实现净盈亏
= 当前市场价值 - 剩余含费成本
```

具体边界：

- 买入手续费进入成本基础，并随平均成本法在后续卖出时按份额移除；
- 卖出手续费直接减少本次净收入；
- `feeRule` 只帮助录入，不参与追溯重算；
- 计算必须使用每笔 Trade 已实际保存的 `fee`；
- USD / USDT 延续当前 `1 USDT ≈ 1 USD` 产品口径，并明确这是近似汇总，不是假装严格美元换汇；
- 净成本和净盈亏仍是派生结果，不存入 C；
- 该修正排在 UI 重构之前，因为首页不能美化一个已知漏费的数字。

## 十、交易与价格的单条安全纠错

### 10.1 交易编辑

允许纠正所有用户业务字段：

- 日期和时间精度；
- BTC / ETH / ADA 等资产；
- 买入 / 卖出方向；
- 数量；
- 单价；
- 总额；
- 币种；
- 手续费和手续费币种；
- 手续费规则引用；
- 备注；
- 原始文本。

不允许编辑：

- Trade ID；
- 原始 `createdAt`。

成功后只更新 `updatedAt`。

保存流程：

```text
点击编辑
→ 将原交易复制到编辑草稿
→ 正式账本暂时不变
→ 用户修改
→ 点击“检查并保存”
→ 生成替换该交易后的完整候选账本
→ 完整时间线、成本、持仓与资源校验
→ 计算修改前后差异和下游影响
→ 用户再次确认
→ 才进入 C 的安全保存流程
```

合法修改也必须显示类似 Git diff 的确认：

- 只显示真正变化的字段；
- 显示受影响资产的数量、成本、已实现盈亏变化；
- 说明多少笔后续交易重新校验通过；
- 确认按钮使用明确文案“确认替换这笔交易”，不能只写“确定”；
- 只需要一次内容充分的差异确认，不要求重新输入密码，也不连续弹出多次确认；
- 取消确认时返回仍保留内容的编辑草稿。

若把早期 BTC 买入量改小会导致后续卖出超出持仓，则直接拒绝并定位第一笔受影响的卖出，原交易保持不变。

### 10.2 交易删除

- 一次只能删除一笔；
- 删除前先构造完整候选账本并重放；
- 删除合法时显示交易详情和持仓、成本、净盈亏变化；
- 使用明确红色按钮“确认删除这笔交易”；
- 不要求额外输入交易 ID；
- 删除会破坏后续时间线时直接拒绝；
- 本阶段不引入回收站、软删除或 tombstone schema。

### 10.3 价格编辑与删除

8 月 3 日范围同时包含价格快照纠错，不只做交易。

- 手工价格可以单条编辑或删除；
- Binance 快照若被人工修改，必须明确提示“将转为手工价格”；
- 转换后 `source = manual`；
- 删除结构化 Binance provenance；
- 可在备注中记录“原为 Binance 快照，已由用户手工修正”；
- 不允许手工修改数值后继续冒充 Binance 原始数据；
- 价格纠错同样使用候选、校验、差异预览和二次确认。

## 十一、首页与信息架构

总体风格固定为“简洁私人理财”，不是专业交易终端。

### 11.1 页面骨架

- 只有一个主首页；
- 不增加底部或顶部主导航栏；

- “清空账本”等危险操作放在设置中的独立危险区域，不长期占据首页；
- 右下角固定 `+` 用于新增交易；
- 桌面端新增交易使用覆盖层或右侧面板；
- 未来移动端可改为底部 sheet；
- 完整交易历史通过“查看全部”进入，不再增加第二个悬浮按钮；
- 首页只保留最近交易摘要，完整筛选、编辑和删除进入“查看全部”；
- 本阶段不做动画和背景图片。

### 11.2 顶部摘要

首页第一眼固定显示：

1. 组合当前市场价值；
2. 剩余持仓成本；
3. 未实现净盈亏；
4. 已实现净盈亏。

累计手续费进入详情，不挤入顶部四项。

### 11.3 三层图表

#### 第一层：组合总价值与持仓成本

第一层横跨整页，使用同一 USD 总额纵轴：

- 组合总市场价值：普通线，随可用市场价格变化；
- 剩余持仓成本基础：阶梯线，在买入、卖出时发生水平 / 垂直变化；

- 市场价值高于成本代表当前持仓浮盈；
- 市场价值低于成本代表当前持仓浮亏；
- 左上角当前只显示固定 `USD 等值`；
- 欧元、人民币或加密货币换算属于未来能力，本阶段不做选择器。

不得在该图加入“全组合平均买入价”第三条线，因为：

- 市值和成本的单位是 USD 总额；
- BTC 平均成本单位是 USD / BTC；

- ADA 是 USD / ADA；
- 不同资产的单位成本不能合成一条可比较的组合线。

未来单资产详情可显示：

- BTC / ETH / ADA 自身 K 线；
- 该资产的平均买入价虚线；
- 买入和卖出标记。

#### 第二层：当前资产分配

第二层是一个完整卡片内的左右结构：

- 左侧约三分之一为饼图；
- 右侧约三分之二为按占比从高到低排列的资产；
- 排名显示资产、占比，并可同时显示金额和数量；
- 不是只放一个孤立圆圈。

#### 第三层：交易活跃热力图

- 完整保留最近 365 天交易热力图；
- 显示哪些自然日发生过交易；
- 点击日期可继续联动交易列表；
- 不折叠成隐藏功能。

### 11.4 缺价时的真实性

示例：

```text
BTC 当前价值：6,500 USD
ETH 当前价值：4,400 USD
ADA 当前价值：未知
```

## 十二、成交价、估值快照与外部 K 线必须分层

三类价格的业务含义不同：

| 数据 | 示例 | 用途 | 是否属于核心账本 |
| --- | --- | --- | --- |
| 交易成交价 | 0.1 BTC 以 50,000 USD 买入 | 计算真实成本 | 是，属于 Trade |
| 账本估值快照 | Binance / 手工记录 BTC 65,000 | 计算某时点市值与未实现盈亏 | 是，属于 PriceSnapshot |
| 外部 K 线 | BTCUSDT 日 / 周 / 月 OHLCV | 查看市场背景和单资产行情 | 否，属于 Market Data 层 |

当前 Binance 真实行为：

- 使用公开 `exchangeInfo` 和 `/api/v3/ticker/price`；
- 只查询最新价；
- 解锁后自动尝试一次，也可手工刷新；
- 只刷新非零持仓；
- 同一资产同一天重复刷新时更新当天 canonical Binance 快照；
- 不保存每分钟河流式价格；
- 不接历史 K 线。

### 12.1 第一版 provider、缓存和离线边界

历史 K 线第一版采用 Binance-first：

- 第一来源使用 Binance 公共市场数据与 `/api/v3/klines`；
- 第一版不同时接入第二来源，也不把“双来源结果一致”设为打开资产详情页的前提；
- CoinGecko 或其他第二来源只作为未来可替换或降级方向；
- Binance 只是第一个 provider，不成为核心账本依赖；
- provider 负责 candles、请求限制、失败和来源信息，账本核心只接收显示所需的标准化行情结果。

K 线允许使用独立、可重建的 `MarketDataCache`：

- 缓存可以落在 IndexedDB 等浏览器存储中，但必须与账本文件句柄元数据和正式账本数据分开；
- 缓存不进入 `LedgerData`、B 或 C，不成为第二份官方账本；
- 缓存删除、损坏或换浏览器后可以重新下载，不触发账本迁移；
- K 线只用于市场背景和单资产图表，不写成 `PriceSnapshot`，不参与当前市值或盈亏估值；
- 资产有历史交易时，第一版最多向前取到该资产最早一笔 Trade 之前 30 天；没有交易时取最近 365 天；
- 这条时间边界控制第一版需要获取和保留的数据范围，不代表供应商永久可用或历史数据天然完整。

离线或 Binance 请求失败时：

- 有缓存就显示最后一次可用 K 线，并紧贴显示来源和更新时间；
- 没有缓存就明确显示行情暂不可用；
- 不清空 C，不清除既有缓存，不把缺失 K 线替换为 `0`、成交价或成本价；
- 过期或未完成的 K 线也不能进入估值链。

### 12.2 单资产详情页与 K 线周期

K 线进入独立的单资产详情页，不增加新的主导航：

- 可以从持仓表、资产配置图和交易列表中的 BTC / ETH / ADA 名称进入；
- 已清仓资产仍可以从历史交易进入；
- 详情页默认显示日 K，可切换日 K、周 K、月 K；
- 不在第一版加入 5 分钟、15 分钟等短周期；
- 默认视窗分别显示最近 90 根日 K、52 根周 K、24 根月 K；
- 用户可以拖动或缩放回看，最远不超过该资产已获取的第一版时间边界；
- 当前选择的周期、缩放和滚动位置属于会话界面状态，不进入 C。

### 12.3 账本事实覆盖层

K 线图叠加两类由账本事实临时派生的信息：

1. 含手续费的历史平均成本阶梯线；
2. 买入和卖出标记。

成本线规则：

- 必须按当时已经发生的交易重放，不能把今天的平均成本倒推到历史；
- 仓位归零时中断，重新买入后从新成本段开始；
- 只从 Trade 派生，不写回 K 线缓存、`LedgerData` 或 C。

买卖标记规则：

- 买入标记放在对应 K 线最低价下方，使用买入色；
- 卖出标记放在对应 K 线最高价上方，使用卖出色；
- 同一根 K 线有多笔同向交易时合并显示数量，例如“买 3”或“卖 2”，买卖仍分别位于下方和上方；
- hover 或点击后显示该组每一笔交易的日期 / 时间、数量、成交价、总额和手续费；
- `note` 与 `rawText` 留在交易详情，不塞入 K 线悬浮信息。

### 12.4 刷新规则

- 进入资产详情页时先显示缓存，再自动尝试一次 Binance 刷新；
- 不轮询、不接 WebSocket；
- 用户可以手工刷新；
- 当前尚未收盘的 K 线必须标成“未完成”，并显示本次获取时间；
- 刷新失败时保留缓存和页面中的账本覆盖层，不影响 C 的打开、编辑或保存。

Binance 官方当前支持历史 K 线，但“当前可用”不等于未来永远免费或稳定。第二来源以后可以接在同一 provider 边界后面，不需要迁移 Trade、PriceSnapshot 或 C。

## 十三、NLP 课程与自然语言录入的已确认边界

以下是 2026-07-28 确认的原优先级：8 月 3 日真实使用 Gate 通过后，到 2026-09-25 DEIK.AI Demo 截止前，主要开发时间优先给 NLP Type 1 与比赛 Demo，Tauri、Keychain 和 Touch ID 不抢占这段窗口。2026-07-31 因纯浏览器无法满足严格文件事务合同，产品负责人已把 Mac 桌面端提前为下一阶段优先方向；新的实际顺序以 §16.3 为准，NLP 与比赛目标保留但时间安排必须在后续计划模式重新评估。

2026-07-27 的机器环境事实为：Mac 使用 M5、16 GB 内存，当时尚未安装 Ollama。第一版模型方向已经固定为 Ollama 本地运行的 `qwen3:8b`；真正实施前仍需重新检查安装状态、实际速度和可用资源。

### 13.1 已确认路线

- 课程选择 Type 1 Multi-Agent；
- 所有 Agent 使用 Ollama 本地运行；
- 第一版统一使用 `qwen3:8b`，提取 Agent、审核 Agent 和单 Agent baseline 共享同一个基础模型，按顺序调用；
- 模型通过可替换的连接边界接入，不把 Qwen 专有字段写进 `TradeDraft`、`LedgerData` 或 C；以后换模型时重新验收，不迁移账本；
- 产品第一版只接收文字；
- 中文是主要产品语言，英文只作为明确标注的兼容范围，不因少量英文成功案例宣称完整双语；
- NLP 第一阶段只提出新增交易草稿；
- 不允许 NLP 修改或删除既有交易；
- 不允许生成投资建议；
- 不允许未经用户确认静默写入；
- 缺失或歧义字段必须询问用户；
- 不得编造资产、价格、数量、币种、手续费或日期；
- 最终业务合法性由确定性 Validator 判断；
- Agent 不能替代持仓时间线、金额容差、资源策略和写入规则。

目标链：

```text
用户的一行或多行文本
→ 按换行切成独立交易原句
→ 提取 Agent 逐行提出候选
→ 审核 Agent 对照每行原句找错读、幻觉和歧义
→ 有原文依据的错误最多自动反馈修正两轮
→ 缺失、真实歧义或可计算的缺项由用户补充或确认
→ 形成整批 TradeDraft
→ 确定性 Validator 按输入顺序预检整批
→ 用户查看整批摘要并明确确认
→ 现有交易写入链整批成功或整批不写
→ C
```

### 13.2 为什么需要两个 Agent

角色不能为了满足“至少两个 Agent”机械拆分。

有价值的角色边界是：

- 提取 Agent：只把原句映射为候选字段，并显式标记缺失；
- 审核 Agent：逐字段检查候选是否得到原句支持，找出擅自补值、单位错读、币种混淆和未处理歧义；
- 审核 Agent 不直接成为第二个随意提取器；
- 原句明确写“5 美元手续费”，却被填成 `5 USDT` 时，可以退回修正；
- 原句只写“手续费 5”时，必须询问用户，不能靠多轮对话把猜测包装成确定；
- 原句缺少的信息不能因为多轮反馈变成“模型已经确认的事实”；
- 自动反馈达到两轮仍未解决时停止，并把问题交还用户。

第一版不为了增加 Agent 数量再造“合法性 Agent”“写入 Agent”或“计算 Agent”。业务合法性、精确十进制计算和正式写入继续由确定性程序负责。

### 13.3 第一版文本批量录入

第一版支持一次输入一笔或多笔，但采用受约束的批量格式：

- 正式分隔符是换行，一行只描述一笔交易；
- 空行可以忽略；
- 每一行必须自包含，不从上一行继承资产、价格、手续费或其他事实；
- 逗号、冒号和分号不作为正式交易分隔符；
- 一行中混写多笔时要求用户拆行，不让模型自由猜测交易边界。

数量、单价和成交总额中缺少一项但另外两项明确时，确定性程序可以算出候选值，但不能静默补入：

```text
用户：花 6500 USD 买了 0.1 BTC，手续费 5 USD
系统：根据 6500 ÷ 0.1，候选单价为 65000 USD，是否正确？
用户确认后：该值才进入候选 TradeDraft
```

这形成两道不同的确认门：

1. 字段补齐门：缺失信息由用户补充；可精确计算的候选值也要把公式和结果展示给用户确认；
2. 整批写入门：所有交易完整并按顺序通过 Validator 后，再由用户确认整批写入。

手续费未出现时不得自动当成 `0`；用户必须明确提供手续费，或明确回答“无手续费”。只要一笔未补齐、未通过或未确认，整批都不能写入 C；已经识别正确的其他行可以保留在确认页面等待修正。

### 13.4 写入 C 的边界

用户确认后，C 只保存：

- 正常结构化 Trade；
- 触发该交易的用户原句与后续用户澄清，按发生顺序保留在该 Trade 的 `rawText`。

不进入 C：

- Agent 对话；
- 审核批评；
- 置信度；
- 迭代日志；
- 课程实验结果；
- prompt；
- 模型响应原文。

`rawText` 只保留用户说过或输入过的内容，不保存 Agent 推理、批评、置信度或内部工作记录。课程数据和实验日志使用独立评测材料，不污染正式金融事实。该设计不要求修改 `LedgerData` 的四个核心集合。

### 13.5 后续扩展边界

以下能力不进入第一版文字录入范围：

- 语音：以后作为独立的“语音 → 文本”前置层，再复用同一 TradeDraft 链；
- 图片：以后先做本地 OCR / 视觉提取，再把每一笔候选交易送入同一审核和确认链；
- 账本问答：以后把“上个月赚了多少”等问题转成结构化查询，由账本确定性计算程序给出数字，模型只负责理解问题和组织表达；
- RAG 可以以后帮助检索备注或文字材料，但不能代替结构化账本计算财务数字。

这些扩展不要求现在增加第三个 Agent，也不改变 `LedgerData` 或 C 的第一版合同。

### 13.6 课程必须保留的实验要求

- 与单 Prompt、单 Agent baseline 公平比较；
- baseline 与 multi-agent 使用可比较的模型、输入、字段合同和测试集；
- 指标至少覆盖字段正确率、缺失 / 歧义识别、幻觉字段、错误写入风险和延迟；
- 最终材料能整理为 Jupyter notebook、5–10 分钟视频和可运行应用；
- 不能只展示几个成功例子就宣称 multi-agent 显著更好。

### 13.7 暂停讨论、尚未决定

当前只固定能保护产品边界的 NLP 大方向，不继续照亮课程实验细节。以下内容仍是未来议题：

- 数据集规模、难例分层和标注方法；
- baseline 与 multi-agent 的严格公平协议和主要成绩计算方式；
- 中文主集与英文兼容集在课程评测中的具体数量和比例；
- prompt、temperature、context window 和重复运行规则；
- 课程 notebook、视频与应用的具体结构。

语音、图片和账本问答的具体实现同样后移。任何后续 AI 不得把这些课程实验或扩展实现细节擅自写成已确认方案。

## 十六、iCloud、桌面端、移动端和生物识别的长期依赖

### 16.1 当前阶段

- Chrome 使用 File System Access 打开用户选定的 C；
- 正式 Mac App 之前继续使用终端启动 Chrome 版，不为过渡阶段单独开发一键启动器；
- C 可以由用户放入 iCloud Drive；
- 浏览器只能确认文件已经写入用户选择的位置；
- macOS / iCloud 何时上传、是否产生冲突副本不由当前 Web 应用完全控制；
- 因此不能宣传“已经实现 iCloud 自动同步和冲突处理”；
- 用户当前不选择自建同步服务器，原因是维护成本和额外攻击面；后续设备共享优先建立在加密 C 与 Apple 平台能力上；
- 无网络、iCloud 暂时不可用或同步延迟时，本机账本仍必须可以打开和保存，云能力不能反过来破坏 local-first。

### 16.2 2026-07-28 确认的原顺序

本节保留当时的真实决策过程，不再作为 2026-07-31 之后的直接执行顺序；最新顺序边界见 §16.3。

```text
Chrome + C 真实使用地基
→ NLP 课程与 9 月 Idea / Demo
→ 论文 benchmark 重新启动
→ Mac 桌面 App
→ 原生 iCloud 文档协调
→ 本机 Keychain + Touch ID
→ iPhone 第一版只读
→ iPhone 写入与多设备冲突处理
```

说明：

- Mac / 桌面预计在前三到五个月内是唯一写入者；
- iPhone 第一版只读取和展示 C，不新增、编辑或删除；
- iPhone 只读版不得把自己打开过的旧 C 或任何派生状态回写到 iCloud；
- 手机只读时不需要解决两个设备同时写；
- 只有进入手机写入阶段，才需要 revision、冲突检测、用户决策和可能的合并；
- iCloud、Keychain、Touch ID / Face ID 是不同问题，不能写成一个功能；
- Keychain / 生物识别必须在原生 App 阶段接入；
- Tauri 是 Mac App 的当前方向；
- 移动端最终采用 Capacitor、Tauri mobile 或其他方案尚未最终确认。

跨端复用边界：

- 可以复用：`LedgerData`、交易与价格 Validator、成本 / 盈亏计算、加密合同、导入导出核心、主要 React 组件，以及以后 NLP 生成 `TradeDraft` 的业务链；
- 必须分别实现和验收：Mac / iPhone 的文件访问、iCloud 文档协调、Keychain、Touch ID / Face ID、小屏交互，以及设备写权限；
- “复用同一核心”不等于把网页一键打包成两个完全相同且无需原生工作的 App。

### 16.3 2026-07-31 桌面端提前决定

第三批历史导入已经证明：纯浏览器可以完成 B 预检、正常写入、复读验证和仍有权限时的补偿恢复，但不能在 Chrome 崩溃、权限永久丢失或外部程序先改写后继续执行严格回滚。产品负责人因此确认以下新顺序边界：

```text
固定当前浏览器候选与 BLOCKED 证据
→ 先用计划模式确认当前位置、复用范围、严格桌面事务合同和批次地图
→ Mac 桌面端成为下一阶段优先方向
→ 在桌面地基稳定后再重排 NLP、比赛、benchmark 和原 07～20 产品批次
→ 手机端继续后移
```

当前已确认：

- Mac 桌面端提前，当前纯浏览器版本只作为过渡候选和兼容参考，不再继续用浏览器能力逼近无法兑现的绝对事务合同；
- 继续复用 `LedgerData`、Validator、成本 / 盈亏计算、`.lftl` 加密合同、B 导入预检、主要 React 组件和现有正式测试；
- 安全关键的文件写入必须进入原生能力边界，至少讨论同目录临时文件、文件与目录同步、原子替换、稳定文件锁、启动恢复和进程崩溃验收；
- 手机端当前不实施；桌面迁移不顺手扩张为 iCloud、Keychain、Touch ID、Windows、移动端或完整原生 UI 重写；
- 03A、03B 和未来 Git 合入继续保留为历史事实；源码进入 `main` 不把 03 的 BLOCKED 改写为 PASS。

尚未决定，必须留到计划模式：

- Tauri 静态前端与本地 Ollama 的最终连接方式；
- 原生文件事务的精确威胁模型、提交 / 回滚 / 启动恢复合同和外部程序协作边界；
- Chrome 旧数据、C connection record 与桌面端文件授权的迁移方式；
- macOS 自用、签名公证、自动更新和跨平台发布分别在哪个阶段进入；
- 新桌面地基占用几个正常批次，以及原 07～20 的编号和依赖如何调整。

在上述问题完成计划模式讨论前，不得自动生成桌面开发执行文档，也不得把“Tauri 是当前方向”扩写成已经完成技术选型和实施设计。

## 十九、给后续 AI 的使用说明

开始任何实现前：

1. 先读 `AGENTS.md` 和 `ledger-workflow`；
2. 再读当前开发状态、源码 README 和真实相关源码；
3. 把本文当成最新产品决策背景，而不是已实现能力；
4. 明确本次只处理哪一个问题；
5. 用 BTC、ETH、ADA 场景向用户说明取舍；
6. 优先使用自然、中文逻辑的表达；专业术语只在必要时使用，并立即用人话解释；
7. 一次优先讨论一个真正会改变方案的问题，不连续抛出大量抽象选择；

本文的作用是让后续 AI 知道“用户已经决定了什么、为什么这样决定、哪些边界不能越过”。它不替代 00B 总需求快照或任何批次执行文档，也不授权任何 Agent 直接按本文大包实施。
