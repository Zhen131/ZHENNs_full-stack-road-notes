## 3. 合同与数据流结果

### 3.1 `.lftl V1`

三类版本保持独立：

| 版本 | 当前值 | 作用 |
| --- | --- | --- |
| `fileFormatVersion` | `1` | `.lftl` 外壳 |
| `cryptoVersion` | `1` | C 的 KDF、cipher 与 AAD |
| `ledgerSchemaVersion` | `1` | 解密后的 `LedgerData` |

现有 IndexedDB `StoredLedgerEnvelopeV2.formatVersion = 2` 没有并入、扩展或复用为 C 合同。

文件外壳只接受精确技术字段：

```text
fileFormatVersion
fileId
crypto
current
previous
```

每代解密 payload 只接受：

```text
savedAt
ledgerData:
  schemaVersion
  assets
  trades
  priceSnapshots
  feeRules
```

`Position[]`、图表数据、K 线、页面状态和其他派生字段不进入 C。Validator 成功后只使用重建的 `.value`，每代再分别执行集合/字符串资源策略和 8 MiB 规范 JSON 字节策略。

### 3.2 加密与 AAD

- PBKDF2-SHA-256，600,000 次，16-byte salt；
- AES-256-GCM，128-bit tag，12-byte IV；
- 同一 C 会话只派生一次不可导出 key；
- 每个真实 generation 使用独立新 IV；
- AAD 从已校验技术字段重新按固定键顺序构造；
- `current / previous` 槽位名和 ciphertext 不进入 generation AAD，原 current 可以逐字段原样移动为 previous；
- file、crypto、revision、parent、schema、IV 等技术字段均受认证；
- 业务事实只存在于 AES-GCM 密文中。

### 3.3 创建、打开与保存

```text
新建：
用户点击 save picker
→ 取消则无副作用
→ 只接受 .lftl 和零字节目标
→ createInitialLedgerData()
→ current + previous:null
→ write
→ close
→ 同一句柄 readback
→ 完整验证后才返回 C session
```

```text
保存：
规范候选与最后已验证 current 相同
→ no-op

真实变化
→ 固定 pending intent
→ 新 revision / savedAt / IV / ciphertext
→ 原 current 原样进入 previous
→ write
→ close
→ 同一句柄 readback
→ fileId、revision、parent、两代 AAD、两代解密、
  Validator、两类 ResourcePolicy、当前候选和上一代原样性全部通过
→ Repository.save() 才 resolve
```

同一 `{fileId, baseRevisionId, serializedCandidate}` 的失败保存重试复用同一个 intent；如果磁盘已经是预期 revision，只重新完成完整复读确认，不再制造新一代。
