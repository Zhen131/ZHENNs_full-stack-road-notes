## 四、F-01（P0）修复合同

### 4.1 根因

当前 `LedgerFileCrypto` 缓存会话 key 和 crypto metadata。Repository 解析回读文件后，generation 解密仍用缓存 metadata 构造 AAD，却没有先确认磁盘 `file.crypto` 与会话绑定 metadata 完全一致。因此磁盘 salt 从 S1 漂移为另一个格式合法的 S2 时，当前会话仍可能用 K1 + S1 通过回读，随后却无法按磁盘 S2 用正确密码重开。

### 4.2 固定修复方向

选择“会话绑定 metadata + 磁盘完整精确比较”，因为当前会话 key 已由原 salt 派生，而无条件信任磁盘 metadata 会掩盖文件身份漂移。

在任何 generation 解密、verified state 更新、pending intent 清除或 Repository 成功返回之前，必须完成：

```text
parse + strict validate on-disk LedgerFileV1
→ 取得会话创建或解锁时绑定的期望 crypto metadata
→ 对 file.crypto 做完整字段精确比较
→ 完全一致才允许用会话 key 认证 current / previous
→ 其余 FILE-001 / FILE-004 / FILE-005 核对全部通过
→ 才允许发布成功
```

精确比较至少包含：

- `cryptoVersion`
- `kdf.name`
- `kdf.hash`
- `kdf.iterations`
- `kdf.saltBase64Url`
- `cipher.name`
- `cipher.keyLength`
- `cipher.tagLength`

实现要求：

- 使用专门、可测试的 metadata 比较或断言逻辑，不依赖对象引用相等。
- 不依赖未经 Validator 保证字段顺序的任意 `JSON.stringify` 巧合。
- metadata 不一致必须 fail closed，不得继续尝试 current / previous，也不得自动解释为空账本。
- 对外不得泄露“密码错误”与“metadata 被修改”的底层认证差异；内部错误必须足够稳定，便于 Repository 测试断言。
- create、普通 save、pending-intent reconcile 必须走同一条 metadata 绑定规则，不能只修普通 save。
- `this.verified`、`persistedVersion` 和最后已验证快照只能在完整回读通过后推进。

### 4.3 失败后的状态

- create 首次回读发现漂移：创建失败，不返回可挂载 session，不显示已保存。
- 普通 save 回读发现漂移：`save()` reject；Repository 内最后已验证账本保持保存前版本；Hook 保持 dirty 并进入 error。
- pending-intent reconcile 发现漂移：不得把磁盘新 revision 确认为 committed，不清除 pending intent，不生成另一份假 revision。
- 本次不新增 FILE-006 恢复 UI，也不承诺对仍被外部修改的磁盘文件自动修复。
- 测试必须区分“内存仍保留上一个 verified 账本”和“磁盘已经可以重开”；不得用前者冒充后者。

## 五、F-02（P1）修复合同

### 5.1 根因

当前 Controller 只有一个 `pendingSelection`。`selectExisting()` 的旧 Promise 在 await 后可以无条件发布或清空选择；`cancelPendingSelection()` 只清空当前值，Gate unmount 也只修改 React `mountedRef`，没有使 Controller 内仍在等待的旧操作失效。

### 5.2 固定修复方向

Controller 必须维护单调递增的 operation generation/token：

```text
每次 select / create 开始
→ 取得新的 token

每次新 select / create / cancel / Gate unmount
→ 使所有旧 token 失效

异步步骤返回
→ token 仍是当前值：才允许发布或清空 pendingSelection
→ token 已过期：忽略旧结果，不修改任何较新状态
```

实现要求：

- slow A / fast B 中，最终只能保留 B。
- 旧 A 成功返回不能覆盖 B；旧 A 失败也不能清空 B。
- cancel 必须同时清空当前选择并使仍在等待的选择失效。
- create 开始即使旧选择失效；成功创建后，旧选择结果不能重新出现。
- Gate unmount 必须调用 Controller 的失效入口；只检查 `mountedRef.current` 不算修复。
- `operationRef` 只属于 UI 防重复提交，不能代替 Controller 自己的并发正确性。
- 不能只设置 `AbortSignal.aborted` 或让旧 Promise 永不返回；即使底层 Promise 最终真实 resolve，旧结果也必须无副作用。
- 只有当前 token 才能发布 `pendingSelection`，也只有当前 token 才能在错误路径清空它。
- 若使用现有 `cancelPendingSelection()` 同时承担失效职责，命名、接口和 Gate cleanup 必须保持语义一致；若新增方法，必须补齐接口假实现和测试。

### 6.1 Salt 三路径

使用格式合法但与会话 S1 不同的 16-byte S2，只修改磁盘外层 `crypto.kdf.saltBase64Url`，不修改 ciphertext/tag。

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| S1 | create 的 close 后、第一次 readback 前替换 salt | create reject；不返回 Repository/session；旧实现下该测试先失败 |
| S2 | 普通 save 的 close 后、readback 前替换 salt | save reject；`repository.load()` 仍是保存前 verified 账本；verified revision 不推进 |
| S3 | 首次写入已发生但 readback 失败，retry/reconcile 时磁盘 salt 已漂移 | reconcile reject；pending intent 不被确认为 committed；不额外生成 revision/IV |

要求：

- 复用或扩展现有 `AtomicLedgerHandle.mutateAfterClose`，在确定时点注入变异。
- 不能只测试“关闭应用后重新打开失败”；必须直接证明同一会话的回读也会拒绝。
- 既有 fileId、revision、current/previous ciphertext 等 mutation matrix 必须继续通过。

### 6.2 Hook 保存状态门

使用真实 `LedgerFileRepository` 或足以完整保留 close→readback→metadata 漂移语义的集成 fixture，证明：

- mutation 后先进入 `saving`。
- salt 漂移使 Repository save reject。
- `persistenceStatus === "error"`，不得为 `saved`。
- `mutationVersion > persistedVersion`，persistedVersion 不推进。
- `isDirty === true`。
- 页面账本保留用户当前内存修改，但错误文案明确“尚未保存”。
- 不能通过 mock 一个普通 reject 来代替 metadata 漂移主链。

### 6.3 四个 deferred Promise race

必须使用可手工 `resolve/reject` 的 deferred Promise 控制顺序，不使用不稳定 sleep 或真实计时器。

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| R1 | A 先发起，B 后发起；B 先完成，A 最后完成 | 最终只能解锁 B；A 无权覆盖 B |
| R2 | A 等待期间取消，随后 A 完成 | `unlockSelected()` 返回 `NO_SELECTION`；A 不复活 |
| R3 | A 等待期间 Gate unmount，随后 A 完成 | Controller 不发布 A；不挂载 Dashboard；没有卸载后状态更新 |
| R4 | A 等待期间成功创建新 C，随后 A 完成 | 新 C session 不被 A 覆盖；旧 A 不能重新成为待解锁文件 |

补充断言：

- 增加“旧 A 最后 reject 不能清空较新 B”，防止只保护成功路径。
- R3 必须覆盖真实 `LedgerAccessGate` cleanup 与 Controller 失效入口的连接，不能只直接调用 Controller 冒充组件卸载。
- 测试结束时必须真实释放 A，不能让旧 Promise 永久 pending。

2. 在未修生产代码时运行定向测试，记录预期失败的测试名、数量和错误事实。
