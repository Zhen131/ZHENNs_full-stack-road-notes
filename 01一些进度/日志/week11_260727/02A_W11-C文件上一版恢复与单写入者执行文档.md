## 三、固定验收场景

### 场景 A：恢复上一版

原 C：

- previous 为 R301，含 BTC、ETH、ADA 共 301 笔，完整有效；
- current 为 R302，比 R301 多一笔 ADA，但 current 密文、AAD、payload 或业务时间线已损坏。

必须达到：

- 不挂载普通 Dashboard；
- 显示“最新一次保存没有恢复，现在恢复的是上一版”；
- 取消时零写入；
- 确认后在原 C 中生成新的 current；
- 新 current 的账本内容精确等于已验证 previous，不得伪装仍有 R302 的 ADA；
- 完成 write → close → 同句柄 readback → 完整验证后才进入账本。

### 场景 B：两个页面选择同一物理 C

- 标签页 A 已进入可写会话；
- 标签页 B 再选择同一个实际文件。

B 必须在 Dashboard 和可写 Repository 发布前被拒绝，并显示“该账本已在另一标签页使用”。A 释放后 B 才可重试。

### 场景 C：旧页面覆盖外部新版本

- 页面 A 加载 R301；
- 外部程序或同步过程把同一物理 C 更新为 R302，并新增一笔 ETH；
- A 随后尝试保存一笔 ADA。

A 必须拒绝保存、保持 dirty / error、要求重新打开；磁盘 R302 和其中 ETH 不得被覆盖。

### 场景 D：Finder 复制件

原件和复制件字节相同、`fileId` 相同，但属于两个物理文件。程序不得只按 `fileId` 把它们锁成一个文件，也不得扫描、登记原件/副本关系、自动合并或修改另一份。

## 四、FILE-006 恢复状态机

### 4.1 恢复资格

打开 C 时分别验证 current 与 previous，但只有以下组合可以返回 `recovery-required`：

```text
密码正确
+ 外层合同、crypto metadata、fileId 和可用于恢复的 revision 关系可信
+ current 不可用
+ previous 不为 null
+ previous 独立通过 AES-GCM、payload、ResourcePolicy、LedgerData Validator
= recovery-required
```

以下情况全部拒绝恢复：

- 错误密码；
- previous 为 null；
- current 与 previous 都坏；
- current 有效但 previous 损坏；
- 外层 metadata、`fileId` 或 revision 链不足以安全确定恢复来源；
- previous 的认证、结构、资源或业务时间线任一失败。

不得用不同文案泄露“密码错”还是具体密文认证失败。`recoveryAvailable` 只能表示内部证据，不能等于已经恢复。

### 4.2 确认前

- Controller 返回独立的恢复候选，不返回普通可写 session。
- Gate 进入 `recovery-required`，清空密码输入，不挂载 Dashboard。
- 页面只显示必要信息：最新一版未恢复、将恢复上一版、可能缺少最新变化。
- 恢复候选绑定本次操作代号、同一文件句柄、`fileId`、原始文件基线、previous revision 和已验证 previous 数据。
- 用户取消：候选失效、释放会话占用、零写入、回到文件入口。

### 4.3 用户确认后的唯一写入算法

1. 防重复点击，只允许一个恢复意图执行。
2. 保持同一物理文件会话占用，并取得短时写锁。
3. 重新读取同一句柄；确认文件仍是用户看到恢复提示时的完整基线。任何 metadata、`fileId`、revision 或代际变化都停止恢复，要求重新打开。
4. 以已验证 previous 的 `LedgerData` 创建新的规范 payload，`savedAt` 使用本次恢复写入时间。
5. 保持同一 `fileId` 与 crypto metadata；生成新的随机 `revisionId` 和 IV。
6. 新 current 的 `parentRevisionId` 指向被恢复的 previous revision。
7. 原 verified previous 原样保留在 previous 槽；损坏的旧 current 不再进入新两代。
8. 写入原 C，关闭 writable，再从同一句柄复读。
9. 核对 fileId、crypto metadata、新 current、parent、previous 原样性、两代认证解密、规范 payload、ResourcePolicy 和完整 LedgerData。
10. 全部通过后才发布普通 session；任一步失败都保持恢复失败状态，不显示 saved，不挂载 Dashboard。

同一恢复意图在“文件可能已写入但 readback 未确认”时必须安全 reconcile；不得重复生成 revision、IV 或第三代。取消、选择新文件、卸载后晚到的旧 Promise 必须失效。

## 五、FILE-007 单写入者与外部变化

### 5.1 文件身份

- `LedgerFileHandle` 增加实际文件比较能力，对应浏览器 `FileSystemHandle.isSameEntry()`。
- 会话占用以两个实际句柄的 `isSameEntry()` 结果为准，不能只使用文件名、路径猜测或 `fileId`。
- `fileId` 继续负责账本身份与 revision 认证，不承担物理文件锁键职责。
- 如果浏览器不能可靠比较实际文件或不能提供运行期协调，本轮对 C 可写入口 fail closed，显示能力不支持；不得静默降级。

参考：[File System Standard](https://fs.spec.whatwg.org/)、[Web Locks API](https://www.w3.org/TR/web-locks/)。

### 5.2 会话占用

新增可注入、可测试的文件占用协调边界，至少提供：

```text
acquireSession(handle) → lease | in-use | unsupported
lease.release()        → 幂等释放
withWriteLock(handle, operation) → operation result
```

生产实现只使用浏览器原生能力，不新增第三方依赖。不同标签页之间必须能用实际文件句柄完成同一物理文件判断；Web Locks 可用于串行化争用，但不能只以 `fileId` 命名物理会话锁。

取得时机：

- 新建 C：picker 返回后、首次写文件前取得；创建失败、取消、旧操作失效时释放。
- 打开 C：密码与文件通过验证后、普通 session 或恢复页面发布前取得；取得后重新核对磁盘基线。
- 第二个页面不得排队后静默进入；立即返回 `file-in-use`，由用户稍后主动重试。

释放时机：

- 正常离开账本、React Gate 卸载、路由跳转、创建/解锁失败、恢复取消或操作失效；
- `LedgerSession.release()` 必须幂等；
- 标签页关闭或崩溃后由浏览器运行期机制释放；
- 不写永久 `locked=true`，不创建锁文件，不提供强制抢锁。

### 5.3 短时写锁和写前复核

每一次真正写文件，包括普通 save、pending intent reconcile 和恢复写入，都必须在同一短时写锁内完成：

```text
取得写锁
→ 同一句柄重新读取磁盘
→ 核对 fileId、crypto metadata、current revision、parent 和完整基线
→ 准备或 reconcile 唯一写入意图
→ write
→ close
→ 同一句柄 readback
→ 完整验证
→ 释放写锁
```

候选与当前账本完全相同的 no-op 不实际写文件，不制造 revision 或 IV。

外部程序不参与浏览器锁，所以 revision 复核仍是强制项。磁盘与最后已验证基线有任何意外变化时：

- 抛出独立的 external-change 错误；
- 零写入，不自动合并；
- Repository 不推进 verified revision；
- Hook 不清 dirty、不推进 persistedVersion、不显示 saved；
- 页面明确要求重新打开。

## 六、接口与职责

### Adapter

- 增加 `isSameEntry` 边界及 unsupported / comparison-failed 错误。
- 继续负责 picker、读取、write / close / readback，不解释恢复或 revision 业务。

### 占用协调模块

- 负责会话 lease、短时写锁、跨标签页争用和幂等释放。
- 不读取账本明文，不登记原件/副本关系，不持久化锁状态。

### Repository

- 把普通打开与 `recovery-required` 明确区分，不再只抛一个带布尔值的通用错误。
- 保存与恢复统一经过写锁、写前磁盘复核和既有 readback 验证。
- 增加明确错误：恢复不可用、外部变化、锁能力不可用；不改变 `LedgerData` 或 C V1 外层字段。

### Controller / Composition

- 管理 pending selection、操作代号、session lease 和恢复候选生命周期。
- 暴露恢复确认、恢复取消、file-in-use、unsupported 和 external-change 结果。
- 旧操作晚到不得释放新 lease、清空新选择或发布旧 session。

### Gate / Session / Hook

- Gate 增加恢复页、文件占用、能力不支持和外部变化的用户文案。
- `LedgerSession` 增加幂等 `release()`；IndexedDB session 使用 no-op release，保持现有行为。
- Dashboard 只接收已经取得 lease 且完全验证的 file session。
- Hook 保持既有 dirty / saving / saved / error 真实性；锁冲突和 revision 冲突都属于保存失败。
