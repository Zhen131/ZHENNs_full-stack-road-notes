## 四、全阶段共同合同

### 4.1 不变的数据合同

- `.lftl V1` 外层、`fileFormatVersion / cryptoVersion / ledgerSchemaVersion`、AAD、Base64URL、资源上限保持不变。
- `current + previous` 仍是两份相邻、完整、可独立认证和校验的账本，不增加第三代。
- `LedgerData` 仍只保存事实；`Position[]`、图表、权限、lease、连接状态、密码、CryptoKey、页面状态不进入 C。
- B 仍是明文救援 / 迁移材料。本批不修改、移动、删除或上传 B，也不开放 C 的 B 导入。

### 4.2 四种身份必须分开

| 事实 | 作用 | 不能替代什么 |
| --- | --- | --- |
| `LedgerFileHandle` | 指向浏览器知道的实际文件条目 | 不能由文件名或路径猜测 |
| `isSameEntry()` | 比较两个 handle 是否同一实际文件 | `fileId` 不能替代它 |
| `fileId` | C 内受认证的账本身份；复制件会保留相同值 | 不能作为物理文件锁键 |
| `revisionId / parentRevisionId` | 表示当前会话最后验证的文件版本关系 | 不能代替 AES-GCM 或会话锁 |

### 4.3 统一的会话与旧异步规则

- 文件选择、权限请求、重连、解锁、恢复、普通 session、立即锁定都必须共享单调 operation / session generation。
- 旧操作在取消、换文件、刷新、卸载、立即锁定或新 session 建立后晚到，只能被忽略；不得清空新状态、发布旧 session、释放新 lease 或显示旧成功。
- 已发布的 `LedgerSession` 只能在 quiesce token 后幂等 lock / release，并且只释放自己的 lease；IndexedDB legacy session 如仍存在，底层 lease release 可为 no-op，但仍不能绕过 Hook drain。
- Dashboard 只能接收“文件完整验证 + lease 已取得 + session generation 仍有效”的 C session。
- 不在 C 或 IndexedDB 写永久 `locked=true`，不创建锁文件，不提供强制抢占。

### 4.4 分阶段断言不能互相打架

- 阶段一、二结束前，C `clear / B import` 仍必须在 UI、Hook、Repository 阻断；阶段三完成后，只有 C clear 被明确开放，B import 仍阻断。
- 阶段一、二仍不得声称 C 已正式取代 IndexedDB；阶段三通过后，正常产品入口必须翻转为 C 唯一正式来源。
- 最终回归不能同时要求“C clear 永远不支持”和“FILE-010 已完成”，也不能同时要求“C 尚未接管”和“FILE-003 已完成”。

## 六、阶段一：原 02，只处理 FILE-006 / FILE-007

### 6.1 固定用户场景

#### 恢复 R301

- previous 为 R301，含完整 BTC / ETH / ADA 数据；
- current 为 R302，比 R301 多一笔 ADA，但 current 密文、AAD、payload、资源或业务时间线损坏；
- 正确密码下只进入恢复页，不挂载 Dashboard；
- 页面必须明确显示：“最新一次保存没有恢复，现在恢复的是上一版”；
- 取消零写入；
- 确认后恢复内容精确等于 R301，不能伪装保留 R302 的 ADA；
- write → close → 同句柄 readback → 完整验证全部通过后才进入账本。

#### 同一实际文件双页面

标签页 A 已取得 C lease；标签页 B 再选择同一实际文件。B 必须在可写 Repository / Dashboard 发布前得到 `file-in-use`，不得排队后静默进入。A 正常释放后，B 才可主动重试。

#### 外部版本变化

页面 A 打开 R301；外部程序把同一 C 更新为含 ETH 的 R302；A 再尝试保存 ADA。A 必须零写入、保持 dirty / error、要求重新打开；磁盘 R302 和 ETH 不得被覆盖。

#### Finder 复制件

原件与字节复制件 `fileId` 相同但不是同一实际文件。两者不能因 `fileId` 被误锁；程序也不得扫描、登记、合并或联动修改。

### 6.2 FILE-006 恢复资格

只有以下证据同时成立，才返回独立的 `recovery-required`：

```text
密码正确
+ 外层合同、crypto metadata、fileId、revision 关系可信
+ current 确实不可用
+ previous 不为 null
+ previous 独立通过 AES-GCM、payload、ResourcePolicy、LedgerData Validator
= recovery-required
```

以下情况全部拒绝恢复：

- 密码错误；
- previous 为 null；
- current 和 previous 都坏；
- current 有效但 previous 损坏；
- metadata、`fileId`、revision / parent 关系不足以确认恢复来源；
- previous 的认证、结构、资源或业务时间线任一失败。

错误密码和低层认证失败对 UI 使用同一通用提示，不形成认证 oracle。`recovery-required` 只表示“可以让用户决定”，不表示已经恢复。

### 6.3 待扩展的恢复接口

现有 `recoveryAvailable` 布尔错误不得继续直接驱动页面。改为等价的显式结果：

```ts
type LedgerFileUnlockResult =
  | { status: "unlocked"; session: LedgerSession }
  | { status: "recovery-required"; recoveryId: string }
  | { status: "error"; code: LedgerFileAccessErrorCode };

interface LedgerFileAccessController {
  // 保留 create / selectExisting / unlockSelected
  confirmRecovery(recoveryId: string): Promise<LedgerFileUnlockResult>;
  cancelRecovery(recoveryId: string): Promise<void>;
  releaseActiveSession(): Promise<void>;
}
```

类型名可按项目命名调整，但边界不能变：

- verified previous、handle、fileId、crypto、revision 和 lease 只留在 Controller / Repository 的恢复候选中，不进入 React 业务 state；
- Gate 只持有不透明 `recoveryId`；
- 取消使候选和 operation generation 失效、释放 lease、零写入、回到安全入口；
- 旧恢复 Promise 晚到不得发布 session。

### 6.4 确认恢复后的唯一写入算法

1. 防重复点击，只建立一个 recovery intent。
2. 保持同一实际文件 session lease，取得短时写锁。
3. 在写锁内重新读取同一句柄，核对恢复提示形成时的完整序列化基线；metadata、fileId、revision、parent、代际内容任一变化都停止。
4. 使用已验证 previous 的规范 `LedgerData` 创建新 payload；`savedAt` 使用本次恢复时间。
5. 保持同一 `fileId` 和 crypto metadata；生成新随机 revision 与 IV。
6. 新 current 的 parent 指向被恢复 previous 的 revision。
7. verified previous 原样保留在 previous 槽；损坏 current 不进入新两代。
8. 写入原 C，关闭 writable，再从同一句柄复读。
9. 核对 fileId、crypto、新 current、parent、previous 原样性、两代认证解密、规范 payload、ResourcePolicy 和完整 LedgerData。
10. 全部通过才发布普通 session；任一步失败都不显示 saved、不挂载 Dashboard。

文件可能已写入但 readback 未确认时，重试必须 reconcile 同一 recovery intent，不重新生成 revision、IV 或第三代。

### 6.5 FILE-007 实际文件协调接口

扩展 custom handle：

```ts
interface LedgerFileHandle {
  readonly name: string;
  getFile(): Promise<LedgerFileLike>;
  createWritable(options?: { keepExistingData?: boolean }): Promise<LedgerFileWritable>;
  isSameEntry(other: LedgerFileHandle): Promise<boolean>;
}
```

新增可注入协调边界：

```ts
type AcquireLedgerFileSessionResult =
  | { status: "acquired"; lease: LedgerFileSessionLease }
  | { status: "in-use" }
  | { status: "unsupported" | "coordination-failed" };

interface LedgerFileSessionLease {
  readonly sessionId: string;
  runExclusiveWrite<T>(operation: () => Promise<T>): Promise<T>;
  release(): Promise<void>;
}
```

生产实现只使用浏览器原生能力，不新增第三方依赖。安全默认实现必须满足：

- 使用全局 admission lock 串行化“有哪些活跃 C → 实际文件比较 → 建立新 lease”的竞态；
- 活跃标签页通过运行期通道交换可结构化克隆的 handle，并由持有者执行 `isSameEntry()`；
- 每个活跃 session 持有浏览器运行期 lease；标签页崩溃或关闭后由浏览器释放；
- 任一活跃持有者未响应、比较抛错、handle 不能克隆、Web Locks / 运行期协调缺失时 fail closed，关闭 C 写入入口，并用用户可理解的文案说明当前浏览器缺少安全协调能力；
- 不用 `fileId`、文件名、路径或自行生成的永久编号冒充物理文件身份；
- 第二页面立即返回 in-use，不在后台排队后自动进入；
- `release()` 幂等，旧 session 不能释放新 session。

如果执行者选择等价的浏览器原生实现，02B 必须说明它如何关闭“两个页面同时开始、持有者崩溃、比较失败、复制件同 fileId”四类竞态。

### 6.6 所有真实写入的统一锁内算法

普通 save、pending-intent reconcile、恢复写入和后续 clear 都必须进入同一个 `runExclusiveWrite`：

```text
取得短时写锁
→ 同一句柄重新读取磁盘
→ 验证完整 C，核对 fileId / crypto / current revision / parent / 完整序列化基线
→ reconcile 已存在 intent，或创建唯一新 intent
→ write
→ close
→ 同一句柄 readback
→ 两代与预期状态完整验证
→ 更新 verified 状态
→ 释放短时写锁
```

要求：

- 每次 `save()` 在判断 no-op 前也先核对磁盘基线；外部变化不能被“候选相同”掩盖。
- 外部变化返回独立 `external-change` 错误，零写入、不自动合并。
- Repository 不推进 verified revision；Hook 不清 dirty、不推进 persistedVersion、不显示 saved。

### 7.2 FILE-008 连接记录

新增独立 Adapter，不复用保存完整 `StoredLedgerEnvelopeV2` 的 `StorageAdapter`：

```ts
type LedgerFileConnectionRecordV1 = {
  connectionFormatVersion: 1;
  handle: LedgerFileHandle;
  expectedFileId: string;
};

interface LedgerFileConnectionAdapter {
  read(): Promise<LedgerFileConnectionRecordV1 | null>;
  write(record: LedgerFileConnectionRecordV1): Promise<void>;
  clear(): Promise<void>;
}
```

固定边界：

- IndexedDB 只保存结构化克隆的 handle、连接合同版本和 expected fileId；不保存 `LedgerData`、密文 generation、密码、CryptoKey、salt 副本、session token、lease 或页面状态。
- record 只在 C 已成功创建 / 打开、完整验证且 session 仍有效后写入；失败、取消、错密、恢复未确认时不更新。
- `handle` 表示预期实际文件；`expectedFileId` 表示预期账本身份；本次打开后验证到的 revision 才是保存基线。
- Finder 复制件可能 fileId 相同，不能只凭 expectedFileId 把复制件当成原连接文件。

### 7.3 刷新后的权限与重连状态机

Adapter / handle 待扩展：

```ts
type LedgerFilePermissionMode = "read" | "readwrite";
type LedgerFilePermissionState = "granted" | "prompt" | "denied";

interface LedgerFileHandle {
  queryPermission(options: { mode: LedgerFilePermissionMode }): Promise<LedgerFilePermissionState>;
  requestPermission(options: { mode: LedgerFilePermissionMode }): Promise<LedgerFilePermissionState>;
}
```

启动顺序固定：

```text
读取 connection record
→ 没有 record：显示新建 / 明确选择 C
→ 有 record：queryPermission(readwrite)
  → granted：读取并验证 expected fileId，进入密码解锁
  → prompt：显示明确“重新连接”按钮；只在用户点击后 requestPermission
  → denied：停在安全入口，说明未授权；不创建空账本
  → handle / 文件不可读、删除、移动或合同损坏：显示重新连接；不创建空账本
```

用户手动重新选择时：

1. 选择操作绑定新的 operation generation。
2. 新 handle 必须与 connection record 中的旧 handle 通过 `isSameEntry()` 判定为同一实际文件。
3. 再读取 C，核对 `fileId === expectedFileId` 和完整合同。
4. 任一比较失败、`false`、fileId 不同、文件损坏或权限拒绝都不得写入，不得替换 connection record。
5. 只有实际文件和账本身份都匹配、随后解锁 / 恢复成功时才更新 record。

若旧 handle 已损坏到无法执行实际身份比较，fileId 单独不足以证明同一实际文件；重连必须 fail closed。用户可以通过一个明确的“忘记失效连接并选择另一本账”动作退出重连语义，但不得在“重新连接原 C”流程中静默改绑。

权限查询、请求、picker、读取、解锁或恢复的旧 Promise 在取消、新选择、立即锁定、卸载后晚到均失效。

### 7.4 FILE-009 密码建立和运行期边界

固定规则：

- 新建 C 继续使用现有 `validatePassphrase(...)`：12–128 个 Unicode code point，不 trim、不 normalize。
- 两次输入必须逐字符一致；不一致或长度不合规时不弹 save picker、不创建 C。
- 创建前明确提示：忘记密码将永久失去访问；没有找回密码、恢复码、备用密码、管理员后门或绕过入口。
- 明文密码只存在于当前表单和本次派生调用；成功、失败、取消、切换、刷新、卸载后清空。
- 不可导出 CryptoKey 和可直接解密的 Repository / Crypto 对象只存在于当前运行 session 的可达对象图。
- 不写入 connection IndexedDB、旧 ledger IndexedDB、localStorage、sessionStorage、日志、错误报告、URL、React 业务 state 或持久化调试信息。
- JavaScript 不能证明浏览器进程物理内存被逐字节抹除；可验证合同是：清空字符串、失效 generation、丢弃所有可达 Key / Repository 引用、释放 lease，不夸大为物理内存擦除。
- 本阶段不做闲置计时自动锁定，不实现核心密码找回或原地换密。

### 7.5 立即锁定

现有已确认材料没有决定一个产品细节：点击“立即锁定”时如果页面仍有未成功保存的 dirty 更改，是“一次点击即放弃并锁定”，还是“先要求明确放弃 / 重试保存，再执行锁定”。开发 AI 不得自行选择。进入本节实现前必须向用户提出该具体问题并把决定写入 02B；未取得决定时，FILE-009 与阶段二为 BLOCKED，不进入阶段三。

无论用户选择哪种 dirty 交互，真正开始锁定后的底层顺序相同。扩展 `LedgerSession`，并在 Controller / session、Hook 与 lease 之间建立显式收口合同。类型名可以调整，但不能只在 Gate 卸载时让旧结果失效：

```ts
declare const sessionQuiesceRequestBrand: unique symbol;
type SessionQuiesceRequest = {
  readonly sessionId: string;
  readonly generation: number;
  readonly [sessionQuiesceRequestBrand]: true;
};

declare const sessionQuiesceTokenBrand: unique symbol;
type SessionQuiesceToken = {
  readonly sessionId: string;
  readonly generation: number;
  readonly [sessionQuiesceTokenBrand]: true;
};

type LedgerSession = {
  storageKind: LedgerStorageKind;
  repository: LedgerRepository;
  capabilities: LedgerSessionCapabilities;
  beginQuiesce(reason: "immediate-lock" | "route-leave"): SessionQuiesceRequest;
  lockAfterQuiesce(token: SessionQuiesceToken): Promise<void>;
  releaseAfterQuiesce(token: SessionQuiesceToken): Promise<void>;
};

interface PersistentLedgerState {
  drainForSessionQuiesce(
    request: SessionQuiesceRequest,
  ): Promise<SessionQuiesceToken>;
}
```

`SessionQuiesceRequest` 与 `SessionQuiesceToken` 都是不透明、绑定当前 sessionId / generation、只能消费一次的内部凭证。已发布 active session 不得暴露无 token 的 `release()` 绕过接口；创建、解锁或恢复失败前尚未发布的候选 lease，由 Coordinator 自己的内部 abort 路径释放。

Gate 必须把完整 session 或等价生命周期回调交给 Dashboard；不能继续只传 `repository / capabilities / storageKind` 后直接卸载。

用户按已确认的 dirty 交互作出最终锁定动作后，必须：

1. Gate 先同步调用 `session.beginQuiesce("immediate-lock")`。该调用在返回 request 前推进 Controller / session generation，禁止旧 permission、picker、unlock、recovery 和新文件操作再发布。
2. Gate / Dashboard 随即调用 `drainForSessionQuiesce(request)`；该函数在返回 Promise 前同步推进 Hook generation、禁用新 mutation / save / clear，并立即让 Dashboard 离开可编辑状态，显示“正在安全锁定”。
3. Gate 暂时保留不可再被 UI 使用的 session 和 lease；不能在 drain 前清空唯一引用或释放文件。
4. drain 等待 Hook 已接受的完整队列尾：既包括已经进入 Repository / 短时写锁的操作，也包括已排队但尚未调用 `repository.save / clear` 的操作。它们只能按原合同完成或失败，结果不得重新挂载 session、显示 saved 或恢复旧 UI。
5. 只有队列与活动 persistence operation 全部 settled，Hook 才返回一次性 `SessionQuiesceToken`；request / token 的 sessionId 与 generation 不匹配时 fail closed。
6. Gate 随后调用 `session.lockAfterQuiesce(token)`，丢弃 Repository / CryptoKey 的可达引用并幂等释放自己的文件 lease；释放完成后回到 C 入口。
7. 正常路由离开和 Gate 卸载复用 `beginQuiesce → drainForSessionQuiesce → releaseAfterQuiesce`。旧 token、重复消费、旧锁定或旧 drain 不得释放新 session 的 lease。
8. 页面崩溃由浏览器运行期释放，不能依赖异步卸载回调完成安全写入；不写永久锁。

“立即”指最终锁定动作发生后，Controller、session、Hook generation 与可编辑 UI 同步失效；不允许为追求表面瞬时释放而中断原子操作或先释放 lease、后执行旧队列。若底层操作失败，仍完成锁定，但不得回滚、覆盖或声称新状态已验证；下一次打开必须按磁盘实际内容进入正常验证 / 恢复，不得显示保存成功。

页面刷新和关闭不持久化密码或 Key；浏览器运行期机制释放 lease。`beforeunload` 可保留 dirty 警告，但不能成为秘密持久化或强制抢锁。

### 8.2 FILE-003 正式接管

- 正常 mutation 不再把完整 `LedgerData` 写入 IndexedDB；connection Adapter 是账本范围内持续允许的 IndexedDB 用途。
- 不存在“C 一份正式账本 + IndexedDB 另一份正式账本”的双重真相。
- 旧 `ledger:v1` 只按用户确认的退出合同处理；任何删除都必须晚于所需迁移 / 导出、C write-close-readback 和用户确认。
- FILE-003 最终 PASS 时，IndexedDB 中不得继续保留完整 legacy LedgerData；临时隔离只读保留只是一种暂停状态，不是完成状态。

- 页面不得仅靠变量名、文案或 `storageKind` 宣称接管；必须有 raw IndexedDB 和真实 C 数据流证据。

阶段三修改现有 IndexedDB 主链时，必须按用户决定明确：

### 8.3 FILE-010 清空当前 C

C clear 不是删除文件，也不能复用 `IndexedDbStorageAdapter.clear()`。它是 C Repository 的一个强制新 generation 操作。

现有单个 `canClear` 同时开放 ready clear 和 hydration-error recovery clear，不能直接把 `LEDGER_FILE_CAPABILITIES.canClear` 翻成 true。必须拆成等价的明确能力：

```ts
type LedgerSessionCapabilities = {
  canClearReadyLedger: boolean;
  canClearHydrationError: boolean;
  canImportBackup: boolean;
};
```

- 阶段一、二的 C：两种 clear 都是 false；
- 阶段三最终 C：`canClearReadyLedger:true`、`canClearHydrationError:false`；
- 损坏、未解锁、未完成恢复或 hydration error 的 C 永远不能通过“清除损坏数据”绕过 FILE-006，UI、Hook 和 Repository 直接调用都要拒绝；
- legacy IndexedDB 在退出期间若仍保留原 recovery clear，也必须与 C 能力分开，不能用 `storageKind` 文案猜测。

capability 只负责 UI / Hook 是否展示，不能单独充当 Repository 授权。C 的无参通用 `LedgerRepository.clear()` 必须继续 fail closed；ready C 使用专用、受控端口或等价的不可伪造授权：

```ts
declare const readyLedgerClearAuthorizationBrand: unique symbol;
type ReadyLedgerClearAuthorization = {
  readonly sessionId: string;
  readonly generation: number;
  readonly fileId: string;
  readonly verifiedRevisionId: string;
  readonly confirmationNonce: string;
  readonly [readyLedgerClearAuthorizationBrand]: true;
};

interface LedgerFileReadyClearPort {
  authorizeReadyClear(confirmationNonce: string):
    | ReadyLedgerClearAuthorization
    | null;
  clearReadyLedger(
    authorization: ReadyLedgerClearAuthorization,
  ): Promise<void>;
}
```

- 授权只能由当前已解锁、ready、完整验证且持有 lease 的 C session 在确认文案通过后生成；
- authorization 绑定 session generation、fileId、最后验证 revision 和本次确认，只能使用一次；
- Repository 在写锁内复读后再次核对 authorization 与实际基线；过期、跨 session、重复、伪造或 hydration-error 调用全部零写入拒绝；
- legacy hydration-error clear 即使保留，也使用不同内部授权和 Adapter，不能传给 C；
- 类型名可以调整，但不得继续依靠一个布尔值加无参 `clear()` 证明 Repository 层安全。

ready C 的正式流程为：

```text
用户打开“清空当前 C 账本”
→ 页面明确说明：只清空当前 C 的账本内容，不删除 .lftl，不影响其他 C
→ 明确固定文本确认
→ session lease + 短时写锁
→ 同句柄复读并核对完整磁盘基线
→ 使用 createInitialLedgerData() 形成合法空事实账本
→ 强制生成新 current（即使当前已经是空事实账本也不走普通 save no-op）
→ 原 current 原样成为 previous
→ write
→ close
→ 同句柄 readback
→ 两代认证、身份、revision、payload、ResourcePolicy、LedgerData 全验证
→ Hook replace 页面状态
→ 才显示“当前 C 账本内容已清空”
```

固定规则：

- 保留当前 `fileId`、crypto metadata、C V1 外壳和合法文件结构。
- 新 current 使用新 revision、IV、savedAt，parent 指向清空前 current。
- previous 保留清空前完整 current；页面必须如实说明“双代合同仍保留上一可用版”，不能把“清空”描述成不可恢复物理擦除。
- 不删除 `.lftl` 文件，不触碰未选中的 C，不修改 B。
- 未确认、取消、重复点击、旧 clear Promise、错误 session 均零写入。
- clear 与普通 save、恢复、pending intent 共用写队列、session lease、短时写锁和磁盘版本复核。
- 外部 revision 已变化、双页面占用、write / close / readback 任一失败时不替换页面、不显示成功。
- clear 只能在 ready、可写且当前 session 有效时进入；存在 dirty 或已排队 save 时必须按统一队列安全定序，不能绕过或伪造完成；旧 save 不得在 clear 成功后晚到并把旧账写回。
- clear 已写入但 readback 未确认时，重试只能 reconcile 同一个 clear intent、同一个 revision / IV 和预期两代；不得再生成一代，也不得把清空前 current 从 previous 挤掉。

阶段三后只开放 ready C clear；hydration-error clear 与 `canImportBackup` 仍保持关闭。

### 8.4 阶段三正式测试

必须覆盖：

1. 正常产品入口不再组装或进入完整 IndexedDB 正式账本写链。
2. 新建、选择、刷新、重连、展示、普通保存和清空的 raw IndexedDB 只含允许的 connection record。
3. legacy `ledger:v1` 按用户确认合同处理；取消 / C 失败时旧记录保留，成功删除不会误删 connection record。
4. 缺少 C capability 时 fail closed，不建立空账本，不回退 legacy autosave。
5. C clear 的明确确认、取消、错误文本、重复点击和绕过调用。
6. ready C clear 开放，但 hydration error、损坏、未解锁、恢复未确认的 C 在 UI、Hook 和 Repository 三层都拒绝且零写入；无 authorization、伪造、过期、跨 session、重复 token 以及无参通用 `clear()` 也全部拒绝。
7. clear 后 fileId / crypto 不变，新 current / previous 相邻、内容分别为空事实账本 / 清空前账本。
8. 当前 C 清空不影响另一个 C；文件仍存在且可重新打开。
9. write / close / readback / Validator / ResourcePolicy / external revision / session lease 任一失败均不显示成功。
10. clear 已写但 readback 未确认后的重试只 reconcile 同一 clear intent，不新增 revision / IV、不制造第三代、不挤掉清空前 previous。
11. clear 与在途普通 save、恢复、立即锁定、外部 R302 组合时不覆盖、不复活旧状态。
12. 阶段一、二与 01 批全部强制回归继续通过。

### 8.5 阶段三开发侧通过线

- 已有明确、可追溯的 legacy IndexedDB 退出决定并按决定实现；
- C 是正常产品唯一正式账本来源；
- IndexedDB 不再接收第二份完整 LedgerData；
- connection record 不含秘密或账本；
- C clear 形成合法新 current / previous，未删除文件或影响其他 C；
- 所有成功文案都晚于 close-readback 完整验证；
- 阶段三定向测试、阶段一 / 二回归、01 批回归、typecheck、lint 通过。

任一双重真相、静默删除旧数据、空账本冒充原账本、clear 错文件、失败显示成功或强制项失败，阶段三与合并批次开发侧均不通过。

## 十、容易复发的组合问题

必须在开发侧测试中显式覆盖：

- 恢复成功后 lease 未建立、重复建立或未释放；
- 重连错文件后仍保留旧密码、旧 Repository 或旧 session；
- 立即锁定后旧 save / recovery / permission Promise 晚到；
- C 接管后 legacy Hook、fallback 或错误恢复路径仍偷偷写完整 IndexedDB；
- clear 与外部 revision、普通 save、恢复、立即锁定同时发生；
- clear 后 current 损坏时，FILE-006 可能恢复出清空前 previous，页面仍必须准确提示数据回退；
- 权限从 granted 变 denied 后旧页面仍尝试保存；
- 页面切换、Gate 卸载、路由变化和崩溃后的 lease 生命周期；
- 恢复、重连、保存、clear 的 UI 成功状态与真实磁盘状态不一致。
