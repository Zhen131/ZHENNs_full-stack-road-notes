## 5. Finding

### F-04 — P2 / 强制合同失败：C V1 的 KDF 仍绑定 IndexedDB V2 常量

源码证据：

- `src/encryption/ledgerFileCrypto.ts:9–12` 导入共享 `deriveLedgerKey(...)`；
- `src/encryption/ledgerFileCrypto.ts:28` 与 `:46` 在 setup / unlock 时调用该函数；
- `src/encryption/webCryptoEncryptionService.ts:108–135` 的共享函数直接读取 `LEDGER_CRYPTO_CONSTANTS`；
- `src/encryption/ledgerFileContract.ts:11–27` 虽声明独立 `LEDGER_FILE_V1_CONSTANTS`，实际派生没有使用其 KDF / keyLength 参数。

历史证据：

- `Z99Archive/01C_W11-C文件合同与安全保存静态预审历史记录.md` 已把同一问题记录为 `P2-02`；
- 正式 `01C` T2 明确要求 C V1 的 KDF / cipher 行为由自己的版本常量显式决定，并把随 V2 常量静默变化列为强制失败；
- 正式 `01D` 只记录 F-01～F-03，遗漏了该既知项；`01D-1` 与 `01D-2` 因而也没有修复它。

用户影响：

- 当前两套参数相同，现有候选文件可以创建、保存和重开，不是当前数据已经损坏；
- 未来若只升级 IndexedDB V2 的 KDF 或 key length，C V1 会在文件 `cryptoVersion` 未变化时改变真实解锁规则；
- 旧 C 可能无法按其声明的 V1 合同复现派生，形成兼容性和可恢复性风险。

修复要求：

1. 抽取接收显式 KDF / cipher 参数的底层派生 primitive。
2. C 调用时显式传入 `LEDGER_FILE_V1_CONSTANTS`；IndexedDB V2 继续传自己的常量。
3. 保持现有 IndexedDB V2 字节合同不变。
4. 增加测试证明两套 version constants 可独立演进，并证明既有 C V1 fixture 仍可解密。
