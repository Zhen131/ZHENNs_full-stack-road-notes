## 结论

00 层长期保存产品共识和总需求状态；01、02、03 等数字代表一次次独立开发批次。每批完成独立审查和验收后，才回到 00B 勾选对应目标。

## 00 层

| 文件 | 用途 | 更新规则 |
| --- | --- | --- |
| `000_W11-规划文件关系与批次命名规则.md` | 解释文件关系和命名 | 流程规则变化时更新 |
| `00A_W11-产品战略重构已确认共识.md` | 保存产品选择、架构边界、理由和未决问题 | 只补录用户新确认的共识，不记录普通执行进度 |
| `00B_W11-总需求快照与待办清单.md` | 从 00A 提取稳定编号、目标、通过线和前置关系 | 需求范围按快照管理；最终验收通过后更新勾选和证据 |

00B 不能代替 00A。需要理解“为什么这样做”或“哪些边界不能越过”时，必须回读 00A。

## 开发批次

`NN` 使用两位递增编号，例如 01、02、03：

| 文件 | 用途 |
| --- | --- |
| `NNA` | 用户从 00B 选定目标后生成的本批详细执行文档 |
| `NNB` | 执行者记录实际修改、源码提交、测试结果和已知风险；状态为等待审查 |
| `NNC` | 独立代码审查结果 |
| `NND` | 独立测试与最终验收结果 |

第一批使用 `01A–01D`，第二批使用 `02A–02D`，依次递增。批次编号不得复用。

## 固定流程

```text
00A 产品与架构共识
→ 00B 总需求快照与待办清单
→ 用户从 00B 选择目标编号
→ NNA 本批详细执行文档
→ 目标模式修改源码
→ NNB 本批实现记录
→ NNC 独立代码审查
→ NND 独立测试与最终验收
→ 全部通过后回到 00B 勾选目标并登记证据
→ 下一批使用新的 NN 编号
```

## 硬规则

1. 00B 中只有取得最终验收证据的目标可以从 `[ ]` 改为 `[x]`。
2. NNB 是执行者报告，不是最终完成证明。
3. NNA 只能包含用户选中的目标；发现缺少前置任务时必须提醒，不得静默扩大范围。
4. NNA 生成前必须重新核对当前源码、测试和 Git 状态，不能只依赖 00A、00B。
5. 审查或验收失败时，00B 保持未勾选；修复使用下一个可用批次编号，旧文件保留为证据。
6. 00A–00B 和批次文档属于工作区根 Git 仓库；源码修改属于独立的 `LocalFirstTradingLedger` Git 仓库，两者不得混合提交。
