# Week 11 规划文件关系与批次命名规则

日期：2026-07-28

## 结论

00 层长期保存产品共识、总需求、批次地图和延期缺陷；01、02、03 等数字代表一次次独立开发批次。每批的 `A` 与 `C` 是执行前同时生成的两份目标模式输入文档，`B` 与 `D` 是对应 AI 执行后生成的两份事实报告。只有独立测试审查最终通过后，才回到 00B 勾选对应目标。

`NND = FAIL / BLOCKED` 只暂停本批目标和依赖它的后续路线，不再自动冻结整个项目。非阻塞问题进入 00D，允许先做前置已满足且与该问题无依赖的批次。每批最多立即安排一轮阻塞修复，命名为 `NNR1A / NNR1B / NNR1C / NNR1D`；复验仍未通过时暂停相关路线，不自动继续生成 R2 或一串 D 后缀。任何开发侧 PASS 都不能替代独立 PASS。

| `00C_W11-NLP前预计开发批次清单.md` | 把 NLP 之前的未完成目标建议拆成可独立验收的小批次 | 正常功能编号保持稳定；阻塞修复使用本批 R1，不占后续编号 |

00B 不能代替 00A，00C 也不能代替 00B，00D 不能代替 NND。需要理解“为什么这样做”或“哪些边界不能越过”时，必须回读 00A；需要核对目标、通过线和前置时，必须回读 00B；需要判断还有哪些已知问题、卡住什么路线和最迟何时处理时，读取 00D。

## 开发批次

`NN` 使用两位递增编号，例如 01、02、03：

| 文件 | 用途 |
| --- | --- |
| `NNA` | 开发目标模式输入：详细规定本批要实现什么、允许改什么、技术合同和开发完成线 |
| `NNB` | 开发执行报告：由执行 NNA 的 AI 记录实际修改、源码状态、测试结果、偏差和已知风险 |
| `NNC` | 独立测试审查目标模式输入：详细规定如何独立审查、测试 A/B 与源码，固定通过线、失败线和阻塞线 |
| `NND` | 独立测试审查报告：由执行 NNC 的另一 AI 记录逐项证据、通过项、失败项、阻塞项、Finding 和最终判定 |

第一批使用 `01A–01D`，第二批使用 `02A–02D`，依次递增。批次编号不得复用。

`NNA` 与 `NNC` 必须基于同一批目标、同一产品合同和同一通过线成对生成。`NNC` 不是等 NNB 生成后才临时编写的结果文件；它必须在开发开始前就把“将来怎样证明代码正确”固定下来，避免执行者写完代码后再降低验收标准。

若 `NND` 出现必须立即处理的阻塞项，本批最多增加一组：

| 文件 | 用途 |
| --- | --- |
| `NNR1A` | 只修本批已确认的阻塞 Finding |
| `NNR1B` | 记录修复事实和开发侧验证 |
| `NNR1C` | 冻结该轮独立复验范围 |
| `NNR1D` | 记录独立复验结果 |

R1 不得夹带新功能，也不改变后续正常批次编号。R1 再失败时，Finding 保留在 00D，相关路线暂停；后续是否集中修复由用户另行选择。

## 固定流程

```text
000 文件治理与批次命名
→ 00A 产品与架构共识
→ 00B 总需求快照与待办清单
→ 00C NLP 前预计开发批次清单
→ 用户从 00B 选择目标编号
→ 同时生成 NNA 开发执行文档 + NNC 独立测试审查执行文档
→ 开发 AI 用目标模式执行 NNA、修改源码
→ 开发 AI 生成 NNB 开发执行报告
→ 另一独立 AI 用目标模式执行 NNC，只审查和测试 NNA、NNB 与实际源码
→ 独立 AI 无论 PASS / FAIL / BLOCKED 都生成 NND 独立测试审查报告
→ 协调步骤把尚未关闭的 Finding 去重登记到 00D
→ PASS：回到 00B 勾选目标并登记证据
→ FAIL / BLOCKED：00B 保持未勾选，只暂停本批和依赖路线
→ 必须立即处理：本批最多生成一轮 NNR1A / NNR1C
→ 可延期：保留在 00D，转去前置已满足且无依赖的批次
→ 下一正常批继续使用 00C 已固定的 NN 编号
```

## 硬规则

1. 00B 中只有取得 `NND = PASS` 最终证据的目标可以从 `[ ]` 改为 `[x]`。
2. NNA、NNC 是执行输入；NNB、NND 是执行报告。任何 AI 不得把输入文档中的预期写成已经发生的事实，也不得把 NNB 的执行者自测当成最终完成证明。
3. NNA 与 NNC 只能覆盖用户选中的同一批目标；发现缺少前置任务时必须提醒，不得静默扩大范围。
4. NNA / NNC 生成前必须重新核对当前源码、测试和 Git 状态，不能只依赖 00A、00B；两份文档必须同时固定同一目标范围、业务样例和不可降低的通过线。
5. 开发 AI 只执行 NNA 并生成 NNB；独立 AI 只执行 NNC 并生成 NND。独立 AI 默认保持源码仓库只读，不顺手修源码；如需补充测试，只能使用不污染正式工作树的临时副本或由用户另行授权。
6. NND 无论 PASS、FAIL 或 BLOCKED 都必须生成；不得因为失败而不留报告，也不得把缺少证据写成通过。
7. NND 为 FAIL 或 BLOCKED 时，00B 保持未勾选。该结论只暂停本批目标和依赖它的路线，不得据此自动冻结没有依赖关系的工作。任何开发侧 PASS 都不得冒充独立 PASS。
8. NNA / NNC 一旦交给目标模式开始执行，不得事后改写通过线来配合现有实现；如合同本身确实错误，必须停止、保留旧文档并由用户确认修订。
9. 00A–00C 和批次文档属于工作区根 Git 仓库；源码修改属于独立的 `LocalFirstTradingLedger` Git 仓库，两者不得混合提交。
10. 用户选中的目标必须先做前置闭包检查：前置要么已经完成，要么由用户同时选入本批；仍有未决 DEC 时停止生成，不得自行补全。
11. 00B 的“直接适用 GATE”必须同时进入 NNA 的开发边界和 NNC 的深度验收矩阵，不能变成额外开发目标；全部 23 项 GATE 仍需快速复核，发现疑点才升级为深测。
12. 当前开发状态、源码 README、00A 和 00B 出现事实冲突时，必须先按当前源码与 Git 核对并修正文档，不能带着冲突生成 NNA / NNC。
13. 00C 的正常功能编号保持稳定。阻塞修复使用本批 `NNR1A–NNR1D`，不占用后续正常编号；未通过的相关目标不得被后续依赖批次绕过。
14. P0 一律阻塞相关路线；涉及写错、丢失、密码泄露、文件身份、旧页面覆盖或虚假保存成功的 P1 也阻塞。当前目标任一强制通过项失败时，无论标成什么级别，都按阻塞处理。
15. 不触发强制失败线、也不影响数据与密码安全的普通 P1、P2、P3，可以在 NND 中如实记录并进入 00D；它们本身不要求把最终判定降为 FAIL。
16. 00D 只登记尚未关闭的问题。01D-6 已独立关闭的历史问题不重新列为待办，但相关 salt / metadata 漂移、旧异步选择、Hook 保存状态、KDF 解耦、双代和 close-readback 测试必须保留为后续回归。
17. 独立审查 AI 只生成 NND，不直接修改 00B、00D 或源码。NND 完成后的协调步骤负责去重登记 00D；重复发现引用既有缺陷编号，不新建第二条。
18. 00D 只有取得独立复验证据后才能勾选。开发侧声称修复、关闭页面功能或用户允许继续其他路线，都不等于该缺陷已经关闭。
