## 三、判定规则

最终判定只有三种：

| 判定 | 条件 |
| --- | --- |
| `PASS` | 全部强制审查项、自动化、回归和可执行的真实验收均通过；没有 P0 / P1；无关键证据缺口 |
| `FAIL` | 任一 FILE / 直接适用 GATE 的强制合同失败，或出现 P0 / P1；即使同时存在环境阻塞，也优先 FAIL |
| `BLOCKED` | 没有已证明的 P0 / P1 或强制失败，但关键证据因外部环境无法取得，且没有等价的确定性证据 |

优先级固定为：

```text
P0
→ P1 / 任一强制通过项失败
→ BLOCKED
→ P2 / P3
```

- P0：可能造成已报告保存成功但数据不可恢复、写错 C、泄露核心密码或破坏唯一可信账本。
- P1：违反文件身份、认证、双代、复读、旧异步失效或单一后端边界，可能在真实使用中写错、丢失或错误发布状态。
- P2：非当前强制合同的中风险实现或测试证据缺口；必须记录，但只有未触发强制通过项失败时才不自动决定 FAIL。
- P3：低风险可维护性或表达问题。

### T1：FILE-001 文件合同与资源边界

独立核对并测试：

1. `.lftl V1` 外层只接受 `fileFormatVersion / fileId / crypto / current / previous`，缺字段、额外字段、错误 null / object 和未知版本全部拒绝。
2. `fileFormatVersion`、`cryptoVersion`、`ledgerSchemaVersion` 三种版本独立，不能复用 IndexedDB `StoredLedgerEnvelopeV2`。
3. Base64URL 禁止 padding 和非规范字符；salt、IV、ciphertext 长度与类型严格。
4. 解密 payload 只接受 `savedAt + ledgerData`；LedgerData 只接受事实字段，派生 Position、图表、K 线和 UI 状态不得进入。
5. 单代规范 payload 正好 8 MiB 接受，8 MiB + 1 byte 拒绝。
6. 外层正好 32 MiB 可以进入后续解析，32 MiB + 1 byte 必须在 JSON.parse 前拒绝。
7. 非法 UTF-8 必须由 fatal decoder 拒绝。
8. 写入前、加密输入和 readback 比较使用 Validator 重建后的同一规范账本，而不是调用方原对象。

失败线：任一 exact 字段、版本、资源或规范输入规则被宽松接受，FILE-001 失败。

### T2：FILE-001 加密、AAD 与磁盘 metadata 认证

必须逐项证明：

- PBKDF2-SHA-256、600,000 次、16-byte salt；AES-256-GCM、128-bit tag、12-byte IV；
- 同一 C 的 generation 使用同一合同与 salt，但每个真实 generation 使用新 IV；
- AAD 由已验证字段重新按固定顺序构造；
- fileFormatVersion、fileId、cryptoVersion、KDF、salt、cipher、tagLength、revisionId、parentRevisionId、ledgerSchemaVersion、IV 任一变化都会被拒绝；
- current / previous 槽位移动不要求用旧 IV 重加密，revision 链仍能发现删除、交换或伪造；
- C V1 的 KDF / cipher 行为由自己的版本常量显式决定，不能暗中读取 IndexedDB V2 常量。

必须增加以下对抗性测试：

```text
创建或保存时使用 salt S1 和 key K1
→ write / close 后把复读文件外层 salt 替换成另一个合法 16-byte S2
→ 当前会话仍持有 K1
→ readback 必须失败
→ verified generation 不更新
→ Hook 保持 dirty，不能显示已保存
→ 重新打开也不能把损坏文件解释为空账本
```

create、普通 save 和 pending-intent reconcile 三条路径都必须拒绝 on-disk crypto metadata 漂移。只证明“换 salt 后重新开文件解密失败”不够；必须证明同一会话的 close 后复读不能用缓存 metadata 绕过。

失败线：复读使用会话缓存的 crypto metadata 代替真实文件 metadata，或 C V1 会随 IndexedDB V2 常量变化而静默变化，均记强制失败。

### T3：FILE-002 文件选择、身份与异步生命周期

必须核对并测试：

- save picker 取消无写入；同名目标由系统先询问是否替换，用户确认后允许创建新 C；零字节目标只允许新建流程初始化；
- open picker 取消无副作用；零字节、损坏、未知版本文件拒绝且零写入；
- 同名不同 fileId 可由用户分别明确选择；绑定后 readback 返回其他 fileId 必须拒绝；
- 错误密码与认证失败零写入，不挂载 Dashboard，不泄露低层认证差异；
- 密码输入在成功和失败后清空，passphrase、CryptoKey 和句柄不进入业务 state、IndexedDB、localStorage 或日志。

必须用 deferred Promise 增加四类旧异步结果测试：

1. A 选择慢、B 选择快，B 完成后 A 才返回：最终只能保留 B。
2. A 尚未返回时用户取消：A 后续返回不能恢复 pending selection。
3. A 尚未返回时 Gate 卸载：A 后续返回不能发布句柄或挂载 Dashboard。
4. A 尚未返回时开始新建或另一选择：旧 A 不能覆盖较新的操作。

测试必须让旧 Promise 在取消或替换后真实 resolve；只检查 `AbortSignal.aborted` 或让旧 Promise 永不返回，不算证明。

失败线：任一旧选择可以在取消、卸载或新选择后重新发布旧句柄，FILE-002 与 GATE-004 失败。

### T4：FILE-004 双代与保存状态机

使用固定虚构账本独立证明：

| 动作 | 必须得到 |
| --- | --- |
| create 300 笔 | `current:300 / previous:null` |
| 新增第 301 笔 | `current:301 / previous:300` |
| 再新增第 302 笔 | `current:302 / previous:301` |
| 保存同一规范账本 | no-op，不产生新 revision / IV / write |

每一次真实 generation 必须有新 revision 和新 IV；previous 必须与保存前已验证 current 逐字段相同，不能重加密、拼增量或保留第三代。

同一失败保存的 retry 必须复用完全相同的 `savedAt / revision / IV / ciphertext / serialized file`。第一次实际写入成功但 readback 暂时失败时，第二次先验证同一 revision，不能再制造一代。

必须分别覆盖：

- candidate Validator、集合 / 字符串策略、8 MiB 失败时零 writable；
- 加密、createWritable、write、close、getFile、arrayBuffer、fatal decode 的独立失败；
- fileId、current revision、parent、savedAt、canonical candidate、current ciphertext、previous ciphertext 和完整 crypto metadata 的逐项错配；
- current / previous 分别独立认证、解密、Validator 和 ResourcePolicy；
- current 失败、previous 可用时不得自动恢复；previous 失败也不得把保存报告为成功。

失败线：出现第三代、previous 不是原 current、retry 生成新意图、任一失败推进 verified 状态，FILE-004 失败。

## 五、必须重点攻击的两个风险

旧流程下的静态预审曾提出两个风险。它们不是预设结论，但本次 01C 不得跳过：

1. **复读 metadata 风险**：验证 `decryptGeneration(...)` 是否使用复读文件中的 `file.crypto`，并与会话绑定 metadata 做 exact equality；必须执行 T2 的合法 salt 替换测试。
2. **旧文件选择复活风险**：验证 Controller 是否具有单调 selection generation / token，取消、卸载和新选择是否能使旧异步结果失效；必须执行 T3 的四类 deferred 测试。

如果源码已修复，01D 写明对应代码和通过证据；如果仍可复现，分别按数据不可重开 / 写错 C 的实际影响评级，不能因为这是已知线索而降低等级。

## 六、01D 固定输出结构

01D 无论最终结果如何都必须生成，并至少包含：

1. 最终判定：PASS / FAIL / BLOCKED。
2. 源码与两个 Git 仓库快照；明确区分 clean / dirty 与 ahead / behind。
3. 01B 陈述逐项核对表。
4. T0–T9 逐项结果、命令、退出码和证据位置。
5. FILE-001、002、004、005 逐项目标判定。
6. GATE-001–023 复核表，直接适用项提供证据。
7. 全部 Findings：等级、文件与行号、可复现路径、用户影响、违反合同、修复要求。
8. PASS 项、FAIL 项、BLOCKED 项分别列出，不能混写。
9. 正式源码工作树执行前后哈希核对，证明独立测试没有修改源码。
10. 明确写出是否允许回写 00B。

最终规则：

- `PASS`：允许用户决定是否回写 00B；01D 本身不擅自回写、不提交源码。
- `FAIL`：不允许回写 00B；使用下一编号同时生成修复 NNA 与复验 NNC。
- `BLOCKED`：不允许回写 00B；保留已取得证据，说明解除阻塞所需的最小条件。
