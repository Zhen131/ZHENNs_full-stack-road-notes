## 四、A、B、C 三类数据的固定含义

### 4.1 A：原始自然语言记录

A 是用户已有的原始交易材料，例如：

> 今天 65000 美元买入 0.1 BTC，手续费 5 美元。

已确认边界：

- 完整历史约 200–400 条；
- A 是原始事实来源，离线保留；
- 本阶段不开发 A → B 的专用自然语言转换器；
- 用户可使用其他 AI 或人工转换；
- 如果外部 AI 不是本地模型，必须先脱敏，不得上传不必要的真实隐私；
- 无论 B 由外部 AI 还是人工整理，转换结果都属于不可信输入，必须经过用户核对和账本确定性校验；
- A 不因 B 或 C 创建成功而删除。

### 4.2 B：账本现有导入导出格式的明文 JSON

B 不是新设计的“批量交易格式”，而是当前账本已经能导入、也能导出的 `BackupEnvelopeV1` JSON。

外层结构固定为：

```json
{
  "backupFormatVersion": 1,
  "appVersion": "...",
  "exportedAt": "...",
  "ledgerSchemaVersion": 1,
  "ledgerData": {
    "schemaVersion": 1,
    "assets": [],
    "trades": [],
    "priceSnapshots": [],
    "feeRules": []
  }
}
```

已确认边界：

- TypeScript 只负责在源码中定义合同；用户实际保存和导入的是 JSON；
- 【建议】先由账本导出合法样板，再让外部 AI / 人工填充历史交易；这是降低格式错误的稳妥做法，不是唯一允许的转换方式；
- BTC、ETH、ADA 内置资产可直接保留；
- 没有历史价格或手续费规则时，相应集合保持空数组，不能删除字段；
- 每笔交易应保留 A 中对应原句到现有 `rawText`；
- B 是明文敏感文件，必须离线或在用户认可的位置保存；
- 程序只读取 B，不移动、不删除、不主动上传 B；
- B 是救援与迁移材料，不是日常工作数据库；
- 首次历史迁移后，用户还计划定期主动导出新的 B 并保存到离线硬盘；这是人为维护的灾难恢复点，不等于自动备份，也不保证天然包含最后一次导出后的交易。

### 4.3 C：唯一正式加密工作文件

C 是账本程序日常打开和持续写入的加密文件。

已确认边界：

- 用户在系统文件选择器中决定 C 位于 Documents、iCloud Drive 或其他本地可见位置；
- iCloud Drive 在此阶段只是用户选择的文件位置，不等于应用已实现完整 iCloud 同步协议；
- 同一账本在文件夹中只出现一个正式 C；
- 程序不得为了备份自动制造一串 `C1 / C2 / C3`；
- IndexedDB 只允许保存文件句柄等元数据，不再保存第二份完整官方账本；
- 持仓、图表和其他派生结果继续临时计算，不写入 C；
- C 不承担 B 的明文导入导出身份；
- “清空账本”只能在明确确认后清空 C 内的账本内容，不能悄悄删除整个 C 文件。

## 六、C 的“左脚踩右脚”安全模型

用户对 C 的固定心智模型是“左脚踩右脚”：文件夹中只有一个 C，但 C 内始终保留最近两代可用的完整账本。

【建议】对外术语使用：

- 当前可用版；
- 上一可用版；
- 候选版只存在于一次保存过程。

示例：

```text
C 当前包含：
当前可用版：300 笔
上一可用版：299 笔

新增一笔 BTC 后：
先在内存生成 301 笔候选版
→ 完整校验
→ 加密
→ 安全写入
→ 关闭文件
→ 重新读取、解密、完整校验
→ 全部通过后，C 变为 301 + 300

再新增一笔 ETH：
302 候选版完成同样流程
→ 成功后，C 变为 302 + 301
```

核心规则：

1. 候选版是一份完整账本，不是只保存一条增量补丁。
2. 候选版没有通过完整 Validator 前，旧的可用版不能被覆盖。
3. 写入流关闭后必须重新读取同一个 C。
4. 只有解密、结构校验、资源策略和业务时间线全部通过，UI 才能显示“已保存”。
5. 当前版损坏但上一版可用时，程序进入明确的恢复状态，告诉用户最新一次保存没有恢复。
6. 恢复不得静默发生；用户必须知道自己打开的是上一版。
7. C 整个被删除、硬盘损坏或 iCloud 文件彻底丢失时，两代内容会一起丢失；双版本只解决最近一次写入损坏，不解决整个文件消失。
8. Git、Time Machine 或云盘可以作为外部灾难恢复，但不能代替程序自己的安全保存。
9. Git 不进入 8 月 3 日必做范围，日常保存安全不能依赖用户是否记得提交加密文件。

该模型应位于加密文件与存储层，不修改 `LedgerData` 的业务集合。

## 七、C 的单写入者、重开与密码规则

### 7.1 同一个 C 只允许一个 Chrome 标签页进入

禁止同一文件被两个账本页面同时编辑。

正确模型：

- 第一个标签页获得只存在于浏览器运行期的独占锁；
- 第二个标签页立即显示“该账本已在另一标签页使用”；
- 标签页关闭、跳转或崩溃后，运行时锁自动释放；
- 不在 C 或 IndexedDB 写永久 `locked=true`；
- 不提供日常“强制抢锁”按钮；
- 每次真正写文件时再取得短时文件写锁；
- 写入前比较磁盘版本和当前页面加载版本；
- 发现 C 被其他程序或外部同步修改后，拒绝旧页面覆盖，要求重新打开；
- 极端浏览器故障的恢复方式是完全退出并重开 Chrome，不要求重启电脑或手工删除占位文件。

### 7.2 再次打开

- IndexedDB 只记住上次 C 的文件句柄；
- 有权限时直接进入该 C 的解锁页；
- 权限失效时显示“重新连接此文件”；
- C 被移动、删除或选错时，不自动创建空账本；
- 当前 C 的身份必须可核对，不能因文件名相同就认为是同一本账。

### 7.3 密码

- C 只有一个用户设定的核心密码；
- 没有恢复码、管理员后门或第二套解锁秘密；
- 新建时必须明确提示：忘记密码将永久失去对该 C 的访问；
- 用户必须两次输入一致；
- 密码只在当前标签页解锁期使用，刷新、关闭或点击“立即锁定”后失效；
- “立即锁定”同时清除内存中的解锁材料并释放当前 C 的标签页占用；
- 不做闲置自动锁定；
- 不跨 Chrome 重启保存可直接解密 C 的凭据；
- B 可用于用户自行救援，但程序不承诺 B 包含最后一次导出后的交易。

未来 Keychain / 生物识别规则：

- 核心密码仍是跨设备的唯一通用秘密；
- 每台新设备第一次必须输入核心密码；
- Mac 只在本机 Keychain 保存设备侧凭据，并由 Touch ID 放行；
- iPhone 同理使用本机 Keychain + Face ID；
- 不通过 iCloud Keychain 自动同步解锁凭据；
- 换新设备仍必须知道核心密码；
- 生物识别信息不写入 C。

## 八、B 导入 C 的固定语义

用户看到的首次流程：

```text
新建账本
→ 设置核心密码
→ 进入空账本
→ 点击导入
→ 选择 B JSON
→ 校验和确认
→ 完整数据进入并保存到用户选择的 C
```

是否先在磁盘写出零交易 C 属于实现细节，不能改变用户合同。

导入规则：

1. B 导入新空账本时采用整本替换，不做合并。
2. B 有 300 笔，成功结果就是 B 的完整 300 笔，不是与测试交易拼成 303 笔。
3. 任一硬错误都拒绝整本导入。
4. 不允许“跳过第 147 笔，先导入其余 299 笔”。
5. 失败时 B 原封不动，C 保持导入前完整状态。
6. JSON 语法错误尽可能定位行、列。
7. 业务错误至少给出 `trades[146].quantity` 这类准确路径，并附日期、资产、买卖方向等摘要。
8. 多个错误应提供可复制的完整错误清单，不能让用户每次只修一个再重新发现下一个。
9. 当前 8 MiB 文件上限继续有效；200–400 条通常不会触顶，但必须用真实 B 测量，不能凭估计宣称通过。

重复交易规则：

- 相同 ID 是硬错误；
- ID 不同但业务字段高度相同的交易属于可疑重复；
- 可疑重复必须集中显示给用户确认；
- 不自动合并、不自动删除、不静默接受；
- 两笔同日、同价、同数量交易可能是合法拆单，因此算法只能提出疑点，最终决定属于用户；
- “相似到什么程度”尚未形成最终实现合同，后续需要单独讨论。

## 九、手续费必须进入真实成本和净盈亏

用户确认完整历史手续费全部是 USD / USDT，因此 8 月 3 日不需要处理 BTC、ETH、ADA、BNB 等资产手续费导致的持仓数量变化。

确定性计算规则：

```text
买入后新增成本
= 成交总额 + 买入手续费

卖出净收入
= 成交总额 - 卖出手续费

已实现净盈亏
= 卖出净收入 - 本次卖出移除的含费成本

未实现净盈亏
= 当前市场价值 - 剩余含费成本
```

具体边界：

- 买入手续费进入成本基础，并随平均成本法在后续卖出时按份额移除；
- 卖出手续费直接减少本次净收入；
- `feeRule` 只帮助录入，不参与追溯重算；
- 计算必须使用每笔 Trade 已实际保存的 `fee`；
- USD / USDT 延续当前 `1 USDT ≈ 1 USD` 产品口径，并明确这是近似汇总，不是假装严格美元换汇；
- 净成本和净盈亏仍是派生结果，不存入 C；
- 该修正排在 UI 重构之前，因为首页不能美化一个已知漏费的数字。

## 十、交易与价格的单条安全纠错

### 10.1 交易编辑

允许纠正所有用户业务字段：

- 日期和时间精度；
- BTC / ETH / ADA 等资产；
- 买入 / 卖出方向；
- 数量；
- 单价；
- 总额；
- 币种；
- 手续费和手续费币种；
- 手续费规则引用；
- 备注；
- 原始文本。

不允许编辑：

- Trade ID；
- 原始 `createdAt`。

成功后只更新 `updatedAt`。

保存流程：

```text
点击编辑
→ 将原交易复制到编辑草稿
→ 正式账本暂时不变
→ 用户修改
→ 点击“检查并保存”
→ 生成替换该交易后的完整候选账本
→ 完整时间线、成本、持仓与资源校验
→ 计算修改前后差异和下游影响
→ 用户再次确认
→ 才进入 C 的安全保存流程
```

合法修改也必须显示类似 Git diff 的确认：

- 只显示真正变化的字段；
- 显示受影响资产的数量、成本、已实现盈亏变化；
- 说明多少笔后续交易重新校验通过；
- 确认按钮使用明确文案“确认替换这笔交易”，不能只写“确定”；
- 只需要一次内容充分的差异确认，不要求重新输入密码，也不连续弹出多次确认；
- 取消确认时返回仍保留内容的编辑草稿。

若把早期 BTC 买入量改小会导致后续卖出超出持仓，则直接拒绝并定位第一笔受影响的卖出，原交易保持不变。

### 10.2 交易删除

- 一次只能删除一笔；
- 删除前先构造完整候选账本并重放；
- 删除合法时显示交易详情和持仓、成本、净盈亏变化；
- 使用明确红色按钮“确认删除这笔交易”；
- 不要求额外输入交易 ID；
- 删除会破坏后续时间线时直接拒绝；
- 本阶段不引入回收站、软删除或 tombstone schema。

### 10.3 价格编辑与删除

8 月 3 日范围同时包含价格快照纠错，不只做交易。

- 手工价格可以单条编辑或删除；
- Binance 快照若被人工修改，必须明确提示“将转为手工价格”；
- 转换后 `source = manual`；
- 删除结构化 Binance provenance；
- 可在备注中记录“原为 Binance 快照，已由用户手工修正”；
- 不允许手工修改数值后继续冒充 Binance 原始数据；
- 价格纠错同样使用候选、校验、差异预览和二次确认。

### 11.3 三层图表

#### 第一层：组合总价值与持仓成本

第一层横跨整页，使用同一 USD 总额纵轴：

- 组合总市场价值：普通线，随可用市场价格变化；
- 剩余持仓成本基础：阶梯线，在买入、卖出时发生水平 / 垂直变化；

- 市场价值高于成本代表当前持仓浮盈；
- 市场价值低于成本代表当前持仓浮亏；
- 左上角当前只显示固定 `USD 等值`；
- 欧元、人民币或加密货币换算属于未来能力，本阶段不做选择器。

不得在该图加入“全组合平均买入价”第三条线，因为：

- 市值和成本的单位是 USD 总额；
- BTC 平均成本单位是 USD / BTC；
- ETH 是 USD / ETH；
- ADA 是 USD / ADA；
- 不同资产的单位成本不能合成一条可比较的组合线。

未来单资产详情可显示：

- BTC / ETH / ADA 自身 K 线；
- 该资产的平均买入价虚线；
- 买入和卖出标记。

#### 第二层：当前资产分配

第二层是一个完整卡片内的左右结构：

- 左侧约三分之一为饼图；
- 右侧约三分之二为按占比从高到低排列的资产；
- 排名显示资产、占比，并可同时显示金额和数量；

#### 第三层：交易活跃热力图

- 完整保留最近 365 天交易热力图；
- 显示哪些自然日发生过交易；
- 点击日期可继续联动交易列表；

### 11.4 缺价时的真实性

```text
BTC 当前价值：6,500 USD
```

## 十二、成交价、估值快照与外部 K 线必须分层

三类价格的业务含义不同：

| 数据 | 示例 | 用途 | 是否属于核心账本 |
| --- | --- | --- | --- |
| 交易成交价 | 0.1 BTC 以 50,000 USD 买入 | 计算真实成本 | 是，属于 Trade |
| 账本估值快照 | Binance / 手工记录 BTC 65,000 | 计算某时点市值与未实现盈亏 | 是，属于 PriceSnapshot |
| 外部 K 线 | BTCUSDT 一小时 OHLCV | 查看市场背景和单资产行情 | 否，属于 Market Data 层 |

当前 Binance 真实行为：

- 使用公开 `exchangeInfo` 和 `/api/v3/ticker/price`；
- 只查询最新价；
- 解锁后自动尝试一次，也可手工刷新；
- 只刷新非零持仓；
- 同一资产同一天重复刷新时更新当天 canonical Binance 快照；
- 不保存每分钟河流式价格；
- 不接历史 K 线。

长期架构方向：

- 历史 K 线放在独立 `MarketDataProvider` 边界；
- Binance 只是第一个 provider，不成为核心账本依赖；
- provider 负责 latest quote、candles、限流、失败和缓存；
- `LedgerData` 不塞入大规模、可重新获取的 K 线；
- C 不因 Binance 不可用而无法打开；
- 无行情时保留缺口，允许手工估值，不编造价格；
- 未来可替换第二家供应商，而不迁移 Trade 和核心账本；
- 是否缓存 K 线、缓存多久、采用什么 provider 尚未决定。

Binance 官方现有 `/api/v3/klines` 支持历史 K 线，但“当前可用”不等于未来永远免费或稳定。

## 十三、NLP 课程与自然语言录入的已确认边界

8 月 3 日真实使用 Gate 通过后，到 2026-09-25 DEIK.AI Demo 截止前，主要开发时间优先给 NLP Type 1 与比赛 Demo；Tauri、Keychain 和 Touch ID 不抢占这段固定窗口。

2026-07-27 的机器环境事实为：Mac 使用 M5、16 GB 内存，当时尚未安装 Ollama。该事实只用于解释 Type 1 比 Type 2 更适合作为当前方向；真正实施前仍需重新检查安装状态、模型和可用资源。

### 13.1 已确认路线

- 课程选择 Type 1 Multi-Agent；
- 所有 Agent 使用 Ollama 本地运行；
- 文本输入先于语音输入；
- 语音识别是以后独立的“语音 → 文本”层；
- NLP 第一阶段只提出新增交易草稿；
- 不允许 NLP 修改或删除既有交易；
- 不允许生成投资建议；
- 不允许未经用户确认静默写入；
- 缺失或歧义字段必须询问用户；
- 不得编造资产、价格、数量、币种、手续费或日期；
- 最终业务合法性由确定性 Validator 判断；
- Agent 不能替代持仓时间线、金额容差、资源策略和写入规则。

目标链：

```text
用户文本
→ 提取 Agent 提出候选
→ 审核 Agent 对照原句找错读、幻觉和歧义
→ 必要时迭代修正或询问用户
→ 用户查看并确认
→ 确定性 Validator
→ 现有交易写入链
→ C
```

### 13.2 为什么需要两个 Agent

角色不能为了满足“至少两个 Agent”机械拆分。

有价值的角色边界是：

- 提取 Agent：只把原句映射为候选字段，并显式标记缺失；
- 审核 Agent：逐字段检查候选是否得到原句支持，找出擅自补值、单位错读、币种混淆和未处理歧义；
- 审核 Agent 不直接成为第二个随意提取器；
- 原句明确写“5 美元手续费”，却被填成 `5 USDT` 时，可以退回修正；
- 原句只写“手续费 5”时，必须询问用户，不能靠多轮对话把猜测包装成确定。

### 13.3 写入 C 的边界

用户确认后，C 只保存：

- 正常结构化 Trade；
- 触发该交易的用户原句 `rawText`。

不进入 C：

- Agent 对话；
- 审核批评；
- 置信度；
- 迭代日志；
- 课程实验结果；
- prompt；
- 模型响应原文。

课程数据和实验日志使用独立评测材料，不污染正式金融事实。该设计不要求修改 `LedgerData` 的四个核心集合；现有 `rawText` 已能保留原始输入。

### 13.4 课程必须保留的实验要求

- 与单 Prompt、单 Agent baseline 公平比较；
- baseline 与 multi-agent 使用可比较的模型、输入、字段合同和测试集；
- 指标至少覆盖字段正确率、缺失 / 歧义识别、幻觉字段、错误写入风险和延迟；
- 最终材料能整理为 Jupyter notebook、5–10 分钟视频和可运行应用；
- 不能只展示几个成功例子就宣称 multi-agent 显著更好。

### 13.5 暂停讨论、尚未决定

2026-07-27 主动暂停了 NLP 细节讨论。以下内容仍是未来议题：

- 自动反馈最多一轮、两轮还是其他停止规则；
- 中文、英文或双语输入范围；
- M5 / 16 GB 机器上的 Ollama 模型；
- 数据集规模、难例分层和标注方法；
- baseline 与 multi-agent 的严格公平协议；
- 澄清回答如何与原始 `rawText` 一起保存；
- 课程 notebook、视频与应用的具体结构。

任何后续 AI 不得把这些未决项擅自写成已确认方案。

## 十六、iCloud、桌面端、移动端和生物识别的长期依赖

### 16.1 当前阶段


17. 不得把 Agent 日志写进 `LedgerData`。
18. 不得把历史 K 线塞进核心账本并让产品依赖单一供应商。
19. 不得把 iCloud Drive 文件位置表述成已完成的自动同步与冲突处理。
20. 不得把比赛 Demo、课程实验和论文 benchmark 互相冒充。
21. 不得让只读 iPhone 把旧账本或派生状态写回 iCloud。
22. 不得让云端可用性成为打开和保存本机 C 的前置条件。

## 十九、给后续 AI 的使用说明

开始任何实现前：

1. 先读 `AGENTS.md` 和 `ledger-workflow`；
2. 再读当前开发状态、源码 README 和真实相关源码；
3. 把本文当成最新产品决策背景，而不是已实现能力；
4. 明确本次只处理哪一个问题；
5. 用 BTC、ETH、ADA 场景向用户说明取舍；
6. 优先使用自然、中文逻辑的表达；专业术语只在必要时使用，并立即用人话解释；
7. 一次优先讨论一个真正会改变方案的问题，不连续抛出大量抽象选择；
8. 任何会改变产品方向的选择先由用户确认；
9. 另行生成可执行计划、接口设计和验收标准；
10. 未获得实现授权时，不修改源码。

本文的作用是让后续 AI 知道“用户已经决定了什么、为什么这样决定、哪些边界不能越过”。它不替代未来的 Week 11 Checklist，也不授权任何 Agent 直接按本文大包实施。
