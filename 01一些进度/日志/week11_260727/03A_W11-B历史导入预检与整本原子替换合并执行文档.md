### 4.3 分层校验与一次汇总

校验顺序固定：

1. 以实际 UTF-8 byte length 执行 8 MiB 文件上限。
2. JSON 解析；失败时尽可能从真实 parser 信息提取行、列，无法可靠提取时明确“位置不可得”，不得编造。
3. 验证 `BackupEnvelopeV1` 外层元数据和 schema。
4. 验证 LedgerData 结构与所有可安全到达的实体字段，保留准确路径。
5. 对历史导入额外验证每笔 `trades[i].rawText` 为非空原句；缺失、非字符串或全空白时返回类似 `trades[146].rawText` 的硬错误，不修改通用 Trade schema。
6. 执行 JSON/集合/字符串 ResourcePolicy。
7. 对可独立验证的交易建立带原数组索引的投影；即使另一笔交易有硬错误，也要允许合法 ETH 重复组被发现。
8. 对可安全执行的完整业务规则运行 `validateLedgerImportPolicy()`。
9. 对有效交易投影运行可疑重复分组。

不得为了“多报错”制造级联假错误。某一步的前置不可用时：

- 记录已发现的硬错误；
- 在结果中记录被跳过的检查及原因；
- 不把“未执行”写成“通过”；
- 不生成可写入候选。

同一个 B 中的非法 BTC 数量、可疑 ETH 重复和两笔合法 ADA 拆单必须在一次预检中同时表现为：

- BTC 精确路径硬错误；
- ETH 一个可疑组；
- ADA 拆单不被标成必须删除；
- C 零写。

### 4.4 问题模型、排序与报告上限

每个硬错误详情至少包含：

- `code`；
- `path`，例如 `trades[146].quantity`；
- 交易摘要：能安全取得时只包含日期、资产、买卖方向等必要字段；
- 中文说明；
- JSON 语法错误的可选 `line`、`column`。

每个可疑组详情至少包含：

- 等级：高度可疑或一般可疑；
- 组内原始路径/索引；
- 交易摘要；
- “未自动修改、删除或合并”的说明。

确定性排序固定为：

1. 硬错误先于可疑组；
2. 硬错误按校验阶段、路径、错误码稳定排序；
3. 可疑组按最小原交易索引排序；
4. 同组索引升序。

“详情”指硬错误项与可疑组的合并序列：

- 页面显示两个独立总数：硬错误总数、可疑重复组总数；
- 页面内部滚动区展示合并序列前 50 项；
- 内存保留、Markdown 复制最多前 1000 项；
- 总详情数超过 1000 时，报告明确写出总数、保留数和“第 1001 项后已截断，请修正后重新检查”；
- 页面 50 项上限不得截掉用于复制的第 51～1000 项。

Markdown 第一段必须提醒：报告可能包含交易日期、资产、数量和金额等隐私。复制失败要给诚实错误，不能显示“已复制”。

### 4.5 可疑重复算法

只对不同 ID 的有效交易判断。相同 ID 只进入硬错误，不再形成可疑组。

核心比较字段：

- 日期/时间规则；
- `type`；
- `assetSymbol`；
- `quantity`；
- `price`；
- `totalValue`；
- `currency`。

明确排除：

- `id`；
- `createdAt`；
- `updatedAt`；
- `note`；
- `rawText`；
- `feeRuleId`。

数值字段必须用现有 decimal 工具做语义比较，`0.10 == 0.1`。不得使用浮点转换或原字符串相等。

时间规则：

| A | B | 提示条件 |
| --- | --- | --- |
| 都是精确时间（minute/second） | 时间完全相同 | 核心字段全部相同才提示 |
| 至少一笔是 day | 同一自然日 | 核心字段全部相同才提示 |
| 都是精确时间 | 精确时间不同 | 即使同日、同价、同数量也不提示 |

建议先按上表为真实可疑关系建立边，再把相连交易收成一个组；组中要保留实际触发关系，不能因为 day 精度交易把两个不同精确时间的交易间接写成“二者时间相同”。这既避免两两展开，也能诚实表达“两个精确时间记录分别与同一条 day 记录可疑”的情况。

分级：

- 核心字段相同，且 `fee` 与 `feeCurrency` 也相同：高度可疑。
- 核心字段相同，但手续费数值或手续费币种不同：一般可疑。
- 整组所有成员的 `fee + feeCurrency` 都相同才标高度可疑；组内任一差异则标一般可疑。

分组必须从真实可疑边构造稳定 connected group，并保留触发边。不得把这条非传递关系误写成数学等价关系。N 条完全相同交易只形成一个组并列出 N 个索引，不展开为两两组合。

以下只影响分组结果，不得修改候选：

- note/rawText/timestamps/feeRuleId 差异；
- 合法的 BTC、ETH、ADA 拆单；
- 用户取消；
- 用户对全部可疑组做一次明确确认。

确认必须绑定当前 B identity、当前可疑组 identity 和当前 selection generation；重新选择、重新预检、取消、文件内容变化后确认失效。

### 4.6 BackupControls 状态机

`BackupControls` 只负责展示和事件编排，不承载校验算法。

建议/待实现地把现有单一 `canImportBackup` 语义拆成：

- 可选择并纯预检 B；
- 是否存在可提交到 C 的 session-bound import port。

正式 C 可以开放纯预检入口，但阶段一不得拥有写能力。状态至少区分：

```text
idle
reading
preflighting
preflight-blocked
ready-without-suspicions
awaiting-suspicion-confirmation
committing
restoring-verified-base
success
error
```

每次选择、取消、重选、卸载都使旧 `File.text()`、旧 preflight Promise、旧复制结果和旧确认 token 失效。迟到结果不得复活按钮、报告或写入。

存在硬错误时：

- 可以展示和复制完整报告；
- 可疑组可以同时展示；
- “继续导入”必须不存在或 disabled；
- 即使调用伪造确认回调，也不能到达 C import port。

## 七、阶段二当前实现阻断

### 7.1 post-close 失败零写

goal-objective 已固定：

- 任一 write、close、readback 或完整验证失败都不能显示成功；
- 失败时 C 保持导入前完整状态；
- 失败零写是阶段二通过线。

当前真实链是：

```text
createWritable
→ write
→ close
→ 同句柄 readback
```

现有正式测试已证明：`close` 成功后，readback 抛错时磁盘可能已经是新 bytes。Repository 现有 `PendingSaveIntent` 只说明结果尚未确认；它不证明旧 C 保持不变，而且 `save()` 在 reconcile 得到 base 后会再次写同一 pending intent。

因此本批固定：

- `commit-unconfirmed` 不能成为阶段二终态、通过线或开发完成条件。
- import 必须使用专用、可证明的原子/补偿方案；任何失败返回前都要复读并证明导入前 C 的 bytes、current、previous、revision 和完整 LedgerData 已恢复。
- 若内部短暂进入 pending/unknown，只能作为未完成的恢复过程；最终必须收敛为“完整验证成功”或“旧 C 已恢复并完整验证的失败”。
- import 专用 reconcile 得到 base 时必须终止为零写失败，`writable/write/close` 都为 0；不得沿用普通 `save()` 的“base 后再次写同一 intent”语义。
- 既不能验证候选成功，也不能恢复并验证旧 C 时，阶段二 implementation BLOCKED，不得生成成功或失败终态，不得写“03A 开发侧完成”。

不得用与当前 adapter 事实相反的 fake 断言伪造零写；也不得通过修改 C V1、KDF、AAD、两代合同或制造额外可见 C 偷换要求。若当前平台能力无法满足，03B 如实记录阶段二未进入。

### 7.2 生命周期变化后旧导入不得继续

goal-objective 已固定：取消、卸载、换文件、锁定、Repository generation 变化或旧 `File.text()`/preflight Promise 晚到，都不能让旧导入继续，也不能覆盖新状态。

当前 `beginQuiesce()` 会同步拒绝新公共调用，但 `drainForSessionQuiesce()` 和 session lease 会等待已接受 import/write 收尾。只忽略旧 UI 结果不能证明底层导入没有继续。

因此本批固定：

- import 专用状态机必须先把可 drain 的工作同步登记，再允许任何异步 authorization/driver claim，避免“已获准但 quiesce 看不见”的窗口。
- 取消、卸载、重选、立即锁定、换 session 或 generation 变化一旦使当前导入失效，旧 authorization/claim 必须撤销，后续 writable/write/close 为 0。
- 登记后、claim 前 quiesce；driver 延迟 claim；旧 receipt 晚到，都必须零副作用。
- 若物理写已经开始，方案仍必须满足本节与 7.1：生命周期事件后旧导入不得继续为新 current，且导入前 C 最终恢复并验证；不能用“继续写完但不更新 React”替代。
- 现有普通 import 的 drain 行为可以保留给其原有场景，但不得冒充新的 C import 合同。

若无法同时安全中断并保留旧 C，阶段二 implementation BLOCKED。执行 AI不得自行把固定合同改成“claim 后安全 drain”。

只有用户未来主动修改产品合同并先重写成对的 03A/03C，才允许采用不同通过线；本文件不授权这种变更。

## 八、阶段二建议/待实现架构

### 8.1 “新空 C”的固定技术判定

本批建议固定为全部满足：

- storage kind 是正式 `ledger-file`；
- session active、hydration ready、非 read-only、operation idle；
- 页面与 Repository 已验证 LedgerData 都规范化等于 `createInitialLedgerData()`；注意内置 BTC/ETH/ADA assets 存在，不能用“四个数组全空”误判；
- C 的 `previous === null`，当前 generation 的 `parentRevisionId === null`；
- 当前没有 dirty、failed snapshot、pending save、pending clear 或 pending import；
- 写前同句柄复读仍匹配授权中的 fileId 与 verified revision；
- sessionId、session generation、Hook generation 自授权后未变化。

`previous === null + parentRevisionId === null` 是本批选择的最小可测实现路径，用于排除 lineage 已前进、清空过或已有交易的 C；它不能识别一次完全 no-op、未产生新 generation 的历史 `save()` 调用，也不得把这种不可观察调用写成已识别事实。00A 已确认“是否先物理写出空 C”属于实现细节：若等价方案直接以 B 创建新 C，但仍能证明全新目标、整本替换、失败零写和生命周期合同，则不因物理写入顺序单独请求产品决定；只有改变用户流程、C 格式或安全合同才停止确认。

### 8.2 session-bound import port

不得只把 `LEDGER_FILE_CAPABILITIES.canImportBackup` 改成 `true`，也不得让 UI 直接调用 `repository.save(candidate)`。

建议/待实现地仿照 ready-clear 新增：

- opaque `ReadyLedgerImportAuthorization`；
- `LedgerReadyImportDriver`；
- `LedgerReadyImportPort`；
- 单次 claim 的 execution context。

名称可在实现时微调，但职责不得变。授权至少绑定：

- sessionId 与 session generation；
- fileId 与 verified revision；
- B 内容 identity 与规范化 LedgerData identity；
- selection generation；
- hardErrorCount 必须为 0；
- suspicious group identity；
- 无可疑组或一次确认的 nonce；
- 新空 C 判定证据；
- 单次消费状态。

Hook 必须先同步登记 import operation/promise，使 quiesce 能看见并撤销该工作，然后才允许异步 driver authorization/claim。授权必须由仍 active 的 session 在执行点同步 claim；跨 session、跨 generation、跨 fileId、跨 revision、重新选择、重新预检、二次消费或伪造对象全部拒绝且零写。不得先 claim/开始 Repository 写入，再把 Promise 塞进 drain refs。

可以借鉴 `ReadyLedgerClearAuthorization` 和 `LedgerFileMigrationReceipt` 的绑定方式，但不得复用 migration receipt 品牌或把 legacy 迁移冒充 B 导入。

### 8.3 唯一写入链

阶段二唯一允许的写链：

```text
冻结的 preflight candidate
→ 用户一次确认（如有可疑组）
→ usePersistentLedger 同步登记可撤销 import operation
→ session-bound import authorization 与执行点同步 claim
→ import 专用写队列
→ LedgerFileRepository 的 import 专用原子路径
→ session lease 内写前复读
→ 新 revision，旧空 current 进入 previous
→ write
→ close
→ 同句柄 readback
→ fileId/revision/parent/精确密文 generation/完整 LedgerData 验证
→ Repository verified 更新
→ 当前 Hook/session 仍有效时 ledger/replace 与 saved
```

不得：

- UI 先替换 reducer 再等自动保存；
- 绕开 Repository 直接调 adapter；
- 为 import 建第二套 C writer；
- 在验证前清空当前 C；
- 把 B 与初始/测试交易合并；
- 跳过第 147 笔后写 299 笔；
- 写完整 B 或 C 到 legacy IndexedDB。

import 专用路径必须复用 `LedgerFileRepository` 的 Validator、ResourcePolicy、session lease、写前复读、revision、加密和完整 readback 验证，不得复制出第二套 writer；但不能直接继承普通 `save()` 在 pending reconcile 为 base 后再次写入的语义。若必须抽取共用私有 primitive，应以正式回归证明普通 save 合同未漂移。

### 8.4 结果状态

阶段二结果必须能区分：

| 状态 | 证据 | 页面与后续 |
| --- | --- | --- |
| verified success | 精确 readback 与完整 LedgerData 全部通过 | 当前 session 才发布 300 笔和 `saved` |
| verified zero-write failure | 授权前拒绝，或失败后已恢复并复读证明精确等于导入前基线 | 页面与 C 保持导入前状态，可修正后重新预检 |
| implementation blocked | 无法证明候选成功，也无法恢复并证明旧基线 | 不发布终态；阶段二不能完成，03B 记录阻断 |

`commit-unconfirmed`、stale accepted write 或“继续 drain 但忽略旧 UI”都不能作为本批可交付状态。若内部出现，必须在本次操作和开发完成前收敛到前两行；否则只能是 implementation BLOCKED。
