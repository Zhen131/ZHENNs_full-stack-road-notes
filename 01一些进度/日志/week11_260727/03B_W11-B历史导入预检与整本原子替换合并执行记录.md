### 1.1 通俗解释

现在的实现能做到：

1. 写之前把旧 C 的完整内容和身份记下来。
2. 把新内容写入并关闭文件后，立即重新读取、解密和校验。
3. 如果后续检查失败，而且还能确认文件里正是本次刚写入的新内容，就尝试把旧 C 原样写回并再次读取确认。
4. 如果不能证明安全恢复，就停止当前会话继续写，不把结果伪装成成功。

但浏览器做不到绝对保证：新内容一旦在 `close()` 后进入文件，Chrome 可能立刻崩溃，系统可能收回文件权限，文件也可能被其他程序改掉。此时网页已经没有能力继续执行“写回旧 C”。

这不是少写一个异常分支，而是浏览器没有提供单文件事务、compare-and-swap 或进程死亡后的强制回滚能力。File System Access 的公开模型仍是创建 writable、写入、关闭和重新读取；`close()` 才把变更提交到磁盘，权限或外部变化仍可能使后续操作失败：

- [WHATWG File System Standard](https://fs.spec.whatwg.org/)
- [Chrome File System Access API](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

因此当前候选是纯浏览器单 `.lftl` 合同下能做到的安全上限，但不满足 03A 的绝对措辞。

## 四、阶段二实现

### 4.1 授权与候选固定

- import port 在异步 claim 前注册为正在执行。
- 候选在进入 session import port 时同步 `structuredClone`，调用方后续修改对象不能改变待写内容。
- 授权绑定：
  - repository session；
  - session generation；
  - hook generation；
  - fileId；
  - verified revision；
  - B content identity；
  - candidate identity；
  - selection generation；
  - 可疑组 identity 与确认 identity。
- 只允许本次会话中新建且仍为空的 C。

### 4.2 写入、复读和 lineage

- 导入进入 repository 专用互斥队列，与普通 save、clear 和其他 import 互斥。
- 底层 `createWritable()` 固定使用 `keepExistingData: false` 与 `mode: "exclusive"`。Chrome 121 起支持该独占 writer；它能拒绝同一 Chromium File System Access 范围内的第二个 writer，但不是操作系统文件锁，且 `close()` 后锁即释放。
- 写前读取并保存旧 C 的完整序列化内容、fileId、current revision 和 previous。
- 加密前、加密后均重新确认磁盘基线没有变化。
- 为候选创建新 revision，把旧 current 放入 previous。
- 执行 write-close-readback 后，重新解密并运行完整 validator。
- 只有文件内容、fileId、revision、parent、previous 和候选 LedgerData 全部一致才返回成功并替换页面。

### 4.3 补偿恢复与 fail-closed

- post-close 异常后，先读取磁盘。
- 只有磁盘仍与本事务的精确 candidate 相同，才允许写回旧 C，避免覆盖外部程序的新改动。
- 写回后再次读取，必须精确等于导入前序列化内容才报告 `LEDGER_IMPORT_BASE_RESTORED`。
- 如果无法证明磁盘是本事务 candidate，或无法证明旧 C 已恢复，返回 `LEDGER_IMPORT_RECOVERY_BLOCKED`。
- blocked 后 repository 的 `load()` 和后续写入继续 fail-closed，不让用户在不确定文件上继续操作。
- UI 明确写成“尝试恢复并复读”；不再承诺取消后必然恢复。

### 4.4 生命周期绑定

- claim、abort 和当前 target 切换均不在 React render 阶段发生。
- repository + session 在 commit phase 作为整体绑定。
- 每个 session 用 `WeakMap` 保留自己的 port、accepted work 和 drain。
- 取消、卸载、锁定、换文件、session/generation 变化都会中止对应 import。
- 已经接受的旧 session 工作由旧 drain 等待并释放，不会被新 session 提前接管。
- dirty blocked switch 不会把新 hydration 覆盖到脏页面。
- 未提交的并发 render 不会 claim、取消或污染真实 session。

最终只读审计记录两个非阻断范围说明：

1. `src/backup/backupContentIdentity.ts` 不在 03A §10.1 的字面清单中；它是预检、确认和导入共用的纯 identity helper，没有 I/O。

## 八、严格阻塞与可选解决方法

若坚持 03A 原句“任何 post-close 失败在函数返回前都必须恢复并复读为旧 C”，纯浏览器单文件方案无法完成。

最终完成性审计没有发现遗漏的可用浏览器事务 API：

- `createWritable()` 的交换文件只保证一次 `close()` 尽量呈现旧或新，`close()` 发布新内容后才进入 readback；[WHATWG File System Standard](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable)。
- `mode: "exclusive"` 自 Chrome 121 稳定，但只排斥 Chromium FSA writer，不能锁住原生程序；[Chrome 官方说明](https://developer.chrome.com/blog/new-dev-trial-for-multiple-readers-and-writers/)。
- 页面或浏览器在 close 后、readback / rollback 前终止时，不再有 JavaScript 执行补偿；[Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。
- 用户可以撤销权限，后续读取或创建补偿 writer 会被拒绝；[WICG File System Access permissions](https://wicg.github.io/file-system-access/#permissions)。
- 外部应用可以改变文件，规范把外部变化如何反映留给浏览器实现；没有 OS lock 或 compare-and-swap；[WHATWG concepts](https://fs.spec.whatwg.org/#concepts)。
- `createSyncAccessHandle()` 只适用于 bucket / OPFS 文件；非 OPFS `move()` 仍在 flag 后，而且单文件句柄没有父目录能力；[WHATWG sync access](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createsyncaccesshandle)、[Chrome move 说明](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access#renaming_and_moving_files_and_folders)。
- Web Locks 只是网页脚本协作锁，IndexedDB 事务也不能与外部文件 close 组成同一事务；[Web Locks](https://w3c.github.io/web-locks/)、[IndexedDB transactions](https://w3c.github.io/IndexedDB/#transaction-concept)。

现有永久测试还明确保留两条反例：补偿写回与最终读取都失败时，或磁盘已不是本事务精确 candidate 时，repository 正确返回 `IMPORT_RECOVERY_BLOCKED`，但磁盘不能被证明等于旧基线。它们证明 blocked 是诚实的安全出口，不是严格合同已解决。

可选解决方法只有改变运行环境或存储合同：

1. **原生桌面封装**：写同目录临时文件、`fsync`、原子 rename、目录 `fsync`，并配合文件锁和启动恢复。
2. **浏览器目录 / 多文件日志**：把 revision 写成 append-only 文件，使用 commit marker；启动时扫描 journal 并恢复最后一个完整 revision。

两种方法都会改变当前“浏览器直接维护一个权威 `.lftl` 文件”的架构或用户合同，需要新的明确决定和设计任务。

如果用户接受“尽力补偿；无法确认就 fail-closed”的现实合同，那么当前候选可作为后续评审对象；这仍不能反向改写 03A 的绝对完成线。
