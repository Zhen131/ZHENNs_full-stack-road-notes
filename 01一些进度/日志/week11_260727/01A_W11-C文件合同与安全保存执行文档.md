- 对应 00A：§4.4、§4.5。
- 目标：建立严格、可运行时校验的 UTF-8 加密 JSON 合同，分开文件、加密和账本三种版本。
- 可复用能力：`cryptoEncoding.ts` 的 Base64URL；现有 PBKDF2 / AES-GCM 参数；`validateLedgerData(...)`；当前固定字段顺序 AAD 测试方式。
- 新增或调整职责：
  - 新增 `.lftl V1` 类型、常量、严格外壳 Validator、解密 payload Validator 和固定顺序 AAD builder。
  - 新增加密 / 解密一代完整账本的文件专用服务。
  - 只复用加密原语，不复用 `StoredLedgerEnvelopeV2`、`formatVersion: 2` 或其 AAD。
- 通过线：
  - 外层只包含解锁和验证必需的技术字段与密文。

- 对应 00A：§4.3、§7.2。
- 目标：通过系统文件选择器新建或选择一个 `.lftl`，为新 C 生成一次稳定随机 `fileId`，本次 C 会话只绑定用户明确选中的句柄。这里的“唯一正式 C”指该 C 会话唯一操作这个文件；全局持久化接管仍属于 FILE-003。
- 可复用能力：现有 Access Gate 的检查、设置密码、解锁、操作互斥和“未解锁不挂载 Dashboard”边界。
- 新增或调整职责：
  - 新增文件选择与句柄 Adapter，隔离 `showSaveFilePicker`、`showOpenFilePicker`、`getFile()` 和 writable stream。
  - 新增 C 访问 Controller，负责 create / open / unlock，成功后返回文件 Repository 会话。
  - Access Gate 只调用 Controller，不直接读取句柄、解析 JSON、派生密钥或写文件。
- 通过线：
  - 取消选择是无副作用结果，不创建空 C、不切换 Repository、不显示保存成功。
  - 新建 C 固定使用当前生产 `createInitialLedgerData()` 作为第一代：包含内置 BTC / ETH / ADA，交易、价格快照和手续费规则为空，`previous:null`。300 笔场景通过同一个底层 create primitive 注入完整候选测试，不为此实现临时 B 导入。

  - 不扫描目录、不登记副本、不按文件名合并、不自动制造 C1 / C2 / C3。
  - 文件名可以变化；`fileId` 才是文件身份。相同文件名且 `fileId` 不同不能被当成同一 C。

### FILE-004：C 保留真实的当前版与上一版

- 对应 00A：§4.5、§6、§7.2。
- 目标：同一个 C 内只保留最近两代完整加密账本。
- 可复用能力：现有加密服务的新 IV 机制、整账 Repository 边界、完整 LedgerData Validator。
- 新增或调整职责：
  - C Repository 持有最近一次已验证的外壳和解密账本。

  - 每次真实修改生成新 `revisionId`、新 IV 和新 current；原 current 原样成为 previous；更老一代丢弃。
- 通过线：
  - current 和 previous 都是完整 `LedgerData` 密文，不是补丁。
  - 两代可独立认证、解密和校验。

### FILE-005：关闭写入流后复读同一个 C 才能报成功

- 对应 00A：§6、§7.3。
- 目标：把“写入完成”与“保存成功”分开；只有同一句柄关闭 writable stream 后重新读取并完整验证，Repository `save()` 才 resolve。
- 可复用能力：`usePersistentLedger` 的保存队列、dirty / retry、Repository generation 失效和成功状态；B 恢复的“保存成功后才替换页面”编排。
- 新增或调整职责：
  - C Repository 在写前验证候选，在写后重新读取同一句柄。
  - 复读核对 fileId、预期 revision、parent 链、两代 AAD、解密 payload、Validator、两类 ResourcePolicy 和保存意图一致性。
  - 失败一律 reject；由现有 Hook 保持 dirty、显示错误并允许安全重试。
- 通过线：
  - writable stream 未关闭时绝不显示“已保存”。
  - readback 尚未完成时仍是 saving。
  - 任一核对失败都不能推进 `persistedVersion`。
  - 只有复读 current 的 savedAt 与规范 LedgerData 都和保存意图完整一致，且 previous 的 generation 技术字段、IV、ciphertext 和解密 payload 都与保存前已验证 current 原样一致时才成功。
- 明确不做：自动恢复 previous、静默回退、跨标签页抢锁、重新连接权限。

## 五、`.lftl` 第一版合同

### 5.1 固定类型边界

后续实现可以按当前项目命名习惯调整类型名，但数据边界必须等价于：

```ts
type LedgerFileV1 = {
  fileFormatVersion: 1;
  fileId: string;
  crypto: {
    cryptoVersion: 1;
    kdf: {
      name: "PBKDF2";
      hash: "SHA-256";
      iterations: 600000;
      saltBase64Url: string;
    };
    cipher: {
      name: "AES-GCM";
      keyLength: 256;
      tagLength: 128;
    };
  };
  current: EncryptedLedgerGenerationV1;
  previous: EncryptedLedgerGenerationV1 | null;
};

type EncryptedLedgerGenerationV1 = {
  revisionId: string;
  parentRevisionId: string | null;
  ledgerSchemaVersion: 1;
  ivBase64Url: string;
  ciphertextBase64Url: string;
};

type DecryptedLedgerPayloadV1 = {
  savedAt: string;
  ledgerData: LedgerData;
};
```

固定规则：

- 文件扩展名是 `.lftl`；新建时使用小写扩展名，打开时用 `handle.name.toLowerCase().endsWith(".lftl")` 判断，不接受 `.lftl.json`。内容是严格 UTF-8 JSON，不是普通 `.json` B，也不是自定义二进制。
- 第一版固定 `fileFormatVersion: 1`、`cryptoVersion: 1`、`ledgerSchemaVersion: 1`。
- KDF 固定 PBKDF2-SHA-256、600,000 次、16-byte 随机 salt。
- cipher 固定 AES-256-GCM、12-byte 独立 IV、128-bit tag。
- 同一个 C 的两代共享同一 salt 和会话密钥；每个新 generation 使用新 IV。
- `fileId` 只在新建 C 时随机生成一次；移动或重命名不改变它。
- `revisionId` 每个真实 generation 随机生成；第一代 `parentRevisionId = null`。
- `savedAt` 使用注入时钟生成的严格带时区 ISO datetime，并位于密文内。
- `LedgerData` 是完整事实集合；`Position[]`、图表数据、估值模式、筛选状态、K 线和 Agent 状态不得进入 payload。
- 加密输入只能来自 `validateLedgerData(candidate).value` 重新构造出的账本；不得序列化调用方传入的原对象。现有 Validator 会重建 `LedgerData` 并丢弃未知字段，因此其成功结果才是写入、字节检查和 readback 比较的唯一权威值。

当前项目以 `globalThis.crypto.randomUUID()` 和可注入 `generateId` 生成业务随机 ID。文件实现应沿用“生产随机生成、测试注入依赖”的方式；ID 在合同中保持不透明，不编码文件名、时间、路径或账本业务信息。

### 5.2 三种版本不得混淆

| 合同 | 当前或目标值 | 所属系统 |
| --- | --- | --- |
| `StoredLedgerEnvelopeV2.formatVersion` | `2` | 当前 IndexedDB record |
| `.lftl fileFormatVersion` | `1` | 新 C 文件外壳 |
| `.lftl cryptoVersion` | `1` | C 的 KDF、cipher 与 AAD 合同 |
| generation `ledgerSchemaVersion` | `1` | 解密后的 `LedgerData` 业务结构 |

`StoredLedgerEnvelopeV2.formatVersion = 2` 与 `.lftl fileFormatVersion = 1` 是两套独立版本系统，不存在升级或降级关系。不得把 `StoredLedgerEnvelopeV2` 扩展成 union 后交给文件 Adapter，也不得把 C V1 写入 IndexedDB 固定槽位。

### 5.3 Runtime Validator

文件合同 Validator 必须：

1. 固定 `MAX_LEDGER_FILE_V1_BYTES = 32 * 1024 * 1024`。Adapter 先读取 `File.size`，超过 32 MiB 时在 `arrayBuffer()` 和 `JSON.parse` 前拒绝；取得 bytes 后复核 `byteLength`，再用 `new TextDecoder("utf-8", { fatal: true })` 解码，非法 UTF-8 受控拒绝。32 MiB 是双代 Base64URL 密文容器的防御上限，不是把单代账本业务上限放宽到 32 MiB。
2. 拒绝非对象、未知字段、缺字段、额外字段、错误数组 / null 形态和不支持的版本。
3. 校验 salt、IV、ciphertext 是无 padding 的规范 Base64URL，并要求解码后 salt 恰好 16 bytes、每代 IV 恰好 12 bytes、每代 ciphertext 至少 16 bytes 且不超过 `8 MiB + 16-byte GCM tag`。
4. 对 `fileId`、`revisionId` 和 `parentRevisionId` 使用非空、有界、不可解释的技术 ID 规则；安全上限可复用当前 128 字符 ID 上限。
5. `previous = null` 时要求第一代 current 的 `parentRevisionId = null`。
6. `previous !== null` 时要求：
   - `current.revisionId !== previous.revisionId`；
   - `current.parentRevisionId === previous.revisionId`；
   - current 与 previous 的 IV 不同。
7. 解密 payload 顶层只接受准确的 `savedAt` 和 `ledgerData`；`ledgerData` 顶层只接受 `schemaVersion / assets / trades / priceSnapshots / feeRules`，`savedAt` 必须是严格带时区 ISO datetime。
8. `generation.ledgerSchemaVersion` 必须等于解密后 `ledgerData.schemaVersion`。
9. current 和 previous 解密后分别执行以下固定链路：
   - `validateLedgerData(payload.ledgerData)`，只保留成功结果 `.value`；
   - `evaluateLedgerResourcePolicy(validated.value)`，检查集合和字符串；
   - 以固定键顺序构造 `{ savedAt, ledgerData: validated.value }` 并 `JSON.stringify`；
   - `evaluateLedgerJsonResourcePolicy(serializedPayload)`，要求每代规范 UTF-8 明文 payload 不超过现有 8 MiB 上限。
10. 写入前使用同一链路。候选字节检查、加密 plaintext 和 readback 一致性比较必须共享同一个规范序列化结果，不能一个检查原对象、另一个加密清洗后的对象。

固定 32 MiB 的理由是：每代规范明文最多 8 MiB，AES-GCM 再增加 16-byte tag，Base64URL 约膨胀至 `4 / 3`，两代合计约 21.34 MiB，再加有界外层技术字段仍明显低于 32 MiB。实现不得把“每代 8 MiB”和“外层 32 MiB”互换，也不得只执行集合 / 字符串检查而漏掉字节检查。

### 5.4 AAD 固定合同

每一代使用固定字段顺序创建 AAD，等价结构为：

```ts
type LedgerFileGenerationAadV1 = {
  fileFormatVersion: 1;
  fileId: string;
  crypto: {
    cryptoVersion: 1;
    kdf: {
      name: "PBKDF2";
      hash: "SHA-256";
      iterations: 600000;
      saltBase64Url: string;
    };
    cipher: {
      name: "AES-GCM";
      keyLength: 256;
      tagLength: 128;
    };
  };
  generation: {
    revisionId: string;
    parentRevisionId: string | null;
    ledgerSchemaVersion: 1;
    ivBase64Url: string;
  };
};
```

AAD builder 必须从已校验字段重新构造新对象，再按固定键顺序 UTF-8 编码；不得直接 stringify 不可信输入对象。

`current` / `previous` 的槽位名称不进入 generation AAD。原因是成功保存时原 current 必须原样移动为 previous，不能为了换槽位重新使用旧 IV 加密，也不能制造一代假的新 revision。槽位关系由严格外壳规则保证：新 current 的 `parentRevisionId` 必须等于 previous 的 `revisionId`；删除、交换或伪造槽位都会因 AAD 或 revision 链失败。

密文内的 `savedAt` 和 `ledgerData` 由 AES-GCM 密文本身认证。`ciphertextBase64Url` 不重复进入 AAD。

## 六、双代安全保存状态机

### 6.1 主数据流

```text
已加载并验证 current；首次创建则没有 base generation
→ 形成完整候选 LedgerData
→ Validator，并只采用重建后的 value
→ 集合 / 字符串 ResourcePolicy
→ 构造并检查不超过 8 MiB 的规范 payload
→ 与最后已验证 current 相同则 no-op
→ 生成新 revision 和新 IV
→ 加密完整候选版
→ 有 base 时原 current 原样成为 previous；首次创建时 previous:null
→ 写入同一个 C
→ 关闭写入流
→ 重新打开并读取同一个 C
→ 核对 fileId、revision 链、AAD、current 和 previous
→ 分别解密并完整校验
→ 核对复读 current 完整 payload 等于保存意图、previous generation 与保存前 current 原样一致
→ 全部通过后 Repository.save() 才 resolve
→ usePersistentLedger 才推进 persistedVersion 并报告已保存
```

### 6.2 三种代际结果

| 操作 | current | previous |
| --- | --- | --- |
| 生产 UI 新建 C | 内置 BTC / ETH / ADA、0 笔交易，revision N，parent `null` | `null` |
| 首次创建 300 笔账本 | 300 笔，revision A，parent `null` | `null` |
| 第一次真实新增 BTC | 301 笔，revision B，parent A | 原 300 笔 revision A |
| 再次真实新增 ETH | 302 笔，revision C，parent B | 原 301 笔 revision B |

- current 和 previous 都是完整账本，不是增量补丁。
- 第三次及以后保存只保留最近两代；更老 generation 不再进入 C。
- “真实修改”以规范序列化候选是否不同于最后已验证 current 为准；Hook mutation version 只负责 UI 排队，不能单独制造 generation。同一失败保存的重试不是新修改。
- 底层 `create(initialLedgerData)` 必须接受任意通过本批完整校验的候选，所以 Repository 测试可直接创建 300 笔第一代。生产“新建 C”固定传入 `createInitialLedgerData()`；未来“从 B 首次创建 300 笔 C”由 IMPORT-002 使用同一 primitive，但本批不得实现 B 读取、导入按钮或用先写空 C 再导入来伪造 `previous:null`。

### 6.3 失败与重试

- Validator、集合 / 字符串 ResourcePolicy 或 8 MiB 规范 payload 检查失败：不得打开 writable stream，旧 C 字节、已验证 envelope 和 persistedVersion 全部不变。
- 加密失败：不得写入，旧 C 不变。
- write 或 close 失败：Adapter 对仍可用的 writable stream 执行 best-effort `abort()` 并失败退出，不能把部分内容发布为应用内有效 C；不得在没有真实 Chrome 证据时宣称操作系统上的旧字节必然原样保留。
- close 后复读失败：不得显示“已保存”，不得更新内存中的“最后已验证 generation”，页面保持 dirty 并进入可重试错误状态。
- current 可用而 previous 不可用：本批判定保存失败并报告上一版不可用，不允许成功；不进入 FILE-006 恢复 UI。
- current 不可用而 previous 可用：只识别“上一版可用”并返回明确恢复所需状态；不得自动加载 previous、替换页面或声称最新已保存。
- current 与 previous 都不可用：阻断打开或保存，不得创建空账本覆盖。

同一 mutation 的重试必须幂等：

1. Repository 用 `{ fileId, baseRevisionId, serializedCandidate }` 识别保存意图；生成后保留同一 savedAt、新 revision、IV、ciphertext 和完整序列化候选。只有三项都相同才可复用旧意图。
2. 重试先读同一 C：
   - 已是预期新 revision：重新完成全部 readback 验证，成功后直接确认，不再生成一代。
   - 仍是保存前 base revision：重写同一保存意图，再关闭和复读。
   - 是其他 revision 或其他 fileId：拒绝覆盖并要求重新打开；不得把 FILE-007 的完整并发方案顺手做进来。
3. 新 mutation 到来时，先确定磁盘上一个保存意图是否已经完整可验证，再决定以上一代还是原 base 形成新候选；不得跳过一份已实际成功的 generation。

这里的重试前复读只用于协调本 Repository 自己尚未确认的 pending intent。它不实现 `navigator.locks`、BroadcastChannel、跨标签页占用或一般性的保存前外部 revision 锁；发现意外 fileId / revision 时只允许 fail closed，FILE-007 仍留给下一批。

### 6.4 成功核对清单

Repository `save()` resolve 前必须同时成立：

- 复读来自创建 writable stream 的同一个 `FileSystemFileHandle`。
- 外壳 exact validator 通过。
- `fileId` 等于会话绑定的 fileId。
- current revision 等于本次预期 revision。
- 首次创建时 current parent 为 null；后续保存时 current parent 等于保存前 current revision。
- 有 previous 时，previous revision 等于 current parent。
- current / previous revision 和 IV 关系合法。
- current 和 previous 分别通过 AES-GCM 认证和解密。
- 两份 payload 的时间与 schema 合法，且各自的规范序列化 UTF-8 字节不超过 8 MiB。
- 两份 `LedgerData` 分别通过 Validator、集合 / 字符串 ResourcePolicy 和字节策略。
- current 的规范序列化完整 payload 与本次保存意图完全一致，包含预期 `savedAt` 和规范 `LedgerData`。
- previous 存在时，复读的 previous generation 与保存前最后已验证 current generation 逐字段相同，并在独立解密后得到同一规范 payload；首次创建时 previous 必须为 null。

### 6.5 Adapter 写入与关闭顺序

Adapter 的最小唯一写法固定为：

```text
拿到本次绑定的 FileSystemFileHandle
→ createWritable({ keepExistingData: false })
→ 写入一次完整 UTF-8 LedgerFileV1 JSON
→ await close()
→ close 成功后才 handle.getFile()
→ 检查 File.size 与 arrayBuffer.byteLength
→ fatal UTF-8 解码、JSON.parse
→ 交给 Repository 完整复读验证
```

- `write()` 成功不等于保存成功；`close()` Promise 未完成前不得调用 readback。
- create / write / close / getFile / arrayBuffer / UTF-8 decode 任一步失败都向上返回失败阶段，且不得更新最后已验证 envelope、账本、revision 或 UI 成功状态。
- 新建 C 只接受 save picker 返回的句柄。系统对同名文件显示替换确认时，用户取消必须零写入；用户主动确认替换后，句柄可按新 C 初始化。应用不得绕过 picker 静默写入其他文件。
- 自动化 fake handle 必须证明应用层的旧快照不被污染；真实 Chrome 验收再记录失败时磁盘文件的实际行为。本文不把浏览器实现细节夸大为所有文件系统上的绝对原子保证。

### 页面允许与禁止

页面只允许：

- 请求 Controller 新建或选择 C。
- 提交密码 / 确认密码。
- 接收结构化的取消、等待、解锁、保存失败和恢复所需状态。
- 将 Controller 返回的单一 Repository 会话交给现有 Dashboard / Hook。

页面不得：

- 直接调用 `showOpenFilePicker`、`showSaveFilePicker`、`createWritable`、`File.text()` 或 `File.arrayBuffer()`。
- 直接构造 `.lftl` JSON、AAD、revision、IV 或 ciphertext。
- 持有可导出的密钥。
- 在 C 保存之外再调用 IndexedDB Repository 镜像写入。
- 以文件名判断文件身份。

### 单一后端会话

Controller 成功结果必须等价于：

```ts
type LedgerSession = {
  storageKind: "indexeddb" | "ledger-file";
  repository: LedgerRepository;
  capabilities: {
    canClear: boolean;
    canImportBackup: boolean;
  };
};
```

类型名可以按现有命名规范调整，但语义不得改变：

- Access Gate 先由用户选择后端，再挂载 Dashboard；一个已挂载 Dashboard 在整个会话中只持有一个 `LedgerSession`。
- `indexeddb` 会话完整复用当前 inspect / setup / unlock / reset 流程，`canClear:true`、`canImportBackup:true`。
- `ledger-file` 会话只通过 C Controller create / open / unlock，`canClear:false`、`canImportBackup:false`；本批不提供 Dashboard 内“切换 C”按钮。
- `LedgerRepository.load() === null` 的“空库”语义只属于现有 IndexedDB；文件 Repository 遇到零字节、无 current 或无效 C 必须 reject。否则现有 Hook 会把 `null` 变成 `createInitialLedgerData()`，造成错误文件被空账本覆盖。
- 现有 Repository generation / dirty 切换保护必须继续回归，但它只是防御旧异步结果，不能被解释成已实现 C 会话内任意切换。
- 如果文件 Repository 为兼容现有 `LedgerRepository.clear()` 必须实现该方法，直接调用时也必须在打开 writable stream 前返回“不支持”；页面 capability 是第一层保护，不是唯一保护。
- C Dashboard 必须隐藏 B 导入入口，并由 Hook / operation boundary 在绕过页面调用时仍拒绝导入、保证 C Repository 零写入；否则现有 `replaceLedgerFromBackup(...)` 会意外把 IMPORT-002 带入本批。现有明文 B 导出可以保留原行为和风险警告，因为它只读当前账本，不改变 C 或 B 合同。

### 新建、打开与密码的固定最小流程

```text
新建 C：
选择“新建 C”
→ 显示忘记密码无法恢复的明确警告
→ 两次输入同一 12–128 字符密码
→ 用户点击“选择位置并创建”
→ 该点击直接触发 save picker
→ 取消则无副作用
→ 返回句柄后拒绝非 .lftl；系统已取得的同名替换确认视为用户明确授权
→ createInitialLedgerData()
→ create(initialLedgerData)
→ close 后复读通过
→ 才挂载 C Dashboard

打开 C：
选择“选择 C”
→ 该点击直接触发 open picker
→ 取消则无副作用
→ Controller 读取并验证外壳，把所选文件的 fileId 记录为 pending expected identity
→ 显示密码输入
→ 正确密码使 current 与 previous 全部通过认证、解密和校验
→ 将 pending fileId 固定为本会话绑定身份
→ 才挂载 C Dashboard
```

- picker 必须由用户点击直接触发，不能在异步密码派生结束后自动弹出而丢失浏览器 user activation。
- 打开已有 C 在密码和完整验证成功前零写入；错误密码与认证失败对 UI 使用同一提示。
- Controller 只用 passphrase 派生不可导出 CryptoKey，不保存 passphrase 字符串；页面在成功或失败后都清空密码输入。CryptoKey 和底层句柄引用只留在本次 Controller / Repository 会话内，不作为独立值进入 React 业务 state、IndexedDB、localStorage 或日志；salt 只按合同保存在所选 C 的外层技术字段中，不另行复制到 IndexedDB。
- C 创建或打开失败时不得复用现有 IndexedDB “清空本地加密账本”恢复入口；用户未获得一个已验证 C session 前，任何 C 错误处理都必须零写入所选文件。
- 本批复用当前 12–128 字符密码基线、两次输入和无恢复后门警告，是完成加密新建所需的最小能力；不实现 FILE-009 的立即锁定、刷新后自动重连、占用释放、原地换密或完整生命周期重构。

### 防止提前完成 FILE-003

- 当前 IndexedDB Access Controller、V2 envelope 和 Repository 保留，既有用户路径不在本批迁移或删除。
- C 会话和 IndexedDB 会话互斥；同一 Dashboard 只接收一个 Repository。
- 选择 C 后，该会话的 mutation 只写 C；不得双写 IndexedDB。
- 本批不把完整 C 或完整 LedgerData 复制进 IndexedDB，也不持久化“第二份官方账本”。
- 本批不承诺下次启动自动回到 C，不清理已有 IndexedDB record，不宣布 IndexedDB 已淘汰。
- 若 `LedgerRepository.clear()` 的现有接口迫使文件 Repository提供方法，该方法在本批必须明确返回不支持，并由 capability 阻止页面调用；不得借机实现 FILE-010。
- C 会话不得复用当前 B 导入写入链；只保留既有 IndexedDB 导入回归，避免顺手实现 IMPORT-002。

## 八、错误语义

本批固定错误类别、责任边界和用户语义，不预先锁死最终错误码名称。

| 错误类别 | 责任层 | 用户可见语义 |
| --- | --- | --- |
| 用户取消文件选择 | Adapter / Controller | 正常取消；不创建、不切换、不报“文件损坏” |
| 不支持的扩展名 | Adapter / Controller | 请选择 `.lftl`；不读取为 B 或普通 JSON |
| 新建时目标文件已存在 | 系统 picker / Adapter | 系统必须先询问是否替换；取消则零写入，用户明确确认替换后按新 C 创建 |
| 打开时选中零字节文件 | Controller / Repository | 该文件不是已创建的 C；不挂载 Dashboard、不创建初始账本、不写入 |
| C 外层超过 32 MiB | Adapter | 文件超过本版防御上限；在读取文本和解析前拒绝 |
| 非法 UTF-8 | Adapter | 文件不是合法 UTF-8 C；不尝试替换字符后继续解析 |
| 不支持的外壳版本 | 合同 Validator | 当前版本不能打开；不得迁移或覆盖 |
| 文件结构错误 | 合同 Validator | 文件不是合法 C；不得尝试宽松修复 |
| 加密参数不支持 | 合同 Validator | 当前版本不支持该加密合同；不得降级参数 |
| AAD 认证 / ciphertext 解密失败 | crypto / Repository | 文件认证失败；在解锁场景与密码错误使用不泄露细节的统一提示 |
| 密码错误 | Controller | “密码错误或文件认证失败”；不写文件、不暴露认证 oracle |
| current 校验失败 | Repository | 最新版不可用，不进入 Dashboard / 不报告保存成功 |
| previous 校验失败 | Repository | 上一版不可用，本次保存不成功；FILE-006 恢复 UI 尚未实现 |
| fileId 不一致 | Repository | 复读的不是当前会话绑定的 C；拒绝继续 |
| revision 链不一致 | Repository | 文件版本关系变化或损坏；拒绝旧状态覆盖 |
| LedgerData Validator 失败 | Repository | 账本结构或业务时间线不合法；候选不写入 |
| ResourcePolicy 失败 | Repository | 账本或文件超过安全边界；候选不写入 |
| C 会话请求 clear | session capability / Repository | 本批不支持清空 C；零写入，不调用底层 Adapter |
| C 会话请求导入 B | session capability / Hook | 本批不支持向 C 导入 B；零写入，不调用 C Repository |
| 写入失败 | Adapter / Repository | 原候选仍 dirty；不得显示成功 |
| close 失败 | Adapter / Repository | 写入未提交；不得复读为成功 |
| 关闭后复读失败 | Adapter / Repository | 无法确认刚才的文件；保持 dirty，可安全重试 |
| 复读内容与候选不一致 | Repository | 文件没有保存预期账本；拒绝成功 |

结构错误、错误密码和认证失败在日志中可以保留不同内部阶段，但 UI 不显示攻击者可利用的低层加密细节，也不得把任何失败解释成“已经保存”。

## 九、测试与验收设计

### 9.1 纯合同测试

默认文件：`src/encryption/ledgerFileContract.test.ts`

- exact V1 外壳通过；缺字段、额外字段、未知版本、错误 null / object 形态全部拒绝。
- `.lftl fileFormatVersion: 1` 与 IndexedDB `StoredLedgerEnvelopeV2.formatVersion: 2` 同时存在且互不接受。
- salt、IV、ciphertext 的 Base64URL 和字节长度受控。
- ciphertext 解码长度在 16 bytes 到 `8 MiB + 16 bytes` 内；过长值在解密前拒绝。
- `previous:null` 只接受第一代 parent 为 null。
- 有 previous 时要求 current parent 指向 previous revision，并拒绝相同 revision / IV。
- payload 顶层只接受 `savedAt + ledgerData`，LedgerData 顶层只接受 schemaVersion 与四个事实集合；写入只序列化 `validateLedgerData(...).value`，调用方附带的 `Position[]`、图表、K 线、UI 或其他未知字段不能进入 C。
- 解析后的外层除合同技术字段和 ciphertext 外不出现任何业务字段；测试使用带引号和字段名的明文 JSON 片段或非 Base64URL 哨兵值检查泄露，不得因随机密文中偶然出现 `BTC` 三个字母就误报。
- 单代规范 payload 在正好 8 MiB 时接受，8 MiB + 1 byte 时拒绝；集合 / 字符串通过不能代替该字节检查。
- C 外层在正好 32 MiB 时进入后续解析，32 MiB + 1 byte 时必须在 `arrayBuffer()` / `JSON.parse` 前拒绝；不得把整个 C 错限为 8 MiB。
- 非法 UTF-8 bytes 必须由 fatal decoder 拒绝，不得以替换字符继续 JSON.parse。

### 9.2 加密与 AAD 测试

默认文件：`src/encryption/ledgerFileCrypto.test.ts`

- 同一密码和 salt 可分别认证、解密 current 与 previous。
- 错误密码、不同 salt、ciphertext 篡改和错误 tag 全部失败。
- 对 fileFormatVersion、fileId、cryptoVersion、KDF、salt、cipher、tagLength、revisionId、parentRevisionId、ledgerSchemaVersion、IV 逐项修改后，使用被修改字段形成的 AAD 解密必须失败；不支持值在正式入口还应先被合同 Validator 拒绝。
- AAD 字节顺序固定，并明确不包含人类可读业务字段。
- 同一会话只派生一次 key；两代共享 salt，但每个真实 generation 使用不同 IV。
- 同一保存意图重试只复用同一 plaintext / revision / IV，不允许同一 IV 加密不同 plaintext。

### 9.3 Adapter 测试

默认文件：`src/adapters/ledgerFileHandleAdapter.test.ts`

- open / save picker 只返回用户选中的一个句柄。
- 用户取消不调用 createWritable，不留下应用创建的空 C。
- 新建建议名使用小写 `.lftl`；打开时扩展名按 ASCII 大小写不敏感匹配，`.json`、`.lftl.json` 或其他扩展名不被当成 C。
- save picker 取消必须零写入；fake handle 的非空检查可保留为额外防御，但不能把用户已在系统窗口明确确认的“替换”误判为产品缺陷。
- open picker 返回零字节文件时必须拒绝，不能返回 `load():null`，不能让 Hook 自动创建空账本。
- `File.size > 32 MiB` 时不调用 `arrayBuffer()`；声明大小未超限但 `arrayBuffer.byteLength > 32 MiB` 时不调用 UTF-8 decode / `JSON.parse`。
- write 完成但 close 未完成时 readback 不开始。
- write、close、getFile、arrayBuffer 或 fatal UTF-8 decode 失败分别向上返回不同阶段。
- 写入 / close 失败时 fake atomic handle 的旧字节保持不变。
- close 后复读确实使用同一个绑定句柄，不按文件名重新搜索。
- 旧的异步读取在取消、选择新句柄或组件卸载后不能发布结果，复用现有 BackupControls 的 token / lifecycle 测试模式。

### 9.4 Repository 与保存状态机测试

默认文件：`src/repositories/ledgerFileRepository.test.ts`

建立确定性的 300 笔合法 fixture，交易分布覆盖 BTC、ETH、ADA，使用固定时钟、固定 ID 序列和固定随机字节：

1. 生产新建入口传入 `createInitialLedgerData()` 后：
   - current 含内置 BTC / ETH / ADA，交易、价格和手续费规则为空；
   - previous 为 null；
   - 正确 close + readback 后才返回可挂载 session。
   - Dashboard 随后的 `load()` 返回该已验证账本，不返回 `null`。
2. 直接调用底层 create primitive 创建 300 笔 C 后：
   - current 解密为 300 笔；
   - previous 为 null；
   - current parent 为 null；
   - write、close、readback 全部发生一次后才 resolve。
3. 新增一笔 BTC 后：
   - current 为 301 笔；
   - previous 为原 300 笔；
   - 新 current parent 等于 300 版 revision。
4. 再新增一笔 ETH 后：
   - current 为 302 笔；
   - previous 为原 301 笔；
   - 300 版不再进入文件。
5. 每次复读的 current `savedAt + LedgerData` 与该保存意图完全一致；previous generation 与保存前 current 的 revision、parent、schema、IV 和 ciphertext 逐字段相同。
6. current 与 previous 分别独立认证、解密、Validator、集合 / 字符串策略和 8 MiB payload 字节策略通过。
7. 三次真实 generation 的 revision 和 IV 两两不同，salt 保持一致。
8. 再次保存与最后已验证 current 相同的规范账本是 no-op，不生成 savedAt、revision、IV 或写入。
9. 传入非法 LedgerData、超集合 / 字符串策略或超 8 MiB payload 候选时，Adapter 零写入且原 C 字节不变。
10. 加密失败、write 失败、close 失败时不得 resolve，最后已验证 generation 不变。
11. close 后 readback 失败、current 失败或 previous 失败时不得 resolve。
12. fileId、预期 revision、parent 关系、savedAt 或候选规范内容任一不一致时拒绝成功。
13. 同一 `{fileId, baseRevisionId, serializedCandidate}` 失败保存重复 retry 复用 savedAt / revision / IV / ciphertext；若第一次实际写入成功但第一次 readback 暂时失败，第二次验证同一 revision 后成功。
14. 用户在新会话明确打开同名但不同 fileId 的文件时，各自按所选文件绑定；已绑定句柄的 readback 若返回不同 fileId，则不能满足“同一个 C”的身份核对。
15. 打开一个字节复制件时保留文件内原 fileId，不因句柄或文件名变化生成新身份，也不读取或修改另一个复制件。
16. 解密 payload 精确包含 `savedAt + ledgerData`；其中 ledgerData 精确包含 `schemaVersion + assets / trades / priceSnapshots / feeRules`，`Position[]`、图表数据、K 线和 UI 状态不存在。

默认扩展：`LedgerAccessGate.test.tsx`、`DashboardShell.interaction.test.tsx`；只有现有测试无法隔离 picker Adapter 时，才在同目录新增文件访问组件测试。
