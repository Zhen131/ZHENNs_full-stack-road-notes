## 三、判定顺序

```text
P0
→ 数据安全类 P1 / 任一强制通过项失败
→ 关键证据 BLOCKED
→ 普通 P1 / P2 / P3
```

- P0、数据安全类 P1、FILE-006/007 任一强制合同或直接 GATE 失败：最终 FAIL。
- 没有强制失败，但关键真实 Chrome 或平台证据无法取得且无等价确定性证据：BLOCKED。
- 强制合同全部通过时，普通 P1、P2、P3 可以随 PASS 记录，之后由协调步骤登记 00D。
- 不得为了继续开发把强制失败降成 P2，也不得把证据缺口猜成 PASS。

02D 只决定 02 目标是否通过。FAIL / BLOCKED 只暂停 02 和依赖路线，不替用户冻结没有依赖的其他工作。

## 五、T1：恢复资格矩阵

至少逐项证明：

| 场景 | 预期 |
| --- | --- |
| 正确密码，current 损坏，previous 完整有效 | 只进入 recovery-required |
| current 有效，previous 损坏 | fail closed，不进入普通 session |
| current、previous 都损坏 | 拒绝，不显示可恢复 |
| previous 为 null，current 损坏 | 拒绝，不显示可恢复 |
| 错误密码 | 通用解锁失败，零写入，不形成认证 oracle |
| salt / crypto metadata 漂移 | 拒绝 |
| fileId 漂移 | 拒绝 |
| revision 链异常 | 拒绝 |
| current payload / Validator / ResourcePolicy 失败，previous 完整 | 可进入明确恢复 |
| previous 任一认证、结构、资源或业务失败 | 不允许恢复 |

必须直接检查普通 Dashboard 尚未挂载，恢复候选没有被当成普通 Repository 发布。

## 六、T2：恢复确认、取消与写入

使用固定 R301 / R302 场景：

- previous R301 含 301 笔完整 BTC / ETH / ADA；
- 损坏 current R302 多一笔 ADA；
- 页面明确显示“最新一次保存没有恢复，现在恢复的是上一版”。

必须证明：

1. 确认前不写文件、不挂载 Dashboard。
2. 取消零写入、释放占用、旧恢复操作失效。
3. 确认后恢复内容精确等于 R301，R302 特有 ADA 不得出现。
4. 新 current 使用新 revision、IV 和本次 savedAt；parent 指向 R301。
5. verified R301 原样留在 previous；损坏 R302 不进入新两代。
6. 只有 write、close、同句柄 readback、两代认证解密和完整 Validator 全部通过后才进入账本。
7. write / close / readback 任一步失败都不显示恢复成功。
8. 重复点击只产生一个恢复意图；重试不制造第三代。

## 七、T3：恢复过程中的漂移与旧异步

用 deferred Promise 和可变 fake handle 覆盖：

- 用户看到恢复页后磁盘 metadata、fileId、revision 或代际发生变化；
- 确认前另一个合法写入完成；
- 用户取消后旧恢复 Promise 真正 resolve / reject；
- 选择新文件后旧恢复 Promise 晚到；
- Gate 卸载后旧恢复 Promise 晚到；
- 旧失败不得清空较新的选择、错误或 lease；
- 实际写入可能已完成但 readback 暂时失败时，重试只能 reconcile 同一意图。

只检查 AbortSignal、让旧 Promise 永远 pending 或没有证明晚到结果被忽略，不算通过。

## 八、T4：同一物理文件单写入者

必须覆盖：

1. 标签页 A 取得实际文件 session lease 后进入 Dashboard。
2. 标签页 B 选择同一个物理文件，立即得到 file-in-use；不挂载 Dashboard、不取得可写 Repository。
3. A 正常离开、路由跳转或 Gate 卸载后释放；B 主动重试后可进入。
4. 创建失败、解锁失败、恢复取消、旧操作失效不留下幽灵占用。
5. release 重复调用安全，不释放别的 session。
6. 异常关闭依赖浏览器运行期释放，不写永久标记或锁文件。
7. 两个不同物理文件可以分别进入。
8. Finder 字节复制件即使 `fileId` 相同，也不得被 `fileId` 粗暴误锁、扫描、合并或改写。
9. `isSameEntry()` 或运行期协调能力缺失 / 失败时，可写入口 fail closed 并清楚提示。
10. 旧 lock Promise 在取消、卸载或新选择后晚到时不能发布旧 session。

需要核对会话占用发生在普通 Dashboard 和可写 Repository 发布前。

## 九、T5：短时写锁与旧 revision 防覆盖

至少覆盖：

- 磁盘仍是当前完整基线时允许保存；
- 磁盘 current 已从 R301 变成含新 ETH 的 R302 时，旧页面保存 ADA 被拒绝；
- 冲突后 R302 和 ETH 保持原样；
- 磁盘 `fileId`、crypto metadata、current revision、parent 或完整基线任一意外变化都拒绝；
- revision 相同但代际内容不同也不得继续写；
- 写锁覆盖重新读取、比较、write、close、readback 全区间；
- 外部程序不参加浏览器锁时，写前 revision 检查仍生效；
- 锁等待期间候选更新、pending intent retry 和 reconcile 不死锁、不写旧候选、不制造第三代；
- no-op 不实际写文件；
- 冲突或锁错误时 Hook 保持 dirty / error，persistedVersion 不推进，UI 不显示 saved；
- 恢复写入同样经过短时写锁与基线复核。

## 十、T6：第一批强制回归

以下不是历史待修问题，而是必须继续通过的防复发测试：

- create、普通 save、pending-intent reconcile 三条 salt / crypto metadata 漂移；
- 真实 Repository → Hook 在 readback 失败时保持 dirty / error；
- slow A / fast B、取消后旧 A、卸载后旧 A、新选择或 create 后旧 A；
- 旧 A reject 不清空较新 B；
- C V1 KDF 与 IndexedDB V2 常量独立；
- 固定 C V1 fixture 与 IndexedDB V2 包装回归；
- 300 → 301 → 302、no-op、同一 intent retry、两代独立认证和 close-readback；
- C clear / B import capability 在 UI、Hook、Repository 继续阻断；
- C session 不镜像写 IndexedDB。

任一已通过强制回归被本批改坏，按相关强制项判定 FAIL。

## 十五、PASS / FAIL / BLOCKED

### PASS

- FILE-006、FILE-007 所有强制合同通过；
- 直接适用 GATE 通过；
- 第一批强制回归通过；
- 全量 test、typecheck、lint、build 通过；
- 真实 Chrome 关键场景有证据；
- 没有 P0、数据安全类 P1或关键证据缺口。

PASS 可以带不触发强制失败线的普通 P1、P2、P3，但必须如实写入 02D，之后登记 00D。

### FAIL

任一情况直接 FAIL：

- 静默恢复 previous、错误密码触发恢复提示、确认前写入或挂载 Dashboard；
- 恢复写入未完成 close 后同句柄复读；
- 同一物理 C 的第二页面取得可写 session；
- 只按 `fileId` 锁住复制件或无法识别同一物理文件却继续写；
- 外部 revision 已变化仍被旧页面覆盖；
- 冲突后清 dirty、推进 persistedVersion 或显示 saved；
- 第一批强制回归、现有 test、typecheck、lint 或 build 失败；
- 任一 FILE 强制通过项或直接 GATE 失败。

### BLOCKED

没有已证明强制失败，但关键平台能力、真实 Chrome 或必要证据无法取得，且没有等价确定性证据。
