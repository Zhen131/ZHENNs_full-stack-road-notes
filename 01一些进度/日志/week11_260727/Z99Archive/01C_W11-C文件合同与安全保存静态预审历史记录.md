## 6. Findings

### P0-01 复读使用缓存 salt 构造 AAD，可把不可重开的 C 报告为保存成功

- 等级：P0
- 源码：
  - `src/encryption/ledgerFileCrypto.ts:99–130`
  - `src/repositories/ledgerFileRepository.ts:453–545`
  - `src/repositories/ledgerFileRepository.ts:551–559`
- 测试缺口：
  - `src/encryption/ledgerFileCrypto.test.ts:51–95`
  - `src/repositories/ledgerFileRepository.test.ts:388–440`

代码证据：

1. `decryptGeneration(fileId, generation)` 构造 AAD 时使用 `this.metadata`。
2. `this.metadata` 是 create/open 时留在会话中的 crypto metadata，不是复读得到的 `file.crypto`。
3. `verifyGeneration(...)` 只把复读的 `fileId` 和 generation 交给 crypto。
4. `verifyLedgerFile(...)` 检查 fileId、revision、payload 和 previous，但没有要求复读 `file.crypto` 与绑定会话 metadata 逐字段一致。

因此可以出现以下静态可推导路径：

```text
创建或保存时使用 salt S1
→ key K1 与 AAD(S1) 生成合法密文
→ close 后复读外壳的 salt 被替换为另一个合法 16-byte S2
→ exact validator 接受 S2
→ 当前会话仍用 K1 + AAD(S1) 解密并通过
→ verified.file 却记录了外层 S2，UI 可以显示保存成功
→ 下次重开按 S2 派生 K2
→ current 和 previous 都无法解密
```

违反：

- FILE-001：salt 与全部加密参数必须受认证；
- FILE-005：复读必须验证刚写出的真实文件，而不是会话内预期 metadata；
- GATE-006：未经完整复读确认的文件不得显示成功；
- 01B §3.2“file、crypto 等技术字段均受认证”的陈述。

实际影响：

用户已有 300 笔 BTC / ETH / ADA，新增第 301 笔 BTC 后页面显示“已保存”。关闭页面再次选择同一 C 时，程序使用 S2 派生错误密钥，301 和 300 两代都无法打开。若没有最新明文 B，最后一次可信数据可能无法恢复。

修复要求：

- readback/open 的认证输入必须来自已验证的 on-disk `file.crypto`，并与会话绑定 metadata 做 exact equality 检查；
- 初次 create readback、普通 save readback、pending-intent reconcile 都必须拒绝任何 salt/crypto metadata 漂移；
- 增加“同一会话 key 不变、只替换复读外壳 salt”的确定性测试，证明 create/save 均失败、`verified` 不更新、Hook 保持 dirty；
- 修复后再复核所有 AAD 字段，而不是只测 tagLength 和 generation 字段。

### P1-01 旧异步文件选择可在取消、卸载或新选择后复活旧句柄

- 等级：P1
- 源码：
  - `src/composition/ledgerFileAccessController.ts:109–130`
  - `src/composition/ledgerFileAccessController.ts:178–180`
  - `src/components/security/LedgerAccessGate.tsx:80–87`
  - `src/composition/ledgerAccessComposition.ts:15–16,37–40`
- 测试缺口：
  - `src/composition/ledgerFileAccessController.test.ts:109–150`

代码证据：

- `selectExisting()` 在 `await inspectLedgerFile(...)` 返回后无条件覆盖 `pendingSelection`。
- `cancelPendingSelection()` 只把当前值设为 `null`，不会使正在进行的旧操作失效。
- Access Gate 卸载只把 `mountedRef` 设为 false，没有通知文件 Controller 取消 pending selection。
- production 使用跨组件挂载保留的 singleton file Controller。

这意味着较早的 A 选择仍在读取时，组件卸载或另一个 Gate 实例选择 B；若 B 先完成、A 后完成，A 可以覆盖 B 的 pending handle。随后相同密码可能解锁 A，Dashboard 再把原本准备写入 B 的 BTC 新交易保存到 A。

违反：

- FILE-002：本次会话只能绑定用户当前明确选择的一个句柄；
- GATE-004：不得操作当前选择之外的 C；
- 01A §9.3 对取消、新句柄和组件卸载后旧异步结果失效的明确要求。

修复要求：

- Controller 增加单调 selection generation/token；每次选择、取消和会话结束都使旧 token 失效；
- 只有仍为最新 token 的 inspect 结果可以发布 `pendingSelection`；
- Gate 卸载应显式取消当前 pending selection；
- 增加 A 慢、B 快、取消后 A 返回、卸载后 A 返回四类 deferred 测试，最终只能保留 B 或 null。

### P2-02 C V1 的 KDF 实际绑定 IndexedDB V2 常量，削弱版本独立性

- 等级：P2
- 源码：
  - `src/encryption/ledgerFileCrypto.ts:21–47`
  - `src/encryption/webCryptoEncryptionService.ts:108–135`

`LedgerFileCrypto` 声明了独立的 `LEDGER_FILE_V1_CONSTANTS` 和 `cryptoVersion:1`，但实际派生通过共享 `deriveLedgerKey(...)`，后者读取 `LEDGER_CRYPTO_CONSTANTS`。当前数值相同，所以当前密文可以工作；但未来只调整 IndexedDB V2 的 KDF/cipher 常量时，C V1 的真实派生行为会在 `cryptoVersion` 未变化的情况下随之变化，破坏已确认的版本独立边界。

修复要求：

- 抽取接收显式 KDF/cipher 参数的底层 primitive，C 调用时传 `LEDGER_FILE_V1_CONSTANTS`；
- 保留 IndexedDB V2 现有调用和字节合同；
- 增加测试证明两套 version constants 可独立演进，且 C V1 已有 fixture 仍可解密。
