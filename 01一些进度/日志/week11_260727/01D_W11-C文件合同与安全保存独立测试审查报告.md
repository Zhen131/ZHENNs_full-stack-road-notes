## 8. FILE 合同判定

### FILE-001：FAIL

文件表面上包含完整 crypto 元数据，但回读解密使用的是会话中缓存的 metadata，不是从磁盘文件读取并验证后的 `file.crypto`。这让磁盘 salt 可以漂移而不触发当前回读失败。

### FILE-002：FAIL

controller 只有一个可被覆盖或清空的 `pendingSelection`，没有选择代次/operation token。旧 Promise 晚到后仍可发布句柄，取消、卸载、创建新文件都不能使旧结果失效。

### FILE-004：FAIL

正常 current/previous generation、revision 链和 300→301→302 行为通过；但 salt 漂移后，系统可以确认一个在当前文件自带 crypto 元数据下无法用正确密码重开的 generation，故安全 generation 合同不成立。

### FILE-005：FAIL

实现形式上执行了 `close -> getFile -> arrayBuffer -> parse -> verify`，正常重试也不会重复写入；但回读 verify 被缓存 metadata 绕过，Hook 仍可把不可重开的磁盘状态发布为 `saved`，所以安全保存门不成立。

## 10. Findings

### F-01 — P0：磁盘 crypto metadata 漂移可绕过回读认证

**源码位置**

- `src/encryption/ledgerFileCrypto.ts:14-19`
- `src/encryption/ledgerFileCrypto.ts:99-130`
- `src/repositories/ledgerFileRepository.ts:429-438`
- `src/repositories/ledgerFileRepository.ts:453-559`

**机制**

- `LedgerFileCrypto` 在构造时缓存会话 metadata。
- 解密构造 AAD 时使用 `this.metadata`。
- repository 解析磁盘文件后，没有把 `file.crypto` 与会话绑定的期望 metadata 做完整精确比较。
- generation 解密仍走缓存 metadata。
- 因而只修改磁盘 `file.crypto.kdf.salt`，当前回读仍可能通过；但下次按文件自带 salt 派生密钥时无法打开。

**最小复现**

1. 使用 S1 创建或打开 C。
2. 在 `close` 之后、`getFile` 回读之前，把磁盘外层 `crypto.kdf.salt` 替换为合法 Base64URL 的 S2，ciphertext/tag 保持不变。
3. 创建、普通保存或 reconcile 被错误确认成功。
4. Hook 可进入 `saved`。
5. 用正确密码按磁盘 S2 重开，认证失败。

**用户影响**

- UI 告诉用户“已保存”，实际文件不可再次打开。
- 内存 verified revision / persisted version 可能错误推进。
- 这是数据可用性与保存真实性缺陷，不能由“当前会话还能解密”来降级。

**违反合同**

- `FILE-001`
- `FILE-004`
- `FILE-005`
- `GATE-006`

**修复通过线**

- 对磁盘解析后的完整 `file.crypto` 与当前会话绑定的期望 metadata 做精确比较，任何字段漂移都必须在发布 verified state 之前失败。
- 或者用经过严格验证的磁盘 metadata 构造认证上下文；不能继续无条件使用缓存 metadata 掩盖磁盘漂移。
- 创建、普通保存、pending-intent reconcile 三条 salt 测试必须成为正式测试。
- Hook 测试必须证明：失败时保持 dirty，不推进 persisted version，不发布 `saved`，正确密码可重开上一个已确认 generation。

### F-02 — P1：旧 picker Promise 可在边界之后重新发布句柄

**源码位置**

- `src/composition/ledgerFileAccessController.ts:59`
- `src/composition/ledgerFileAccessController.ts:109-131`
- `src/composition/ledgerFileAccessController.ts:178-180`
- `src/components/security/LedgerAccessGate.tsx:80-87`

**机制**

- controller 只有单一 `pendingSelection`，没有单调递增的选择代次。
- `selectExisting` await 返回后无条件写入；失败时也无条件清空。
- `cancelSelection` 只清空当前值，无法让正在等待的旧 Promise 失效。
- Gate unmount 只更新 mounted ref，没有使 controller 中的选择操作过期。

**最小复现**

- 发起慢 A，再发起快 B；B 先完成，A 后完成。
- 或发起 A 后取消。
- 或发起 A 后卸载 Gate。
- 或发起 A 后成功创建新文件。
- 最后释放 A：四种情况下 A 都能重新成为当前待解锁文件。

**用户影响**

- 用户看到或认为自己选择了 B/取消了/已经创建新文件，但实际解锁的是旧 A。
- 在多文件账本场景中可能对错误文件继续读写。

**违反合同**

- `FILE-002`
- `GATE-004`

**修复通过线**

- 为选择/创建/取消引入单调递增的 operation token。
- 每次新选择、创建、取消和 Gate unmount 都必须使旧 token 失效。
- 只有当前 token 才能发布或清空 pending selection。
- 四个 deferred race 场景必须成为正式、确定性测试。

### F-03 — P2：正式测试集缺少两组强制对抗场景

**源码位置**

**机制**

- controller 测试覆盖顺序执行的 select/cancel/open/unlock，没有延迟 Promise 的新旧操作竞争。

**用户影响**
