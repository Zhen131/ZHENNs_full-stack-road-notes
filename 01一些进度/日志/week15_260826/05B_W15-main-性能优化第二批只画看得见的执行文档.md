## 1.1 基线来源

**本批不重新测量改动前基线。** 直接引用 04 批阶段三的实测数字作为"改动前"。理由：04 批阶段三刚刚用同一把尺子、同一个种子、同一台机器跑完，重测既浪费数小时，又会因热漂移引入新的不可比因素。

## 1.2 阶段一唯一要新做的事：M-9 量尺

在动任何产品代码之前，先把"同时渲染的元素数"这把尺子造出来，并用它测一遍改动前的数字。

**原因与 04 批阶段一同源：改动前的数字只有这一次机会。** 分页做完之后，就再也测不到"不分页时页面上有多少个元素"了。

### M-9 定义

| 项目 | 要求 |
| --- | --- |
| 名称 | M-9「同时渲染的元素数」 |
| 测什么 | 交易页处于活动状态、筛选条件为默认全开时，页面中的 DOM 元素数量 |
| 怎么测 | 两个数字都要：①整个文档的元素数 ②`[data-workspace-page="transactions"]` 子树内的元素数 |
| 单位 | 个。整数，不取中位数，同一状态下应当完全确定 |
| 采样 | 每档 1 次即可。若同档两次不同，如实记录两个值并说明原因 |
| 实现位置 | `benchmarks/`，不得写进 `src/`（C-06） |
| 档位 | 10²、10³、10⁴。**10⁵ 改动前无法取得**（`04C-1` 5.2：交易页导航 30 秒超时），如实记为"未取得（前置失败：交易页导航超时）" |

M-9 是 `03A` 的 R-3 第一次变得可验证。**它的意义是：改动后这个数字必须与账本规模无关。**

### 陷阱：定位跳转（`05A` U-4）

现有的日期定位实现位于 `src/features/activity/ActivityTable.tsx:90-144`，它在 `items` 中查找目标日期对应的行，找不到就回报 `"missing"`（`:96`），找到则 `scrollIntoView`（`:127`／`:132`）。

**分页之后，若 `ActivityTable` 只拿到当前页，目标日期在别的页时会被误判为"不存在"。** 这是本批最容易出的错。

要求：

| 编号 | 要求 |
| --- | --- |
| I-6 | 定位跳转必须先在**完整的筛选结果**中确定目标日期的位置、算出它在第几页、翻过去，再执行既有的滚动与高亮 |
| I-7 | 目标日期确实不在当前筛选结果中时，仍须走既有的 `"missing"` 路径，行为与改动前一致 |
| I-8 | 跳转成功后停留在目标页，不得跳回第 1 页 |

### 其余行为合同

`05A` 第三节的 U-1 至 U-8 全部为硬性要求，逐条须有对应测试。特别提醒两条最容易做反的：

- **U-2 改筛选 → 回第 1 页**
- **U-3 删除一条 → 停留在当前页**；若删完当前页变空且不是第 1 页，退到前一页
