## 一、为什么必须单独立项

`08A` 原来的假设是「大文件之所以大，是因为里面塞了很多函数」。2026-09-01 摸底证明该假设不成立：

| 文件 | 总行数 | 其中单个巨型函数／组件 | 占比 |
| --- | ---: | ---: | ---: |
| `usePersistentLedger.ts` | 1,963 | **1,674**（第 180–1854 行，一个 hook） | 85% |
| `DashboardShell.tsx` | 1,575 | **1,398**（第 163–1561 行，一个组件） | 89% |
| `LedgerAccessGate.tsx` | 1,276 | 974 | 76% |
| `ledgerFileAccessController.ts` | 1,172 | 850（一个 class） | 73% |

`usePersistentLedger.ts` 那个 hook 内含 **12 个 `useState`、7 个 `useEffect`、30 个 `useRef`、13 个 `useCallback`、5 个 `useMemo`**，互相依赖。

React 依靠**调用顺序**而非名字来定位 hook。把其中一段提成子 hook，或在 hook 之间重新分配 `useRef`／setter，**都会改变注册结构与数据流——那是逻辑改动**，直接违反 `08A` 的 A-1。

**两批混做会同时毁掉两批的可验收性**：08 的全部价值在于其 diff 可被机械核对；一旦同一批提交里混入逻辑改动，`08D` 即失去审查能力，一千行的 diff 里藏几十处逻辑改动没有人审得动。

## 三、绝对边界（草案，正式定义时须复核）

| 编号 | 约束 |
| --- | --- |
| A-1 | **不得改变任何外部行为。** 与 `08A` A-1 同精神，但本批允许改变内部的 hook 组织方式，因此**必须另行证明行为不变**，不能靠「diff 是纯搬运」这一条 |
| A-2 | **hook 的展开调用序列必须逐个不变。** 把提出去的子 hook 就地展开后，`useState`／`useEffect`／`useRef`／`useMemo`／`useCallback` 的类型与顺序须与改动前完全相同 |
| A-3 | **不得新增 `React.memo`、`useMemo`、`useCallback` 做性能包装。** 那属于性能改动，须另立批次并配性能量尺 |
| A-4 | **不得改动任何文件格式、版本号、加密参数或派生计算** |
| A-5 | **不得修改既有测试的断言或阈值** |
| A-6 | **不得修改结构守卫以迁就改动** |
| A-7 | 不得引入新依赖 |
| A-8 | **分阶段实施，一个大文件一个阶段**，阶段之间必须能独立回滚 |

## 四、本批必须新增的验证手段（草案）

`08A` 的 Q-2（用例名不变）**不足以保护本批**——逻辑改动可以在用例名全不变的前提下发生。因此本批必须另外建立：

| 编号 | 手段 |
| --- | --- |
| V-1 | **hook 展开序列对照表**：每个被改动文件，给出改动前后逐个 hook 的类型与顺序，人工逐行比对 |
| V-2 | **effect 执行顺序断言**：为被拆分的 hook 补一条测试，断言各 `useEffect` 的执行先后不变 |
| V-3 | **渲染次数断言**：为被拆分的组件补一条测试，断言给定交互下的渲染次数不变，防止组件边界变化悄悄改掉 05 批的性能优化 |
| V-4 | **性能回归对照**：本批须重跑 03 批的浏览器量尺（至少 M-1 冷启动、M-3 记一笔、M-5 页面切换），与 08／09 合入后的基线对照 |

**V-2、V-3 是本批唯一允许新增的测试**；除此之外不得新增、删除或修改任何测试。
