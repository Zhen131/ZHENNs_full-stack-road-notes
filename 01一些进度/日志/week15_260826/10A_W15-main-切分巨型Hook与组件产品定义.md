## 结论

本批做 08 批**明确不做**的那件事：**真正切开四个大文件里的巨型 hook 与巨型组件。**

08 批只搬家具、一根电线不碰；本批就是重新布线。**因此本批的风险性质与 08 完全不同，验收手段也必须不同。**

## 一、为什么必须单独立项

`08A` 原来的假设是「大文件之所以大，是因为里面塞了很多函数」。2026-09-01 摸底证明该假设不成立：

| 文件 | 总行数 | 其中单个巨型函数／组件 | 占比 |
| --- | ---: | ---: | ---: |
| `usePersistentLedger.ts` | 1,963 | **1,674**（第 180–1854 行，一个 hook） | 85% |
| `DashboardShell.tsx` | 1,575 | **1,398**（第 163–1561 行，一个组件） | 89% |
| `LedgerAccessGate.tsx` | 1,276 | 974 | 76% |
| `ledgerFileAccessController.ts` | 1,172 | 850（一个 class） | 73% |

`usePersistentLedger.ts` 那个 hook 内含 **12 个 `useState`、7 个 `useEffect`、30 个 `useRef`、13 个 `useCallback`、5 个 `useMemo`**，互相依赖。

React 依靠**调用顺序**而非名字来定位 hook。把其中一段提成子 hook，或在 hook 之间重新分配 `useRef`／setter，**都会改变注册结构与数据流——那是逻辑改动**，直接违反 `08A` 的 A-1。

**两批混做会同时毁掉两批的可验收性**：08 的全部价值在于其 diff 可被机械核对；一旦同一批提交里混入逻辑改动，`08D` 即失去审查能力，一千行的 diff 里藏几十处逻辑改动没有人审得动。

## 修订 A（2026-09-02）：以 AST 实测替换第一、二、五节，确定「只搬函数体」路线

### A. 上文第一节的 hook 清单不可用，已作废

上文写「`usePersistentLedger.ts` 那个 hook 内含 **12 个 `useState`、7 个 `useEffect`、30 个 `useRef`、13 个 `useCallback`、5 个 `useMemo`**」。**该清单有两处错，整张表作废。**

1. **每一项都多 1**，来自文件开头 `import { useCallback, useEffect, ... } from "react"` 中每个名字各出现一次被一并计入。
2. **完全漏掉 `useReducer` × 2 与 `useLayoutEffect` × 1**——与 `00-当前开发状态.md` 已登记的「`08C` I-7 的 hook 正则漏抓 `useReducer`／`useLayoutEffect`／`useId` 共 5 个」**是同一个正则 bug，第二次踩**。

**漏掉的这两个恰恰最要紧**：第 98 行的 `useReducer` 持有 `ledgerData`，**即整本账的核心状态**，是该文件里最重要的一个 hook；`useLayoutEffect` 与 `useEffect` 执行时机不同（前者在浏览器绘制前同步执行），本批要保证「hook 顺序与类型逐个不变」，连它属于哪一类都数错则该保证落空。

**今后要求：hook 清点一律用 TypeScript 编译器建 AST，禁止用正则。** 本项目已两次因此出错。

### C. 本批路线：**只搬函数体，hook 调用原地不动**（产品负责人 2026-09-02 裁决）

上文第三节 A-1／A-2 要求「hook 的展开调用序列必须逐个不变」，但没说怎么做到。**本修订确定做法：**

> **把大块的回调函数体搬到独立模块，`useCallback`／`useEffect` 调用本身留在原地，依赖数组逐字不动。**

形态：

```ts
// 改动前
const replaceLedgerFromBackup = useCallback(async (...) => {
  /* 355 行 */
}, [ /* 依赖数组 */ ]);

// 改动后
const replaceLedgerFromBackup = useCallback(async (...) => {
  return doReplaceLedgerFromBackup({ mountedRef, ledgerDataRef, /* ...共 37 个 */ }, ...);
}, [ /* 依赖数组：逐字节不变 */ ]);
```

**为什么这条路成立**：hook 调用的位置、类型、顺序、依赖数组全部不动，React 的注册结构因此逐位不变；搬走的函数体可与原文逐字节比对。**本批因此保留了 08 批那种机械可验性**，这是它与「重新组织 hook」方案的根本区别。

**为什么函数体不是「逐字不变」**：函数体一旦离开原文件，就够不着原来闭包里的 `ref`／setter，必须改为参数传入。因此本批的通过线是**「函数体语句逐字节相同 + 新增参数与原闭包变量一一对应」**，不是 08 批那种整块逐字节相同。**这一条必须写进 `10D` 的验收口径。**

### D. 被否决的方案：打包一个共享 `ctx` 对象

**候选方案 B**：把那些身份恒定的 `ref` 与 setter 打包成一个 `ctx` 对象（`useMemo(() => ({...}), [])`），各调用点只传 `ctx`。预期可把收尾行数压到约 580 行，优于方案 A 的约 780 行。

**产品负责人 2026-09-02 裁决：不采用，本批走方案 A。**

理由：`ctx` 对象是**新造的构造物，原代码中不存在对应物**，因此**无法与任何东西做逐字节比对**——装错一样、漏装一样，只能靠人眼发现。而本项目已反复证明「没有机械验证手段的地方就是缺陷藏身处」（09 批 5 处中文被静默改写、1,185 条测试全绿零发现；08 第一轮报告完成实为 10%）。
