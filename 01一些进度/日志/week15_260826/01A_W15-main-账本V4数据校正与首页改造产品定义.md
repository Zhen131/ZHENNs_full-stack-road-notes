# 第一部分：数据校正与 V4

## 一、问题确认

账本数量与真实数量不一致，来源是三条互相独立的缺口：

| 编号 | 缺口 | 性质 |
| --- | --- | --- |
| G-1 | 账本只能表达“买卖”与“现金进出”，无法表达充币、提币、空投、理财利息、平台赠送 | schema 能力缺失，非计算错误 |
| G-2 | 历史转换的中段窗口使用自然语言笔记范围，而非交易所全量成交 | 数据源不完整 |
| G-3 | 永续合约盈亏与资金费只登记了两个窗口，其余月份未入账 | 转换决定不完整 |

G-1 已由既有转换决定记录自行证明：其 `decisions.json` 明确写有“V3 无资产转入类型”，并因此采用变通手段维持可重放性。G-1 是本批主因，G-2 与 G-3 在重新生成 B 文件时一并修正。

判定 G-1 为主因的证据：由交易所账单还原的“买卖净增”与账本显示的持仓数量在受影响币种上完全一致，说明重放算法正确，差额全部来自无法表达的非买卖获得。

## 二、账本边界

账本边界包含用户自己控制的全部位置：交易所、冷钱包、冷钱包理财。判断一笔转入转出属于哪一类，唯一标准是**币是否跨越了这条边界**，与交易所记录把它叫“充币”还是“提币”无关。

从交易所提币到自己的冷钱包，在交易所记录里是“提币”，在账本里是内部转移，总量不变。

## 三、资产转入转出事实

新增一类账本事实，覆盖一切非买卖引起的持仓数量或存放位置变化。

| 字段 | 规则 |
| --- | --- |
| 时间 | 与既有事实一致，支持日、分、秒三种精度；不得晚于今天 |
| 币种 | 必须是账本中已存在的本地资产 |
| 数量 | 高精度十进制，必须为正；方向由类别决定 |
| 类别 | 内部转移 / 外部转入 / 外部转出 / 白拿 |
| 原因 | 充币、提币、内部搬家、空投、利息、平台赠送 |
| 单价 | 外部转入与白拿必填，USDT 计价；内部转移与外部转出不得填写 |
| 链上手续费 | 可选，以该币种计价，见第五节 |
| 存放位置 | 来源与去向；内部转移两者都必填且不得相同 |
| 备注 | 可选，上限与既有事实一致 |

### 四种类别与成本口径

| 类别 | 典型场景 | 总数量 | 剩余成本 | 已实现盈亏 | 现金 |
| --- | --- | --- | --- | --- | --- |
| 内部转移 | 交易所与自己冷钱包之间搬动 | 不变，只改位置分布 | 不变 | 不变 | 不变 |
| 外部转入 | 从账本外部收到的币，非白拿 | 增加 | 加 数量 × 单价 | 不变 | 不变 |
| 外部转出 | 转给他人、转到账本外 | 减少 | 按当前平均成本等比减少 | 减少同额 | 不变 |
| 白拿 | 空投、理财利息、平台赠送 | 增加 | 加 数量 × 单价 | 不变，另计收益 | 不变 |

四类共同边界：**都不影响 USDT 现金余额**。币的搬动与获得不是买卖，不产生现金流。

外部转出把成本转为已实现亏损，而不是让成本凭空消失。理由：币离开账本后不再是用户资产，为它花掉的钱也没有以任何形式回来；若只减成本不记亏损，总投入与总盈亏就对不上账。

白拿必须按到账当日单价计入成本，不得按零成本计入：零成本会在用户未支出任何资金的情况下压低平均购价，使平均购价失去指导买卖的作用。白拿计入成本的同额金额另行累计为“白拿收益”，与已实现盈亏分开展示。

平台赠送单独标记，不计入个人本金口径。

## 四、买卖的位置归属

交易本身不携带存放位置。买入的币一律记入交易所位置，卖出的币一律从交易所位置消耗。币要出现在冷钱包，只能通过内部转移。

卖出时若交易所位置数量不足，即便总持仓足够也必须拒绝——这代表用户把币提走了却还想在交易所卖出，是真实的记录错误。

## 五、链上手续费

提币与转账会在链上扣掉一部分币，这部分币真的消失了，必须有地方安放，否则总量对不上。

| 项目 | 规则 |
| --- | --- |
| 适用类别 | 内部转移与外部转出 |
| 计价 | 以被转移的币种本身计价，不是 USDT |
| 数量影响 | 来源位置扣减 数量 + 链上手续费；目的位置只增加 数量 |
| 成本影响 | 手续费对应的成本按当前平均成本等比扣减 |
| 盈亏影响 | 该部分成本计入已实现亏损 |
| 边界 | 内部转移在扣掉手续费后总量会减少，这是本节的唯一例外，与第三节“内部转移总量不变”并不冲突：不变的是被搬动的那部分，消失的是手续费 |

## 六、拒绝规则

- 内部转移或外部转出的数量加链上手续费大于该币种当前总量、或大于来源位置数量时拒绝
- 外部转入或白拿缺少单价时拒绝
- 内部转移或外部转出填写单价时拒绝
- 内部转移缺少来源或去向、或两者相同时拒绝
- 原因与类别不匹配时拒绝
- 未来日期的转入转出比照既有未来事实规则隔离

## 七、永续合约

本批不为账本增加合约交易能力。历史合约盈亏与资金费按月汇总，折为既有现金事实写入，备注注明来源为合约。现金时间线因此可对齐，现货持仓与平均购价不受污染。

后续若需要合约建模，另行立项，不在本批范围。

## 八、存放位置

持仓引入存放位置维度，取值为交易所、冷钱包、冷钱包理财，三者必须始终同时存在，无持仓时为零而不是缺省。

| 项目 | 规则 |
| --- | --- |
| 计入范围 | 三个位置的持仓全部计入总资产、平均购价与未实现盈亏 |
| 展示 | 持仓明细增加存放位置列 |
| 数据来源 | 交易所位置由交易所记录推导；冷钱包与冷钱包理财由用户提供清单，账本不联网获取 |
| 理财利息 | 冷钱包理财产生的利息按白拿记录，目的位置为冷钱包理财 |

托管型等量代换资产按独立币种处理，不与原生币种合并计算平均购价。

## 九、V4 通过线

- `LedgerData schemaVersion` 升至 4，明文导入导出升级为 `BackupEnvelope V4`
- V3 与 V2 的 B 文件、承载 V3 的 `.lftl` 只识别并明确拒绝，零迁移、零写回、零自动删除
- 加密、双代保存、恢复与文件安全外壳不重新设计，只让其内部账本承载 V4
- 现有导入准入不变：仍只允许写入同一会话中新建且仍为空的 C

# 第二部分：数字显示规则

## 十、问题确认

所有数字直接把完整精度插入界面，金额出现二十位小数，无法阅读。既有 `formatDecimal` 已存在于共享算术模块，但全项目从未调用。

## 十一、核心算法

不使用币种查表，不使用按币种枚举的条件分支，只有一个函数：

```
显示位数(x, N, 大数固定位):

  若 x 为零:
      按 (大数固定位 ?? 0) 补零输出，不去尾零
  若 |x| >= 1 且 设了“大数固定位”:
      保留该固定位数，不去尾零
  否则:
      从第一位非零数字开始，保留 N 位有效数字
      去掉末尾多余的零，但至少保留 (大数固定位 ?? 0) 位
      小数最多 12 位

  整数部分加千分位逗号，负号在最前
```

## 十二、三种配置

| 用途 | N | 大数固定位 |
| --- | --- | --- |
| 金额、单价、成本、盈亏（USDT 计价） | 6 | 2 |
| 币的数量 | 8 | 无 |
| 百分比 | 不适用 | 固定 2 位，带正负号 |

## 十四、边界

- 底层精度不变。高精度算术仍为 40 位，账本文件、导入导出与全部计算继续使用完整精度。本部分只改渲染层。
- 输入框、受控表单值与草稿一律不格式化，用户正在编辑的字符串原样保留。
- 每个被格式化的数字必须可查看完整原值，且该完整值对读屏软件可读。
- 四舍五入沿用既有 `ROUND_HALF_UP`。

# 第三部分：首页持仓成本区与界面修整

## 十五、持仓成本区

替换首页现有的“主要持仓与现金”卡片。按当前市值降序取前五个币种，现金单独一行。

列：币种、当前价格、平均购价、涨跌幅、盈亏金额、持仓量、总花费、当前市值。

| 字段 | 公式 | 状态 |
| --- | --- | --- |
| 持仓量 | 既有 `Position.quantity` | 已有 |
| 平均购价 | 既有 `Position.averageCost` | 已有 |
| 当前价格 | 既有 `Position.latestPrice` | 已有 |
| 当前市值 | 既有 `Position.marketValue` | 已有 |
| 盈亏金额 | 既有 `Position.unrealizedPnl` | 已有 |
| 涨跌幅 | （当前价格 − 平均购价）÷ 平均购价 | 新增 |
| 总花费 | 该资产历史买入现金流出合计 | 新增 |

只有两个字段是新的，其余必须复用既有 `Position`，不得重算。

“总花费”与“平均购价 × 持仓量”是两个不同口径：前者是历史累计投入（含已卖出部分），后者是剩余持仓成本。既有盈亏摘要只算全账本合计买入流出，需要拆成按资产分组。

排序复用既有的按市值取前 N 函数，上限由 3 改为 5，不另写一套。

着色：涨为绿、跌为红。现金行不参与涨跌计算与着色。缺当前价格的币种沿用既有规则，不参与排名并单独提示。平均购价为零时显示为不可计算，不得除零。

## 十六、首页布局调整

八列表格放不进当前那个只占三分之一宽的卡片，因此调整首页纵向结构：

| 行 | 内容 |
| --- | --- |
| 1 | 四个指标卡 |
| 2 | 资产趋势（左）＋ 记一笔交易与资产分配饼图（右） |
| 3 | **持仓成本区，独占整行** |
| 4 | **交易活动热力图，独占整行** |

日历式热力图本来就需要横向空间，独占整行同时解决了它现在大片留白的问题。首页因此比现在略高，允许出现纵向滚动；表格在窄屏下允许横向滚动，但不得让整个页面横向滚动。

## 十七、界面修整（三项）

| 编号 | 缺陷 | 病根 | 修法 |
| --- | --- | --- | --- |
| U-01 | 饼图悬停提示框被裁切 | 图表卡片外层设有 `overflow-hidden`，提示框渲染在容器内被裁；首页紧凑模式图表高度仅 144px，多行提示必然溢出 | 提示框改为挂载到 `body`，脱离容器裁剪。不使用 `confine` |
| U-02 | 饼图币种过多、颜色重复 | 全部扇区无条件绘制；调色板仅 5 色，十余个资产循环复用配色导致不同币同色 | 占比低于 2% 的扇区合并为“其他”，最多显示 8 个扇区含“其他”；“其他”悬停展开被合并币种与各自金额；调色板扩至至少 10 个可区分颜色，“其他”用中性灰 |
| U-03 | 首页热力图大片留白 | 首页使用手写网格版本，格子被固定最大宽度限制，外层为居中弹性布局 | 放开宽度限制，配合第十六节的整行布局让网格填满卡片 |
