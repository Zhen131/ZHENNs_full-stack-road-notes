# 阶段二：不重复算

## 2.1 四处修改，各自独立提交

按此顺序执行，每处完成后立即跑等价性测试与定向指标：

### P-1 历史曲线（收益最大，先做）

现状：按区间内每一天，重放一次截至该日的账本前缀，另加每天约 0.11 倍全量重放的固定开销。10⁴ 档单独耗时 1,384 ms。

要求：改为**单次顺序扫描**——按时间顺序遍历事实一遍，边遍历边记录每日收盘状态，区间筛选在扫描结果上完成。目标复杂度与账本规模成线性，与区间天数无关。

通过线：10⁴ 档全部五个区间的 M-7 中位数，与同档 M-8 中位数处于同一量级（不超过 3 倍）。

### P-2 写入后的增量更新

现状：记一笔新事实后全量重放，10⁴ 档写入 7,652 ms。

要求：新增一笔事实后，只更新受该事实影响的部分。若因确定性排序要求无法完全增量，允许"追加式重放"（从受影响的最早时间点起重放），但必须在 `04C` 中写明退化到全量重放的具体条件。

通过线：10⁴ 档 M-3 中位数 ≤ 300 ms。

### P-3 输入草稿下沉

现状：价格输入框每敲一个字符触发整本账本重放约 30 遍，10⁴ 档单字符输入 1,535 ms。

要求：输入过程中的草稿状态与账本派生完全解耦。**敲字期间不得触发任何账本重算**，派生只在用户提交时发生。

通过线：10⁴ 档 M-6 输入与删除中位数均 ≤ 100 ms。

### P-4 派生结果缓存

现状：切换页面重新计算全部派生，10⁴ 档页面切换 1,686～2,409 ms。

要求：缓存派生结果，只在事实真正变化时失效。

| 约束 | 说明 |
| --- | --- |
| 失效条件 | 必须由事实变化驱动。**不得依赖定时器、轮询或手动刷新** |
| 存放位置 | 只在内存。不得写入 `.lftl`、B 文件、IndexedDB 或任何持久层 |
| 会话边界 | 账本锁定、切换文件、重新解锁时缓存必须整体丢弃 |
| 必须有测试 | 至少覆盖：新增一笔后缓存失效、删除一笔后缓存失效、撤回删除后缓存失效、切换账本后缓存不串 |

通过线：10⁴ 档 M-5 四个方向中位数均 ≤ 200 ms。

## 2.2 每一处修改后必须立即执行

1. 等价性测试：三档派生结果与阶段一快照逐字段比对，必须完全相同
2. 该处对应的定向指标，10⁴ 档，production 模式
3. 默认全量测试

**任何一处修改导致等价性测试不通过，立即停止该处修改并在 `04C` 中记录，不得继续往下做。**

## B.1 背景与目的变更

10⁴ 档浏览器层实测耗时约 24 分钟（dev 约 16 分、production 约 8 分）。按同样规则外推，10⁵ 档完整采样需数小时，且多数指标会撞上量尺单条命令 180 秒的上限而记为超时。

**产品负责人决定：10⁵ 与 10⁶ 两档的目的从「统计采样」改为「极限探测」。**

要回答的问题不再是"中位数是多少"，而是：**在这个规模下，一次操作要等多久；到什么程度算不能用了。**这一改变同时服务论文——论文要论证的是"改造前该规模不可用、改造后可用"，为此需要的是量级与判定，不是分位数。

10²／10³／10⁴ 三档**不受本修订影响**，继续按原合同完整采样。这三档是论文的主数据，必须保持统计强度。

## B.2 10⁵ 与 10⁶ 的新采样规则

| 档位 | 层 | 原规则 | 新规则 |
| --- | --- | --- | --- |
| 10⁵ | Node | 每项 3 次 | **不变，仍为 3 次**（Node 层快且便宜，是论文主要素材） |
| 10⁵ | 浏览器 production | 每项 3 次 | **每项 1 次，无预热**，如实记录单次耗时 |
| 10⁵ | 浏览器 dev | 每项 3 次或记超时 | **每项 1 次探测**，超时或失败即记，不重试 |
| 10⁶ | 全部 | 1 次探测 | **不变** |

配套规则：

| 编号 | 要求 |
| --- | --- |
| B-13 | 单次探测的结果必须标注 `n=1`，不得写成中位数，也不得与三档主数据放进同一张表而不加区分 |
| B-14 | 单条命令的 180 秒上限保持不变。命中上限时记为"超时（>180 s）"，并写明是哪一个操作、卡在哪一步 |
| B-15 | 允许某个指标因前一步失败而无法开始（例如账本打不开则写入无从测起）。此时记为"未取得（前置失败：<具体步骤>）"，不得留空，也不得用估算值填充 |
| B-16 | 不得为了拿到数字而重试、更换种子、缩短跨度或降级账本结构 |

## B.3 可用性判定线

为使"不可用"成为可核验的结论而非主观感受，本批采用交互响应时间的通用三档界限作为判定标准：

| 界限 | 用户感受 | 出处 |
| --- | --- | --- |
| 0.1 秒 | 感觉是即时反应 | 交互响应时间的经典三界限（Miller 1968；Nielsen 1993 归纳） |
| 1 秒 | 感觉到延迟，但思路不中断 | 同上 |
| 10 秒 | 注意力流失，用户会转去做别的事 | 同上 |

据此对每个档位给出一行判定：

| 操作 | 可用 | 勉强可用 | 不可用 |
| --- | --- | --- | --- |
| M-6 单字符输入 | ≤ 0.1 s | ≤ 1 s | > 1 s |
| M-5 页面切换 | ≤ 0.2 s | ≤ 1 s | > 1 s |
| M-3 记一笔 | ≤ 0.3 s | ≤ 3 s | > 10 s |
| M-4 查询 | ≤ 0.2 s | ≤ 1 s | > 1 s |
| M-1 冷启动 | ≤ 3 s | ≤ 10 s | > 30 s |

M-1 单列，因为按 `03A` R-2 它是允许与账本总量成正比的四件事之一；但即便如此，超过 30 秒仍判为不可用。

`04C-1` 必须为每个档位给出一张判定表：逐操作标出可用／勉强可用／不可用，并用一句话总结该档位整体是否可用。**该判定必须直接引自实测数字，不得因为"只差一点"而放宽。**

## B.4 交付追加要求

`04C-1` 除 1.5 已列各项外，还须包含：

1. 各档位的可用性判定表与一句话结论
2. 10⁵、10⁶ 两档"在哪一步先失效"的完整链条：生成 → 校验 → 序列化 → 导入预检 → 导入 → 打开 → 渲染 → 计算，逐步标注通过、超时或失败
3. 一句话回答：**按现有实现，这个账本在哪个规模上开始不可用？**

## C.2 授权修复两项失败测试

以下两处**授权修改，且仅授权本节明确写出的内容**。修改后必须在 `04C` 中逐条列出实际改法。

### C.2.1 `src/platform/files/ledgerFileContract.ts`：常量值修正

将 `MAX_LEDGER_FILE_V2_BYTES` 由 `512 * 1024 * 1024` 改为 `384 * 1024 * 1024`。

理由与推导见 `04A` 修订 C 的 C.2。这不是放宽也不是收紧，是修正一个**超过 JavaScript 单条字符串物理上限（0x1fffffe8 = 511.999977 MiB）的错误值**。

**改完之后 `src/platform/files/ledgerFileHandleAdapter.test.ts` 无需任何修改即可通过。** 该测试本就使用 `MAX_LEDGER_FILE_V2_BYTES` 常量而非写死数字，唯一的问题是常量值本身够不着。经实测确认：384 MiB 下该文件 22/22 通过，用时约 348 ms，远低于该用例既有的 10,000 ms 超时。

若执行方认为该测试标题中的字面文字"32 MiB"需要同步更正为不写死数字的表述，**允许只改标题字符串**，断言与结构一律不动。

### C.2.2 `src/platform/files/ledgerFileContract.test.ts`：断言改为引用常量

该用例把 `8 * 1024 * 1024` 写死在测试里，上限改为 128 MiB 后失效。授权改法**仅限**：

| 位置 | 改法 |
| --- | --- |
| 文件顶部 import | 新增 `import { DEFAULT_LEDGER_RESOURCE_LIMITS } from "@/core/validation/resourcePolicy";` |
| 用例内 | `"x".repeat(8 * 1024 * 1024)` 改为 `"x".repeat(DEFAULT_LEDGER_RESOURCE_LIMITS.fileBytes)` |
| 用例标题 | 允许由写死 8 MiB 的表述改为不写死数字的表述 |

**断言本身一个字不动**：仍然是"恰好上限返回 `{ ok: true }`、多一字节返回 `ok: false`"。这是让测试跟着常量走，不是放宽测试。

经实测确认该改法下该文件 13/13 通过，用时约 182 ms；V8 对 `repeat` 与模板拼接采用惰性字符串，实测 RSS 未见明显上升。

## C.4 补齐 B.3 判定线的空缺区间

修订 B 的 B.3 表中，M-3 一行定义了 `≤ 0.3 s 可用`、`≤ 3 s 勉强可用`、`> 10 s 不可用`，**3 s 至 10 s 之间没有定义**。`04C-1` 实测 10⁴ 档为 7.440 s，正好落在该空缺内，执行方按合同保留未判，处理正确。

现补齐：

| 操作 | 可用 | 勉强可用 | 不可用 |
| --- | --- | --- | --- |
| M-3 记一笔 | ≤ 0.3 s | ≤ 3 s | **> 3 s** |

即取消 3～10 s 的空缺，`> 3 s` 直接判不可用。理由：记一笔是高频主动操作，不是 `03A` R-2 允许与总量成正比的四件事之一；按 B.3 引用的经典三界限，超过 1 秒已中断思路，3 秒是本产品能接受的最宽界限。

据此，`04C-1` 第 7 节的 10⁴ 档 M-3（7.440 s）**追认为「不可用」**。该档位的总判定原已为"不可用"，本次补齐不改变该结论，也不要求重写 `04C-1`。

### C.5.1 修订 A 的 A-5 有两格漏标

`04C-1` 第 1 节称"对 10²/10³/10⁴ 已取得数据逐项检查，最大值均未超过同格中位数两倍"。独立复核对第 3.2 与 4.2 两节共 150 个 `中位数[最小, 最大]` 格子逐格复算，发现 **2 格超过 2 倍**：

| 出处 | 档位／模式 | 指标 | 中位数 | 最大 | 最大÷中位数 |
| --- | --- | --- | ---: | ---: | ---: |
| 第 3.2 节（E-1） | S-10K dev | M-4 | 50.130 | 108.469 | 2.164 |
