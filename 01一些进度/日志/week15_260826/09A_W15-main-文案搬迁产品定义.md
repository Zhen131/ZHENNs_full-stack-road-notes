## 结论

本批只做一件事：**把 07 批之外剩下的全部界面文案，搬进 07 建好的文案表。**

这是纯体力活，**但它会产出本项目至今波及面最大的一次 diff**。因此本批的重点不是「怎么搬」，而是**「怎么让这个巨型 diff 仍然可以被逐行核对」**。

## 二、`core` 那 11 处：本批唯一要动逻辑的地方

`src/core` 是纯计算层，**不应生成用户可见文案**。但目前有 11 处直接写着中文，例如：

```
core/policies/ledgerFactPolicy.ts:127
  message: "未来交易已隔离，必须删除、替换账本或清空后才能恢复普通写入"
```

**处理方式：改为错误码，由界面层翻译。**

该模式在本项目已有先例——`TradeValidationErrorCode`、`LedgerFileContractErrorCode` 等共 5 处错误码类型定义，只是未贯彻到底。本批照既有先例执行，不另发明。

| 编号 | 要求 |
| --- | --- |
| C-1 | 每处中文文案改为一个语义清晰的错误码常量；界面层按码查文案表 |
| C-2 | **不得改变任何判定逻辑、触发条件或错误的语义。** 只改「这条错误怎么被表达」 |
| C-3 | `core` 与 `platform` 改完后**不得引用 `@/ui`**；错误码是它们与界面层的唯一接口 |
| C-4 | 该部分**独立于文案搬运提交**，不与批量搬运混在同一笔 |

## 三、这个批次真正的难点：巨型 diff 怎么审

本项目的质量依赖**逐行读 diff**——`04D` 曾在 1,107 个测试全绿的情况下，靠人工读 diff 查出被删除的测试断言。**一个波及百余文件、上千行的 diff 是这种审查方式最容易失效的地方。**

因此本批设四条硬约束：

| 编号 | 约束 |
| --- | --- |
| **D-1** | **按页面分批提交，一个页面一笔。** 不得一次提交搬完所有文件。每笔提交的 diff 必须小到能被逐行读完 |
| **D-2** | **每一笔提交都必须是纯搬运**：把字面量换成 `t(key)`，并在文案表中新增对应条目。**同一笔提交里不得出现任何其他改动** |
| **D-3** | **中文渲染结果必须逐字不变。** 搬运后界面显示的中文与搬运前完全相同；这是既有 821 处测试断言无需修改的前提 |
| **D-4** | **key 命名必须遵循 07 批冻结的规则**，不得另立一套。若发现某类文案无法用既有规则命名，停止申报 |

**D-1 是本批的生命线。** 分批提交把「一个不可审的巨型 diff」变成「几十个可审的小 diff」，代价只是多几笔提交。

## 修订 A（2026-09-01）：允许与 08 同分支连做，并把「停止申报」降为三档处置

**上文原文一字不改写。** 凡与上文冲突处，以本修订为准。

### A. 前置条件放宽：08 与 09 可在同一分支上连续执行

原「前置」与第六节要求 08 批**合入 `main`** 之后才开 09。原第六节的两条理由中，一条已消失：

- **key 命名规则已由 07 批冻结**，即 `区域.组件或语义分区.用途`（`07C` R-3），不再是未知；
- 文件清单确实仍取决于 08 的拆分结果，**但本批的文件清单本就应由执行者自行检索得出**（第一节已要求口径自证），不需要合同预先给定。

因此**允许 08 与 09 在同一条分支上连续执行**，条件是：

| 编号 | 条件 |
| --- | --- |
| **M-1** | **必须有一条清晰的缝。** 08 的全部提交在前，09 的全部提交在后，**中间记录一个 commit SHA 作为分界**，`09C` 须写明 |
| **M-2** | **不得回头修改缝之前的任何提交。** 不得 `amend`、`rebase`、`squash`。发现 08 阶段的问题，记进 `09C`，用**新的提交**修，且该提交须明确标注属于哪一批 |
| **M-3** | **过缝之前必须先跑一遍全部闸门并记录原始输出。** 08 阶段没有全绿，不得开始 09 阶段 |
| **M-4** | 08 与 09 的改动**不得出现在同一笔提交里**，一次都不许 |

**原第五节风险表「08 必须完全合入后才开 09」的用意是「两批的 diff 必须能分开审」，M-1～M-4 已以更直接的方式达成该用意。** 独立验收照旧分开进行：`08D` 读缝之前的提交，`09D` 读缝之后的。

**代价已向产品负责人明示并接受**：若 `08D` 判定 08 阶段有问题，09 的成果搭在其上，可能连带返工。

### B. 「停止申报」降为三档处置

与 `08A` 修订 A 同精神——06 批四次停摆的复盘结论是合同措辞把执行者逼进死胡同，而非规矩过严。**每一条禁令必须配一条「那你该怎么办」。**

| 档 | 处置 | 适用 |
| --- | --- | --- |
| **一档（默认）** | **跳过它，保留该处中文原样不动，记进 `09C`，继续下一处。不停止。** | 原 N-3（某条既有文案依赖语法数）、原 D-4（某类文案无法用既有 key 规则命名）、原 N-1（某处搬运会迫使既有断言改动）、任何拿不准是不是纯搬运的地方 |
| **二档（少数）** | **走预先批准的退路，继续。不停止。** | 某个文件的中文与逻辑纠缠过深、搬运即等于改逻辑 → **整个文件跳过**，记录后继续下一个文件；`core` 的错误码改造若牵动 `core` 的判定逻辑 → **该处不改，保留中文**，记录后继续 |
| **三档（仅下列三条）** | **立即停止并申报** | 见下表 |

**三档停止申报，只有这三条**：

| 编号 | 条件 |
| --- | --- |
| **H-1** | 四个版本号中任何一个发生变化 |
| **H-2** | 04 批冻结派生等价性快照不是 7/7 |
| **H-3** | 结构守卫 `sourceLayout.test.ts` 失败（含 `core`／`platform` 引用 `@/ui` 被拦） |

**原第三节 D-4、第四节 N-1／N-3 中的「停止申报」字样，一律按本修订降为一档处置。** 理由：这三处的风险都是**局部且可逆**的——跳过一处文案，屏幕上那句话仍是原来的中文，不损坏任何数据、不影响其余文案的搬迁；而停下来等裁决的代价是整批停摆。

**D-1（按页面分批提交）、D-2（每笔提交纯搬运）、D-3（中文渲染逐字不变）三条不降级、不放宽**——它们是本批可被审查的前提。
