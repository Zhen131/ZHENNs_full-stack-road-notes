## 一、为什么先造尺子

三条理由，任何一条单独成立都足够：

1. **改之前的数字只有一次机会。** 一旦动了代码，「原来多慢」就永远无法复现，后续所有「快了多少」的说法都失去参照。
2. **没有大账本，就无法判断改对了没有。** 只修好眼前 640 条事实的卡顿，架构仍是全量重放，一年后原地复发，且那时代码更多、更难改。
3. **尺子在修复时当刹车用。** 改完立刻跑，10⁴ 档从若干秒降到若干毫秒是证据；没降就说明改错了地方，当场发现而不是三批之后。

## 二、性能设计三条硬规则

本批**不实现**这三条，只把它们固定为长期产品规则，供 04、05 及以后每一批当验收标准。这三条比任何一段具体代码活得都久。

| 编号 | 规则 |
| --- | --- |
| **R-1** | 用户日常操作的耗时，只能与「这次操作直接涉及的事实数量」有关，**不得与账本总量有关**。日常操作包括：切换页面、在输入框打字、展开或收起明细、翻页、筛选、记一笔新事实、删除一笔事实。 |
| **R-2** | 允许与账本总量成正比的操作**只有四件**：打开账本、导入、导出、全量校验。这四件事本身就是要把整本读一遍，允许出现明确的进度提示。 |
| **R-3** | 同时渲染的界面元素数量，只能与「当前屏幕装得下多少」有关，**不得与列表总行数有关**。 |

三条规则的产品含义：**打开账本时转一次圈可以接受；打开之后，每一个操作都必须瞬时，而且账本再厚也一样瞬时。**

违反 R-1 的现存例子（本批只记录，不修复）：在价格输入框敲一个字符会触发整本账本重放约 30 遍。
违反 R-3 的现存例子：704 行流水渲染出约 17,390 个元素，且隐藏的交易页仍完整挂载。

## 三、目标规模与天花板

| 项目 | 决定 |
| --- | --- |
| 产品通过线 | **10⁶（一百万笔交易）** |
| 论文 Month 5 范围 | 10²～10⁵，与产品线不冲突，产品线更高一档 |
| 明确排除 | 10⁷ 及以上 |

排除 10⁷ 的理由必须写清楚，因为它不是「代码不够好」，而是架构的物理边界：

一笔交易存成文字约 300 字节。10⁶ 约 300 MB 明文，加密文件量级相当。本产品是「本地加密单文件」设计，**文件必须被完整读进内存才能解密**，10⁷ 就是约 3 GB，个人电脑的浏览器无法承受。

这个天花板将来若要突破，方向是分块存储与按需加载（单个加密文件内部再分片，只加载需要的分片）。该方向**不在当前产品线范围内**，本批不为它预留任何实现，只在此记录方向，避免将来误以为需要推翻现有设计。

**好消息也要写明**：若严格遵守第二节三条规则，将来真撞到天花板时，卡住的会是 R-2 允许的那四件事（打开、导入、导出、校验），而不是日常使用。届时的解法是文件分片，不需要推翻本批与 04、05 建立的任何结构。

## 四、合成账本生成器

### 4.1 规模档位

| 档位 | 交易笔数 | 预估明文体积 | 本批用途 |
| --- | --- | --- | --- |
| S-100 | 10² | 约 30 KB | 完整测量 |
| S-1K | 10³ | 约 300 KB | 完整测量 |
| S-10K | 10⁴ | 约 3 MB | 完整测量 |
| S-100K | 10⁵ | 约 30 MB | 完整测量，允许部分指标记为超时 |
| S-1M | 10⁶ | 约 300 MB | **只做单次探测**：能否生成、能否打开、耗时多少。允许记为「无法完成」 |

### 4.2 结构比例

生成的账本必须在结构上像一本真账本，而不是一万条一模一样的记录。比例参照当前真实账本的形状（只用比例，不用任何真实数值）：

| 事实种类 | 相对交易笔数的比例 |
| --- | --- |
| 交易 | 1（即档位数字本身） |
| 现金事件 | 约 0.4 |
| 价格快照 | 约 0.15 |
| 资产转入转出 | 约 0.05，四种类别都要出现 |
| 资产种类 | 10～20 种 |

时间跨度按档位放大，使每日事实密度保持在合理范围，不得把 10⁶ 笔全部堆在同一天。

### 4.3 必须满足的约束（这是生成器的真正难点）

生成器输出的账本**必须能通过账本自身的全部校验规则**，否则量出来的是错误路径的耗时，毫无意义：

- 卖出数量不得超过当时持仓，且交易所位置数量必须足够
- 转出与内部划转的数量加链上手续费不得超过来源位置数量
- 外部转入与白拿必须带单价；内部划转与外部转出不得带单价
- 原因与类别必须匹配
- 现金事件不得使余额出现不允许的状态
- 全部事实时间不得晚于生成时设定的「今天」
- `ledgerSchemaVersion` 与当前正式版本一致

### 4.4 可重现与不入库

| 项目 | 规则 |
| --- | --- |
| 随机性 | 必须使用**固定种子的确定性伪随机**，同一种子同一档位必须生成逐字段完全相同的账本 |
| 入库范围 | **只提交生成器代码与种子。生成出来的账本文件一律不进 Git**，运行时现造，用后即弃 |
| 理由 | 一是体积（10⁵ 档 30 MB、10⁶ 档 300 MB）；二是原则（账本内容不入库，无论真假） |
| 数据性质 | 全部虚构。资产代号使用明显虚构的名称，不得使用可能被误认为真实持仓的组合 |

## 五、量什么

对齐论文 Month 5 的四项指标，另加两项直接对应用户体感的指标，再加两项用于定位根因的诊断指标。

| 编号 | 指标 | 定义 | 层 |
| --- | --- | --- | --- |
| M-1 | 冷启动时间 | 从选定账本文件到首页可交互 | 浏览器 |
| M-2 | 全账本盈亏计算时间 | 首页五个派生计算完整跑一遍 | Node |
| M-3 | 写入延迟 | 记一笔新交易，从提交到界面完成更新 | 浏览器 |
| M-4 | 查询延迟 | 交易页按日期筛选，从操作到列表完成更新 | 浏览器 |
| M-5 | 页面切换延迟 | 记账↔首页↔交易 三个方向 | 浏览器 |
| M-6 | 单字符输入延迟 | 价格输入框输入与删除各一个字符 | 浏览器 |
| M-7 | 历史曲线构建时间 | 单独计时，区间分别取 1 天／7 天／30 天／365 天／全部 | Node |
| M-8 | 单次全量重放时间 | 持仓重放与现金重放各一次 | Node |

M-7 与 M-8 是诊断指标：**M-7 除以 M-8 应该约等于区间天数。** 若成立，即从数字上证明了「历史曲线按天重复重放整本账本」这一根因；若不成立，说明根因判断有误，必须在 `03C` 中如实记录并停止推进 04 批的相应设计。

### 5.1 采样次数

| 档位 | 次数 | 报告方式 |
| --- | --- | --- |
| S-100 / S-1K / S-10K | 每项指标 10 次 | 中位数、最小值、最大值 |
| S-100K | 每项指标 3 次 | 三次全列 |
| S-1M | 1 次探测 | 单值或「无法完成」 |

第一次运行结果一律丢弃不计入，避免首次加载的额外开销污染数据。

论文 Month 5 要求的四分位距留到 06 批补齐，本批不做。

### 5.2 环境要求

每一项指标都必须**分别在开发模式与 production 模式下各记录一组**。两组数字必须分开呈现，严禁用其中一组解释另一组。

同时记录：操作系统、浏览器版本、CPU 型号、内存大小、是否插电。这些在跨机器对比时是必需的。

## 六、量尺分两层

### 6.1 Node 层（M-2、M-7、M-8）

直接调用产品的计算函数，不经过浏览器与界面。

- 优点：便宜、稳定、可进自动化测试、以后每批都能跑
- 用途：回答「算一遍要多久」，这是卡顿的根源指标
- 形式：一条独立的 npm 脚本，输出结构化结果

### 6.2 浏览器层（M-1、M-3、M-4、M-5、M-6）

用 Playwright 驱动真实浏览器操作真实页面。

- 优点：量的是用户真实感受到的延迟
- 用途：回答「点一下要等多久」
- 形式：一条独立的 npm 脚本，与单元测试分开，默认不随 `npm test` 运行

### 6.3 浏览器层的关键障碍与解法

**障碍**：产品通过浏览器原生的文件选择框打开账本。浏览器自动化无法点击操作系统的原生对话框，因此无法用常规方式让 Playwright 打开一个账本。

**解法**：在测量脚本中，于页面加载前替换掉浏览器提供的文件选择接口，改为返回一个由脚本自己掌握的内存文件句柄。

| 项目 | 规则 |
| --- | --- |
| 替换发生在哪 | **只在测量脚本内**。产品代码一行不改 |
| 被绕过的是什么 | 只有「弹出系统对话框让人选文件」这一步 |
| 仍然是真的是什么 | 密码校验、密钥派生、加密解密、文件读写、账本装载、页面渲染，全部走真实产品代码 |
| 绝对禁止 | **不得在产品中加入任何测试模式开关、环境变量后门或跳过校验的分支。** 源码仓库是公开的，且这会直接破坏产品的 fail-closed 安全设计 |

若该解法在实施中被证明不可行，允许**降级交付**：本批只交付 Node 层，浏览器层五项指标记为「未取得」，并在 `03C` 中写明失败原因与已尝试的方案。**不允许为了取得浏览器数据而在产品中开后门。**
