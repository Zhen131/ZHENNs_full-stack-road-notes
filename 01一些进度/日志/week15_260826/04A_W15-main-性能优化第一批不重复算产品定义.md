1. **固定证据**：放宽资源上限，补齐 10⁵ 档的改动前基线，把 10²～10⁴ 三档的派生计算结果整份快照冻结成测试夹具。

## 零、先修正一个结论

`03C` 第 5.2 节与第 7 节判定"历史曲线按天重复重放"这一根因被证伪，并要求 04 批重新论证方向。**该判定已由 `03D` 的 O-1 收窄，本批据收窄后的结论执行。**

收窄理由：合成账本的时间跨度按档位固定为 `spanDays = max(10, ceil(交易笔数 / 100))`，即 10²／10³ 档只有 10 天、10⁴ 档 100 天、10⁵ 档 1000 天。区间长于账本跨度的格子（365d、all）在物理上不可能产生等于区间天数的倍率，用它们证伪属于比错对象。

只看区间不超过跨度的格子：

| 档位 | 跨度 | 1d | 7d | 30d |
| --- | ---: | ---: | ---: | ---: |
| 10⁴ | 100 天 | 1.059 | 7.176 | 27.341 |
| 10⁵ | 1000 天 | 1.063 | 7.685 | 33.347 |

几乎精确等于 1／7／30，是对原根因的强支持。

**本批采用的成本模型**：历史曲线的构建成本 ≈ 对区间内每一天，重放一次截至该日的账本前缀，另加每天约 0.11 倍全量重放的固定开销。原描述"每天完整重放整本账本"在措辞上不精确（是前缀不是整本），在方向上完全成立。

## 一、阶段一：放宽资源上限

### 1.1 现状与实际天花板

`src/core/validation/resourcePolicy.ts` 当前的上限：

| 项目 | 当前值 |
| --- | ---: |
| `fileBytes` | 8 MiB |
| `trades` | 25,000 |
| `cashEvents` | 25,000 |
| `assetTransfers` | 25,000 |
| `priceSnapshots` | 5,000 |
| `assets` | 500 |

按 `03C` 实测，每笔交易连带其现金、价格与转账事实的明文体积约 694 字节。因此 **`fileBytes` 先于所有集合上限撞上，实际容量约 12,000 笔交易**。`priceSnapshots` 的 5,000 条可能更早撞上：每日为 10 个资产各存一次价格，约 500 天即满。

这两条都不是"很久以后"的问题，本批一并处理。

### 1.2 新的上限

| 项目 | 当前 | 改为 | 理由 |
| --- | ---: | ---: | --- |
| `fileBytes` | 8 MiB | **128 MiB** | 10⁵ 档明文备份为 69,369,153 字节，须留出余量 |
| `trades` | 25,000 | **250,000** | 10⁵ 档需 100,000，留 2.5 倍余量 |
| `cashEvents` | 25,000 | **250,000** | 10⁵ 档需 40,000 |
| `assetTransfers` | 25,000 | **250,000** | 10⁵ 档需 5,000 |
| `priceSnapshots` | 5,000 | **50,000** | 10⁵ 档需 15,000；同时解掉一年半就满的隐患 |
| `assets` | 500 | **500**（不变） | 未撞上，不动 |
| `MAX_LEDGER_FILE_V2_BYTES` | 32 MiB | **512 MiB** | C 文件存两代密文并做 Base64，体积约为明文的 2×4/3 倍；`fileBytes` 抬到 128 MiB 后不跟着抬会卡在这里 |

`LEDGER_FILE_OUTER_V2_CONSTANTS.maximumCiphertextBytes` 由 `fileBytes` 派生，自动跟随，不单独改。

### 1.3 这不是升版本

**放宽上限不改变任何文件的长相，因此不升任何版本号。** `backupFormatVersion` 仍为 3，`fileFormatVersion` 仍为 2，`cryptoVersion` 仍为 1，`ledgerSchemaVersion` 仍为 4。这些上限是写在代码里的规矩，不是写在文件里的字段。本批不触发黄金样例规则，不需要迁移器。

### 1.4 放宽的代价（产品决定）

这些上限当初存在的理由是**资源保护**：一个过大的文件在读入与解析时会耗尽标签页内存，浏览器直接崩溃。放宽之后，程序面对超大文件不再给出"文件太大，拒绝"，而是可能卡死。

**这是资源耗尽，不是安全漏洞。** 账本文件里只有数据，不会被当作代码执行；放宽上限不会引入代码注入或数据窃取的风险。风险仅仅是"点钞机一次数不完这么多张"。

产品决定：**Alpha 阶段接受该风险**，唯一使用者为作者本人，不存在第三方投喂恶意文件的场景。

**进入 Beta 之前必须重新处理**，二选一：把上限收紧回一个保守值，或改成流式读取与边读边检查，使超限在耗尽内存之前被发现。该要求写入本文件，不随本批结束而失效。

### 1.5 阶段一必须产出的证据

| 编号 | 证据 |
| --- | --- |
| E-1 | 放宽上限**前**，10²／10³／10⁴ 三档的 Node 层与浏览器层完整数字（复跑，不引用 `03C`） |
| E-2 | 放宽上限**后**，同三档同样跑一遍，证明放宽本身不改变性能 |
| E-3 | 放宽上限后，10⁵ 档的 Node 层与浏览器层完整数字（这是新增的、此前拿不到的一格） |

### 1.6 派生结果快照（等价性夹具）

**优化的唯一失败模式是"算快了但算错了"，而且很难被发现。** 因此阶段二改动之前，必须先把"正确答案"钉死。

做法：对 10²／10³／10⁴ 三档，用固定种子生成账本，把首页五个派生计算的**完整输出**逐字段序列化，存入源码仓库测试夹具。阶段二改完后，重新计算的结果必须与快照**逐字段完全相同**，一位小数都不许变。

| 项目 | 要求 |
| --- | --- |
| 覆盖 | 持仓重放、现金重放、盈亏摘要、资产分配、历史曲线（1d／7d／30d／365d／all）、交易热力图 |

**这条与既有的黄金样例规则同源：没有可信的"改动前"参照，就无法证明改动没有破坏正确性。**

# 修订 C（2026-08-29，阶段一交付后追加）

## C.1 背景

`04C-1` 交付后，阶段一有两项证据触发了对本文件的修正，均由产品负责人裁决：

1. 1.2 表中的 `MAX_LEDGER_FILE_V2_BYTES = 512 MiB` **写错了**。该值超过 JavaScript 单条字符串的物理上限，导致"恰好达到上限的 C 文件"永远无法被读取。
2. 2.2 表中 `M-3 写入 ≤ 300 ms` 这条必达线，很可能超出本批能力范围，须重新定位。

本修订不推翻阶段一任何已完成的测量，**不需要重跑任何量尺命令**，理由见 C.4。

## C.2 修正一：外层文件上限 512 MiB 改为 384 MiB

### C.2.1 512 MiB 为何是错的

账本 C 文件在读取时会被整体解码为一条 JavaScript 字符串，再交给 JSON 解析。V8 对单条字符串有硬上限：

```
JS 单条字符串上限 0x1fffffe8 = 536,870,888 字节 = 511.999977 MiB
04A 1.2 原定的 512 MiB     = 536,870,912 字节
差额                        = 24 字节
```

**原定值比物理上限还大 24 字节。** 因此一个恰好达到上限的 C 文件在 `TextDecoder` 阶段就会抛 `ERR_STRING_TOO_LONG`，被产品包装为 `LedgerFileAdapterError(stage: "utf8")`，用户永远读不到它。上限设成了一个够不着的数。

该现象已在 `04C-1` 第 9 节由执行方如实报告，并经独立复核实际复现：

```
Caused by: Error: Cannot create a string longer than 0x1fffffe8 characters
Serialized Error: { code: 'ERR_STRING_TOO_LONG' }
```

### C.2.2 新值与推导

| 项目 | 原定 | 改为 |
| --- | ---: | ---: |
| `MAX_LEDGER_FILE_V2_BYTES` | 512 MiB | **384 MiB** |

推导：

```
明文账本上限 fileBytes           = 128 MiB
C 文件保存 current 与 previous 两代 → × 2
两代密文均以 Base64 编码          → × 4/3
最坏情况所需                      = 128 × 2 × 4/3 = 341.33 MiB
```

384 MiB 覆盖该最坏情况并留约 12% 余量，同时远低于 511.999977 MiB 的物理上限。

`04A` 1.2 表中 `MAX_LEDGER_FILE_V2_BYTES` 一行的目标值以本节为准，原 512 MiB 作废。其余六个数值（`fileBytes` 128 MiB、`trades`／`cashEvents`／`assetTransfers` 250,000、`priceSnapshots` 50,000、`assets` 500 不变）全部不变。

### C.2.3 这仍然不是升版本

同 1.3：改的是写在代码里的规矩，不是写在文件里的字段。四个版本号一个都不动，不触发黄金样例规则，不需要迁移器。

## C.3 记录给 06 批：第三堵墙第一次露头

C.2.1 暴露的不是一个笔误，而是架构天花板的第一次实际接触。

`03A` 第三节已记载：本产品是"本地加密单文件"设计，文件必须被完整读进内存才能解密。现在可以把这句话说得更具体——**瓶颈的精确位置是"整个文件必须先变成一条 JavaScript 字符串"，而这条字符串的硬上限是 511.999977 MiB。**

按 `04C-1` 第 6 节实测，10⁶ 档在明文备份序列化阶段即抛 `RangeError: Invalid string length`，与此为同一堵墙。

因此 06 批分块存储的设计目标必须包含一条：**读取与写入路径都不得要求把整本账本变成单条字符串。** 该要求写入本文件，供 06A 起草时直接引用。

## C.4 为何不需要重跑任何测量

`04C-1` 第 5 节记录 10⁵ 档已通过导入预检并完成导入。按 `03C` 4.1，10⁵ 档明文备份为 69,369,153 字节（约 66.2 MiB），其 C 文件最坏情况约 66.2 × 2 × 4/3 ≈ 176.5 MiB。

**176.5 MiB 同时低于原定的 512 MiB 与新定的 384 MiB**，即该常量从 512 改为 384 不改变阶段一任何一次测量的成败与耗时。E-1、E-2、E-3、E-4 全部数据继续有效，不重跑。

## C.5 修正二：M-3「记一笔」通过线重新定位

### C.5.1 问题

2.2 表定 `M-3 写入 ≤ 300 ms` 为 10⁴ 档必达。`04C-1` 实测改动前为 7,439.782 ms。

按量尺实现（`benchmarks/measure/browserMetrics.ts` 的 `measureWrite`），M-3 测的是**从点击提交按钮开始，到表单 `aria-busy` 变为 `false` 且画面帧安定为止**。这段时间内至少发生三件性质完全不同的事：

| 发生了什么 | 归属批次 | 目前可确定的量 |
| --- | --- | ---: |
| 重算全部派生数字 | **04 批（本批）** | 约 1,504 ms（`04C-1` 4.1 Node M-2） |
| 整本序列化、加密、写入两代完整密文、复读验证 | **06 批** | 未知 |
| 重画页面，含始终挂载未卸载的交易大表 | **05 批** | 未知 |
| 合计 | — | 7,439.782 ms |

也就是说，7,439.782 ms 中目前只能确定约 1,504 ms 属于本批职责范围，**其余约 5,936 ms 归属不明，且很可能主要由 05 与 06 批的问题构成。**

### C.5.2 产品决定

在取得分项数据之前，**不调整也不放弃该通过线**。改为：

1. 阶段二开工的第一件事是**测出 M-3 的分项构成**（要求见 `04B` 修订 C 的 C.3）。
2. 分项数据取得后，M-3 的通过线按下述规则重新判定：
   - 若本批职责内的部分（重算）降到 300 ms 以内，即视为 **P-2 达标**，无论 M-3 总耗时是多少。
   - M-3 总耗时的剩余部分，按分项归属登记到 05 批或 06 批，**不计入本批未完成**。
3. 若分项测量显示重算部分本就不足 300 ms（即 M-3 的慢与本批无关），必须在 `04C` 中明确写出，**不得把 05／06 批的改善或恶化算到本批头上**。

其余四项必达线（M-6 ≤ 100 ms、M-5 ≤ 200 ms、M-4 ≤ 200 ms、M-2 ≤ 200 ms）**不变，仍按 2.2 原文执行**。

### C.5.3 为何不直接放宽

因为放宽通过线是本批最容易发生的自我欺骗。本节不是放宽，是**把一个混合指标拆成可归属的分项**：本批只对自己造成的那部分负责，也必须对那部分完全负责。若拆完发现重算部分仍高于 300 ms，本批照旧判未完成。
