## 一、05 批：卡的不是图表，是表格

### 1.1 图表不是瓶颈

图表库为 ECharts 6.1（见 `package.json` 的 `dependencies`）。ECharts 绘制在 canvas 上，**整张图在页面结构里只占一个元素**，与数据点数量无关。因此图表不是页面元素爆炸的来源。

`03A` 记录的"704 行流水渲染出约 17,390 个元素"，除下来约 **25 个元素每行**，来源是交易流水表格 `src/features/trades/TradeTable.tsx`（493 行），不是图表。

按此推算：

| 交易笔数 | 页面元素数 |
| ---: | ---: |
| 704 | 约 1.7 万 |
| 10,000 | 约 25 万 |
| 100,000 | 约 250 万 |

### 1.2 非活动工作区从未卸载

`src/app/TransactionsWorkspace.tsx` 第 527 行：

```
className={active ? "grid min-w-0 gap-4" : "hidden"}
```

工作区切换只是用 CSS 隐藏，**组件始终挂载**。因此用户在首页时，交易页的全部元素仍然存在并参与浏览器的每一次布局与样式计算。

这解释了 `03C` 中一个反直觉的数字：切换到首页（首页并不含大表）在 10⁴ 档 production 下仍需 1,686 ms。

`DashboardShell.tsx` 中 `active` 属性传给 `HomeWorkspace`、`RecordWorkspace`、`TransactionsWorkspace`、`TransferWorkspace`、`SettingsWorkspace` 五个工作区，同一模式。

### 1.3 真正卸载的代价：状态会丢

CSS 隐藏而非卸载，**很可能是为了保留跨页面状态**，不是疏忽。改为真正卸载会丢失筛选条件、展开的详情、滚动位置、未提交的记账草稿。

因此 05 批的实际工作量不是"把 hidden 换成卸载"，而是：**先把需要跨页面存活的状态提升到工作区之外持有，再让工作区可以安全卸载与重建。**

05A 必须明确列出状态保留合同，建议至少覆盖：

| 状态 | 建议 |
| --- | --- |
| 交易页筛选条件 | 必须保留 |
| 记账页未提交草稿 | **必须保留**，丢失不可接受 |
| 展开的详情行 | 可不保留 |
| 滚动位置 | 最好保留 |

### 1.4 05 批的三件事（待 05A 正式确认）

1. 交易表格虚拟化：只渲染视口内的行
2. 非活动工作区真正卸载，配合 1.3 的状态提升
3. 图表数据点降采样（次要，ECharts 自带抽样能力）

## 二、06 批：黄金样例的两个缺口

### 2.1 现状

`test-fixtures/golden/` 当前只有两个文件：

| 文件 | 大小 | 内容 |
| --- | ---: | --- |
| `golden-backup-format-v3-ledger-schema-v3.json` | 163 KB | 有内容 |
| `golden-backup-format-v3-ledger-schema-v4.json` | 2.2 KB | 1 资产、**0 笔交易**、现金／转账／价格／费率各 1 条 |

### 2.2 缺口一：V4 样例是空壳

`ledgerSchemaVersion = 4` 的黄金样例**一笔交易都没有**。迁移器最容易出错的地方恰恰是交易之间的关系——卖出扣的是哪次买入的成本、同一资产跨位置的分布、带链上手续费的转账。这些情形在 0 笔交易的样例里全部缺席，拿它测迁移器测不出交易相关的错误。

处理方式：**不修改现有样例**（已提交的黄金样例不得修改），另行新增一份有代表性内容的样例。

### 2.3 缺口二：C 文件一份黄金样例都没有

现有样例全是 B 文件。`fileFormatVersion` 一直为 2、`cryptoVersion` 一直为 1，尚未触发补样例的规则。

但 06 批若将 `fileFormatVersion` 从 2 升到 3，届时需要一份"外壳仍为 2"的 C 文件样例，而那时代码已不再产出 2。

C 文件样例的额外要求：它是加密的，需要固定密码，且该密码必须记录在 `benchmarks/README.md` 或夹具说明中（样例内全为虚构数据，密码不是秘密）。

**现成条件**：`benchmarks/measure/browserMetrics.ts` 已经能走完整产品流程新建加密账本，只是运行结束即清理。产出 C 文件样例所差的只是一个保留文件的出口。

### 2.4 时点

建议作为 **06 批的第零步**，在 05 批完成之后、06 批动格式之前执行。过早执行会因为不知道新格式的形状而漏掉需要覆盖的情形。

## 三、06 批：双代保护在大账本下会翻倍代价

`src/platform/files/ledgerFileContract.ts` 的 `LedgerFileV2` 含 `current` 与 `previous` 两个 `EncryptedLedgerGenerationV4`，**每一个都是整本账本的完整密文**。

因此每保存一次，程序要把整本序列化、加密，并使文件中保存两份完整副本。这是 10⁴ 档写入耗时 7,652 ms（production）的主要来源——其中真正用于计算的仅约 50 ms。

06 批设计分块存储时，双代保护必须一并重新设计：不能对整本存两份，应改为只对发生变化的块保留前一版本。该问题在 06A 中必须有明确结论。
