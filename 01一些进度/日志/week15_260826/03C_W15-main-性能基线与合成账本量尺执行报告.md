# W15 main 性能基线与合成账本量尺执行报告

## 结论

本批开发执行候选为 **PASS**。合成账本生成器、Node 层量尺和浏览器层量尺均已交付，浏览器层没有降级；默认产品测试仍为 92 个文件、1081 项测试。全部改动都位于 `benchmarks/`、量尺专用配置、`.gitignore` 与开发期依赖配置，`git diff main...HEAD -- src/` 为空。

数据同时证伪了原先的简化根因：M-7 除以 M-8 并不稳定地约等于区间天数。既有历史曲线实现确有随日期重复处理账本前缀的成本，但不能等同为“每天完整重放整本账本”。**04 批的历史曲线改写方向需要重新论证。**

产品边界也已经明确：`S-100K` 在 69,369,153 字节明文备份的产品预检阶段先失效，未进入导入；`S-1M` 更早在明文备份序列化阶段触及 JavaScript 运行时字符串上限，未进入产品打开、渲染或计算。

开发侧全绿不等于独立验收通过，后续仍需由另一执行者完成 `03D`。

## 5. 4.3 六个问题的明确回答

### 5.1 全账本盈亏计算一遍，各档分别多久？

M-2 中位数为：`S-100` 5.502 ms；`S-1K` 48.142 ms；`S-10K` 1,484.066 ms；`S-100K` 18,040.043 ms；`S-1M` 在 180 秒命令上限内未取得。这里的 M-2 是首页五个派生计算完整跑一遍，不是单独的持仓重放。

### 5.2 历史曲线比值是否约等于天数，根因是否成立？

**否，原简化根因被证伪。** 例如 `S-10K` 的 1d / 7d / 30d / 365d / all 比值分别为 1.059 / 7.176 / 27.341 / 81.107 / 58.185，而对应天数为 1 / 7 / 30 / 365 / 100；`S-100K` 的 30d 比值为 33.347，但 365d 与 all 已在 180 秒命令上限内超时。小档位的 365d 比值也只有 40.397 和 35.878，远非 365。

实际实现更接近“按日期筛选或分割截至该日的前缀，再对逐渐增长的子集重复计算”，还混有筛选、分组和固定开销；并非每一天都完整重放整本账本。因此，**04 批的历史曲线改写方向需要重新论证。**

### 5.3 dev 相对 production 的额外开销是多少，卡顿能否归因于 dev？

下表是 dev 中位数 ÷ production 中位数：

| 档位 | M-1 | M-4 | M-5 记→首 | M-5 首→记 | M-5 记→交 | M-5 交→记 | M-6 输入 | M-6 删除 | M-3 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| S-100 | 1.555 | 1.035 | 1.249 | 1.245 | 0.838 | 1.222 | 1.099 | 1.116 | 1.458 |
| S-1K | 2.055 | 1.591 | 2.129 | 2.047 | 1.739 | 2.215 | 2.223 | 2.333 | 2.192 |
| S-10K | 2.176 | 1.343 | 2.387 | 2.395 | 1.980 | 2.373 | 2.501 | 2.456 | 2.085 |

dev 通常带来约 1.0～2.5 倍总耗时，`S-100` 的“记账→交易”一次出现 production 更慢的 0.838 倍。开发模式会放大卡顿，但不是主要事实的全部解释：production 在 `S-10K` 仍有约 1.535 秒单字符输入、1.686～2.409 秒页面切换、7.652 秒写入和 5.710 秒冷启动。

### 5.4 从哪个档位开始单字符输入超过 100 ms？

- dev：从 `S-1K` 开始；输入 196.831 ms，删除 208.332 ms。
- production：从 `S-10K` 开始；`S-1K` 仍为 88.547 / 89.301 ms，`S-10K` 升至 1,535.178 / 1,534.484 ms。

### 5.5 从哪个档位开始页面切换超过 200 ms？

- dev：从 `S-1K` 开始，四个方向中位数均为 252.652～290.218 ms。
- production：从 `S-10K` 开始；`S-1K` 四方向最高中位数 166.858 ms，`S-10K` 为 1,685.692～2,409.078 ms。

### 5.6 S-100K 与 S-1M 在哪一步先失效？

- `S-100K`：生成、Validator、Node 重放和 69,369,153 字节明文 B 序列化均成功；dev 与 production 都在产品的 `backup-preflight` 先失效，因为该文件超过产品 8 MiB 导入资源上限，页面没有给出导入确认。它尚未进入导入、重新打开、渲染或页面计算。
- `S-1M`：内存生成、Validator、持仓和现金重放成功，但明文 B 序列化先报 `RangeError: Invalid string length`；浏览器探针相应标记 `backup-serialization`。它比 `S-100K` 更早，连可供产品预检的 B 文件都无法形成，更没有进入打开、渲染或页面计算。

因此，两个高档都不是“渲染先失效”：`S-100K` 的首要边界是产品备份资源策略，`S-1M` 的首要边界是单字符串序列化方式。后续批次优先级必须先区分文件格式／流式处理与产品允许规模，再讨论这些档位的页面渲染优化。

## 6. 浏览器层交付与异常处理

浏览器层 **没有降级**。最终方案使用临时 persistent Chrome profile 内的 OPFS 原生 `FileSystemFileHandle`，只替代系统原生文件选择对话框；错误密码仍被拒绝，真实加解密、写入、复读、校验、导入和渲染均保留。

实际遇到并解决的量尺问题：

1. 受限环境最初不允许监听 localhost；获准仅为本地 benchmark 启动服务后继续。
2. 页面初始化注入最初受打包辅助符号影响；改为量尺侧原始初始化脚本。
3. `S-1K` production 首次启动时，先前 dev 运行覆盖了 `.next`；重新 `npm run build` 后取得有效 production 数据，失败尝试未混入结果。
4. `S-100K` 首次用 buffer 上传命中 Playwright 50 MiB 上限；改为系统临时文件路径上传并自动清理后，才测得真正的产品 `backup-preflight` 边界。

浏览器元素定位只使用稳定 workspace 属性、元素角色／类型、表单结构和 benchmarks 侧注入的顺序选择器，不依赖列名、按钮文字或其他中文文案。没有只能依赖中文文案定位的地方。

## 7. 根因验证结论

结论为 **证伪原简化描述**。曲线构建成本的确会随区间和账本规模急剧增长，但 M-7/M-8 不稳定等于 N；完整比值见 4.5。现有证据支持“重复处理随日期增长的账本前缀和额外分组／筛选开销”，不支持“每天完整重放整本账本”这一精确说法。

因此，**04 批的历史曲线改写方向需要重新论证。** 后续应先用调用次数、每日输入子集大小和各派生步骤的分段计时证明实际成本构成，再决定缓存、增量化或算法改写；本批没有实施任何优化。
