# 阶段一：合成账本生成器

## 1.1 目录与文件

新建顶层目录 `benchmarks/`，不放进 `src/`，避免触发既有的源码结构守卫。建议布局：

```
benchmarks/
  README.md                       用途、怎么跑、结果怎么读
  generator/
    deterministicRng.ts           固定种子伪随机
    syntheticLedger.ts            账本生成器
    syntheticLedger.test.ts       生成器自测
  measure/
    nodeMetrics.ts                M-2 / M-7 / M-8
    browserMetrics.ts             M-1 / M-3 / M-4 / M-5 / M-6
    filePickerStub.ts             浏览器文件选择接口替身
    report.ts                     结果格式化
  results/                        运行产物，不入库
```

`.gitignore` 新增 `/benchmarks/results/` 以及任何生成账本的扩展名与路径。

## 1.2 随机性要求

- 必须实现**确定性伪随机**，不得使用 `Math.random`。
- 同一种子、同一档位，连续两次生成的账本必须逐字段完全相同。
- 种子作为参数传入，默认种子写死在代码中并在 `README.md` 记录。

## 1.3 档位与结构比例

| 档位 | 交易笔数 |
| --- | --- |
| `S-100` | 100 |
| `S-1K` | 1,000 |
| `S-10K` | 10,000 |
| `S-100K` | 100,000 |
| `S-1M` | 1,000,000 |

以交易笔数为基准，其余事实按比例生成：

| 事实种类 | 比例 |
| --- | --- |
| 现金事件 | 约 0.4 |
| 价格快照 | 约 0.15 |
| 资产转入转出 | 约 0.05，四种类别都必须出现 |
| 资产种类 | 10～20 种 |

时间跨度随档位放大，保持每日事实密度合理，不得把全部事实堆在少数几天。

资产代号使用明显虚构的名称。

## 1.4 生成器必须满足的账本约束

生成结果必须能通过账本自身的完整校验，一条都不能被拒绝。实现时需要在生成过程中维护一份运行态持仓，据此约束后续事实：

- 卖出数量不得超过当时总持仓，且交易所位置数量必须足够
- 内部划转与外部转出的 `数量 + 链上手续费` 不得超过来源位置数量
- 外部转入与白拿必须带单价；内部划转与外部转出不得带单价
- 原因与类别必须匹配
- 现金事件不得使余额进入不被允许的状态
- 全部事实时间不得晚于生成时设定的「今天」
- `ledgerSchemaVersion` 与当前正式版本一致

## 1.5 输出形式

生成器至少提供两种输出：

1. **内存中的账本对象**，供 Node 层量尺直接使用
2. **明文备份文件**，供浏览器层量尺通过产品自身的导入流程装载

## 1.6 阶段一测试合同

| 编号 | 断言 |
| --- | --- |
| T1-01 | 同一种子同一档位连续生成两次，结果逐字段完全相同 |
| T1-02 | `S-100` 与 `S-1K` 生成的账本通过账本自身完整校验，无一条被拒绝 |
| T1-03 | 生成结果的事实比例落在 1.3 节规定范围内 |
| T1-04 | 四种资产转入转出类别在 `S-1K` 中均出现至少一次 |
| T1-05 | 不同种子生成的账本不相同 |
| T1-06 | 生成的账本能被产品的持仓重放与现金重放完整处理而不抛错 |
| T1-07 | 全部事实时间均不晚于设定的「今天」 |

`S-10K` 及以上档位的校验因耗时较长，不进默认测试，只在跑基线时验证一次并记入 `03C`。

## 2.4 根因验证（本阶段最重要的一项）

必须显式计算并在报告中给出：

```

```

**若该比值约等于 N**，即从数字上证实「历史曲线按天重复重放整本账本」这一根因，04 批的算法改写方向成立。

**若明显不等于 N**，说明根因判断有误。此时必须在 `03C` 中如实记录实际比值与推测原因，并明确写出「04 批的历史曲线改写方向需要重新论证」。**不得为了让结论好看而调整测量方式。**

# 阶段三：浏览器层量尺

## 3.1 量什么

| 编号 | 指标 | 操作定义 |
| --- | --- | --- |
| M-1 | 冷启动时间 | 从选定已有账本文件、输入密码，到首页可交互 |
| M-3 | 写入延迟 | 在记账页提交一笔新交易，到界面完成更新 |
| M-4 | 查询延迟 | 在交易页按日期筛选，到列表完成更新 |
| M-5 | 页面切换延迟 | 记账→首页、首页→记账、记账→交易、交易→记账 四个方向 |
| M-6 | 单字符输入延迟 | 价格输入框输入一个字符、删除一个字符 |

## 3.2 新增依赖

- 加入 Playwright 作为**开发期依赖**，并在 `README.md` 写明首次使用需要单独安装浏览器二进制。
- 不得成为运行时依赖，不得进入 production 打包产物。
- 提供独立 npm 脚本，例如 `bench:browser`，默认不随 `npm test` 运行。

## 3.3 文件选择接口替身（本阶段的关键障碍）

**障碍**：产品通过浏览器原生文件选择框打开与新建账本。浏览器自动化无法操作操作系统的原生对话框。

**唯一允许的解法**：在测量脚本中，于页面脚本执行之前替换掉浏览器提供的文件选择接口，使其返回由脚本掌握的内存文件句柄。

| 项目 | 规则 |
| --- | --- |
| 替换位置 | **只在测量脚本内**，通过在页面初始化前注入脚本实现。产品代码一行不改 |
| 被绕过的范围 | 仅「弹出系统对话框让人选文件」这一步 |
| 必须仍然真实的部分 | 密码校验、密钥派生、加密与解密、文件读写、版本校验、账本装载、页面渲染，全部走真实产品代码 |
| 替身必须实现 | 产品实际调用到的全部句柄能力，包括读取文件、创建可写流、写入、关闭、权限查询与申请 |
| 绝对禁止 | 在产品中加入任何测试开关、环境变量后门或跳过校验的分支 |

**若该解法被证明不可行**：允许降级交付，本批只交付 Node 层，M-1／M-3～M-6 记为「未取得」。`03C` 必须写明失败的具体原因、已尝试的方案、以及建议的后续路径。**降级是允许的，开后门不允许。**

## 3.4 必须遵循的测量场景

为保证测的是真实产品路径，装载账本必须走产品自身的正常流程：

1. 通过替身的「另存为」接口新建一个空账本文件，设置密码
2. 通过产品的导入流程，导入阶段一生成的明文备份
3. 在该状态下测量 M-3、M-4、M-5、M-6
4. 关闭页面后重新打开，通过替身的「打开」接口选中同一文件、输入密码，测量 M-1

不得跳过导入直接注入账本数据，那样测不到真实的装载与解密成本。

## 3.5 采样与环境

- 采样次数与阶段二相同。
- **每项指标必须分别在开发模式与 production 模式下各记录一组。** 两组数字分开呈现，严禁互相解释。
- `S-100K` 档允许某些指标记为超时，须写明超时阈值。

| T3-01 | 替身能让产品在无人操作的情况下完成新建账本、设置密码、导入备份的完整流程 |
| T3-02 | 密码错误时产品仍然拒绝，证明替身没有绕过密码校验 |
| T3-03 | 五项指标在 `S-100` 档各取得 10 次有效采样 |

## 4.2 结果呈现要求

## 4.3 必须回答的六个问题

`03C` 中必须给出明确答案：

1. 全账本盈亏计算一遍，各档分别要多久？
2. 历史曲线构建时间与单次全量重放时间的比值，是否约等于区间天数？根因是否成立？
3. 开发模式相对 production 的额外开销倍数是多少？卡顿能在多大程度上归因于开发模式？
4. 从哪一个档位开始，单字符输入延迟超过 100 毫秒？
5. 从哪一个档位开始，页面切换延迟超过 200 毫秒？
6. `S-100K` 与 `S-1M` 档，产品在哪一步先失效？是打开、是渲染，还是计算？
