- 轨道：长期账本产品 `main`
- 状态：产品定义已确认；执行合同见 `05B`

## 结论

本批只做一件事：**交易页的流水表改为分页，每页 100 条。**

04 批解决的是"同一件事算了很多遍"，本批解决的是"看不见的东西也画了出来"。10⁴ 档一次页面切换耗时 2,345.594 ms，其中约 1,504 ms 是重算（04 批负责），剩下约 703～841 ms 是渲染，**这部分 04 批碰不到，`04A` 2.2 的 M-5 ≤ 200 ms 通过线光靠 04 批达不到。**

**本批不做虚拟化，不做图表降采样，不卸载非活动工作区，不改文件格式与任何版本号。** 理由见第五节，三项都有明确的证据支撑，不是省事。

真实账户金额与持仓数量一律不写入本文件及任何开发日志，全文只使用虚构数据。

### 1.5 贵在渲染，不在计算——有一组干净的对照

`04C-1` 第 4.2 节，10⁴ 档 production，同一个交易页：

| 动作 | 中位数 |
| --- | ---: |
| M-5 记账→交易（不筛选，全部渲染） | 2,345.594 ms |
| M-5 记账→首页（同样要跑全部派生，但页面元素少） | 1,642.792 ms |
| M-4 在交易页改一次日期筛选（筛后只剩一天的行） | 41.137 ms |

三个数字放在一起，结论非常清楚：

- **计算的活一点没少**：改筛选同样要把 14,000 条过一遍（`TransactionsWorkspace.tsx:492` 的 `filteredItems`），只花 41.137 ms。
- **切到首页和切到交易页的差额 702.802 ms，就是那张大表多出来的渲染成本。**
- 派生计算的部分由 Node 层独立测得为 1,504.608 ms（`04C-1` 4.1 的 M-2），与 M-5 记账→首页的 1,642.792 ms 同一量级，互相印证。

由此可估出**每个 DOM 元素的渲染成本约 1.9～2.3 微秒**：

```
下界：702.802 ms ÷ 14,000 行 ÷ 26 元素 = 1.93 微秒
上界：(2,345.594 − 1,504.608) ms ÷ 14,000 行 ÷ 26 元素 = 2.31 微秒
```

**该系数是本批全部容量估算的基础，`05C` 须用改动后的实测数字复核它。**

### 1.6 10⁵ 比 10⁴ 慢得远超 10 倍

按 1.5 的系数线性外推，10⁵ 档 3,640,000 个元素应耗时约 7.0 秒。**`04C-1` 第 5.2 节实测为"打开后导航至交易页 30 秒超时"，dev 与 production 均如此。**

10 倍的行数花了远超 10 倍的时间，说明存在超线性因素。已定位到一条：

`src/features/activity/ActivityTable.tsx:148`：

```
<table className="block w-full text-left text-sm sm:table">
```

全库无 `table-fixed`／`table-layout`（已搜索确认），即宽屏下使用浏览器默认的**自动列宽**。自动列宽要求浏览器量完**所有行**的所有单元格才能确定每一列的宽度，行数越多，这一步的开销涨得比行数更快。

**本批不改这一点**，理由见 5.4。

## 二、产品决定

| 项目 | 决定 |
| --- | --- |
| 方案 | **分页**。本批不实现虚拟化 |
| 每页行数 | **100 条**，必须定义为单一具名常量，改动该数字不得牵动任何其他代码 |
| 默认视图 | **全部记录的第 1 页**。筛选条件的默认值保持现状全开，一个字不改 |
| 排序 | 倒序，最新在前。**这已是现状**（`src/features/activity/activityService.ts:41` 使用 `compareLedgerActivityItemsDescending`），本批不改动排序逻辑 |
| 筛选栏 | 保持现状。位置、控件、默认值均不动 |

### 2.1 每页 100 条的依据

按 1.5 的系数：

| 每页行数 | 元素数 | 估算渲染耗时 | 相对 M-5 的 200 ms 通过线 |
| ---: | ---: | ---: | --- |
| 50 | 1,300 | 2.5～3.0 ms | 余量 98% |
| **100** | **2,600** | **5.0～6.0 ms** | **余量 97%** |
| 200 | 5,200 | 10.0～12.0 ms | 余量 94% |
| 500 | 13,000 | 25～30 ms | 余量 85% |
| 现状（10⁵，不分页） | 3,640,000 | > 30 秒 | 超标 150 倍以上 |

100 与 200 的差别是 5 毫秒与 11 毫秒，**在人的感知阈值以下，二者体感完全相同**。选 100 是取更大的安全余量，不是因为 200 有风险。

**该系数取自 14,000 行的拥挤状态，自动列宽的全局牵制最严重；100 行时每个元素只会更快，故上表为保守上界。**

### 2.2 为什么要求它是具名常量

产品负责人当前无法确知 100 条用起来是否顺手（真实账本约 640 条，100 条一页即 7 页）。把它固定为单一具名常量之后，**将来调整只需改一个数字，不需要重新评估、重新测试任何行为。** 这条是硬性要求，不是建议。

## 三、四种用法的行为合同

产品负责人明确：四种用法全部都要支持。**分页最容易出错的地方就在这里，以下逐条为硬性合同。**

| 编号 | 场景 | 必须的行为 |
| --- | --- | --- |
| **U-1** | 看最近几天记了什么 | 进入交易页即为第 1 页，最新的在最上面。不得需要任何额外操作 |
| **U-2** | 改筛选条件（时间／资产／类型／日期） | **回到第 1 页。** 因为结果集变了，留在原页码可能落到空白 |
| **U-3** | 删除一条流水 | **停留在当前页。** 不得跳回第 1 页。若删完当前页变空且不是第 1 页，退到前一页 |
| **U-4** | 从首页热力图跳到某一天 | **自动翻到包含那一天的页**，再执行既有的滚动定位与高亮。跳转后的页码必须与该日期在当前筛选结果中的位置一致 |

补充合同：

| 编号 | 约束 |
| --- | --- |
| U-5 | 展开的详情行只作用于当前页；翻页后收起，不跨页保留 |
| U-6 | 页面必须显示当前位置与总量，形如"共 640 条，第 1 / 7 页"。用户任何时候都要知道自己在哪、还有多少没看 |
| U-7 | 分页只作用于渲染。**筛选、排序、计算、删除的既有逻辑与结果一个字不改**；同样的筛选条件下，翻遍所有页得到的集合必须与改动前完全相同 |
| U-8 | 结果为空时保持现有的空状态提示（`ActivityTable.tsx:160-168`），不显示翻页控件 |

**U-4 是本批技术上最难的一条**，因为现有的定位实现（`ActivityTable.tsx:127`／`:132` 的 `scrollIntoView`）依赖目标行已被渲染。分页后必须先算出目标日期落在第几页、翻过去、等该页渲染完成，再执行定位。`05B` 对此另有测试要求。

## 五、本批不做的事

| 编号 | 不做 | 理由 |
| --- | --- | --- |
| N-1 | **虚拟化** | 每页 100 行的渲染成本已降到约 5 ms，虚拟化能优化的空间已不存在。且现有实现有三处硬障碍：行高不固定（`ActivityTable.tsx:188` 窄屏为 `grid`、宽屏为 `sm:table-row`，加上不定高的展开详情行）、定位依赖 `scrollIntoView` 须整体重写、项目当前只有 5 个运行时依赖（`decimal.js`、`echarts`、`next`、`react`、`react-dom`），引入虚拟化库或手写实现均代价显著 |
| N-2 | **图表降采样** | 见 1.1，图表恒为 2 个元素且数据点本就少 |
| N-3 | **卸载非活动工作区**（**有条件**） | 默认不做：分页后交易页 DOM 降到约 2,600 元素，"始终挂载"的代价预期随之消失。**但 04 批实测证明未分页时该代价真实存在且污染全部四个方向，故本项改为条件触发**——分页后 M-5 任一方向超过 200 ms 即必须在本批内补做。详见 5.1.1 与 5.1.2 的 W-1～W-5 |
| N-4 | `table-layout: fixed` | 见 5.4 |
| N-5 | 分块存储、文件格式、任何版本号 | 属 06 批 |
| N-6 | 改动任何派生计算的数值、精度或校验 | 04 批的等价性快照继续是裁判 |

### 5.1 为什么不卸载非活动工作区

`000_W15-05与06批前期调查笔记` 1.2／1.3 提出：五个工作区用 CSS 隐藏而非卸载（`src/app/TransactionsWorkspace.tsx:527` 的 `className={active ? "grid min-w-0 gap-4" : "hidden"}`），改为真正卸载需先把跨页面状态提升出去。

只读核查发现**该提升已经完成**：

- `src/app/useLedgerWorkspaceSession.ts:112-115` 已持有 `tradeDraft` 与 `priceDraft`，位于五个工作区之上
- `src/features/trades/TradeForm.tsx:190` 为 `const form = draft ?? localForm;`，即优先使用已提升的草稿
- `src/app/TransactionsWorkspace.tsx:306` 为 `if (!active) resetPageState();`，交易页切走时本就清空全部筛选与展开状态

**因此卸载工作区在技术上已经很便宜。**

### 5.1.1 04 批的实测推翻了「挂着不要钱」这一判断（2026-08-29 补）

本节初稿写有「分页后交易页只剩约 2,600 个元素，让它挂着的成本可以忽略」。**04 批 P-4 完成后的实测证明，在未分页的状态下挂着是明确要钱的，且四个方向都在付。**

`04C` 3.4 的两轮未提交诊断（10⁴ 档 production，中位数 ms）：

| 做法 | 记→首 | 首→记 | 记→交 | 交→记 |
| --- | ---: | ---: | ---: | ---: |
| 只做 04 批合法的派生缓存 | 402.917 | 392.103 | 1,199.916 | 578.667 |
| 额外缓存那 10,000 行 React 结果 | 254.132 | 317.217 | 972.823 | 323.824 |
| 再加浏览器原生可见性布局复用 | 245.851 | 271.953 | 1,029.002 | 421.949 |

**「记账→首页」这一格最说明问题**：首页根本不含流水大表，但只要把大表的 React 结果缓存起来，它就从 402.917 降到 254.132 ms。**说明那 400 毫秒里有相当一部分，是 React 在走那 14,000 行始终挂载的隐藏行。**

「记账→交易」在两轮诊断后仍为 972.823～1,029.002 ms，几乎不动——那是大表进入可见状态时的真实布局成本，只能靠减少行数解决，正是本批分页要做的事。

### 5.1.2 处理方式（硬要求）

分页把行数从 14,000 降到 100，是 140 倍的削减，**预期足以让上述两部分成本同时消失**。但这是预期，不是实测。

| 编号 | 要求 |
| --- | --- |
| W-1 | 分页核心完成后，**立刻测 M-5 四个方向**（10⁴ 档 production），不得等到阶段三统一测 |
| W-2 | **四个方向全部 ≤ 200 ms**：本项永久关闭，`05C` 写明关闭依据 |
| W-3 | **任何一个方向 > 200 ms：必须在本批内接着做「卸载非活动工作区」，不得推迟到下一批。** 这是 `04A` 修订 D 转移过来的承诺，后面没有批次可以再推 |
| W-4 | 触发 W-3 时，须先把 `RecordWorkspace` 的 `recordTarget`（`RecordWorkspace.tsx:105`）与 `HomeWorkspace` 的 `detailsOpen`（`HomeWorkspace.tsx:57`）提升到会话 hook；`SettingsWorkspace` 的 tab 与确认输入框内容**故意丢弃**（清空账本类危险操作的确认框，切走即清更安全）。交易页无需处理，其状态本就在 `resetPageState()` 中清空 |
| W-5 | 触发 W-3 时不得因此改动 `TransactionsWorkspace.tsx:306` 的既有调用（B-06 仍然有效），只允许在其中增加需要重置的项 |

**W-3 是本批与 04 批之间的正式交接点。** `04A` 修订 D 把 M-5 ≤ 200 ms 从 04 批转移到本批，转移的前提是本批必须真正达到它。

### 5.2 `resetPageState` 不得删除

`src/app/TransactionsWorkspace.tsx:306` 的 `if (!active) resetPageState();` 是**安全设计，不是待优化项**。删除它会导致筛选条件在离开页面后仍然残留，用户下次进入时看到的不是全部流水而是上次的筛选结果，属于行为倒退。`05B` 将其列为硬性禁止。

### 5.3 筛选逻辑不得动

`04C-1` 实测筛选仅耗 41.137 ms，**是当前唯一已经达标的交互**。`TransactionsWorkspace.tsx:488`／`:492` 的两个 `useMemo` 已正确缓存，`allItems` 只在 `ledgerData` 变化时重建。本批不得以"顺手优化"为由改动这两处。

### 5.4 为什么不改 `table-layout`

自动列宽的全局牵制（见 1.6）在 140,000 行时是真实的超线性来源，但在每页 100 行时只需量 100 行，代价可忽略。改为 `fixed` 会改变列宽的视觉表现，属于界面改动而非性能改动，**不应混进性能批次**。本节记录该发现，供将来若真需要更大每页行数时参考。

## 六、待定项：是否新增"序号"列

当前交易页表头为六列：日期、类型、资产、金额、手续费、操作（`ActivityTable.tsx:148-157`），**没有序号列。**

分页之后，程序天然知道每一行的绝对位置，因此可以低成本地提供"第 601–640 条，共 640 条"这类位置信息。

| 方案 | 说明 |
| --- | --- |
| A（默认） | 只按 U-6 在表格外显示"共 N 条，第 X / Y 页"，不新增列 |
| B | 在 A 之外，另加一列显示每行的绝对序号 |

**本项由产品负责人在 `05B` 交付执行前确认。未确认时按 A 执行。** 选 B 属于新增界面功能，须在 `05A` 补充修订后执行，不得由执行者自行决定。
