### 二、论文素材：为什么不采用 SQLite-WASM 作为存储层

**本节是论文 System Design／Discussion 章节的素材，不是执行结论。** 记录于此以免日后重新推导；正式写入论文前须重新验证技术细节。

**问题的由来。** 产品负责人提出：企业级系统普遍使用 SQL 数据库，是否应改用 SQL；并追问 IndexedDB 能否做到同样的事、SQL 能否加密。

**事实基础。** 当前 IndexedDB 在本产品中**不是数据库**，只保存一条连接记录（`connectionFormatVersion`、`handle`、`expectedFileId`），用于记住上次打开的是哪个 `.lftl` 文件——浏览器不允许网页记住磁盘路径，文件句柄只能存在 IndexedDB 中。账本本身全部存于磁盘上的 `.lftl` 加密文件。IndexedDB 没有查询语言、不支持 JOIN，确实做不到 SQL 那类操作。

**SQLite-WASM 的吸引力是真实的。** SQLite 可编译为 WASM 在浏览器内运行，且「一个文件即一个数据库」与本产品的单文件可携带哲学不冲突。更关键的是它按页写盘，改一笔只重写相关页，天然具备本项目 06 批想要的增量写入能力。

**否决理由（性能，不是安全）。** 本系统要求静态加密。与 SQLite 组合只有两条路：

1. **整个数据库文件外套一层加密**——打开时整体解密、保存时整体加密写回。**SQLite 的页级写入优势被整包加密完全抵消，等于没换。**
2. **让 SQLite 自身做页级加密**（SQLCipher 一类）——可保住优势，但其 WASM 环境下的构建成熟度、密钥管理与页级加密正确性均需独立验证，且论文既有的 `AES-256-GCM 加密静态存储` 安全论证须整体重写。

因此结论是：**在静态加密这一硬约束下，SQLite-WASM 不能带来它在无加密场景下的增量写入收益**，故自行设计分块加密格式，在保留单文件可携带性的同时获得增量写入能力。

**必须避免的错误论证（重要）。** 讨论中一度出现「整包加密等于没加密，因为解密后全在内存，攻击内存即可读取全部记录」的推论。**该推论不能写入论文**，理由有二：

- **当前 `.lftl` 设计做的是同一件事**——打开账本时整本解密进内存，`ledgerData` 全程驻留运行时。若以此否定路线 1，等于同时否定本系统自身的设计，评审会立即指出这一矛盾。
- **静态加密（encryption at rest）保护的本来就不是运行中的页面**，而是磁盘上的文件：设备失窃、备份盘、同步目录（iCloud／Dropbox）被他人读取、他人翻看硬盘。这些是真实威胁，加密确实防住了。`04A-毕业论文执行范围调整` 已明确写下该威胁模型：「本轮威胁模型只覆盖浏览器本地静态数据保护，不声称可以抵御已控制运行时、恶意扩展或用户主动导出的明文泄露。」

**故否决 SQLite 的正确论证是性能论证，不是安全论证。** 分块存储同样不改善内存暴露面——派生计算本就需要整本账本在内存中。这一点在论文中应如实说明，不得暗示分块带来了安全收益。

**附带结论：SQL 治的不是本项目的病。** SQL 的强项是数据大到无法全部载入内存、需要靠索引精确检索。本产品是整本读入内存、纯函数计算，10⁵ 档全账本派生仅 167 ms；瓶颈自始至终在存盘（M-3 15,979 ms），不在查询。

### 四、两条产品决定

**数字表示法：全部语言统一用空格作千分位、点作小数点（`1 234 567.89`）。** 产品负责人裁决。理由是同一串 `1,234` 在英文里是一千二百三十四、在匈牙利语里是一点二三四，**差一千倍**，在记钱的软件里是能让人真赔钱的歧义；国际标准（ISO 31-0／SI）推荐空格正是为避开此问题。同时纠正一处常见误解：**中文金融与会计场合的标准同样是三位一撇**，四位一组（万、亿）属口语与摘要场景，不用于账本表格。该决定亦体现「有意识地不做本地化」，是论文中可用的设计判断。

**14 处排序确定性：06 批之后作为独立小批次修复。** 其中 `cashReplay.ts:102` 在计算现金余额的路径上。诚实标注：比较对象是 `2026-08-31`、`BTC` 这类纯 ASCII，实际出错概率很低，**未实测其会出错**；但现状是「碰巧没事」而非「设计上不会有事」，且同文件内已有 3 处显式写了 `"en"`，说明当初想到了却没想全。修复时必须跑 04 批冻结派生快照，确认排序结果一字未变。

**去掉 base64 一项就砍掉近一半**，与 33% 体积膨胀加巨型字符串的预估相符。

### S-2 开工前第四次停止申报

执行者指出：S-2 要求 `previous` 只保留变化部分且新版写坏后仍能完整恢复，但单段 AES-GCM 密文的认证是全有全无的——`current` 认证失败时任何 delta 都没有可信基底；要复用未损坏部分就必须先切成可独立认证的单元，**那正是 S-3**。因此请求裁决：合并 S-2／S-3 并撤销分别归因，或给出另一种表示。

**该推理在其自身前提下完全正确。** 但它只穷尽了「`previous` = current 的差异」这一类实现。

### 裁决：S-2 不合并，但重新定义为「不重写」而非「存差异」

存在第三种实现，既达成 S-2 的目标又完全不需要分块：**`previous` 不是「差异」，而是「上一次写下去、这次一个字节都不去碰的那块区域」。**

体区改为固定槽：`current` 占一个体槽，`previous` 是另一个体槽的引用；普通保存只写新密文所在的体槽与一个头槽，`previous` 槽的字节一个都不重写。**恢复单元是整本 blob，自带独立 IV 与认证标签，与另一槽完全独立**——`current` 认证失败时直接从 `previous` 槽独立解密恢复，不需要 delta，也不需要块。

**这正是执行者自己在阶段一 F-1 中写下的槽机制**（「两个头槽轮换写入……体区按固定槽定位……普通保存只写新密文所在体槽及一个固定头槽」）。S-1 实现采用了连续布局的简化形态，两者的差距即为 S-2 的工作内容。

两步的界线因此清晰：**S-2 把「写两本」变成「写一本」；S-3 把「写一本」变成「写一块」。** 收益可分别测量，分别归因的要求保留。

### 更正：错在合同措辞，不在执行者

`06A` 1.2 把 S-2 写作「`previous` 不再存整本，**只保留发生变化的块的旧版本**」——**在块尚不存在的阶段就使用了「块」**，逻辑上预设了 S-3。S-2 的真实目标始终是 `06A` 0.2 层 C 所述的「去掉存两代造成的双倍写入」，不是「用 delta 表示 previous」。

**这是继修订 B 之后第二次由产品负责人的合同措辞导致的停摆。** 两次的共同教训：**合同里描述某一步时，不得使用只有在后续步骤完成后才存在的概念。**

### 实测确认现状

`ledgerFileContainerV3.ts:153-155` 每次保存执行 `bytes.set(previousCiphertext, offset)`，把上一代完整密文重新拷贝；`ledgerFileHandleAdapter.ts:329-353` 以 `keepExistingData: false` 整file重写。**因此当前仍在每次写两份完整账本**，层 C 的成本一分未减，S-1 的 −48.31% 全部来自去 base64 与去巨型字符串。

### 新增的安全约束

S-2 的局部写入会触及既有原子写与复读校验机制，**该机制是本产品对用户数据最重要的安全承诺，不得为性能让路**。故新增：S2-E 要求逐项论证改动后既有保存合同一条不弱；S2-F 必须证明写坏 `current` 槽后仍能从 `previous` 槽完整恢复；S2-G 必须证明普通保存后 `previous` 槽字节与保存前完全一致。两条硬测试均须通电检查。
