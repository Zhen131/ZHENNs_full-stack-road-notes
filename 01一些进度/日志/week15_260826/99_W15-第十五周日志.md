### 二、论文素材：为什么不采用 SQLite-WASM 作为存储层

**本节是论文 System Design／Discussion 章节的素材，不是执行结论。** 记录于此以免日后重新推导；正式写入论文前须重新验证技术细节。

**问题的由来。** 产品负责人提出：企业级系统普遍使用 SQL 数据库，是否应改用 SQL；并追问 IndexedDB 能否做到同样的事、SQL 能否加密。

**事实基础。** 当前 IndexedDB 在本产品中**不是数据库**，只保存一条连接记录（`connectionFormatVersion`、`handle`、`expectedFileId`），用于记住上次打开的是哪个 `.lftl` 文件——浏览器不允许网页记住磁盘路径，文件句柄只能存在 IndexedDB 中。账本本身全部存于磁盘上的 `.lftl` 加密文件。IndexedDB 没有查询语言、不支持 JOIN，确实做不到 SQL 那类操作。

**SQLite-WASM 的吸引力是真实的。** SQLite 可编译为 WASM 在浏览器内运行，且「一个文件即一个数据库」与本产品的单文件可携带哲学不冲突。更关键的是它按页写盘，改一笔只重写相关页，天然具备本项目 06 批想要的增量写入能力。

**否决理由（性能，不是安全）。** 本系统要求静态加密。与 SQLite 组合只有两条路：

1. **整个数据库文件外套一层加密**——打开时整体解密、保存时整体加密写回。**SQLite 的页级写入优势被整包加密完全抵消，等于没换。**
2. **让 SQLite 自身做页级加密**（SQLCipher 一类）——可保住优势，但其 WASM 环境下的构建成熟度、密钥管理与页级加密正确性均需独立验证，且论文既有的 `AES-256-GCM 加密静态存储` 安全论证须整体重写。

因此结论是：**在静态加密这一硬约束下，SQLite-WASM 不能带来它在无加密场景下的增量写入收益**，故自行设计分块加密格式，在保留单文件可携带性的同时获得增量写入能力。

**必须避免的错误论证（重要）。** 讨论中一度出现「整包加密等于没加密，因为解密后全在内存，攻击内存即可读取全部记录」的推论。**该推论不能写入论文**，理由有二：

- **当前 `.lftl` 设计做的是同一件事**——打开账本时整本解密进内存，`ledgerData` 全程驻留运行时。若以此否定路线 1，等于同时否定本系统自身的设计，评审会立即指出这一矛盾。
- **静态加密（encryption at rest）保护的本来就不是运行中的页面**，而是磁盘上的文件：设备失窃、备份盘、同步目录（iCloud／Dropbox）被他人读取、他人翻看硬盘。这些是真实威胁，加密确实防住了。`04A-毕业论文执行范围调整` 已明确写下该威胁模型：「本轮威胁模型只覆盖浏览器本地静态数据保护，不声称可以抵御已控制运行时、恶意扩展或用户主动导出的明文泄露。」

**故否决 SQLite 的正确论证是性能论证，不是安全论证。** 分块存储同样不改善内存暴露面——派生计算本就需要整本账本在内存中。这一点在论文中应如实说明，不得暗示分块带来了安全收益。

**附带结论：SQL 治的不是本项目的病。** SQL 的强项是数据大到无法全部载入内存、需要靠索引精确检索。本产品是整本读入内存、纯函数计算，10⁵ 档全账本派生仅 167 ms；瓶颈自始至终在存盘（M-3 15,979 ms），不在查询。
