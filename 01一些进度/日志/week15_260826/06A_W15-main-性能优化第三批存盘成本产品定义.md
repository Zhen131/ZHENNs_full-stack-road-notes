## 结论

本批只做一件事：**把「保存一次账本」的成本，从「跟账本总量成正比」改为「跟这次改动量成正比」。**

05 批把渲染的病治完了——同时渲染的元素数四档均在 3,000 上下，与账本规模完全脱钩。**10⁵ 档仍判不可用，原因已 100% 转移到写入：记一笔 15,979 ms。**

**目标：10⁵ 保底达标，10⁶ 尽力尝试。** 若 10⁶ 做不到，最低必须保住 10⁵。论文原文把 >10⁶ 列在 future work，做到即为超额加分项，做不到不算失败，**但不得为凑 10⁶ 而放宽 10⁵ 的通过线**。

真实账户金额与持仓数量一律不写入本文件及任何开发日志，全文只使用虚构数据。

## 零、先看清楚现在保存一次发生了什么

以下每一条都来自 2026-08-31 对 `main@8df62d8` 的只读代码核查，附文件与行号。**后续改动代码后需重新核对行号。**

### 0.1 七个步骤

| 步 | 做什么 | 代码位置 | 产物 |
| ---: | --- | --- | --- |
| 1 | 账本对象序列化成 JSON 文字 | `ledgerFileCrypto.ts:88` 的 `serializedPayload` | 巨型字符串① |
| 2 | UTF-8 转成字节 | `ledgerFileCrypto.ts:113` | 字节数组 |
| 3 | AES-GCM 加密 | 同上 | 密文字节 |
| 4 | 密文转成 base64 文字 | `ledgerFileCrypto.ts:118` `bytesToBase64Url` | 巨型字符串②（比①大 33%） |
| 5 | 装进含 `current` 与 `previous` 的结构 | `ledgerFileContract.ts:62-63` | 两份完整密文并存 |
| 6 | 整个结构再序列化成 JSON 文字 | — | 巨型字符串③（内含两份②） |
| 7 | 一次性写入文件 | `ledgerFileHandleAdapter.ts:21` `write(data: string)`、`:327` | 落盘 |

### 0.2 三层叠加的成本

| 层 | 症状 | 触发点 |
| --- | --- | --- |
| **A. 整本序列化成一根字符串** | 10⁶ 档在明文备份序列化阶段抛 `RangeError: Invalid string length`，RSS 达 2,808,037,376 字节 | JavaScript 单条字符串上限 `0x1fffffe8` = 536,870,888 字节 |
| **B. 每次保存重写整本** | 耗时与账本总量成正比 | 10⁴ 档 1,722 ms、10⁵ 档 15,979 ms |
| **C. 存两代** | 上述成本 ×2 | `ledgerFileContract.ts:62-63`，`current` 与 `previous` 各是一份**整本**密文 |

按 10⁵ 档明文约 69,369,153 字节估算峰值内存中的字符串：字符串① 约 69 MB、字符串② 约 92 MB、上一版 base64 约 92 MB、字符串③ 约 184 MB——**约 440 MB 的字符串，服务于一个 69 MB 的账本**。上述除明文字节数外均为按 base64 膨胀率推算，**未实测**，`06C` 须给出实测值。

### 0.3 base64 不是多余步骤，是「文件为纯 JSON」这一决定的必然代价

加密输出是原始字节（值域 0～255），其中包含 `0`、`10`、`34`、`92`、`255` 等无法直接放进 JSON 字符串的值。**只要容器是纯 JSON，就必须把字节编码成安全文字，base64 是标准做法，代价固定为 +33%。**

因此「去掉 base64」等价于「容器不再是纯 JSON」，二者是同一个决定。

**⚠️ 该决定只影响最外层容器。** 内层 payload（`DecryptedLedgerPayloadV4`，含 `ledgerData`）仍是 JSON、仍是 UTF-8、`note` 等自然语言字段与 `ledgerSchemaVersion = 4` **一个字不动**。base64 编码的是**加密之后**的密文，那一层已不存在「文字」概念，与账本里写的是中文、英文还是匈牙利语无关。

### 0.4 双代保护为什么存在

纯浏览器没有操作系统级的同目录临时文件、稳定文件锁与原子替换（该边界已长期记录在开发状态的「阻塞与风险」中）。`previous` 是浏览器环境下对原子性的替代手段：新版写坏时仍可能从上一版恢复。

**它的设计意图正确，实现方式最笨**：改动可能只有一笔，却要各存一份完整账本。

## 一、产品决定

### 1.1 第零步：补黄金样例（不动任何版本号，必须最先）

**这是本批唯一「晚做就永远做不了」的事。**

`fileFormatVersion` 一旦从 2 升到 3，代码将**永远无法再产出版本 2 的 C 文件**。届时编写迁移器只能凭推测还原旧结构，推错即造成无人能发现的静默数据损坏。规则依据见根 `AGENTS.md`「版本分层与迁移」。

三份产物：

| 编号 | 产物 | 覆盖 | 说明 |
| --- | --- | --- | --- |
| G-1 | 一份 `fileFormatVersion = 2` 的 C 文件样例 | 同时覆盖 `cryptoVersion = 1` | 加密文件，需固定密码；**该密码必须写入索引 README**。样例内全为虚构数据，密码不是秘密而是钥匙 |
| G-2 | 一份**有内容的** `ledgerSchemaVersion = 4` B 文件样例 | 交易之间的关系 | 现有 `golden-backup-format-v3-ledger-schema-v4.json` 是 0 笔交易的空壳，测不出卖出扣哪次买入成本、同资产跨位置分布、带链上手续费的转账。**不得修改现有样例**，另行新增 |
| G-3 | `test-fixtures/golden/README.md` 索引表 | 全部样例 | 每份列出：文件名、覆盖的版本组合、加入日期、**覆盖什么情形**、密码（如有） |

**不加时间戳到文件名。** 理由：日期语义不明（创建日？版本发布日？）、文件名变长易错、Git 已记录加入日期（`git log --diff-filter=A`）。索引表能承载文件名装不下的「覆盖什么情形」，那才是将来写迁移器时真正要查的信息。

**`backupFormatVersion` 1／2 的样例本批不补。** 产品处于 Alpha，遇低版本一律明确拒绝、不提供迁移，尚未触发补样例的必要性。该缺口登记在 G-3 索引表中，待宣布进入 Beta、开始做迁移时再补。

### 1.2 一次升级 `fileFormatVersion` 2 → 3，内含三件事

三件都改文件格式，因此是**一次版本升级、一个迁移器、一份新黄金样例**，不是三次。

| 编号 | 改什么 | 治哪一层 |
| --- | --- | --- |
| **S-1** | **容器改为「JSON 头 + 原始加密字节」**，不再用 base64 | 层 A（字符串上限）＋体积 −33% |
| **S-2** | **`previous` 不再存整本**，只保留发生变化的块的旧版本 | 层 C |
| **S-3** | **按数量分块**，每满 N 条封一块，只重写变化的块 | 层 B |

**执行顺序为 S-1 → S-2 → S-3，每做完一件单独测一次 M-3**，以便分别归因。不得一口气做完再测。

### 1.3 只升 `fileFormatVersion`，另外三个版本号一律不动

| 版本号 | 本批 |
| --- | --- |
| `fileFormatVersion` | **2 → 3** |
| `cryptoVersion` | **1，不变。** 算法、KDF、迭代次数、密钥长度、标签长度一律不改 |
| `ledgerSchemaVersion` | **4，不变。** 账本数据形状一个字段都不动 |
| `backupFormatVersion` | **3，不变。** B 文件不在本批范围 |

依据：根 `AGENTS.md`「四者不得合并，也不得因为其中一个变化就同步升级其余三个。只升真正变化的那一个。」

**四个版本号必须继续保存在明文外层，永不移入加密载荷。** 新容器的 JSON 头必须能在解密前被读取和判版。

## 二、分块的设计合同

### 2.1 按数量分，不按时间分，不按集合分

| 分法 | 判定 | 理由 |
| --- | --- | --- |
| 按集合（交易一块／现金一块／…） | **否决** | 交易本身占事实总量六成以上，记一笔仍要重写最大的那一块，改善有限 |
| 按时间（每月／每年一块） | **否决** | 月度交易量差异可达数千倍，块大小完全不可控，性能不可预测；空白期还要处理空块 |
| **按数量（每满 N 条封一块）** | **采用** | 块大小均匀可预测；新记录只进「正在装的那一块」；改旧记录只重写它所在的一块；不存在空块 |

### 2.2 块与块之间不建立哈希链

**本产品不是区块链，不得照搬其链式结构。**

区块链把块用哈希串起来，是因为它要在互不信任的分布式网络中让「偷偷改历史」可被所有人检测；连锁失效是它的功能。**本产品没有这样的对手**：文件在用户自己的磁盘上、用用户自己的密钥加密，而 AES-GCM 的认证标签（`tagLength: 128`）已为**每一块**独立提供完整性保护——任何一个字节被改动，该块解密即失败。

因此：**每块独立加密、独立认证，块与块互不引用。改一个旧块，其余所有块一个字节都不必改动。**

**这直接决定了「编辑历史交易」这一功能可行**：改两年前的一笔账 = 重写它所在的一块（N 条），不是重写整本。若某个设计导致该功能不可行，该设计即被否决——**存储格式不得绑架产品功能**。

### 2.3 每块必须有自己的 IV，重写必须换新

**AES-GCM 在同一密钥下重用 IV 会导致明文可被推算，这是安全正确性问题，不是性能问题。**

| 编号 | 硬要求 |
| --- | --- |
| K-1 | 每块持有自己的 IV，长度仍为 12 字节 |
| K-2 | **每次重写某块，必须生成新的 IV**，不得沿用该块上一版的 IV |
| K-3 | 必须有测试证明：同一账本连续保存两次，任意两块之间、以及同一块的两代之间，IV 均不相同 |

K-3 是本批**唯一一条安全性硬测试**，`06C` 必须给出它的实现与通电检查结果。

### 2.4 块内不排序；分块是写入优化，与读取无关

文件只是仓库。程序打开账本时把所有块读出拼在一起，**在内存中排序**。因此：

- 新记录一律进入「正在装的那一块」，与它的日期无关
- 修改旧记录只重写它所在的那一块
- 读取需要全部块，账本本就整本载入内存（10⁵ 档全账本派生仅 167 ms）

**不得以「分块提升了读取性能」或「分块改善了内存暴露面」为由主张收益。** 派生计算本就需要整本账本在内存中，分块在这两方面均无改善；本批的收益完全在写入。该表述同样适用于论文。

### 2.5 每块行数是具名常量

与 `ACTIVITY_PAGE_SIZE` 同理：单一具名常量，调整成本为改一个数字。

初值由实测决定，`06A` 不预先钉死。参考：10⁶ 笔按每块 2,000 条计为 500 块，改一笔重写整本的 0.2%；每块零头（IV 12 字节 + 认证标签 16 字节 + 元数据）约 50 字节，500 块合计约 25 KB，可忽略。**倾向区间 1,000～5,000，须由 `06C` 用实测数据支撑最终取值。**

### 2.6 已知且被接受的情形：稀疏块

删除记录会使某些已封块低于 N 条。个人账本删除罕见，**本批不实现合并整理（compaction）**。该情形须在 `06A`／`06C` 与代码注释中明确登记为已知且被接受，不得假装不存在。将来若确实稀疏，另行立项。

## 五、本批不做的事

| 编号 | 不做 | 理由 |
| --- | --- | --- |
| N-1 | 不改 `ledgerSchemaVersion`、`cryptoVersion`、`backupFormatVersion` | 只升真正变化的那一个 |
| N-2 | 不改任何派生计算的数值、精度或校验 | Q-1 是唯一裁判 |
| N-3 | 不实现块合并整理（compaction） | 见 2.6，已登记为已知情形 |
| N-4 | 不实现虚拟列表 | 05 批已用分页解决渲染，不在计划内 |
| N-5 | 不改 B 文件格式 | B 文件是明文 JSON，不受层 A 之外的问题影响；若 10⁶ 的明文备份导出仍撞字符串上限，如实记录并移交后续批次 |
| N-6 | 不做多语言、不动 `src/app/` 目录结构 | 分别属 07、08 批 |

### 考虑过但没选（论文素材，须在 `06C` 保留）

**SQLite-WASM 作为存储层。** 详见 `99_W15` 2026-08-31 日志（二）。否决理由是**性能，不是安全**：本系统要求静态加密，整包加密会完全抵消 SQLite 页级写入的优势；页级加密方案（SQLCipher 一类）在 WASM 环境下的成熟度不足以支撑既有安全论证。**不得使用「整包加密等于没加密，因为解密后全在内存」这一论证**——当前 `.lftl` 设计做的是同一件事，该论证会同时否定本系统自身。

**Event sourcing／只追加账本。** 永不改历史、只追加修正事件、读取时重放。这是银行与会计系统的成熟做法，动机是法律要求原始记录不可篡改。**本产品否决**：读取需重放全部历史会进一步恶化本已 6,625 ms 的冷启动；一笔交易的真实值散落在多条记录中会导致全部派生计算重写、04 批的 7 个冻结快照全部作废；而它能带来的写入收益，分块存储已经提供。**若将来要做「谁在何时改了什么」的修改历史功能，event sourcing 才是对的工具**，届时另行立项。

**按时间分块。** 见 2.1，因块大小不可控而否决。

## 七、本批产出对论文的作用

1. **一个可量化的贡献点**：写入成本从 O(账本总量) 降为 O(改动量)，有四档实测支撑。
2. **一段有分量的设计理由（design rationale）**：为什么不用 SQLite-WASM、为什么不用 event sourcing、为什么不按时间分块——三条都有明确理由与数据。评审最想看到的不是「我选了 X」，而是「我在 X 与 Y 之间权衡过，理由是 Z」。
3. **一条诚实的安全边界**：分块不改善内存暴露面，静态加密保护的是磁盘上的文件而非运行中的页面。该边界 `04A` 早已写明，本批不得暗示扩大。
4. **10⁶ 若达成**，是超出论文原定 stretch 目标（10⁵）的加分项；**若未达成**，如实写明失败点与规模边界，不虚构。
