# 000_W15｜账本版本分层与迁移策略决策记录

- 日期：2026-08-27
- 适用范围：长期账本产品 `main`，B 文件与 C 文件的全部版本演进
- 状态：已确认，长期有效，不随单批开发失效

## 结论

四个版本号各自独立演进，不合并、不同步升级。当前处于 Alpha，遇到低版本一律明确拒绝，不做迁移。进入 Beta 之前切换为“读旧、写新”的单向迁移链，切换时点由用户明确宣布。

**从本次升 V4 起立即执行一条前置动作：每升一次版本，同时把该版本的黄金样例文件存入测试夹具。** 这条现在成本接近于零，缺了它将来无法验证迁移器。

## 一、四个版本号

| 版本号 | 管什么 | 当前值 | 存放形式 |
| --- | --- | --- | --- |
| `fileFormatVersion` | C 文件外壳结构：文件里有哪些字段、双代如何组织 | 2 | 明文 |
| `cryptoVersion` | 加密算法与参数：KDF、迭代次数、密码套件 | 1 | 明文 |
| `ledgerSchemaVersion` | 账本数据形状：事实种类与字段 | 3，本批升 4 | 明文 |
| `backupFormatVersion` | B 文件信封结构：顶层五个键及其顺序 | 3 | 明文（B 全文明文） |

**不得合并成一个版本号。** 四者的变化原因与频率互不相干：更换加密迭代次数只应改 `cryptoVersion`，账本数据形状不应因此升版本；新增一类事实只应改 `ledgerSchemaVersion`，加密与外壳不应因此升版本。合并会使任一处小改动引发全线升版本，并误导用户以为数据格式已变。

## 二、明文版本号是迁移的前提

`ledgerSchemaVersion` 与 `fileFormatVersion`、`cryptoVersion` 一样保存在 C 文件的明文外壳中，与密文并列。程序因此可以在不索取密码、不执行解密的情况下判定版本。

该性质必须长期保持。**任何版本号都不得移入加密载荷内部。** 一旦移入，低版本文件将无法在解密前被识别，用户只能看到含义不明的失败，迁移链也失去入口判断。

## 三、当前策略：Alpha 一律拒绝

产品目前处于 Alpha，唯一使用者为作者本人，且原始交易所记录完整保留在本机私有区，任何时候都可重新生成 B 文件。因此维护迁移链是纯粹的浪费。

| 场景 | 行为 |
| --- | --- |
| 低版本 B 文件 | 明确拒绝并说明不提供迁移 |
| 低版本 C 文件 | 明确拒绝，给出中文提示，不崩溃、不静默失败 |
| 用户原文件 | 原样保留，不清空、不覆盖、不自动删除 |
| 拒绝之后 | 仍可正常新建账本并进入导入流程 |

## 四、切换触发点

**进入 Beta 之前完成切换，具体时点由用户明确宣布，不由 AI 自行判断。**

宣布进入 Beta 之后，规矩变为：每一次 `ledgerSchemaVersion` 升级，必须同时交付对应的迁移器及其测试，缺一不算完成。

## 五、Beta 之后的迁移策略：读旧、写新

只维护单向升级链，不做双向兼容，不做降级。

```
读取：
  1. 读明文外壳，取得各版本号
  2. 外壳版本或加密版本不认识 → 拒绝（无法继续解析）
  3. 解密取得账本数据
  4. ledgerSchemaVersion 低于当前 → 依次执行迁移链 N → N+1 → … → 当前
  5. 迁移结果走完整校验后才进入应用

写入：
  永远只写当前最新版本，不回写任何旧格式
```

### 迁移器四条铁律

| 编号 | 规则 | 违反后果 |
| --- | --- | --- |
| M-1 | 迁移器是纯函数，输入旧形状输出新形状，不读文件、不联网、不读系统时间 | 结果不可重现，无法测试 |
| M-2 | 一经发布即冻结，永不修改 | 早迁移与晚迁移的用户得到不同结果，且几乎无法排查 |
| M-3 | 迁移只在内存中进行，绝不自动覆盖用户原文件；升级结果须由用户确认后另存为新文件 | 迁移出错即造成不可逆的数据损坏 |
| M-4 | 迁移失败必须 fail closed：不写、不删，原文件保持原样 | 半完成状态比失败更难恢复 |

M-3 与既有的“零写回”安全原则一致，不是新增约束。

## 六、黄金样例（现在就执行）

每次升级 `ledgerSchemaVersion`、`backupFormatVersion` 或 `fileFormatVersion` 时，必须同时把该版本的一份完整样例文件存入源码仓库测试夹具。

| 项目 | 要求 |
| --- | --- |
| 内容 | 全部为虚构数据，不得包含任何真实账户数字 |
| 覆盖 | 每个版本至少一份 B 样例；C 样例在外壳或加密版本变化时补充 |
| 命名 | 在文件名中写明版本，例如 `golden-backup-v3.json` |
| 用途 | 将来编写迁移器时作为唯一可信输入；迁移器测试必须以黄金样例为起点 |
| 冻结 | 已存入的黄金样例不得再修改 |

理由：迁移器的正确性只能靠真实的旧格式样例验证。若无样例，编写迁移器时只能凭记忆推测旧结构，推错即造成静默的数据损坏，且不会被任何测试发现。

## 七、本批的具体修正

`01B` 中写有“`BACKUP_FORMAT_VERSION` 改为 4”。按第一节的分层原则，本批只改变了账本数据形状，B 文件信封的五个顶层键未变，因此严格来说应保持 `backupFormatVersion = 3`，只升 `ledgerSchemaVersion` 至 4。

功能上两种写法都能拒绝旧 B（旧 B 的 `ledgerSchemaVersion` 为 3，同样被拒），故不影响本批正确性。该修正在本批验收阶段一并处理，不中断正在进行的执行。
