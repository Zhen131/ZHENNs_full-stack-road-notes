## 三、关键机制复核

### 3.1 确定性（`03B` 1.2）

`deterministicRng.ts` 实现的是 FNV-1a 种子哈希 + xorshift32，纯函数、无外部输入。`benchmarks/` 全目录搜索 `Math.random` 无命中。默认种子 `w15-main-perf-baseline-v1` 与固定合成日期 `2026-08-28` 均写死在 `syntheticLedger.ts` 并记入 `README.md`，符合合同。

同种子逐字段相同这一断言（T1-01）本次未运行验证，但从实现看不存在时间、随机、环境或文件系统输入，具备确定性的必要条件。

### 3.2 默认测试不会跑到量尺（`03B` 2.2 / T2-02）

`vitest.config.ts` 的 `include` 为 `src/**/*.test.{ts,tsx}`；量尺合同文件全部位于 `benchmarks/` 且命名为 `*.contract.ts`，由独立的 `vitest.benchmarks.config.ts` 收集。两者不相交，机制成立，且未改动既有测试的运行行为。

### 3.3 替身没有开后门（`03B` 3.3 / T3-02）

`filePickerStub.ts` 只在页面脚本执行前重定义 `showSaveFilePicker` 与 `showOpenFilePicker` 两个全局函数，返回的是浏览器 OPFS 里真实的 `FileSystemFileHandle`；仅在句柄缺少 `queryPermission` / `requestPermission` 时补上返回 `granted` 的实现。密码校验、密钥派生、加解密、写入、复读、版本校验、备份导入与渲染全部走产品自身代码，未被触及。**被替换的范围严格等于「弹出系统对话框让人选文件」这一步**，与合同一致。

### 3.4 元素定位不依赖中文文案（`03B` 3.3 附则）

`browserMetrics.ts` 使用 `data-benchmark-form` / `data-benchmark-nav` / `data-benchmark-lock` 定位。这些属性在 `src/` 中搜索**零命中**，由量尺在运行期 `setAttribute` 注入（`browserMetrics.ts:443/486/491`），不构成产品改动。

### 3.5 采样规则（`03B` 2.3）

`nodeMetrics.ts` 的 `sampleMetric` 先跑一次并把结果记入 `discardedWarmupMs` 丢弃，再取 `sampleCount` 个正式样本；`defaultSampleCount` 为 `S-1M` → 1、`S-100K` → 3、其余 → 10，与合同一致。`report.ts` 输出 median / minimum / maximum / sampleCount 四项齐全（T2-03 成立）。量尺只写 stdout，无文件输出（T2-04 成立）。

## 四、观察

### O-1（须在 04 批开工前处理）：「根因被证伪」的结论过宽，与 `03C` 自己的数据不符

`03C` 第 5.2 节与第 7 节据 M-7 ÷ M-8 比值判定原根因被证伪，并要求「04 批的历史曲线改写方向需要重新论证」。**本次复算 `03C` 4.5 表后认为该判定不成立。**

关键前提是 `03C` 未纳入比较的一个事实：合成账本的时间跨度按档位固定为 `spanDays = max(10, ceil(交易笔数 / 100))`（`syntheticLedger.ts:67`），即 `S-100` 与 `S-1K` 只有 10 天、`S-10K` 100 天、`S-100K` 1000 天、`S-1M` 10000 天。**一个只有 10 天数据的账本，其 365 天区间在物理上不可能产生 365 倍开销**，因此「比值应约等于 365」这个期望值本身就不适用于这些格子。

只看区间不超过账本跨度的格子（即比较有效的格子）：

| 档位 | 跨度 | 1d 比值 | 7d 比值 | 30d 比值 |
| --- | ---: | ---: | ---: | ---: |
| S-10K | 100 天 | 1.059 | 7.176 | 27.341 |
| S-100K | 1000 天 | 1.063 | 7.685 | 33.347 |
| S-1M | 10000 天 | 0.961 | 7.355 | 未取得 |

**这三行几乎精确等于 1 / 7 / 30。** 这不是证伪，这是相当强的支持。

进一步用「按日重放截至该日的账本前缀」这一模型（比「每天完整重放整本」更精确：越早的日子前缀越短）反算，可以把整张 4.5 表几乎全部对上。尾部 N 天区间的预测比值约为 `N − N²/(2×跨度)`，覆盖整本时约为 `跨度 ÷ 2`，超出跨度的空白天按每天约 0.11 倍固定开销计：

| 格子 | 模型预测 | 实测 |
| --- | ---: | ---: |
| S-10K 7d | 6.75 | 7.176 |
| S-10K 30d | 25.5 | 27.341 |
| S-100K 30d | 29.6 | 33.347 |
| S-100 all（10 天） | 5.0 | 6.506 |
| S-1K all（10 天） | 5.0 | 6.159 |
| S-10K all（100 天） | 50.0 | 58.185 |
| S-100 365d（10 天跨度） | 44.1 | 40.397 |
| S-1K 365d（10 天跨度） | 44.1 | 35.878 |
| S-10K 365d（100 天跨度） | 79.2 | 81.107 |

十个格子全部落在同一个模型上，包括原本被当作反证的 365d 与 all。

**因此正确的结论是：原描述在措辞上不精确（是「重放前缀」不是「每天完整重放整本」），但在方向上完全成立——历史曲线的成本确实是「按日重复重放」，随区间天数与账本规模相乘增长。04 批「不重复算」的改写方向不需要推翻。**

处理要求：在 04 批产品定义中重述根因为上述模型，并把 `03C` 第 5.2 / 第 7 节的结论收窄为「原措辞不精确，方向成立」。`03C` 作为执行报告的原文保留，不改写。

### O-2（登记，不阻塞）：M-2 内部包含一次 M-7

`nodeMetrics.ts` 的 `runDashboardDerivations` 里第四项是 `buildHoldingHistory(…, range:"30d")`。因此 M-2（全账本盈亏派生）本身就含一次 30 天历史曲线构建。以 `S-10K` 为例，M-2 中位数 1484 ms 中约 1384 ms 来自这一项，占 93%。

这不违反合同——首页确实会画这条曲线，M-2 的定义就是「首页五个派生完整跑一遍」——但意味着 **M-2 目前几乎就是 M-7(30d) 的同义词**。04 批据 M-2 判断优化效果时必须知道这一点，否则会把历史曲线的改善误读成五项派生的整体改善。建议 04 批的量尺补一个「排除历史曲线的 M-2」分项。

### O-3（登记，不阻塞）：产品的 8 MiB 导入上限是先于渲染的真实天花板

`03C` 5.6 指出 `S-100K` 在 69 MB 明文备份的 `backup-preflight` 阶段即被产品拒绝，`S-1M` 更早在字符串序列化阶段失败。这意味着 `03A` 路线图中「05 批让 10⁶ 达标」的前置条件不是渲染优化，而是备份文件的分块／流式处理与资源上限策略。该顺序问题应在 05 批产品定义中显式排在渲染优化之前。
