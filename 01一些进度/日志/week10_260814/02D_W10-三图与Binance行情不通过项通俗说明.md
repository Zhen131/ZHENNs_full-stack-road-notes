# Week 10 三图与 Binance 行情不通过项通俗说明

日期：2026-07-25

状态：解释 02C 为什么判定“不通过”

对应正式报告：`02C_W10-三图与Binance行情独立测试结果.md`

## 一句话结论

这次不是“三张图坏了”，也不是“账本算错了”。

真正导致不通过的核心问题只有两个：

1. 当前使用的 Next.js 服务器版本存在一个已经公开的高危安全漏洞。
2. 旧账本出现错误的未来日期时，页面不能让用户逐条删除这些错误记录。

这两个问题互相独立。安全漏洞单独存在就不能进入合并；必测功能没达到验收要求，单独存在也会让本轮验收不通过。

## 不通过点一：服务器框架存在已公开的安全洞

### 出了什么问题

项目当前使用 `next@14.2.35`。这个版本落在官方公布的受影响范围内。

问题发生在 Next.js 自带服务器处理一种“升级连接请求”时。攻击者可能发送专门构造的请求，让我们的服务器替他访问任意内部或外部地址。

通俗地说：原本服务器只应该处理账本页面，但这个漏洞可能让它被陌生人当成“跑腿”，去访问公司内网服务、云服务器内部信息地址或其他本来不该对外开放的位置。

这类问题的正式名称是 SSRF，也就是“服务器端请求伪造”。GitHub 官方公告说明：使用 Next.js 内置 Node.js server 自行部署的应用可能受影响，攻击者不需要登录，也不需要用户点击什么。[官方漏洞说明](https://github.com/advisories/GHSA-c4j6-fc7j-m34r)

### 这是否代表账本数据已经泄漏

不代表。

本轮测试没有发现账本数据已经泄漏，也没有发现攻击真的发生。结论只是：当前服务器版本保留着一个公开、可利用且已经有修复版本的入口，不能把它当作安全通过。

### 我们的项目明明没有做 WebSocket，为什么仍然算问题

因为这个入口由 Next.js 自带服务器处理，不要求我们的业务代码主动实现 WebSocket。

项目 production 使用的是 `next start`，正好属于公告所说的内置 Node.js server。只要以后把这个服务直接暴露给不可信网络，请求就可能到达这个入口。账本自身不用 WebSocket、Binance 行情也不用 WebSocket，都不能自动消除这个框架漏洞。

如果项目永远只在个人电脑本机使用、不对外开放，现实中的即时风险会低很多；但本次验收判断的是“当前代码能否安全进入合并和后续部署”，因此不能用“暂时只在本机跑”代替修复。

### 我们做了什么测试

1. 对正式源码执行 `npm audit --json`。
2. 再执行只看 production 依赖的 `npm audit --omit=dev --json`。
3. 确认 production 依赖中有 2 个 high，其中包括 `next`。
4. 检查项目真实启动命令，确认 production 使用 `next start`。
5. 检查项目是否已有反向代理阻断、网络隔离或其他缓解证据；当前仓库没有。
6. 对照官方公告确认当前版本受影响，修复版本为 `15.5.16` 或 `16.2.5` 及相应更高安全版本。

### 为什么这一项直接不通过

这是一个可以从网络触达的高危框架漏洞。继续合并等于明知存在公开安全洞仍把版本往后推进，所以这一项单独就足以让结果“不通过”。

## 不通过点二：错误的未来记录不能逐条删除

### 什么叫“未来事实”

例如今天是 2026 年，但旧账本或旧备份里误写了一笔 `2099-01-01` 的交易或价格。

这种记录不能进入当前持仓、价格选择和图表，否则会把现在的账本算错。因此程序会进入“未来事实纠正模式”，先隔离这些错误记录。

### 哪些地方其实做对了

测试确认了：

- 2099 年的交易和价格没有进入持仓计算。
- 它们没有进入饼图、曲线和热力图。
- 纠正完成前，普通新增和 Binance 刷新会被暂停，避免继续污染账本。
- 用户仍然可以删除全部未来记录、导入另一份合法账本或清空账本。
- 删除全部未来记录后，普通交易和 Binance 刷新可以恢复。

所以这里不是“未来数据把账本算坏了”，隔离保护本身是有效的。

### 真正失败在哪里

测试标准要求用户可以先删除一条错误记录，再决定是否删除其余记录。

实际页面中：

- 未来交易虽然出现在交易表里，但它的删除按钮是灰的，点不了。
- 未来价格没有提供逐条删除按钮。
- 点击被禁用的按钮后，没有发生保存，错误记录仍然存在。

通俗地说：如果用户只写错了一条 2099 年交易，本来应该只删这一条；现在却只能“把所有未来记录一起删掉”“换一整份账本”或“把账本清空”。这不够精细，也没有达到测试前约定的操作要求。

### 我们做了什么测试

1. 在隔离临时账本中放入一笔 2099 年交易和一条 2099 年价格。
2. 使用正式 `DashboardShell` 打开页面，不使用伪造页面。
3. 检查这两条记录是否被排除在持仓和三张图之外。
4. 检查普通新增和 Binance 刷新是否被暂停。
5. 尝试逐条删除未来交易和未来价格。
6. 记录删除按钮状态、保存次数和删除前后的完整记录 ID。
7. 再验证“删除全部”、合法整账替换、clear、恢复普通交易和恢复 Binance 刷新。

结果是：保护和整体恢复路径通过，但“逐条删除”失败。

### P2 和“合同 FAIL”到底是什么意思

`P2` 只是说它不像安全漏洞那样紧急，也没有造成数据泄漏或数据损坏；它更像一个明确的功能/交互缺口。

“合同 FAIL”不是法律合同。它的意思只是：我们在测试前写了一份“这轮必须做到什么”的验收清单，其中明确要求能够逐条纠正未来记录，实际产品没有做到。

02B 规定：只要已经执行的必测项目没有达到通过线，即使问题本身只是 P2，本轮也必须判定“不通过”，不能为了好看改成“有条件通过”。

## 其他功能有没有坏

本轮没有发现下面这些核心功能失败：

- 41 个测试文件、362 项自动化测试通过。
- lint 和 production build 通过。
- 真实 Binance 刷新 BTC、ETH、ADA 成功。
- 自动价格和手动价格切换正确。
- 饼图、持仓市值/成本曲线、365 天热力图正常。
- Binance 超时、断网、418、429、500 和部分成功时不会清掉旧价格，也不会破坏本地交易。
- 行情旧响应不会覆盖刚刚导入或修改的新账本。
- export、clear、import、刷新后重新解锁的主流程可用。
- 390 和 1280 宽度下没有页面整体横向溢出。

因此，结论不是“Week 10 全部做坏了”，而是“主要功能大部分通过，但还留着一个不能接受的安全洞和一个明确的必测交互缺口”。

## 为什么现在不能进入合并审查

因为两个红线都还没有关闭：

1. Next.js 安全漏洞还在当前 production 依赖中。
2. 未来错误记录仍不能逐条删除。

应先生成独立修复计划，完成依赖安全处理和未来事实单删功能，再重跑对应测试。修复完成前，不进入合并审查。
