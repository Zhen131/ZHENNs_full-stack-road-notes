### 2. 两段删除

- 第一次点击任一未来交易、未来价格或“删除全部”，事实 ID、mutationVersion 和 save 次数不变。

- 只删除目标 ID，不影响同日重复记录或正常事实。

### 3. 交易依赖

- 先删支撑后续卖出的未来买入：拒绝，显示可理解提示，0 mutation、0 save。
- 先删依赖它的未来卖出：成功并保存。

- 内存态可退出纠正模式，但页面只能显示“正在保存”或保存失败，不能显示“已保存”。

- 失败后 remount 恢复最后成功保存版本。
- 使用原重试入口成功保存后，再次 remount 才证明单删持久存在。

### 5. 其他恢复路径

- “删除全部未来事实”仍遵循两段确认并保存正确快照。
- strict import 仍原子拒绝未来事实且不覆盖当前账本。
- 纠正模式仍可救援导出、合法整账替换和 clear。
- 最后一条未来事实成功保存后，普通交易、手动价格和 Binance 刷新恢复。

## 十、T4：竞态、第一次点击副作用与跨午夜

### 1. Binance 映射删除

受控请求已经发出且 Promise 未完成时：

- 第一次点击“删除映射”不得 abort 请求、清空草稿、mutation 或 save。
- 取消 armed 后请求仍在。
- 第二次确认才允许 abort、清草稿并删除映射。
- 受控 client 必须故意忽略 AbortSignal，随后返回旧响应；旧响应不得重新写入 mapping 或价格。
- remount 后仍保持映射已删除，历史 API 价格保留。

### 2. 最新账本保护

分别验证旧行情请求遇到：

| 中间操作 | 旧响应完成后的要求 |
| --- | --- |
| 删除映射 | 不恢复映射，不新增价格 |
| 导入合法整账 | 不污染替换后的账本 |
| 新增普通交易 | 新交易保留；行情最多一次 mutation，并合并到最新账本 |

不能只检查 `signal.aborted`；必须让忽略 abort 的旧 Promise 真正 resolve，再检查 mutation、save、完整快照和 remount。

### 3. Clock 单次快照

使用连续调用会跨日的 fixed Clock：

- `captureLedgerTime` 每次业务操作只调用一次 `clock.now()`。
- 同一次交易、手动价格、映射、备份和 Binance 响应中的 `todayKey` 与时间戳来自同一个 Date。
- Hook render 与 Dashboard 使用同一个 todayKey，不出现一边允许、一边判未来。
- 跨午夜 timer 触发后页面日期刷新。
- `window.focus` 和 `visibilitychange -> visible` 可重新校准。
- 卸载后 timer 与监听被清理，不再触发更新。
- mutation 进入校验前使用新的操作快照，不能沿用过期 render 日期。

## 十一、T5：响应式、加密存储与恢复

本节回到正式 production server 和真实 Chromium，不使用临时副本或 recording Repository。

### 1. 响应式与交互

- 390×844 与 1280px 下 `document.scrollWidth <= clientWidth`。
- 宽表只在自身容器滚动。
- 两段按钮 armed 扩展不撑宽页面。
- 风险提示、未来纠正行、密码眼睛和备份按钮可读可用。
- 浏览器启用 `prefers-reduced-motion: reduce` 时删除按钮无扩展 transition，功能仍可完成。
- console 无未解释 warning/error。

### 2. V2 原始存储

通过浏览器 DevTools、CDP 或同 origin 页面脚本读取：

```text
database: local-first-trading-ledger
store: ledger
key: ledger:v1
```

顶层只能包含：

```text
cipher
ciphertextBase64Url
cryptoVersion
formatVersion
kdf
ledgerSchemaVersion
```

要求：

- `formatVersion=2`、`cryptoVersion=1`、`ledgerSchemaVersion=1`。
- `PBKDF2 / SHA-256 / 600000`。
- `AES-GCM / 256 / tagLength=128`。
- envelope 不出现资产、交易、价格、映射、密码等明文。
- 新 mutation 保存后 IV/ciphertext 与旧值变化。
- reload 后页面锁定，重新输入密码才恢复。
- 解锁后映射、交易、manual/API provenance、图表和估值模式业务结果正确。

若当前浏览器能力无法读取 raw IndexedDB，本项记 `BLOCKED`；页面能恢复不能代替原始加密 envelope 证据。

### 3. 备份安全

- 保存普通、dirty、只读三类导出的实际 Blob/文件名/JSON 结构证据。
- dirty/只读救援文案准确，不把内存新状态说成已保存。
- 8 MiB 边界、超一字节拒绝、非法 JSON、错误 schema、未来事实、取消和 write failure 不回归。
- 导入成功只改变本地加密账本，不声称移动、删除或加密原文件。
- 备份与 IndexedDB envelope 明确是两种格式：前者明文，后者 V2 加密。

## 十四、严重度与总判定

| 等级 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 数据不可恢复、错误删除其他事实、明文秘密泄漏、加密边界被破坏 | 立即不通过 |
| P1 | 核心合同失败、旧响应污染新账本、未来事实进入计算、可达 production high/critical | 不通过 |
| P2 | 非核心但真实的交互、无障碍、异常处理问题，或有充分隔离证据的剩余依赖风险 | 有条件通过或不通过，按是否属于必测合同决定 |
| P3 | 轻微文案、视觉和记录问题 | 可通过并记录 |

`03D` 总结论只能使用：

- **通过**：T0–T6 全部必测项 PASS，无 P0/P1/P2；允许记录 P3。
- **有条件通过**：所有必测合同 PASS、无 P0/P1，但存在已解释 P2，或只有本文件明确允许的真实 Binance 外部限制。
- **不通过**：存在 P0/P1，或任何已经执行的必测合同 FAIL。
- **受阻**：源码基线、权限、production 浏览器、raw IndexedDB、audit/advisory 或证据链使必测合同无法得出结果。

判定顺序：

```text
P0
→ P1 或必测合同 FAIL
→ 必测项 BLOCKED
→ P2 / P3
```

未经执行的必测项不得算 PASS。开发 AI 的既有结果不能填补本轮 `BLOCKED`。

`03D` 必须明确回答：

```text
当前是否可以进入合并审查：是 / 否
是否需要生成新一轮修复计划：是 / 否
```
