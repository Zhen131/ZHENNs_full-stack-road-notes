## 五、目标结构

### 1. 唯一运行时日期来源

复用 `src/utils/ledgerDate.ts` 中现有 `LedgerClock`，不要再创建第二个日期抽象。

目标关系：

```text
system LedgerClock / fixed test LedgerClock
-> usePersistentLedger 生成并暴露本轮 render 的 todayKey
-> DashboardShell 复用同一个 todayKey
-> 持仓、三图、未来事实分区、删除动作、导入 policy
-> 需要完整时间的表单、备份和 Binance 控件复用同一个 clock
```

要求：

- `DashboardShell` 支持注入 `LedgerClock`，production 默认系统 clock。
- `usePersistentLedger` 接受同一 clock，并向 Dashboard 返回本轮使用的 `todayKey`；Dashboard 不再另调一次系统时钟。
- `TradeForm`、`PriceForm`、`MarketDataControls`、`BackupControls` 需要今天或当前时间时，使用同一 clock 或由它派生的依赖，不再各自静默创建会产生不同日期的系统时钟。
- 测试注入固定 clock；禁止依赖宿主机真实日期。
- 不把 `todayKey` 保存进账本；跨日后的下一次正常 render 应从 clock 重新取得日期。

### 2. 普通删除确认组件

新增：

```text
src/components/common/ConfirmDeleteButton.tsx
src/components/common/ConfirmDeleteButton.test.tsx
```

使用上述路径并只保留一个共享实现。组件只管理短暂交互状态，不知道 Trade、PriceSnapshot、Binance 或 Repository。

接口至少包含：

```ts
type ConfirmDeleteButtonProps = {
  label: string;
  confirmLabel?: string;
  ariaLabel: string;
  disabled?: boolean;
  onConfirm(): void | Promise<void>;
};
```

交互合同：

- 初始文案由调用方提供；第一次激活后显示“再次点击确认”。
- armed 状态使用红色背景、轻量横向扩展和约 `180ms` CSS transition。
- 第二次激活只调用一次 `onConfirm`，随后退出 armed 状态。
- 点击组件外空白处或按 `Escape` 取消。
- disabled 变化、组件卸载或业务完成时清除 armed 状态。
- 原生 `button type="button"` 同时覆盖鼠标、触控和键盘 click 语义。
- 使用 `aria-pressed` 或等价可感知状态；armed 文案不能只靠颜色表达。
- 使用 `motion-reduce:transition-none` 或等价规则尊重 reduced motion。
- 不使用 `window.confirm`，不增加动画依赖。

### 3. 密码按住查看

继续复用 `LedgerAccessGate.tsx` 内一个 `PasswordField`，不要复制三套状态。

目标事件：

```text
pointerdown / Space keydown / Enter keydown -> 当前字段 type="text"
pointerup / pointercancel / pointerleave / keyup -> type="password"
window blur / document hidden / disabled / form submit -> type="password"
```

要求：

- 小眼睛是输入框内按钮，使用本地 SVG 或 CSS，不增加 icon package。
- 只显示当前字段；设置密码、再次确认和解锁密码互不联动。
- 行为是 hold-only，不是点击 toggle；普通 click 不能让密码无限期保持明文。
- 控件可聚焦，名称明确为“按住显示设置密码”“按住显示再次输入密码”“按住显示账本密码”或等价准确文案。
- 显示状态只在 `PasswordField` 组件内存中；不得把密码或显示状态发送到日志、Repository 或备份。

### 4. 明文备份提示

系统不会自动上传到 iCloud。
导出或导入后，请将文件安全移动到受保护位置，或在确认无须保留后删除。

导出成功、只读救援导出、dirty 救援导出和导入确认继续保留各自原有业务信息，同时补齐：

- 原文件仍是明文。
- 导入只把内容写入本地加密账本，不会加密、移动、删除或上传用户选择的原文件。
- 系统没有自动 iCloud 上传行为。

不得阻止用户继续使用明文导入/导出，不得在本轮发明加密备份格式。

## 十、Gate 4：未来交易与未来价格逐条删除

### 页面接线

在未来事实纠正面板中为每条记录提供独立按钮：

- `删除未来交易 <资产> <日期>`。
- `删除未来价格 <资产> <日期>`。

按钮使用 Gate 3 的共享组件。

### 行为

- 未来交易第二次确认后 dispatch `trade/delete`。
- 未来价格第二次确认后 dispatch `priceSnapshot/delete`。
- 这两种 action 进入 `usePersistentLedger` 已有 correction allowlist、resource policy、mutation version 和 Repository save 链。
- 删除一个未来事实只删除目标 ID，不影响其他未来或正常事实。
- 只剩另一条未来事实时继续保持纠正模式。
- 最后一条未来事实删除并保存后退出纠正模式，普通交易、手动价格和 Binance 刷新恢复。
- 正常交易删除仍走 `validateTradeRemoval`；未来事实纠正不因正常时间线校验被错误阻断。
- 删除失败、保存失败、只读、Repository 切换或其他 persistence operation 期间不得假装成功。

### 必补交互测试

使用预载旧账本的真实 `DashboardShell + usePersistentLedger + recording Repository`：

1. 至少包含 2 条未来交易、2 条未来价格和正常历史事实。
2. 未来事实不进入持仓和三图。
3. 第一次点击目标按钮，完整事实 ID 和 save 次数不变。
4. 第二次点击，只删除目标 ID，save 增加一次且快照正确。
5. 删除一条后其余未来事实仍存在，纠正模式仍开启。
6. 删除最后一条后普通写入恢复。
7. remount 后删除结果仍存在。
8. strict import 未来事实仍被原子拒绝。
9. “删除全部”仍可用且也遵循两段确认。
