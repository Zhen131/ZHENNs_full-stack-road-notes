## 一、产品形态与网络边界

### 当前形态

- 账本是本地优先、单用户、个人使用的工具，不以公开网站或全天候服务器为当前交付目标。
- 在真正完成桌面或移动端打包前，继续使用本地 Next.js 服务作为过渡运行形态。
- 开发和 production 本地服务只监听 `127.0.0.1`，默认只允许同一台电脑访问，不向局域网或公网开放。
- 监听地址收紧只限制外部设备访问本地页面，不禁止账本主动访问 Binance 公共 API。
- 当前联网能力只服务于 Binance 公共行情；项目不使用业务 WebSocket、私有 Binance API、API Key、代理、轮询或后台常驻同步。

### 未来形态

- 桌面 App、移动 App、静态导出、Tauri、Capacitor 和 iCloud 文件同步均属于后续独立架构任务，不进入 Week 10。
- 未来若决定部署到公网服务器，必须按新的部署模型重新讨论认证、授权、网络出口、反向代理、限流、日志、密钥和持续安全升级；不能直接把当前本地服务暴露到公网。
- “以后可能部署”不等于今天为服务器产品预建全部能力，但也不构成保留低成本可修复漏洞的理由。

## 二、Next.js WebSocket SSRF

### 风险判断

- 当前依赖为 `next@14.2.35`，production 运行面是 Next.js 内置 Node.js server。
- 已知 SSRF 位于 WebSocket upgrade 处理链，不要求账本业务主动编写或使用 WebSocket。
- 攻击结果不只可能表现为“替别人发起 DDoS”。更直接的风险是借账本服务请求内网地址、云元数据或其他原本不应由攻击者访问的网络目标；是否能进一步滥用取决于部署环境。
- 只监听本机可显著降低现实攻击面，但它属于暴露面收缩，不替代依赖修复。只要未来错误开放监听、加入反向代理或改为服务器托管，旧风险就会重新出现。

### 已固定的取舍

- 采用精确目标 `Next 15.5.22 + React 19` 关闭当前 Next.js SSRF，不在本轮把应用改成静态站点。
- 同时收紧开发与 production 的监听地址到 `127.0.0.1`。依赖升级处理已知漏洞，监听收紧减少误暴露，两者职责不同。
- 隔离可行性试验已经证明升级成本可控：Next 15.5.22 可以完成 build，直接使用 ESLint 9 flat config 可以完成 lint，不需要为升级另造业务模块。
- React 19 的 Hooks lint 会把从 `echarts/core` 导入的顶层 `use` 误判为 Hook；该符号采用表达真实职责的名字，例如 `registerEChartsModules`。这属于 React 19 兼容处理，不应被注释成 SSRF 修复本身。
- `next lint` 已弃用，因此同一轮迁移为 ESLint 9 直接 CLI 与 flat config，避免刚升级就留下立即过期的检查入口。

### 依赖风险口径

- `npm audit` 是依赖公告匹配工具，不会扫描 iCloud 文件、账本内容或用户密码。
- 对生产路径真实可达的高风险漏洞优先关闭；对仅存在于传递依赖、构建链或当前未使用能力中的公告，先结合依赖路径和实际调用面归因。
- 不为追求审计数字归零而盲目使用 `npm audit fix --force`，尤其不能用未经评估的破坏性大版本替换真实回归。
- 隔离升级后原 SSRF 已不再出现，但构建或图像链仍可能报告 `postcss`、`sharp` 相关 high。当前应用没有使用 `next/image`，仓库 CSS 仍经过 PostCSS；这些项应单独记录可达性证据，不能冒充“全部安全”，也不能与本次 SSRF 混为同一个问题。

## 三、未来事实逐条删除与统一删除交互

### 未来事实纠正能力

- 纠正模式继续隔离未来事实，错误的未来交易和未来价格不得进入持仓、选价、图表或自动行情逻辑。
- 用户可以逐条删除指定的未来交易，也可以逐条删除指定的未来价格。
- 单删进入既有 Repository 保存链，继续受失败、并发、只读状态、资源策略和持久化操作保护；页面不能另造一条旁路保存。
- 第一次确认不得改变账本或触发保存，第二次确认才产生删除意图。
- 普通历史交易在第二次确认时仍要经过既有交易时间线校验；不能因为统一了交互就绕过会保护后续卖出的业务约束。
- 删除 Binance 资产映射后继续保留已经保存的旧 API 价格，不能把“删除映射”扩大为“删除历史行情事实”。
- “删除全部未来事实”、合法整账替换、救援导出和 clear 能力继续存在，各自保持原有数据语义。

### 普通删除的统一样式

当前和今后新增的普通删除入口默认复用同一套两段式“果冻确认”：

- 第一次点击后，按钮以轻量红色扩展和约 `180ms` 的 CSS 过渡进入待确认态，文案明确提示“再次点击确认”。
- 第二次点击执行删除；点击页面空白处或按 `Escape` 取消并收回按钮。
- 鼠标、触控和键盘都能完成确认；系统开启 reduced motion 时取消或显著减弱位移动效。
- 不引入动画库，动效只用于让用户意识到删除已经进入第二阶段，不承担业务状态。

这套普通删除覆盖：既有交易删除、新增的未来交易单删、新增的未来价格单删、删除全部未来事实、Binance 映射删除。以后若增加未来备注删除，默认也复用该交互，除非另行讨论。

### 高风险删除例外

- 清空整个账本和忘记密码后的本地账本重置继续使用输入指定文本的强确认。
- 不得为了视觉统一把这两类高风险操作降级为普通两次点击。
- 本轮不增加交易或价格编辑功能。用户提出过“左侧编辑、右侧删除”的界面设想，但本轮只固定删除；既有账本事实继续保持不可直接编辑。

## 四、密码按住查看

- 覆盖三个输入框：首次设置密码、再次确认密码、账本解锁密码。
- 每个输入框使用自己的内嵌小眼睛图标，不新增图标依赖。
- 行为固定为“按住显示”，不是点击切换：鼠标、触摸或键盘按住时只显示当前字段，释放后立即恢复隐藏。
- 指针移出、触摸取消、窗口失焦、页面进入隐藏状态或提交表单时，也必须立即恢复隐藏，避免密码因中断操作停留在明文状态。
- 三个字段互不联动；查看一个字段不能同时显示另一个字段。
- 显示状态仅存在于输入组件的当前会话内，不持久化、不记录日志、不写入 `LedgerData`、IndexedDB、备份或未来同步文件。
- 可用性和无障碍语义应说明“按住显示密码”，不能让键盘或读屏用户面对一个只有图形、没有含义的按钮。

## 五、配套工程边界

### 日期与测试确定性

- 可行性试验中出现的 3 个旧测试失败来自样例硬编码 `2026-07-25`，在 Next 14 和 Next 15 环境下都会于 `2026-07-26` 失败，因此不属于升级回归。
- 正确方向不是把日期常量再改一天，而是让 Dashboard 与持久化链共享同一个可注入 `LedgerClock`：生产使用系统时钟，测试使用固定时钟。
- 统一时钟还用于避免页面与持久化 Hook 在跨过午夜时得出不同“今天”的判断；这是业务一致性边界，不只是方便测试。

### 明文备份提示

- 现有明文导入与导出继续作为低频迁移、救援能力独立保留，不把它冒充日常同步方案。
- 当前界面提示应明确：备份文件包含完整账本且未加密；使用后应安全移动或删除；系统不会自动把该文件上传到 iCloud。
- 未来正常 iCloud 同步文件不得复用该明文格式。

### 代码注释风格

- 后续在根 `AGENTS.md` 中正式补充简洁、专业的注释规则，但本文件只记录已经商定的风格，不直接修改协作规则。
- 关键函数或模块使用 TSDoc/JSDoc 说明职责、输入、输出和 invariant；金融、日期、安全、持久化等不直观逻辑使用行内注释解释“为什么”。
- 明显代码和普通 JSX 不堆注释；注释描述当前真实契约，不写变更流水账，也不能给兼容修改编造虚假安全理由。
- 变量和类型名保持英文；注释以中文为主，保留 `Repository`、`LedgerClock`、`SSRF`、`invariant` 等准确英文术语，不要求中英双份复述。

## 六、iCloud 同步的远期产品边界

本节用于保存后续产品方向，避免设想散落；它不属于 Week 10，也不代表方案已经设计完成。

### 文件与设备职责

- 未来以 iCloud 中的一份“官方账本文件”作为设备间传输载体，文件内容整体加密。
- iCloud 负责搬运和保存文件版本；账本应用不能在冲突时静默覆盖，也不能在用户不知道的情况下自动合并。
- 电脑端仍是主要编辑端；首版移动端只考虑查看和快速新增买入/卖出，不提供删除、clear、映射管理或复杂维护。
- 本地 IndexedDB 继续保存加密账本；明文 `BackupEnvelope` 只承担用户主动触发的救援或迁移。
- 未来同步文件使用独立加密文档格式，完整 `LedgerData` 进入密文；文件可公开保存 salt、IV、KDF 等解密所需元数据，但不保存密码。

### 解锁与风险

- 任一受支持设备都可以使用账本密码解锁同步文件。
- 移动端可在后续使用 Apple Keychain 配合 Face ID 或 Touch ID 保存解锁凭据或派生密钥，并保留密码回退；不得保存明文密码。
- 加密保护的是账本内容的机密性，不保护文件可用性。恶意软件仍可能删除或窃取密文，也可能对弱密码做离线暴力猜测，因此版本保留、恢复能力和密码强度仍需独立设计。

### 冲突处理

- 一份逻辑账本可能因为电脑和手机同时离线编辑而产生两个 iCloud 文件版本；“只有一个文件名”不能消除并发分叉。
- 应用解密冲突版本后，向用户展示类似 Git diff 的结构化比较：新增使用绿色 `+`，删除使用红色 `-`，若未来开放编辑，则修改或冲突使用黄色标识。
- 由用户明确选择保留某个版本或组成合并结果，不进行暗中自动合并。
- 用户选出的合并结果仍需满足 `LedgerData` 结构、交易时间线和资源限制；结果无效时不得覆盖官方账本。
- 未被选中的版本重命名为包含设备与时间的加密冲突副本并继续保留，直到用户主动删除。
- 本项目不在近期引入 CRDT 或全自动多端合并；先守住可解释、可回退、由用户确认的文件冲突模型。
