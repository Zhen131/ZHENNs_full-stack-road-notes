# 07-开源账本项目借鉴与落地地图

> 状态：研究参考文档，不是开发计划，也不代表已经采用其中任何方案
> 审查日期：2026-07-29
> 研究对象：[Wealthfolio](https://github.com/wealthfolio/wealthfolio)、[rotki](https://github.com/rotki/rotki)、[Portfolio Performance](https://github.com/portfolio-performance/portfolio)、[Actual Budget](https://github.com/actualbudget/actual)

## 一、先说结论

我现在不用再从一张白纸开始设计每一个问题。

这四个项目不能整个搬进我的账本，但它们刚好分别替我踩过了四类最费时间的坑：

| 我现在最头疼的问题 | 最值得先看谁 | 它已经替我验证过什么 |
| --- | --- | --- |
| 导入前怎么预检，怎样避免一导入就污染正式账本 | Wealthfolio、Actual Budget | 先试跑、给用户看结果、再次确认、最后才真正写入 |
| 手续费、均价、卖出、缺价为什么总能冒出新 Bug | rotki、Wealthfolio | 金融计算不能只测一个正常例子，必须建立成组的回归案例 |
| 浏览器版本以后怎样打包成 Tauri 桌面端 | Wealthfolio、Actual Budget | 业务核心和运行环境要隔开，浏览器、桌面端只是不同的“插头” |
| 一个正式账本文件怎样保存、另存为、备份和恢复 | Portfolio Performance | 文件型投资组合产品需要明确区分打开、保存、另存为、关闭前提醒和恢复 |
| 出了问题，怎样告诉用户到底哪里坏了、该去哪里修 | Wealthfolio | 问题不能只显示“失败”，还要有严重程度、证据、影响和修复入口 |
| 以后做 iCloud 或多设备时，怎样避免旧设备覆盖新数据 | Actual Budget | 必须明确哪一份是真本、设备属于哪一代同步身份、重置后旧设备不能继续写 |

最重要的结论不是“把四个仓库都学完”，而是：

1. 每次只带着一个具体问题，去看其中一个项目的两三个准确文件。
2. 借它们已经验证过的流程和测试案例，不照搬它们的全部架构。
3. 所有借鉴最后都要翻译成我的账本合同，不能因为别人这样做，我就自动这样做。
4. 我当前最值得立刻建立的资产，不是更多功能，而是一套可以反复使用的导入流程、会计回归案例、文件交互规则和问题诊断格式。

这意味着后面的 02A、03A、04A 不必每次都从零思考。我可以先来这份文档找“谁已经做过类似的事”，再决定只研究哪一小块。

## 二、这四个项目分别适合当什么老师

| 项目 | 最适合当我的什么老师 | 和我的项目相近之处 | 最大差异 | 许可证提醒 |
| --- | --- | --- | --- | --- |
| Wealthfolio | 产品架构、导入流程、桌面端分层、数据健康检查 | 本地优先、投资组合、React、Tauri、桌面与移动、多币种、交易导入和收益分析 | 它以 SQLite 和完整投资组合平台为中心，我以加密 `.lftl` 正式文件为中心 | AGPL-3.0。适合学思路、重写测试案例；不能未经判断直接复制代码 |
| rotki | 加密货币会计和极端案例测试 | 隐私优先、加密货币交易、盈亏、历史分析、本地数据 | Python 后端、Vue 前端，链上解析和税务范围远大于我当前项目 | AGPL-3.0，也提供商业许可。默认不直接搬代码 |
| Portfolio Performance | 单文件产品的保存、另存为、备份、恢复与成熟绩效场景 | 一个文件代表一个正式投资组合，支持加密、导入、历史行情和绩效分析 | Java 桌面应用；它的文件会保存部分行情、设置和看板，我的 C 文件不应该这样做 | EPL-1.0。先学产品交互和测试思想，不直接拼接源码 |
| Actual Budget | TypeScript 本地优先核心、导入试跑、跨运行环境和未来同步 | TypeScript、本地优先、桌面端、导入、离线工作、可选同步 | 它是预算软件，不是投资会计；本地数据库默认不加密，自动对账规则也不适合我的 B→C 恢复 | MIT。四者中代码复用相对宽松，但仍要检查文件和依赖的具体许可证 |

一句话记忆：

- Wealthfolio 教我“系统怎么拆、导入怎么审、问题怎么告诉用户”。
- rotki 教我“金融计算到底还会在哪里出错”。
- Portfolio Performance 教我“一个正式文件应该给用户什么感觉”。
- Actual Budget 教我“同一套核心怎样服务 UI、API、桌面端和未来同步”。

## 三、先建立正确的借鉴方式

### 3.1 可以直接借鉴什么

| 类型 | 能不能借鉴 | 正确做法 |
| --- | --- | --- |
| 产品流程 | 可以 | 例如借鉴“预检 → 审阅 → 提交”，再按照我的 B/C 合同重新设计 |
| Bug 场景 | 可以，而且很值得 | 把别人的历史 Bug 改写成我的输入数据和期望结果 |
| 测试分类 | 可以 | 学它怎样覆盖手续费、缺价、部分卖出和版本迁移，但测试代码由我重写 |
| 模块边界 | 可以 | 学“核心逻辑不依赖桌面 API”，再接入我现有的 Adapter、Repository |
| 错误信息结构 | 可以 | 学严重程度、证据、影响、操作入口，不复制原项目文案 |
| 源代码 | 要看许可证 | MIT 项目也要保留版权和许可证；AGPL、EPL 不能当成随手复制的代码仓库 |
| 图标、Logo、项目名称 | 默认不借 | 开源代码不等于商标和品牌素材也可以使用 |

### 3.2 不能犯的错误

1. **不能因为 Wealthfolio 用 SQLite，就把我的 `.lftl` 文件合同推翻。**
2. **不能因为 Actual Budget 会自动匹配相似交易，就让我的导入自动合并、更新或删除交易。**
3. **不能因为 Portfolio Performance 会把历史价格、Dashboard 设置放进文件，我也把 K 线、图表派生状态写入 C。**
4. **不能因为 rotki 支持 FIFO、税务持有期和链上交易，就一次把这些全部塞进我的平均成本账本。**
5. **不能把“别人的项目能运行”当成“它的安全设计已经适合我”。** 加密参数、密钥保存、恢复规则仍要单独审查。
6. **不能为了研究巨型仓库，又给自己增加一个月的阅读工作。** 研究必须由当前问题驱动，并设置停止线。

## 四、Wealthfolio：最值得先研究的整体参照物

### 4.1 它最能帮我的地方

Wealthfolio 和我的产品气质最接近：它是本地优先的投资组合工具，前端使用 React，桌面端使用 Tauri，数据主要保存在本地，也在处理交易活动、导入、收益、多币种、扩展和移动端。

它最有价值的不是“功能多”，而是已经走到功能变多之后，开始不断修正收益、税费、拆股、导入、精度和跨运行环境问题。

它的 [v3.6.2 发布记录](https://github.com/wealthfolio/wealthfolio/releases/tag/v3.6.2) 仍在修这些问题：

- 汇率变化被错误算进持仓收益；
- 分红和调整后价格被重复计算；
- 税费没有正确影响现金余额；
- 只有税没有手续费的活动显示成 0；
- 普通价格、低价资产和平均成本需要不同的精度；
- 桌面端与 Web 端的价格同步重试行为不一致。

这给我的提醒很直接：我在 01D 反复发现新 Bug，不一定说明我的项目“怎么都修不好”。金融软件成熟以后仍然会不断遇到语义和边界问题。真正要改变的是修 Bug 的方法——把每个 Bug 变成永久回归案例，而不是希望一次测试就发现全部问题。

### 4.2 可以借鉴的详细清单

| 借鉴点 | Wealthfolio 怎么做 | 翻译成我的账本后怎么做 | 什么时候值得用 |
| --- | --- | --- | --- |
| 导入分成准备和提交 | 先映射字段，再执行 `prepare`，返回合法、非法和重复项；用户审阅后才 `commit` | B 文件、CSV、未来 NLP 草稿都先进入同一个预检器，不直接写 C | 导入功能、NLP 写入、交易批量录入 |
| 预检阶段零写入 | 准备阶段只检查，不修改正式数据 | 预检失败或用户取消时，C 的字节、revision 和页面状态都不变 | 所有批量写入 |
| 逐行问题定位 | 结果带原始行号、错误、警告和解析后的资产身份 | 显示“第几行、哪一字段、为什么错、怎么修”，不要只写“导入失败” | CSV、TXT、NLP 结果审阅 |
| 预检汇总 | 给出总数、合法数、非法数和重复数 | 先让用户看到这次操作到底会影响多少笔交易 | 导入确认页 |
| 提交前重新校验 | 正式提交时不完全相信之前的预览结果，会再次检查 | 预检完成后如果 C 已被修改，不能拿旧预览直接覆盖；提交前重新读当前 C、核对 revision 和预览指纹 | FILE-007、NLP 提交 |
| 重复项要显式决策 | 重复活动默认跳过，强制导入需要明确选择 | 我的账本不能照抄“自动跳过”或“强制绕过硬错误”；同 ID 是硬错误，相似交易只警告，最终选择必须遵守我的导入合同 | 重复交易处理 |
| 一次导入有统一身份 | 同一批提交带一个 `import_run_id` | 为一次导入生成稳定的批次 ID 或内容指纹，方便审计、重试和定位问题 | 导入日志、回归测试 |
| 审计日志不保存敏感正文 | 日志只保留数量等摘要，不把全部交易内容写进去 | 报告保存错误码、路径和脱敏摘要，不把真实交易、密码、密钥、完整明文备份塞进日志 | 测试报告、诊断中心 |
| 运行环境 Adapter | 同一前端通过统一接口连接 Tauri IPC 或 Web REST | 业务层只调用 `FileAccessAdapter`、`SecretStoreAdapter`、`AppLifecycleAdapter` 等接口；浏览器和 Tauri 分别实现 | FILE-008、桌面端打包 |
| 构建时选择实现 | 不在业务代码各处写 `if desktop` / `if web` | 把环境判断集中到装配入口，业务代码不知道自己运行在浏览器还是 Tauri | 桌面端开始之前 |
| 服务层包住 Adapter | 页面不直接调用底层 IPC 或 HTTP | React 页面调用用例/服务；用例再调用 Repository 和 Adapter | 防止桌面端改造牵一发动全身 |
| 缺失结果有明确状态 | 收益不可用时返回不可用，而不是偷偷拿另一个数字顶上 | 缺行情、缺成本、数据不完整时显示 `N/A + 原因`，不能拿 0、买入价、未来价或旧价格冒充 | 盈亏、Benchmark、图表 |
| 数据健康中心 | 问题带严重程度、分类、证据、影响和操作入口 | 建立统一 `LedgerDiagnostic` 结构；先用于报告，产品界面以后再做 | 02D 以后、长期维护 |
| 自动修复和导航分开 | 有的问题可以修，有的问题只把用户带到正确页面 | “安全自动修复”和“去查看交易”是两种动作，不能把危险修复伪装成普通按钮 | C 恢复、异常交易 |
| API Key 交给系统安全存储 | 桌面端秘密信息可通过操作系统 Keyring 管理 | Tauri 阶段再把行情 API Key 接到 Keychain/系统凭据库；不要把它混进 C 或普通设置 | FILE-009、桌面端 |
| 主动控制功能膨胀 | Roadmap 明确强调简单、聚焦和对抗 feature creep | 每一批只关闭当前 P4/Gate，未进入当前 Gate 的扩展先进入清单 | 防止 01A 变成无底洞 |

### 4.3 最值得抄成我自己的流程：导入预检

我可以把未来所有“外部数据进入账本”的动作统一成这一条路：

```text
选择来源
  ↓
读取原始内容
  ↓
解析和字段映射
  ↓
转成统一的候选事实
  ↓
预检：结构、业务规则、重复、资源上限
  ↓
给用户看汇总和逐条问题
  ↓
用户确认
  ↓
重新读取当前 C，并再次校验 revision / 指纹
  ↓
一次性原子提交
  ↓
关闭句柄后重新打开，确认保存结果
```

这条流程可以同时服务：

- 明文 B 灾难恢复；
- 将来的 CSV/TXT 导入；
- Binance 交易记录导入；
- NLP 生成的 `TradeDraft`；
- AI Challenge 演示中的自然语言记账；
- 批量修改或迁移。

这里最重要的是：**不同入口可以产生不同草稿，但不能拥有不同的正式写入规则。**
不然手动导入能拦住的问题，NLP 入口可能绕过去；浏览器版本能拦住的问题，桌面端又可能绕过去。

### 4.4 不应该照搬的地方

| 不照搬什么 | 为什么 |
| --- | --- |
| SQLite 作为唯一真相 | 我的核心产品承诺是用户选中的加密 `.lftl` 正式文件，不能为了像它而换掉产品模型 |
| 导入失败项跳过、其余继续写入 | 我的 B→C 灾难恢复是整本账本替换；出现硬错误应整批拒绝，不能得到一份用户不知道少了什么的账本 |
| `forceImport` 绕过硬错误 | 可疑重复可以由用户决定，但结构损坏、同 ID 冲突、非法金额等硬错误不能用“仍然导入”解决 |
| 现在就引入 Rust、Tauri、服务端和扩展系统 | 我现在只需要先抽出边界；立刻引入所有运行环境只会增加新的 Bug 面 |
| 直接复制 AGPL 代码 | 必须先决定是否接受许可证影响；默认只读思路并重写 |

## 五、rotki：把它当成“加密货币会计 Bug 题库”

### 5.1 它最能帮我的地方

rotki 的技术栈和我不一样，但它处理的问题非常接近我未来一定会遇到的领域边界：

- 同一种币分多次买入后再部分卖出；
- 卖出数量来自多个历史批次；
- 手续费是否进入成本；
- 手续费用基础币、计价币或第三种资产支付；
- 币币交易；
- 缺少历史价格；
- 不同成本法得到不同结果；
- 历史 Bug 修完后怎样永久防止复发。

我不需要学习它全部链上解析代码。我最应该做的是把它的测试目录当成“别人已经整理好的考试题库”，逐题翻译成我的平均成本模型。

### 5.2 值得建立的会计回归矩阵

| 测试组 | 至少要有的案例 | 我的测试应该确认什么 |
| --- | --- | --- |
| 单次买卖 | 买入一次，全部卖出 | 数量归零、剩余成本归零、已实现盈亏正确 |
| 部分卖出 | 买入一次，分两次卖出 | 第一次卖出后的剩余数量和成本正确；第二次归零 |
| 多次买入 | 不同价格买入三次，再卖出一部分 | 加权平均成本、被释放成本和剩余成本一致 |
| 精确卖空边界 | 正好卖到 0 | 允许；不能残留极小负数或浮点尾巴 |
| 超额卖出 | 卖出数量大于持仓 | 明确拒绝，不生成看似合理的负持仓 |
| 缺少买入来源 | 只有卖出，没有足够历史持仓 | 返回稳定错误，不凭空补成本 |
| 买入手续费 | 手续费以计价币支付 | 明确它是否进入总成本，并与页面展示一致 |
| 卖出手续费 | 手续费以计价币支付 | 明确它是减少卖出收入，还是单独记账；只能有一种真相 |
| 手续费为基础币 | 买 BTC 时手续费扣 BTC | 当前若不支持，要明确拒绝或标记为未来范围，不能偷偷按 USDT 处理 |
| 手续费为第三种币 | 用 BNB 支付 BTC 交易手续费 | 当前若不支持，必须有稳定错误；未来实现时需要独立价格和处置规则 |
| 币币交易 | ETH 换 BTC | 当前若不支持，明确边界；未来需要同时处理卖出 ETH 和买入 BTC |
| 缺历史价格 | 某日没有可靠行情 | 结果是“不可计算及原因”，不能自动用 0、未来价或交易价顶替 |
| 多币种 | USD、USDT、CNY 等混合 | 先固定当前支持范围，汇率缺失时不能装作同币种 |
| 高精度 | 小币价格、极小数量、大额金额 | 中间计算不提前舍入，展示精度与存储精度分开 |
| 顺序变化 | 同一天多笔交易，输入顺序不同 | 明确稳定排序规则，不能因为数组顺序改变盈亏 |

### 5.3 它真正值得我养成的习惯

| 习惯 | 怎么落实到我的项目 |
| --- | --- |
| 一个生产 Bug 对应一个永久测试 | 例如 01D 的 `F-04` 修完后，测试名称或注释保留 Finding ID，后续版本继续跑 |
| 同一组交易跑不同规则 | 当前只正式支持平均成本，但可以用明确的期望值证明代码没有意外变成 FIFO |
| 每一步都检查剩余状态 | 不只看最后盈亏，还检查每次卖出后的数量、平均成本、剩余成本和已实现盈亏 |
| 缺数据是正式状态 | “没有价格”不是普通的 0，也不是临时忽略项；它需要进入类型、UI 和测试 |
| 费用归属必须写成合同 | 买入费、卖出费、第三币种手续费必须逐类说明，不能散落在公式里 |
| 历史缺陷变成题库 | 01D 不是一次性垃圾报告，而是以后所有 A 批次都能复用的反例库 |

### 5.4 不应该照搬的地方

1. 当前不要引入 FIFO、免税持有期、税务地区规则和链上事件解码。
2. 当前不要为了支持所有币币交易，把 `Trade` 模型一次扩成 rotki 的规模。
3. 不要把 Python/Vue 的整体架构搬到现有 React/TypeScript 项目。
4. 不要因为它支持某种手续费，就默认我的产品也已经决定支持。
5. 不直接复制 AGPL 代码；优先重写测试输入和期望结果。

### 6.2 保存与另存为应该怎样翻译成我的产品

| 用户动作 | 说人话的含义 | 我的 `.lftl` 应该遵守的规则 |
| --- | --- | --- |
| 打开 C | “从现在开始，我就在使用这一份正式账本” | 只把用户选中的这一份当成当前 C；不扫描同目录的其他副本 |
| 保存 | “把当前修改写回我正在使用的这份 C” | 使用当前句柄和当前 `fileId`；安全写入、复读验证、失败不伪装成功 |
| 另存为 | “复制当前内容，创建一份新的正式账本” | 新文件必须有新的身份；是否切换到新文件要清楚告诉用户，不能暗中把两份当同步关系 |
| 关闭 | “我不再继续使用这份文件” | 如果有未保存修改，要明确提醒；关闭后不继续持有失效句柄或后台写入 |
| 导出 B | “给我一份救命用的明文备份” | 它不是另一份 C，不自动同步，不由应用管理；继续常驻明文风险提示 |
| 从 B 恢复 | “把一份合法备份恢复成新的或空的 C” | 先完整校验，再整本提交；不与现有 C 自动合并 |

### 6.3 可以借鉴的详细清单

| 借鉴点 | 它给我的启发 | 我的边界 |
| --- | --- | --- |
| Save 与 Save As 明确分开 | 用户始终知道是在覆盖当前文件，还是创建新副本 | 另存为不是自动同步，也不是版本管理 |
| 未保存关闭提醒 | 文件型产品必须有清楚的 dirty 状态 | 提醒不能和实际持久化状态脱节 |
| 保存前留上一份 | 覆盖前保留旧状态能应对误操作 | 我的 C 已有 current/previous 双代设计；不要未经决策再制造旁边的备份文件 |
| 打开后立即保存原始副本 | 用户修改前有一个回退点 | 可以作为未来交互参考，但不能自动生成应用会管理的多个 C |
| 定时保存副本 | 长时间操作时减少损失 | 要先解决单写入者、外部 revision 和文件权限，不能先加定时器 |
| 文件格式明确可见 | 用户知道普通、二进制、加密格式的差异 | 我的正式格式应坚持 `.lftl`，B 明文格式另行命名和警告 |
| Sanity Check / Restore 入口 | 健康检查和恢复不应藏在错误弹窗里 | 可与 Wealthfolio 的诊断结构组合，形成稳定错误码和修复入口 |
| 导入模板 | 同一来源反复导入时可复用字段映射 | 模板只保存字段规则，不保存真实敏感交易 |

### 6.4 明确不能照搬的地方

| 它的做法 | 为什么我的账本不能照搬 |
| --- | --- |
| 文件里包含历史行情、Dashboard、书签和设置 | 我的 C 应保存事实与必要元数据；K 线、图表和会话状态是可重新生成的派生数据 |
| 自动在旁边生成 `.backup`、`.autosave` 文件 | 我的产品已经确认不扫描、不识别、不管理其他 C 副本；要做必须先重新决策 |
| 密码至少 6 位 | 这比我现有密码安全基线更弱，不能倒退 |
| 只因为写着 AES-256 就认为足够安全 | 算法名字不能证明 KDF、salt、nonce、AAD、密钥生命周期和防回滚都正确 |
| GUI 设置跟文件一起迁移 | 可以参考便利性，但 C 不能因此混入窗口宽度、图表布局等非账本事实 |

## 七、Actual Budget：把它当成“TypeScript 本地优先核心老师”

### 7.1 它最能帮我的地方

Actual Budget 不是投资账本，但它是成熟的 TypeScript 本地优先财务应用。它把核心逻辑、桌面客户端、Electron 运行环境和可选同步拆开，这一点比它的预算功能更值得我研究。

最直接可用的两个思想是：

1. UI 导入和 API 导入走同一条正式规则；
2. 同一条导入规则支持 `dryRun`，可以先返回“将新增什么、将更新什么、有哪些错误”，而不修改数据库。

官方 [API 文档](https://actualbudget.org/docs/api/reference/) 明确说明，`importTransactions` 的 `dryRun: true` 会返回可能新增或更新的内容，但不修改数据库。

### 7.2 可以借鉴的详细清单

| 借鉴点 | Actual Budget 怎么做 | 翻译成我的账本后怎么做 |
| --- | --- | --- |
| UI 与 API 共用导入管线 | 文件导入、银行导入、API 导入经过同一组规则 | 手动表单、B、CSV、NLP、AI Challenge 都先产生统一候选事实，再走同一预检和提交 |
| `dryRun` 试跑 | 先报告会新增、更新什么和有哪些错误 | `prepareImport` 返回预览，不改内存正式账本、不改 IndexedDB、不改 C |
| 导入 ID 防重 | 上游提供稳定 `imported_id` 时避免重复导入 | 优先使用明确来源 ID；没有来源 ID 时只做可疑重复提示，不自动认定同一笔 |
| 核心与桌面外壳分开 | `loot-core` 不等于 Electron 外壳 | 账本领域规则、文件格式、校验和计算不能依赖 Tauri API |
| 离线优先 | 网络不可用时本地数据仍能工作 | C 文件主链不依赖行情、AI 或服务器可用 |
| 同步重置有“真本”概念 | 用户选择当前设备的数据成为新的真实版本，并生成新同步 ID | 未来 iCloud/多设备必须有 generation；旧设备不能继续把旧状态写回来 |
| 迁移有测试 | 数据版本升级作为独立风险处理 | C V1/V2 使用固定样本和迁移 Gate；新版本常量不能改变旧版本解密合同 |
| ADR 记录重大决策 | 复杂架构决定单独留下原因和后果 | 对文件身份、同步、密钥和成本法继续使用 DEC/ADR，而不是只写在聊天里 |

参考入口：

- [Actual Budget 仓库](https://github.com/actualbudget/actual)
- [API 与 dry-run 导入](https://actualbudget.org/docs/api/reference/)
- [交易导入说明](https://actualbudget.org/docs/transactions/importing/)
- [跨设备同步与同步重置](https://actualbudget.org/docs/getting-started/sync/)
- [架构决策记录说明](https://actualbudget.org/docs/contributing/leadership/architecture-decision-records/)

### 7.3 它最值得我提前记住的同步教训

Actual Budget 的同步重置会要求用户选择一台设备，把这台设备的本地数据认作“真本”，清除旧同步状态并生成新的同步 ID。其他设备如果不属于这个新 ID，就不能继续当作同一代数据。

这可以翻译成我未来的 iCloud 规则：

```text
恢复旧备份或重置同步
  ↓
当前 C 成为新的真本
  ↓
同步 generation 改变
  ↓
旧窗口、旧设备、旧后台任务全部失效
  ↓
它们必须重新打开或重新授权，不能继续覆盖
```

这不是现在就要开发服务器同步，而是提前避免一个非常危险的设计错误：**恢复成功后，旧设备又把错误数据同步回来。**

### 7.4 不应该照搬的地方

1. Actual 会根据相近日期、金额和收款方自动“对账”或更新已有交易。我的账本不能照搬；相似交易只能警告，不能自动合并、更新或删除。
2. 它的本地设备数据默认仍未加密，官方建议依赖磁盘加密。这不满足我的 `.lftl` 静态加密目标。
3. 当前不需要引入它的自托管服务器和完整同步协议。
4. 它的预算领域模型、规则系统和银行同步不是我的当前范围。
5. 即使是 MIT，也不代表可以不看第三方依赖许可证和版权声明。

## 八、把四个项目组合成我的五套可复用资产

### 8.1 资产一：统一导入管线

来源：Wealthfolio 的 prepare/commit + Actual Budget 的 dry-run/共用核心。

建议的统一对象可以包含：

| 字段 | 用途 |
| --- | --- |
| `sourceType` | B、CSV、Binance、NLP、手动批量录入 |
| `sourceFingerprint` | 确认用户提交的仍然是刚才预览的内容 |
| `baseRevision` | 确认预检后当前 C 没有被其他窗口或任务改过 |
| `summary` | 总数、合法数、警告数、硬错误数、可疑重复数 |
| `issues` | 稳定错误码、行号/路径、字段、原因和修复提示 |
| `duplicateGroups` | 哪几笔看起来相似，以及相似依据 |
| `candidateLedger` | 通过规范化后的候选账本或候选事实 |
| `privacySummary` | 报告是否含敏感数据、日志会保留什么 |

我的硬规则：

- 预检不写正式数据。
- 硬错误存在时不允许提交。
- 同 ID 冲突是硬错误。
- 相似字段但不同 ID 是警告，不自动合并或删除。
- B→C 恢复按整本账本处理，不做部分成功。
- 正式提交前重新检查当前 C 和 `baseRevision`。
- 写入要原子化；失败后旧 C 保持可读。
- 写完关闭并重新打开，验证真正落盘的数据。

### 8.2 资产二：会计黄金案例库

来源：rotki 的会计测试 + Wealthfolio 的真实收益缺陷 + Portfolio Performance 的成熟绩效场景。

黄金案例库不是把测试越写越多，而是把它分成固定层次：

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 事实层 | 输入的数据有没有被改错 | 数量、单价、手续费、币种、时间 |
| 成本层 | 成本怎样进入和释放 | 多次买入、部分卖出、归零 |
| 收益层 | 已实现和未实现盈亏是否同一口径 | 手续费、税费、汇率、缺价 |
| 可用性层 | 数据不完整时有没有撒谎 | 缺行情时显示 N/A，不显示 0 |
| 展示层 | UI 有没有重新发明一套算法 | 页面值必须来自领域层结果 |
| 回归层 | 修过的 Bug 会不会回来 | 每个 P0/P1 Finding 对应永久测试 |

每次 01D/02D 发现新问题时，只做三件事：

1. 判断它属于哪一层；
2. 先写成一个最小反例；
3. 修复后把反例留在黄金案例库。

这样 D-1、D-2、D-3 就不会只是“又发现一批 Bug”，而是在逐步扩大以后所有批次都能复用的防护网。

### 8.3 资产三：文件交互状态机

来源：Portfolio Performance 的文件体验 + Actual Budget 的真本/同步身份 + 我现有的 C 文件合同。

至少要把这些状态说清：

| 状态 | 用户看到什么 | 系统允许什么 |
| --- | --- | --- |
| 未选择 C | 新建或打开 | 不允许假装已经保存 |
| C 已打开且干净 | 当前文件名、已保存 | 允许读、编辑、另存为、关闭 |
| C 已修改未保存 | 明确未保存状态 | 允许保存、放弃、另存为；关闭前提醒 |
| 正在保存 | 明确进行中 | 禁止重复写和换句柄造成竞态 |
| 保存失败 | 旧 C 仍可用、显示可重试错误 | 不显示“保存成功”，不切换到错误快照 |
| 权限丢失 | 告诉用户需要重新授权 | 重新连接后核对文件身份和 revision |
| 检测到外部修改 | 显示冲突，而不是覆盖 | 用户选择重新读取、另存为或放弃；不能自动抢写 |
| C 损坏但 previous 可恢复 | 解释恢复来源和影响 | 恢复前预览，成功后产生新 revision |
| 从 B 恢复 | 明确“覆盖不合并” | 只恢复到新的或符合合同的空 C |
| 另存为完成 | 告诉用户当前使用哪一份 | 新文件身份与旧文件分开，不建立隐式同步 |

### 8.4 资产四：运行环境 Adapter

来源：Wealthfolio 的 Web/Tauri Adapter + Actual Budget 的核心/桌面外壳分离。

第一步不是写 Tauri，而是列出业务真正需要环境提供的能力：

| Adapter | 浏览器实现 | 将来的 Tauri 实现 |
| --- | --- | --- |
| `FileAccessAdapter` | File System Access API / 下载选择器 | 原生文件对话框和文件系统 |
| `SecretStoreAdapter` | 当前受限实现或明确不可用 | Keychain / Credential Store |
| `AppLifecycleAdapter` | `visibilitychange`、页面卸载 | 窗口关闭、系统休眠、应用恢复 |
| `LockAdapter` | Web Locks 或现有单写入者方案 | 原生文件锁或应用级锁 |
| `ExternalChangeAdapter` | 重新授权后复读、revision 检查 | 文件监听 + revision 检查 |
| `MarketDataAdapter` | 浏览器网络请求 | Tauri 网络层或同一受控服务 |
| `BiometricAdapter` | 不提供，不伪装支持 | 桌面/移动端生物识别桥接 |

边界：

- Domain、Validator、计算、文件格式和导入规则不能引用 Tauri API。
- React 组件不能到处直接调用文件系统。
- 不同运行环境可以有不同能力，但不能有不同的账本真相。
- 如果桌面端暂时不支持某项能力，应返回明确的“不支持”，而不是静默降级。

### 8.5 资产五：统一问题诊断格式

来源：Wealthfolio Health Center + Portfolio Performance 的 Sanity Check/Restore。

建议每个可展示问题至少包含：

| 字段 | 说人话的作用 |
| --- | --- |
| `code` | 稳定身份，例如 `FILE_REVISION_CONFLICT` |
| `severity` | 信息、警告、错误、致命 |
| `category` | 文件、权限、加密、交易、价格、成本、导入 |
| `title` | 一句话告诉用户发生了什么 |
| `impact` | 这会影响保存、盈亏、图表，还是只是体验 |
| `evidence` | 哪个文件、哪笔交易、哪个日期或字段证明有问题 |
| `safeAction` | 可以安全自动执行的动作 |
| `reviewAction` | 把用户带到需要人工判断的位置 |
| `privacy` | 这条信息能不能进入日志或报告 |

例如：

```text
错误码：PRICE_MISSING_FOR_PNL
严重程度：警告
发生了什么：BTC 在 2026-07-01 没有可用价格
影响：这一天的未实现盈亏不能计算
系统没有做什么：没有使用 0、未来价格或买入价格代替
你可以做什么：补录价格 / 稍后重试行情源 / 查看受影响交易
```

这样的错误比“计算失败”更容易修，也更容易写成测试。

## 十、怎样研究它们，才不会又掉进另一个无底洞

### 10.1 每次研究的标准流程

1. 先写一句当前问题，例如：“B 导入怎样做到预检期间完全不写 C？”
2. 在这份文档里找最对应的项目。
3. 只打开 README/官方文档和两三个最接近的源码或测试文件。
4. 记录四件事：它的规则、它的失败案例、它的测试方式、它和我的差异。
5. 翻译成我的验收条目，不复制大段代码。
6. 到达时间上限就停止；没有解决的问题进入待研究清单。

### 10.2 建议的停止线

| 研究类型 | 一次最多做到什么程度 |
| --- | --- |
| 产品交互 | 看官方手册 + 一个相关界面/测试 |
| 架构边界 | 看架构说明 + 接口 + 一个实现 |
| 金融 Bug | 看测试输入和期望，不追完整调用链 |
| 安全设计 | 只能形成候选方案，必须另做安全审查 |
| 许可证 | 在复制代码前单独确认，不能凭 README 猜 |

### 10.3 什么时候才需要把仓库下载到本地

满足下面任意一条时再考虑下载：

- GitHub 网页无法完整搜索调用链；
- 需要运行它的某一组测试验证行为；
- 需要比较多个版本的迁移；
- 已经决定研究某个具体实现，而不是泛泛浏览；
- 许可证已经允许准备进一步复用。

如果以后下载，也应该放在明确的“外部参考项目”区域，不塞进 Local-First Trading Ledger 源码仓库，不和我的 Git 提交混在一起。

现在这份第一轮审查不需要下载四个巨型仓库。

## 十二、这份“巨人的肩膀”到底能替我省下什么

它不能替我写完全部项目，也不能保证以后没有 Bug。

但它至少可以替我省下四种最昂贵的重复劳动：

1. 不再从零发明导入流程；
2. 不再等用户或 01D 偶然撞出每一个会计边界；
3. 不再等到打包桌面端时才发现业务代码和浏览器 API 粘死；
4. 不再把每次文件保存、恢复和冲突处理都当成一个全新的问题。

以后真正合理的节奏应该是：

```text
当前需求
  → 查这份地图
  → 选一个最接近的成熟项目
  → 提取少量规则和反例
  → 翻译成我的合同
  → 开发
  → 独立测试
  → 新 Bug 进入永久题库
  → 到达当前通过线就收口
```

这不是偷懒，也不是降低质量。

它是在承认：我没有必要独自重新发现所有人已经踩过的坑。真正属于我的工作，是把这些成熟经验缩小、改造并组合成适合 Local-First Trading Ledger 的那一套。
